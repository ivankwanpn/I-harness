### acp-stdio-jsonrpc-gateway

- what: The ACP (Agent Client Protocol) transport is a persistent newline-delimited JSON-RPC stream on stdio, driven by a two-sided gateway. `acp_channels()` splits an `agent_client_protocol` connection into an unbounded `mpsc` of enqueued `AcpArgs` plus a oneshot response channel; `AcpGatewayReceiver::run` drains that channel and dispatches each variant to the underlying `acp::Agent`/`acp::Client` trait method through the `handle!` macro, which optionally wraps each dispatch in a `tracing::Span` built from the request's `_meta` via an `OnMetaFn` hook (`with_on_meta`) and a pluggable spawner (`with_spawn_fn`, default `tokio::task::spawn_local`). Typed request/response pairing is compile-time: `AcpSide` pins `InMessage`/`OutMessage`, and `acp_define_request_response!` binds each `acp::*Request` to its response type and schema method name (e.g. `acp::SessionNotification` → `()` under `session_update`, so stream updates are fire-and-forget).
- invariants: (1) The gateway receiver must be running for any `AcpGatewaySender` send to make progress — the sender only enqueues; there is no direct write path. (2) `AcpArgs::response_tx` must be consumed exactly once or the caller's oneshot resolves to a cancellation error; `after_request` treats a failed `send` as "receiver dropped" and does not retry. (3) Per-request dispatch is not ordered: each message is spawned independently, so ordering guarantees exist only inside one method's future.
- failurePolicy: mixed / fail-soft. Channel-closed failure is not retried and not escalated: `AcpGatewaySender::enqueue` returns `accepted = false` and logs at `debug` ("receiver dropped, notification discarded"), while `acp_send`'s round-trip paths produce a normal JSON-RPC `INTERNAL_ERROR` (`acp::ErrorCode::InternalError`) carrying a typed discriminant in `err.data["xaiAcpChannelFailure"]` (`send_failed` vs `recv_failed`), recovered by `acp_channel_failure()`. The error *code* stays `INTERNAL_ERROR` deliberately so pre-existing callers are unaffected.
- constants: `STDIN_LINE_CHANNEL_DEPTH=64` (`crates/codegen/xai-acp-lib/src/stdin_reader.rs:56`); `DATA_KEY="xaiAcpChannelFailure"` (`crates/codegen/xai-acp-lib/src/common.rs:41`); `AcpSide::NAME="agent"|"client"` (`crates/codegen/xai-acp-lib/src/message.rs:32`); key `"xaiAcpChannelFailure"` tags `send_failed`/`recv_failed` (`crates/codegen/xai-acp-lib/src/common.rs:45-46`).
- evidence: `crates/codegen/xai-acp-lib/src/gateway.rs:144-159` (the `handle!` macro: span from `_meta`, `before_request`, `conn.$name(request).await`, `after_request`), `crates/codegen/xai-acp-lib/src/gateway.rs:330-334` (`let accepted = self.tx.send(args.into()).is_ok();`), `crates/codegen/xai-acp-lib/src/message.rs:148-151` (`SessionNotification` → `()` on `session_update`), `crates/codegen/xai-acp-lib/src/common.rs:63-68` (`acp_channel_failure_error`).
- notes: Cargo has `agent-client-protocol` pinned with the `unstable` feature (`crates/codegen/xai-acp-lib/Cargo.toml:8`), so `ExtMethod`/`ExtNotification`/`SetSessionModel` variants exist only because of that feature. Nothing in this crate selects a protocol version at runtime; versioning is de-facto the pinned crate version plus the two workarounds below.

### acp-json-wire-compat-shims

- what: Two explicit workarounds for the pinned `agent-client-protocol` envelope, both on the stdin ingress path. (a) `spawn_stdin_line_reader()` owns stdin on a dedicated `std::thread` named `"acp-stdin"` using blocking `std::io` (because `tokio::io::stdin()`'s read cannot be cancelled and tokio itself recommends a dedicated thread); on Windows it first takes a private duplicate of the real stdin handle via `DuplicateHandle` and repoints the process `STD_INPUT_HANDLE` at `NUL` so any stray `std::io::stdin()` read in the process returns immediate EOF instead of deadlocking on the held `StdinLock`. (b) `normalize_json_line()` rewrites only lines the envelope would otherwise silently drop: it prefilters on the two-byte `\/` sequence, forwards byte-identically if `serde_json::from_slice::<agent_client_protocol::RawIncomingMessage>` already accepts the line, and otherwise re-serializes through `serde_json::Value` so `method` becomes borrowable again. Separately, `LineBufferedRead` makes ACP's `BufReader::read_line` cancel-safe by pre-reading whole lines on a task and only returning `Poll::Pending` *between* lines.
- invariants: (1) `normalize_json_line` must never rewrite a line the envelope already accepts, and must preserve the trailing terminator; every line it cannot parse passes through byte-identical because "the acp crate keeps ownership of garbage handling". (2) The stdin reader must be the sole stdin consumer in the agent-stdio/leader-bridge paths; on Windows the `NUL` redirect is what enforces it, and a failure to isolate falls back to `std::io::stdin()` rather than failing. (3) The `\/` prefilter must stay a prefilter — a `\u002F`-escaped method is intentionally not normalized.
- failurePolicy: fail-soft. Read error or EOF just drops the sender and closes the channel (`Ok(0) | Err(_) => break`); a full channel parks the reader thread on `blocking_send` (backpressure, not unbounded growth); a normalization failure forwards the original bytes. Windows isolation failure degrades to the pre-fix behaviour.
- constants: `STDIN_LINE_CHANNEL_DEPTH=64` (`crates/codegen/xai-acp-lib/src/stdin_reader.rs:56`); `MAX_LINE_SIZE=64*1024*1024` (64 MiB, `crates/codegen/xai-acp-lib/src/line_reader.rs:30`); line-channel depth `mpsc::channel(64)` (`crates/codegen/xai-acp-lib/src/line_reader.rs:66`); Windows `STD_INPUT_HANDLE=0xFFFF_FFF6` (`crates/codegen/xai-acp-lib/src/stdin_reader.rs:141`).
- evidence: `crates/codegen/xai-acp-lib/src/stdin_reader.rs:37-45` (`normalize_json_line` contract), `crates/codegen/xai-acp-lib/src/normalize.rs:37-45` (prefilter → envelope-accept → byte-identical), `crates/codegen/xai-acp-lib/src/stdin_reader.rs:175-215` (`isolate_process_stdin`: `DuplicateHandle` then `SetStdHandle(..., nul_handle)`), `crates/codegen/xai-acp-lib/src/line_reader.rs:95-100` (`impl AsyncRead for LineBufferedRead`).
- notes: `normalize.rs` explicitly scopes itself to *process-stdin ingress only* — clients that connect directly to the leader socket bypass it (`crates/codegen/xai-acp-lib/src/normalize.rs:11-12`). The module also records a downstream coupling: the leader bridge's replay sniff in `xai-grok-pager-bin/src/main.rs` matches escaped Foundation input only because this normalization runs upstream. The test at `crates/codegen/xai-acp-lib/src/normalize.rs:77-89` asserts that acp 0.10.4+ parses `method` as `Cow<str>` and therefore already accepts `session\/prompt`, i.e. this workaround is version-conditional in intent.

### workspace-daemon-singleton-lifecycle

- what: Process lifecycle for the standalone workspace-server: Unix self-daemonization (double fork + `setsid()` + `chdir("/")` + stdio redirect, deliberately before the tokio runtime / `tracing_subscriber` / rustls provider start any threads), plus a single-instance lock implemented as an advisory `flock` held for the daemon's lifetime on a pidfile. `PidFile::acquire_or_take_over` upgrades the ordinary `acquire` into a takeover: it reads the advisory pid, refuses if the holder is not an identifiable workspace-server (`PredecessorTarget::open` pins the process via `pidfd_open(2)` on Linux and verifies the argv0 basename *after* pinning, closing the pid-reuse race), sends SIGTERM, polls for the lock for `TAKEOVER_GRACE`, then escalates to a forceful kill and polls for `TAKEOVER_KILL_GRACE`, declining (`Ok(None)`) if it still loses. `apply_workspace_oom_protect()` lowers the server's own `/proc/self/oom_score_adj`.
- invariants: (1) The double fork must happen before any runtime threads exist — forking a multi-threaded process leaves locks held by non-forking threads permanently locked in the child. (2) The lock is never bypassed: a `PidFile` guard is returned only with the flock actually held, and the recorded PID is advisory/diagnostic only. (3) `basename_contains` must match only the basename — matching the full path would let a directory like `/var/lib/workspace-server-data/foo` satisfy the kill gate.
- failurePolicy: fail-closed on singleton-ness, fail-soft on hardening. Two concurrent spawns cannot both run (the loser exits quietly). Daemon-owned files are opened with `O_NOFOLLOW` and mode `0600`; a contended `acquire` returns `Ok(None)` without touching the pidfile. OOM protection is best-effort: a failed write logs to stderr, records `workspace_oom_protect_applied{outcome="failed"}` and returns `false`, and the caller still forces `RESET_CHILD_OOM_ENV` so a partial lower cannot shield user work.
- constants: `WORKSPACE_SERVER_OOM_SCORE_ADJ=-900` (`crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:65`); `PREVIEW_PROXY_OOM_SCORE_ADJ=-500` (`crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:68`); `TAKEOVER_GRACE=2s`, `TAKEOVER_KILL_GRACE=1s`, `TAKEOVER_POLL=50ms` (`crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:52,55,58`); `DEFAULT_PIDFILE_PATH="/tmp/workspace-server.pid"` / `"C:\\Windows\\Temp\\workspace-server.pid"` (`crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:43-45`); `WORKSPACE_SERVER_NAME_FRAGMENT="workspace-server"` (`crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:61`).
- evidence: `crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:7-8` (fork-before-threads invariant), `crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:294-298` (`try_lock_exclusive` + `is_lock_contended` → `Ok(None)`), `crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:441-444` (verify-after-pin), `crates/codegen/xai-grok-workspace-daemon/src/daemonize.rs:121-137` (OOM failure path).
- notes: `set_oom_score_adj` is a no-op returning `Ok(())` off Linux (`daemonize.rs:91-94`). The whole daemonize/takeover surface is Unix/Windows-only; `daemonize()` on other targets is a stub (`daemonize.rs:201`). Consumed by `xai-grok-workspace` (`crates/codegen/xai-grok-workspace/Cargo.toml:45`), so it is wired into the workspace-server binary, not a library-only crate.

### preview-proxy-supervision

- what: The workspace-server supervises the in-guest preview proxy as a child process. `supervise_preview` builds a `BackoffPolicy{base, cap}` and runs `supervise_loop`, which respawns the child on every exit with `base * 2^step` delay saturating at the cap; a run lasting at least `PREVIEW_PROXY_HEALTHY_RUN_SECS` is "healthy" and resets the step counter to zero. The child is spawned via `build_preview_command` with `kill_on_drop(true)`, an argv assembled by `PreviewArgs::to_argv`, and per-session secrets (`GROK_SERVER_KEY`, `GROK_SESSION_ID`) passed by env inheritance, never argv. Two auxiliary scrapers run alongside: `scrape_activity_loop` polls the proxy's loopback `/__control/activity` to feed a `PreviewActivitySink` (which withholds sandbox idle-hibernation while preview activity is live), and `scrape_metrics_loop` polls `/__control/metrics` every 60s and donates the body to an external metrics sink.
- invariants: (1) The proxy log is truncated on every (re)start, so a crash-loop pinned at the backoff cap cannot grow it without bound. (2) `PreviewArgs::enabled` is a supervisor-side gate that is never forwarded to the proxy (the proxy has no such flag) — emitting it would make the proxy reject an unknown flag and crash-loop. (3) `discovery_refresh_ms` stays `None`/unset until the proxy release that understands `--discovery-refresh-ms` has rolled out, for the same reason. (4) Supervisor shutdown SIGKILLs the child without restart; a shutdown racing a child exit must not be counted as a restart. (5) A metrics/activity scrape failure must not tear down the supervisor.
- failurePolicy: fail-soft and self-healing. A spawn or log-open failure backs off and retries rather than dropping the task (`record_restart(SpawnError)`); a missing/unreachable proxy is a quiet no-op (`Err(e) if e.is_connect() || e.is_timeout() => {}`); a client-build failure disables the metrics scraper with a warning instead of failing the daemon. Scrape-first ordering means a short-lived sandbox still emits at least one sample.
- constants: `PREVIEW_PROXY_BIN_PATH="/usr/local/bin/xai-grok-preview-proxy"` (`crates/codegen/xai-grok-workspace-daemon/src/preview_supervisor.rs:26`); `PREVIEW_PROXY_LOG_PATH="/var/tmp/workspace-server/tmp/preview-proxy.log"` (`:31`); `PREVIEW_PROXY_HEALTHY_RUN_SECS=30`, base `1`, cap `30` (`:34,37,40`); `DEFAULT_PREVIEW_CONTROL_PORT=6015` (`:407`); `PREVIEW_ACTIVITY_PATH="/__control/activity"` (`:404`), `PREVIEW_METRICS_PATH="/__control/metrics"` (`:618`), `PREVIEW_METRICS_SCRAPE_INTERVAL=60s` (`:620`), `PREVIEW_ACTIVITY_SCRAPE_TIMEOUT=2s` (`:427`).
- evidence: `crates/codegen/xai-grok-workspace-daemon/src/preview_supervisor.rs:177-193` (`BackoffPolicy::delay`, `next_step`), `crates/codegen/xai-grok-workspace-daemon/src/preview_supervisor.rs:342-354` (spawn-failure backoff, never drops the task), `crates/codegen/xai-grok-workspace-daemon/src/preview_supervisor.rs:358-386` (select on child exit vs shutdown; shutdown kills without restart), `crates/codegen/xai-grok-workspace-daemon/src/preview_supervisor.rs:126-160` (`to_argv` omits absent options and never emits `enabled`).
- notes: `open_truncated_log` reuses `daemonize::daemon_file_options()` (`O_NOFOLLOW`, mode `0600`) so the proxy log gets the same symlink/permission defense (`preview_supervisor.rs:203-212`). The preview child is spawned after daemonize so it inherits the new session/pgid; a `PDEATHSIG` helper is asserted by a test with env var `GROK_PDEATHSIG_HELPER` and expected value `42` (`preview_supervisor.rs:1706,1708`).

### diag-readiness-endpoints

- what: An in-guest axum HTTP server exposing exactly three endpoints — `/ready`, `/statusz`, `/logs` — that is the sandbox readiness gate's view of the workspace-server. State is a `DiagHandle` wrapping `Arc<Mutex<Inner>>`; the server publishes lifecycle transitions into it (`set_connected`, `set_disconnected`, `set_terminal_close(code)`, `clear_terminal_close`, `revive_connected(&[u16])`, `set_shutting_down`, `set_failed(ErrorClass, detail)`, `set_image_capabilities`). `/ready` returns HTTP 200 **only** when `state == Connected` and 503 otherwise, while always serving the body, so naive HTTP probes and body-parsing consumers agree. The `ReadyBody` field set is declared a frozen contract with the sandbox readiness gate.
- invariants: (1) `ReadyBody`'s field set must never be renamed or removed; additions are the only backward-compatible change (`lib.rs:68`). (2) Terminal states are sticky and ordered: `set_connected` no-ops while `shutting_down`, `failed`, or a terminal close code is latched; `set_failed` is terminal for every other transition; `clear_terminal_close`/`revive_connected` no-op after failed or shutting-down. (3) `connected_at` is set with `get_or_insert`, so it freezes at the first connected transition and is not republished by later reconnects. (4) The mutex is not reentrant, so every multi-field reader goes through `ready_body_locked` instead of composing lock-taking methods.
- failurePolicy: fail-closed on readiness, fail-soft on diagnostics. A bind failure is surfaced synchronously (`serve` binds before returning) and in `--daemonize` mode exits with code `5` after writing the grep-able marker; in non-daemonize mode it logs a warning and continues without diagnostics. `/logs` returns 404 for absent/unreadable log, 500 with a generic body for other IO errors (deliberately not echoing the path), and clamps `tail_bytes`.
- constants: `DEFAULT_DIAG_PORT=6016` (`crates/codegen/xai-grok-diag-server/src/lib.rs:31`); `DEFAULT_DIAG_SOCKET_PATH="/tmp/workspace-server.sock"` (`:28`); `EXIT_DIAG_BIND_FAILED=5` (`:37`); `DIAG_BIND_FAILED_MARKER="diagnostics server bind failed"` (`:34`); `DEFAULT_LOG_TAIL_BYTES=64*1024`, `MAX_LOG_TAIL_BYTES=256*1024` (`:40,43`); `MAX_ERROR_DETAIL_BYTES=256` (`:65`); Unix socket mode `0o600` (`:414`).
- evidence: `crates/codegen/xai-grok-diag-server/src/lib.rs:151-158` (`set_connected` guard + `connected_at.get_or_insert`), `crates/codegen/xai-grok-diag-server/src/lib.rs:229-238` (sticky `set_failed`), `crates/codegen/xai-grok-diag-server/src/lib.rs:337-340` (tail clamp), `crates/codegen/xai-grok-diag-server/src/lib.rs:377-384` (200 only when connected).

### workspace-rpc-typed-client

- what: A typed client for the hub-proxied `workspace.*` RPC surface. `WorkspaceClient` wraps a `ToolHarness` and calls the single hub tool id `workspace_rpc` with `{"method": .., "params": ..}`, then decodes the `RpcEnvelope<T>` (`{"ok": T}` / `{"err": {code, message}}`) into the request type's `WorkspaceRpc::Response`. The trait `WorkspaceRpc` requires `METHOD` *and* `ACTIVITY: RpcActivityClass` with no default, so every method is classified explicitly as `Mutation` (counts as human activity, blocks idle hibernation) or `Read` (never counts, including teardown/maintenance exceptions). It carries a shared `Arc<AtomicBool>` connected latch that fast-fails subsequent calls after a fatal transport error, plus an optional per-call deadline.
- invariants: (1) `is_connected()` gates every call at entry: a latch-down client returns `NotConnected` without touching the harness, and only `mark_connected()` (e.g. an SDK `on_reconnect` callback holding the same `Arc`, via `with_connected_flag`) resets it. (2) Latching must happen on `NetworkError` and on a half-closed-WebSocket `Custom{code:"protocol_error"}` only — latching on non-fatal tool errors would wedge a healthy client. (3) `WorkspaceRpc::Response` is bounded `Serialize + DeserializeOwned + Send` because the same struct is serialized into the envelope server-side and deserialized client-side; the method name is the wire identity. (4) The delivered stream must be consumed to its terminal item; a stream ending without one is an error, not an empty success.
- failurePolicy: fail-closed on trust, fail-soft on classification. `NotConnected` is terminal until an explicit reconnect signal (no automatic retry). A `workspace_unavailable` error carrying `retryable: false` maps to `WorkspaceHibernated`, whose message is literally "do not retry". Unknown-method errors are matched across **three** wire shapes (`code == "unknown_method"`, or the legacy `hub_error` whose message contains `"unknown workspace method:"`, or a re-wrapped `"unknown error code: unknown_method: unknown workspace method:"`), so relays that re-wrap the error stay compatible.
- constants: `WORKSPACE_RPC_TOOL_ID="workspace_rpc"` (`crates/codegen/xai-grok-workspace-types/src/rpc/mod.rs:30`); `WORKSPACE_EVENTS_TOOL_ID="workspace_events"` and `WORKSPACE_TOOL_NOTIFICATIONS_TOOL_ID="workspace_tool_notifications"` and `WORKSPACE_CLIENT_EXT_NOTIFICATIONS_TOOL_ID="workspace_client_ext_notifications"` (`:33,36,39`); `TURN_ACTIVE="turn_active"` / `HUB_ERROR="hub_error"` / `UNKNOWN_METHOD="unknown_method"` / `UNKNOWN_METHOD_ERR_PREFIX="unknown workspace method:"` (`crates/codegen/xai-grok-workspace-types/src/rpc/envelope.rs:13,15,17,20`); `MCP_TOOL_NAME_DELIMITER="__"` (`crates/codegen/xai-grok-workspace-types/src/lib.rs:66`).
- evidence: `crates/codegen/xai-grok-workspace-client/src/lib.rs:208-210` (latch gate), `crates/codegen/xai-grok-workspace-client/src/lib.rs:234-242` (hibernated → latch → transport mapping), `crates/codegen/xai-grok-workspace-client/src/lib.rs:115-126` (`is_transport_fatal`), `crates/codegen/xai-grok-workspace-types/src/rpc/envelope.rs:43-45` + `:98-125` (three unknown-method shapes).
- notes: Actively wired. The server side registers the handler under the same constant: `crates/codegen/xai-grok-workspace/src/hub_server.rs:1062-1066` does `ToolId::new(WORKSPACE_RPC_TOOL_ID)`. ### workspace-event-stream-backpressure

- what: The workspace event channel is a single broadcast of `WorkspaceEvent` ("one event per fact") with **client-side** topic filtering via `WorkspaceTopicSet`, a `u32` bitset where `topic_index` assigns stable bit positions to `Fs/Vcs/Discovery/Servers/Index/Config/Tools`. Lag is a first-class wire payload, not an error string: `EventLag::Lagged(u64)` carries the number of dropped events and is serde-tagged `{tag="type", content="data"}` so it rides the gRPC `EventEnvelope.payload` oneof. The enum's design rule is that `WorkspaceEvent` carries only workspace-observed *external* state — sampler-caused state never appears, and tool execution stays on the sampler-caused tool-result path.
- invariants: (1) `topic_index` bit assignments are wire-stable: existing variants must not be reordered without bumping the wire-compat manifest. (2) Only workspace-observed external state belongs on this enum; adding sampler-caused state would duplicate a source of truth the sampler already holds. (3) Hunk events are deliberately absent from the enum — hunks come from tool writes and `act_on_hunk` RPCs (both sampler-caused) and are re-snapshotted via `list_hunks()` instead.
- failurePolicy: fail-open with an explicit signal. A subscriber that falls behind does not stall the producer and does not error out; events are dropped and the drop count is surfaced as `EventLag::Lagged(n)`, so the consumer can re-snapshot rather than silently diverge.
- constants: `WorkspaceTopic::Fs=0, Vcs=1, Discovery=2, Servers=3, Index=4, Config=5, Tools=6` (`crates/codegen/xai-grok-workspace-types/src/events/workspace.rs:198-208`); JSON shape `{"type":"lagged","data":3}` (`crates/codegen/xai-grok-workspace-types/src/events/lag.rs:33`); dedup key `MCP_TOOL_NAME_DELIMITER="__"` for `"server__tool"` (`crates/codegen/xai-grok-workspace-types/src/lib.rs:64-66`).
- evidence: `crates/codegen/xai-grok-workspace-types/src/events/lag.rs:14-18` (`EventLag` enum + `Lagged(u64)`), `crates/codegen/xai-grok-workspace-types/src/events/workspace.rs:24-25` ("One event per fact … Topic filtering happens client-side"), `crates/codegen/xai-grok-workspace-types/src/events/workspace.rs:183-191` (bitset `with`/`contains`).
- notes: The runtime `EventStream<T>` wrapper that reports lag as `Result<T, EventLag>` lives in `xai-grok-workspace`, **not** in this crate — `lag.rs:1-3` states this explicitly, so in this crate the type is a wire payload only and its backpressure behaviour depends on the consumer. The crate is pure-data by policy: no tokio, no async-trait, no I/O (`crates/codegen/xai-grok-workspace-types/src/lib.rs:3-5`). ### subagent-bundle-checksum-cache

- what: A checksum-tracked on-disk cache for the published subagent bundle (personas, roles, agents, skills, workflows) under `<grok home>/bundled`. `write_bundle_to_cache` and `extract_bundle_archive` write each file plus a `manifest.json` recording a SHA-256 per relative path. Ownership is decided by a three-way `BundleFileState` (`Absent` / `MatchesManaged` / `ModifiedOrUnmanaged`) computed by `bundle_file_state`: a file is only overwritten or pruned when its current on-disk checksum still equals the recorded one. Archive extraction is bounded by entry count, per-entry size, and total decompressed size, every path is sanitized before being joined to the root, and unknown top-level paths are skipped.
- invariants: (1) A file the user edited by hand is never overwritten and never pruned; a skipped update retains the previous checksum in the manifest so the file stays classified as unmanaged. (2) `sanitize_relative_path` is the single gate before every `root.join()`: it rejects empty paths, leading `/`, any `\`, and — for nested skill paths — empty/`.`/`..`/control-character components. (3) `sanitize_manifest` must be applied to any manifest read from disk before its keys are used as paths, so a hostile manifest cannot drive a prune outside the cache.
- failurePolicy: mixed. Bounded-resource violations are fail-closed: exceeding the entry count, a per-entry size, or the total decompressed size `bail!`s and aborts extraction rather than partially proceeding. Path/format violations are fail-soft: an unmappable archive path or an unsanitizable manifest key is silently skipped (`continue` / `filter_map` → dropped). A missing `bundle.json` with a `version` field fails the whole extraction. A pruned file that has been user-modified is kept.

### pty-control-headless-session

- what: A headless PTY controller (`ptyctl`) exposing terminal control over HTTP + WebSocket on loopback, plus a CLI (`ptyctl-cli`, binary name `ptyctl`). `build_router` mounts `/query/screen`, `/query/cursor`, `/query/status`, `/query/scrollback`, `/control/send`, `/control/resize`, `/control/stop`, `/ws`, and a top-level `/wait`. Waits are **event-driven, never polling**: the session's feeder bumps a `watch::Sender<u64>` generation after each `term.feed()` and a resize also bumps it, so `WaitHandle::wait_for` re-evaluates the condition only on a generation change, using `borrow_and_update()` before each check to make check-then-wait lost-wakeup-free. On timeout the response carries `WaitDiagnostics` (screen text, cursor, modes, last `RAW_TAIL_CAP` bytes of raw PTY output, generation, and an `ended` flag) so the caller needs no follow-up call.
- invariants: (1) The generation must be bumped *after* `term.feed()` — a waiter woken by the broadcast before the feed would read a stale grid. (2) A long-poll must clone the wait handles and drop the session mutex guard, or `send`/`screen` would block for the entire wait. (3) Terminal-generated PTY write responses and user writes must both be flushed on the single writer task. (4) Exactly one wait condition must be set per `/wait` request.
- failurePolicy: mixed. Bad input is fail-closed at the edge: a missing/ambiguous wait condition is rejected before waiting, an invalid regex is compiled once up front so a bad pattern fails fast instead of on every check (returning 400 with the regex parse detail), and `/wait` clamps `timeout_ms` to the maximum. Runtime degradation is fail-soft: a slow WebSocket consumer is not disconnected — the broadcast `Lagged(n)` is converted into a `{"type":"warning","message":"dropped N output chunks (slow consumer)"}` text frame and streaming continues. A dropped generation sender (child exited, grid final) makes waiters return immediately with `ended: true` rather than spinning to the deadline.
- constants: `WAIT_DEFAULT_TIMEOUT_MS=10_000`, `WAIT_MAX_TIMEOUT_MS=120_000` (`crates/codegen/ptyctl/src/server.rs:57,59`); `RAW_TAIL_CAP=2048` (`crates/codegen/ptyctl/src/wait.rs:16`); broadcast channel capacity `256` chunks (`crates/codegen/ptyctl/src/session.rs:86`); scrollback default `100` lines (`crates/codegen/ptyctl/src/server.rs:275`); default size `80x24`, `--port` default `0` (auto-assign) (`crates/codegen/ptyctl-cli/src/cli.rs:27,31,43`).
- evidence: `crates/codegen/ptyctl/src/wait.rs:97-128` (generation-gated loop, `borrow_and_update`, feeder-gone fast path), `crates/codegen/ptyctl/src/session.rs:170-171` (bump after feed, with the ordering rationale on the preceding line), `crates/codegen/ptyctl/src/server.rs:242-259` (clamp, handle clone, 400 on invalid regex), `crates/codegen/ptyctl/src/server.rs:325-332` (lag → warning frame, no disconnect).
- notes: **A real inertness finding:** `SessionConfig::timeout` and `SessionConfig::linger` are declared and populated from the CLI flags `--timeout` / `-l, --linger`, but **no code ever reads them**. `PtySession::start` never consults `config.timeout` or `config.linger`, nothing stores them on `PtySession` (the struct has only `_shutdown_tx`), and a repo-wide grep for `cfg.timeout` / `config.timeout` / `cfg.linger` / `.linger` finds no reader outside the struct definition and its two construction sites. So `ptyctl run --timeout N` does not auto-shutdown and `--linger` does not keep the server alive past child exit in this revision. Citations: declared `crates/codegen/ptyctl/src/session.rs:25-31`; populated `crates/codegen/ptyctl-cli/src/commands/run.rs:56-66`; documented as functional `crates/codegen/ptyctl-cli/src/cli.rs:54-60`; never read (`PtySession::start` at `crates/codegen/ptyctl/src/session.rs:67`, struct at `:45-63`).

### pty-session-registry

- what: A named-session registry so CLI invocations can address a running PTY server. `SessionInfo{port, pid, command, cwd, started_at}` is persisted one JSON file per session name under `$PTYCTL_SESSION_DIR` or `<dirs::state_dir()>/ptyctl/sessions`, written atomically (temp file + `rename`) with temp files dot-prefixed so `list_sessions` skips them. Liveness is probed by `server_alive(port)`, which GETs `/query/status` and requires **both** HTTP 200 **and** a JSON body containing a `size` key — a bare TCP connect or a bare 200 would misread an unrelated process on a recycled port as live. `ptyctl run --name X` refuses to start when `X` already resolves to a live server unless `--force`.
- invariants: (1) Liveness must be body-shape-checked, not PID-based and not status-only: the recorded PID is the *child*, which may have exited while the server is still up. (2) Registration writes must stay atomic — a reader must never see a partial JSON file. (3) Cleanup on exit must unregister only a registration that still points at *this* server (`info.port == actual_port`), because a `--force` takeover may have replaced it. (4) `--force` replaces the registration; it explicitly does **not** stop the old server.
- failurePolicy: fail-soft on stale state, fail-closed on collisions. A missing registry directory yields an empty list rather than an error; an unparseable session file is skipped during listing; an unreachable/incorrectly-shaped `/query/status` reads as dead and therefore replaceable. But starting a name whose server *is* live is refused with a `bail!` unless `--force`.
- constants: env override `PTYCTL_SESSION_DIR` (`crates/codegen/ptyctl-cli/src/registry.rs:22`); default dir `<state_dir>/ptyctl/sessions` (`:28`); liveness probe timeout `500ms` (`:80`); required body key `"size"` (`:94`); CLI default `--port 0` (auto-assign) (`crates/codegen/ptyctl-cli/src/cli.rs:43`).
- evidence: `crates/codegen/ptyctl-cli/src/registry.rs:39-42` (atomic write), `crates/codegen/ptyctl-cli/src/registry.rs:90-95` (200 **and** body-shape check), `crates/codegen/ptyctl-cli/src/commands/run.rs:31-41` (live-name refusal unless `--force`), `crates/codegen/ptyctl-cli/src/commands/run.rs:110-116` (port-matched cleanup).
- notes: The CLI encodes a deliberate exit-code contract for `wait`: 0 = matched, 1 = timeout, 2 = usage/connection error (`crates/codegen/ptyctl-cli/src/main.rs:99-124`, with `Ok(false) => exit(1)` at `:119`), so a shell consumer can branch on timeout without parsing output. `ptyctl` is consumed by `xai-grok-pager-pty-harness` (`crates/codegen/xai-grok-pager-pty-harness/Cargo.toml:18`), i.e. as a **test harness**, not a product surface — and `ptyctl`/`ptyctl-cli` both declare `publish = false`. ### http-transport-liveness

- what: Shared `reqwest` clients with deliberate connection-pool self-healing, plus a retry combinator that can escape a poisoned pool. `shared_client()` caches one async client in a `OnceLock` configured with a 30s connect timeout, a 30s idle-pool timeout, HTTP/2 keepalive (20s interval / 10s timeout / `keep_alive_while_idle(true)`), and 30s TCP keepalive, because through a load balancer a kept-alive connection can be silently dropped upstream and reqwest would otherwise reuse it for every retry, making a reachable server look unreachable. `send_with_retry_escaping_pool` runs early attempts on that pooled client and swaps the **final** attempt of a multi-attempt run onto a fresh, pool-less HTTP/1.1 client from `fresh_http1_client()`, so a tight-budget caller can escape a half-dead pooled connection without waiting ~20-30s for keepalive/idle eviction. Transport failures are classified rather than string-matched: `TransportFailure::classify` + `certificate_error` downcast `rustls::Error::InvalidCertificate` and split `UnknownIssuer` (fixable by installing a root CA) from every other invalid certificate, and `find_os_error_code` recovers an OS error code through the `source()` chain including the `(os error N)` suffix that a *custom* `io::Error` from a rustls handshake reset leaves behind.
- invariants: (1) Keeping the pool alive is not enough — the idle/TCP eviction and HTTP/2 keepalive ping are load-bearing, not tuning; removing them reintroduces identical failures across every retry. (2) `fresh_http1_client()` is deliberately **not** cached (`pool_max_idle_per_host(0)`) and has no connect timeout; callers must bound each request themselves. (3) A failure to build the escape client must not abort the operation — the final attempt falls back to the pooled client. (4) The retried unit is the caller-supplied `op`, which encompasses send, body read, and decode; the caller keeps its own `is_retryable` policy and supplies the backoff sleep, so this helper is runtime-independent.
- failurePolicy: fail-open with a bounded budget. `max_attempts` is floored at 1 via `max(1)` so at least one attempt runs and `last_err` is always set if the loop falls through; a non-retryable error returns immediately without consuming the remaining attempts; a client-build failure logs a warning and degrades the final attempt to the pooled client rather than erroring. Recovery from a *slow* (traffic-swallowing) connection is explicitly best-effort and may lose to the caller's deadline.
- constants: `STARTUP_FETCH_TIMEOUT=5s`, `STARTUP_AUTH_TIMEOUT=60s`, `STARTUP_AUTH_REFRESH_TIMEOUT=5s`, `SETTINGS_REAPPLY_TIMEOUT=30s`, `SETTINGS_FETCH_MAX_ATTEMPTS=3` (`crates/codegen/xai-grok-http/src/lib.rs:24,27,30,32,34`); `MIN_CLIENT_CONNECT_TIMEOUT=120s` (`:46`); pooled-client `connect_timeout=30s`, `pool_idle_timeout=30s`, `http2_keep_alive_interval=20s`, `http2_keep_alive_timeout=10s`, `tcp_keepalive=30s` (`:292-298`); upload client `pool_max_idle_per_host(2)`, `pool_idle_timeout=10s`, HTTP/1.1-only (`:332-334`); client-mode header `CLIENT_MODE_HEADER="x-grok-client-mode"` (`:256`); env `GROK_CLIENT_NAME` / `GROK_CLIENT_VERSION` (`:83,87`).
- evidence: `crates/codegen/xai-grok-http/src/lib.rs:514-541` (`max_attempts.max(1)`, final-attempt client swap, build-failure fallback), `crates/codegen/xai-grok-http/src/lib.rs:285-302` (`shared_client` config), `crates/codegen/xai-grok-http/src/lib.rs:464-481` (`certificate_error` downcast), `crates/codegen/xai-grok-http/src/lib.rs:390-396` (`parse_os_error` on the `(os error N)` suffix).
- notes: Const-ness is compile-time enforced by two `const _: () = assert!(...)` blocks: the reapply timeout must exceed `STARTUP_FETCH_TIMEOUT * (1 + SETTINGS_FETCH_MAX_ATTEMPTS)` (`:37-41`) and `MIN_CLIENT_CONNECT_TIMEOUT` must stay `>= 2x STARTUP_AUTH_TIMEOUT` (`:47-50`) — a maintainer changing either timeout alone gets a build error. **Crate role note:** `xai-grok-http` is *not* any kind of server despite the name; its own Cargo description is "Shared reqwest HTTP clients and User-Agent construction for the grok CLI" (`crates/codegen/xai-grok-http/Cargo.toml:6`), and it contains no listener, router, or axum dependency — it is a client/transport-utilities crate. TLS policy (backend pin, roots, provider) is not here; it delegates to `xai_grok_extra_ca::build_reqwest_client` (`:290`). Sampling traffic uses a different set of clients owned by `xai_grok_sampler::shared_http` (`:12-15`), so pool tuning for sampling is out of scope for this crate.

### tools-api-shared-contract

- what: A shared API-definition crate that exists so the tools implementation and its gRPC server agree on one contract, and so host services can validate tool config without depending on the tools library. Two mechanisms live here. (a) Protobuf surface: `pb` is generated at build time into `OUT_DIR/xai.grok.tools.v1.rs` by `xai-proto-build` and re-exported at the crate root. (b) Two pure validators that are the *single* source of truth for rules enforced in two places: `parse_params_json` (a `params_json` must parse as JSON **and** be an object; an explicitly-set empty string is a parse error, not "unset", because proto3 `optional` tracks presence) and `validate_name_override` (must satisfy the `ToolId` charset/length contract), plus `first_unknown_tool_id` which returns the first entry whose `id` is not in an `allowed_ids: HashSet<String>` — a client-supplied allow-list check kept pure so backend save-time validation and the tools server cannot drift.
- invariants: (1) `default_client_name` splits on the **first** colon and returns the segment after it (`"GrokBuild:grep"` → `"grep"`, `"ns:a:b"` → `"a"`), so an id with embedded colons resolves predictably; both the advertising server and any client predicting the advertised name must use this one helper or tools silently drop out of prompts. (2) `parse_params_json` must keep rejecting `Some("")`; treating presence-tracking empties as unset would change save-time semantics. (3) Validation errors must carry the offending input and expose `field_path()` (`tools[N].params_json` / `tools[N].name_override`) so callers can render gRPC violations without re-parsing.
- failurePolicy: fail-closed. Every validator returns `Result`/`Option` and cannot be skipped by the caller; a non-object JSON value is rejected with the value preserved in the error, and an invalid `name_override` is rejected before any bind. Nothing here fails open — there is no default-allow path inside the validators themselves (the allow-list semantics live with the caller supplying `allowed_ids`).
- constants: generated module path `concat!(env!("OUT_DIR"), "/xai.grok.tools.v1.rs")` (`crates/codegen/xai-grok-tools-api/src/lib.rs:11`); crate version `0.1.220-alpha.4` (`crates/codegen/xai-grok-tools-api/Cargo.toml:4`); `ToolCategory` string forms `unspecified|file|search|shell|workflow|external|custom` (`crates/codegen/xai-grok-tools-api/src/lib.rs:121-127`).
