### external-otel-opt-in-stream
- what: An opt-in, content-redacted OpenTelemetry stream that ships to the **customer's own** collector, kept independent of xAI product analytics. `ExternalOtelConfig::resolve` layers `OTEL_*` env vars over `[telemetry] otel_*` file config and returns `None` unless a double opt-in holds: `GROK_EXTERNAL_OTEL` (`ENV_MASTER_SWITCH`) is truthy **and** at least one of `OTEL_METRICS_EXPORTER`/`OTEL_LOGS_EXPORTER` parses to a real exporter — `if !metrics_exporter.is_active() && !logs_exporter.is_active() { return None; }` (`external/config.rs:392-394`). The handle is a crate-local `static EXTERNAL: OnceLock<Option<Arc<ExternalTelemetry>>>` — never `opentelemetry::global` — and emission requires `is_settings_gate_open() && ext.active` (`external/mod.rs:335-338`). Every log record is re-validated at export time by `RedactingLogExporter` → `record_is_clean`, which drops the record unless each attribute key is schema-named, each gated key's `ContentGates` flag is open, string values carry no secret shape, and the value is scalar (`external/redact.rs:56-101`); metrics are dropped wholesale by `ValidatingMetricExporter` against `METRIC_ALLOWED_ATTR_KEYS` (`external/schema.rs:580-599`).
- invariants:
  - Providers must never be registered with `opentelemetry::global`; the internal tracer provider owns the global slot (`external/mod.rs:12`), and exporters may carry **only** customer headers parsed from `OTEL_EXPORTER_OTLP_HEADERS`/per-signal headers (`external/config.rs:510-531`) — the module has no `AuthCredentialProvider` dependency.
  - Remote policy is tighten-only by construction: `ExternalOtelRemotePolicy { force_disable, lock_content_gates }` has no enable direction, and `apply_remote_policy_on` can only clear `active` / zero the gates (`external/mod.rs:73-82`, `:395-417`).
  - Content is additive-opt-in and default-off: `log_user_prompts`/`log_tool_details`/`log_tool_content` are `.unwrap_or(false)` and `log_assistant_responses` `.unwrap_or(log_user_prompts)` (`external/config.rs:628-648`).
- failurePolicy: **mixed (record-level fail-closed, activation fail-open over a bounded fail-closed window)**. Any record that violates the pinned schema/gate/secret check is silently dropped and counted (`records_dropped`, `external/redact.rs:130-136`) — dropping is deliberate ("Dropping telemetry on a schema bug is acceptable; leaking is not.", `external/redact.rs:8`). Activation fails open: an unrecognized exporter selection becomes `None` with a warn (`external/config.rs:373-381`), an unrecognized protocol on an *active* signal disables the stream (`config.rs:408-415`), and an exporter-construction failure disables the stream (`external/mod.rs:171-180`). The settings gate is fail-closed-then-open: `SETTINGS_RESOLVED` starts **true** (open) and is closed by the leader before init; if no fleet policy arrives, `settings_gate_window_expired` opens it after the bounded window with a warn (`external/mod.rs:255-266`, `:316-331`). Once a remote force-disable lands, it flushes and drops subsequent emissions in-process (`external/mod.rs:410-416`).
- constants: `ENV_MASTER_SWITCH`="GROK_EXTERNAL_OTEL" (crates/codegen/xai-grok-telemetry/src/external/config.rs:41); `DEFAULT_SETTINGS_GATE_MAX_WAIT`=30s (crates/codegen/xai-grok-telemetry/src/external/mod.rs:263); OTEL exporter timeouts 10_000 ms / metric interval 60_000 ms / logs interval 5_000 ms (crates/codegen/xai-grok-telemetry/src/external/config.rs:680-693); `MAX_CONTENT_BYTES`=60*1024, `MAX_STRING_LEN`=512, `MAX_TOOL_INPUT_JSON_BYTES`=4*1024, `MAX_COLLECTION_ITEMS`=20 (crates/codegen/xai-grok-telemetry/src/external/truncate.rs:6-20); `SCOPE_NAME`="ai.xai.grok_code" (crates/codegen/xai-grok-telemetry/src/external/schema.rs:17); defaults `http://localhost:4318` / `:4317` (crates/codegen/xai-grok-telemetry/src/external/config.rs:234-236).

### telemetry-consent-and-mixpanel-gating
- what: Product analytics ("phones home" to xAI) is a three-state mode that is **off unless configured**, and it is gated at both the client-construction and the call sites. `TelemetryMode` is `Disabled | SessionMetrics | Enabled` with `#[default] Disabled` and `parse` accepting `1/true/yes/on/enabled/full`, `0/false/no/off/disabled`, `session-metrics|session_metrics` (crates/codegen/xai-grok-telemetry/src/config.rs:10-35). `TelemetryClient::init` stores `None` for `Disabled` (`client.rs:462-466`), the Mixpanel client is built only when `config.mixpanel_enabled && mixpanel_token.is_some()` (`client.rs:82-89`), and the emit entry points short-circuit on the installed mode — `log_event` requires `client::is_enabled()` (`session_ctx.rs:137-139`), `log_session_event` requires `is_session_metrics_enabled()` (`session_ctx.rs:170-172`). The effective mode is resolved by the shell as Requirement-pin > `GROK_TELEMETRY_ENABLED` env > `[features] telemetry` > remote settings > **default `Disabled`** (`crates/codegen/xai-grok-shell/src/agent/config.rs:2384-2404`).

An unrecognized mode string logs `TELEMETRY_MODE_UNKNOWN` and deserializes to `Disabled` (`config.rs:91-98`); with no client installed `track` returns immediately (`client.rs:285-292`); transport failures are swallowed (`let _ = client.http_client.post(...).send().await`, `client.rs:345-352`; `mixpanel track failed` warn only, `client.rs:377-380`); a missing client makes `sync_profile` a no-op (`client.rs:396-409`).

### version-bounds-startup-gate
- what: An admin-supplied version window that can refuse to start the CLI. `enforce_version_policy_or_exit()` resolves `VersionPolicy::resolve()`, compares the installed version against `required_minimum`/`required_maximum`, and on a determined violation prints an actionable message and calls `std::process::exit(1)` (`crates/codegen/xai-grok-update/src/version_policy.rs:97-105`). `evaluate_required_range` is the pure decision core returning `InRange | Below | Above` (`version_policy.rs:26-57`), and `check_install_target` separately refuses an explicit `--version` pin below `installable_floor()` while still allowing a pin **above** the ceiling so a too-new install can recover (`version_policy.rs:61-75`). It is wired into the shipping binary on all three entry paths — interactive (`crates/codegen/xai-grok-pager-bin/src/main.rs:2365`), headless (`:2304`), and the `agent` subcommand (`:2132`) — deliberately after recovery subcommands have returned (`version_policy.rs:95-96`).
- invariants:
  - Every ambiguous input must fail **open**: a contradictory range (`has_contradictory_required_range()`) and an unparseable running version both return `InRange` with a warn (`version_policy.rs:27-38`).
  - `minimum`/`maximum` are updater-only knobs; only `required_minimum`/`required_maximum` may gate startup (`version_policy.rs:1-2`).
  - Do not hoist the call in front of the admin-recovery/`setup` subcommands — that locks out the tool an admin needs to fix the pin.
- failurePolicy: **mixed** — policy *evaluation* fails open (malformed/contradictory config can never brick the CLI), while a determined out-of-range version is a hard fail-closed refusal (`std::process::exit(1)` at `version_policy.rs:104`), with `required_range_message` producing the org-facing copy (`version_policy.rs:77-93`).
- constants: exit code 1 (crates/codegen/xai-grok-update/src/version_policy.rs:104); installed-version override env `GROK_TEST_VERSION` (crates/codegen/xai-grok-version/src/lib.rs:7, `:34-38`); `VERSION = option_env!("GROK_VERSION")` else `CARGO_PKG_VERSION` and `IS_DEV_BUILD = option_env!("GROK_VERSION").is_none()` (crates/codegen/xai-grok-version/src/lib.rs:9-15); floor-violation message "the minimum allowed version is {minimum}" (crates/codegen/xai-grok-update/src/version_policy.rs:16-23).

### installer-classified-self-update
- what: A background/leader-driven updater whose allowed direction of version movement is derived from *how the binary was installed*. `get_installer()` resolves `GROK_INSTALLER` > `GROK_MANAGED_BY_NPM`/`GROK_MANAGED_BY_INTERNAL` > `npm_config_user_agent` > `[cli] installer` config > `node_modules` path inspection > `"internal"` (`crates/codegen/xai-grok-update/src/auto_update.rs:459-494`); `installer_allows_downgrade` returns `true` only for the xAI-authoritative backends `internal`/`gh-release` and never for `npm` (`:542-548`), which `needs_update` then applies together with channel rules (stable/enterprise reject pre-release candidates, `:508-535`). The internal path fetches `<base>/grok-<version>-<platform>` preferring `.zst`/`.gz` sidecars (`:1370-1394`), caps decode output at `MAX_DECODED_BYTES` (`:1337-1341`), **smoke-tests** the artifact by exec'ing `--version` with an ETXTBSY retry budget (`:1504-1542`), and only then activates it by swapping `~/.grok/bin/{grok,agent}` atomically with full rollback capture (`:1727-1802`, `:1806-1916`).
- invariants:
  - Verification is the smoke test alone — there is no checksum or signature check on the downloaded artifact (the code path downloads, chmods, smoke-tests, and activates: `:1600-1611`; the "verified by a smoke test, not a checksum" statement is the doc at `crates/codegen/xai-grok-update/src/version.rs:27-28`). - failurePolicy: **mixed/fail-closed on activation, fail-soft on the check path**. A failed smoke test deletes the downloaded binary and leaves the current version untouched (`:1607-1611`); a failed swap rolls back and returns the error (`:1774-1793`). Conversely every "should I update" error path is a silent no-op (`Ok(UpdatePlan::Skip|Unavailable) | Err(_) => return BackgroundUpdateCheck::none()`, `:599-604`; `:705-708`).

### crash-capture-and-previous-session-report
- what: A two-phase crash pipeline. `install()` registers `sigaction` handlers for SIGBUS/SIGSEGV/SIGABRT with `SA_SIGINFO | SA_ONSTACK | SA_RESETHAND` (crates/codegen/xai-crash-handler/src/handler.rs:297-310); SIGABRT is hooked because release builds ship `panic = "abort"`, so a Rust panic otherwise dies as a bare `Aborted` (handler.rs:283-292). The handler is async-signal-safe by construction — PC/FP extracted from the ucontext for linux/macOS x86_64+aarch64 (handler.rs:36-153), a frame-pointer walk doing only raw pointer reads (handler.rs:160-190), an alternate signal stack of `ALT_STACK_SIZE`, and a static `.bss` write buffer (`handler.rs:196`, `:208`). Crucially the blob is written **with the crash PC before frame walking**, so a secondary fault still leaves a usable report (handler.rs:378-387). At next startup `check_previous_crash` parses the fixed-layout `GCRX` blob, symbolicates it, writes a 0600 report, archives to `history/` keeping `MAX_HISTORY`, and deletes the blob (crates/codegen/xai-crash-handler/src/lib.rs:122-149, `:155-179`, `:181-203`).
- invariants:
  - The signal handler must stay allocation-free (raw pointer reads, `libc::write`, atomics — handler.rs:11-14); the write buffer is a static `[u8; MAX_FILE_SIZE]` (handler.rs:196).
  - Crash reports may contain source paths and backtraces, so they must be owner-only, and a *preexisting* 0644 file must be tightened before the write (lib.rs:151-179).
  - `check_previous_crash` must run before `install`, which opens `last-crash.bin` with `O_TRUNC` (lib.rs:12-15).
- failurePolicy: **fail-soft**. Every step is `Option`/`let _ =` (`std::fs::read(&crash_file).ok()?`, `CrashBlob::parse(&data)?`, `let _ = write_owner_only(...)`, `let _ = std::fs::remove_file(...)` — lib.rs:124-138), and a failed report write still returns the `CrashReport`. The process still terminates with the original signal semantics: the handler restores `SIG_DFL` and re-raises, preserving exit status and core dumps (handler.rs:257-269).
- constants: `MAGIC`=b"GCRX", `VERSION`=1, `MAX_FRAMES`=64, `VERSION_STRING_LEN`=32, `HEADER_SIZE`=64 bytes, `MAX_FILE_SIZE`=64+64*8=576 (crates/codegen/xai-crash-handler/src/format.rs:7-33); `MAX_HISTORY`=5 (crates/codegen/xai-crash-handler/src/lib.rs:43); `ALT_STACK_SIZE`=16*1024 (crates/codegen/xai-crash-handler/src/handler.rs:208); paths `last-crash.bin`, `last-crash-report.txt`, `history/crash-<timestamp>.txt` (crates/codegen/xai-crash-handler/src/lib.rs:123, `:131`, `:185`) under `<grok_home>/crash` (crates/codegen/xai-grok-pager-bin/src/main.rs:1955); gate env `GROK_CRASH_HANDLER` (crates/codegen/xai-grok-shell/src/util/config/resolve/crash_handler.rs:5).
- evidence:
  - `crates/codegen/xai-crash-handler/src/handler.rs:297-310`
  - `crates/codegen/xai-crash-handler/src/handler.rs:378-387`
  - `crates/codegen/xai-crash-handler/src/format.rs:7-33`
  - `crates/codegen/xai-crash-handler/src/lib.rs:122-149`
- notes: **Default OFF** and gated, not a cargo feature. `resolve_crash_handler_enabled_layers` orders requirement > `GROK_CRASH_HANDLER` env > user `[diagnostics] crash_handler` > managed > remote settings `crash_handler_enabled`, defaulting `false` (crates/codegen/xai-grok-shell/src/util/config/resolve/crash_handler.rs:13-29), and the sync disk reader used before Tokio starts defaults `false` too (`:74-87`). ## BONUS

### system-power-sleep-gate — what `xai-system-power` actually IS
`xai-system-power` is a small (4-file) cross-platform suspend/resume **notification + query + assertion** crate whose only in-repo consumer is `xai-grok-shell`'s auth refresh sleep gate. It is not lifecycle/host management; it exists so an OIDC refresh is never straddling a suspend.

- what: The crate exposes `PowerEvent { WillSleep, DidWake }` (`crates/codegen/xai-system-power/src/lib.rs:38-56`), `PowerState { FullWake, DarkWake, Unknown }` (`:74-87`), `current_power_state()` (`:95-97`), `hold_awake(reason) -> Option<SleepAssertion>` (`:106-108`), and `SystemPowerListener::start` (`:176-181`). Per-OS: macOS registers `IORegisterForSystemPower` on a dedicated `CFRunLoop` thread and maps `kIOMessageCanSystemSleep` **and** `kIOMessageSystemWillSleep` to `WillSleep` with an ack, `SYSTEM_WILL_NOT_SLEEP`/`HAS_POWERED_ON` to `DidWake`; the `IOAllowPowerChange` ack is sent only **after** the callback returns, so a bounded blocking handler delays the suspend (`src/macos.rs:255-286`, constants `:25-28`); `hold_awake` creates an `IOPMAssertionCreateWithName(PreventSystemSleep)` RAII guard (`src/macos.rs:293-303`, `:357-372`). Linux takes a logind `delay` inhibitor (`Inhibit("sleep","grok","Pause token refresh across sleep","delay")`), subscribes to `PrepareForSleep`, calls back, then **drops the inhibitor only after the callback returns**, re-acquiring it after wake (`src/linux.rs:14-16`, `:49-56`, `:66-85`); its `hold_awake` is `None` (`:104-105`) and `current_power_state` is `Unknown` (`:88-93`). Windows uses `PowerRegisterSuspendResumeNotification` with `DEVICE_NOTIFY_CALLBACK` and no message loop, mapping `PBT_APMSUSPEND`=0x0004 / `PBT_APMRESUMESUSPEND`=0x0007 / `PBT_APMRESUMEAUTOMATIC`=0x0012 (`src/windows.rs:19-23`, `:44-60`); other targets get a no-op `imp` whose `start` returns `None` (`src/lib.rs:128-153`).
- invariants: callbacks fire on a platform thread and must be `Send + Sync`; a `WillSleep` handler may block only within the OS budget (~30s macOS, logind `InhibitDelayMaxSec` default 5s) because ack/inhibitor-release happens after it returns (`src/lib.rs:26-34`); `DidWake` may follow a `WillSleep` with no intervening suspend (a vetoed idle-sleep query), so handlers must be idempotent (`src/lib.rs:46-55`).
- failurePolicy: **fail-soft** — `start` returns `None` (unsupported OS, missing logind, registration failure, screenless Mac) and the dependent feature simply does not engage; `hold_awake` returns `None` and callers "carry on" (`src/lib.rs:166-181`, `:99-108`); Linux intentionally has no clean stop (worker thread runs to process exit, `src/linux.rs:18-28`).
- constants: `SLEEP_GATE_MAX`=120s, `DARK_WAKE_DEFER_MAX`=120s, `SLEEP_ACK_MAX_WAIT`=20s on macOS / 3s elsewhere (crates/codegen/xai-grok-shell/src/auth/manager/sleep_gate.rs:28, `:41`, `:50-53`); `K_IOPM_ASSERTION_LEVEL_ON`=255, `ASSERTION_TYPE_PREVENT_SYSTEM_SLEEP`="PreventSystemSleep", `CFRunLoopRunInMode` timeout 5.0s (crates/codegen/xai-system-power/src/macos.rs:226, `:293`, `:303`); `ALT`/D-Bus names `org.freedesktop.login1` (crates/codegen/xai-system-power/src/linux.rs:14-16); `GROK_AUTH_FORCE_DARK_WAKE`=1|0 forces the dark-wake answer (crates/codegen/xai-grok-shell/src/auth/manager/sleep_gate.rs:251-264).

### requirements-pinned-managed-policy-enforcement (fail-closed)
Found while reading the telemetry/update/version paths; lives mostly in `xai-grok-config` + `xai-grok-shell`, not in the assigned crates.

- what: `[telemetry] otel_*` keys present in merged `requirements.toml` act as **pins** (managed-env model). `RequirementOtelPins::from_requirements` turns each listed key into an env override and **traps omitted content gates**: if *any* of `CONTENT_GATE_KEYS` is listed, every unlisted sibling is force-set to `"0"` so a developer env var cannot inherit it (`crates/codegen/xai-grok-shell/src/agent/external_otel_pin.rs:16-21`, `:178-199`, `:281-285`). `names_to_strip()` computes the env names the production path must `remove_var` — whole generic/signal families, client cert/key families, and CA siblings (`:302-324`) — and `hide_unlisted_file_siblings` removes the same holes from the user/managed TOML table so file config cannot retarget a pinned endpoint (`:330-344`). `strip_conflicting_process_env`/`apply_process_env_strip` perform the actual `std::env::remove_var` sweep at the composition root (`:376-404`), and `getenv_with_pins` overlays pins on an injected getenv without mutating env (`:352-366`). - invariants: a generic-key pin must strip the unlisted per-signal siblings (`GenericSignalFamily::apply`, `:128-139`); a CA pin strips only CA siblings and must **not** strip endpoints (`:109-121`, `:318`, test `:578-592`); a client cert/key pin *does* strip endpoints (`:167-172`); the env strip must run exactly once from a single-threaded composition root (unsafe fn contract, `:368-375`).

The inherit trap turns "admin listed one gate" into "the other three are off"; unreadable/absent managed policy is treated as armed elsewhere (`fail_closed_policy_armed_at` returns `true` when `requirements.toml` exists but is unreadable, `crates/codegen/xai-grok-config/src/managed_cache.rs:184-198`). `FAIL_CLOSED_KEY`'s env override `GROK_MANAGED_CONFIG_FAIL_CLOSED` applies only to `requirements.toml` (`crates/codegen/xai-grok-config/src/validation.rs:28-30`), and a non-boolean `fail_closed` value is treated as **false** with a warn (`validation.rs:18-25`).
