## What a "mechanism" is

A named **capability**, not a module and not a command. Examples of the right granularity:

- "four-tier input admission (send / followup / steer / inject) differing on inbox boundary × wake"
- "append-only shadow projection: compaction never rewrites the log, `deriveMessages` hides by union of shadow sets"
- "startup-applied OS sandbox that REFUSES TO START rather than run unprotected"
- "guardian auto-review subagent: 90s fail-closed timeout, strict JSON contract, per-turn denial breaker"

`core-agent` alone contains several distinct mechanisms (turn loop, tool-batch commit ordering, budget ladder, serial lane). Do **not** emit one entry per module.

## Per-mechanism schema

```
{
  "name":            "short canonical kebab-case name for the CAPABILITY",
  "what":            "2-4 sentences: what it does and how it is implemented",
  "invariants":      ["design constraints a maintainer must not break"]   // 0-3
  "failurePolicy":   "fail-open | fail-closed | fail-soft | mixed — and what actually happens on failure",
  "constants":       [{"name":"...","value":"...","evidence":"path:line"}]  // 0-4
  "evidence":        ["path:line", "path:line-line"],   // AT LEAST ONE, a real line in this repo
  "modules":         ["which of your modules implement it"],
  "verified":        true   // ONLY if you actually opened the cited lines
}
```

## Module coverage — use PATTERNS

`moduleCoverage` must account for **every** module in your checklist, but it does **not** need one line per module. It accepts glob patterns:

```json
"moduleCoverage": {
  "core-agent": "turn loop; tool-batch commit ordering; budget ladder",
  "client/*":   "web-client UI plugin host plumbing — hosts the browser UI, contributes no engine capability",
  "util/*":     "shared utilities — no capability claim",
  "codex-rs/ansi-escape": "ANSI escape handling — infrastructure"
}
```

`*` matches within one path segment, `**` across segments. The assembler resolves patterns, and a module covered only by a pattern counts as accounted for. **Be honest**: a pattern is a claim covering every module it matches, so if the group is not uniform, list the exceptions individually.

## Also produce

- `hintCorrections`: `[{module, hintWas, assigned, why}]` — modules where the classifier's domain hint is wrong. This is expected and valuable; it is the evidence that machine classification cannot replace reading the source.
- `domainsAbsent`: `[{domain, why}]` — domains where your source genuinely has nothing.

## Hard rules

1. **NO CLAIM WITHOUT `file:line`.** If you cannot cite it, set `verified:false`. An adversarial verification pass samples these and reports a forgery rate.
2. **README/docs are NOT sufficient evidence.** Go to `src/`.
3. **Mechanism, not module.** One entry per package is wrong.
4. Where a capability exists in code but is **not wired into any shipped host**, or is **behind a flag whose default is off**, or is **inert in this build**, say so explicitly in `what`. That distinction changes what the comparison means and is one of the most valuable things you can report.
5. **Do NOT evaluate, praise or criticise.** Record what IS. Disposition is decided later by other agents.
