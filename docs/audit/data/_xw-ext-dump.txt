--- NAME: lsp-integration-with-one-server-per-run-scheduling  [verified=True]
WHAT: A Content-Length-framed JSON-RPC connection over a spawned subprocess with an initialize handshake, a SERIALIZED abortable query queue and transient didOpen/didClose lifecycles. Only Content-Length is parsed and every frame is bounded: the decoder rejects a missing/odd header and an oversized message by throwing, and the connection treats an undecodable frame as stream corruption and fails ALL pending requests. Abort is protocol-level (an already-aborted signal rejects immediately; a later abort sends $/cancelRequest, drops the pending entry and rejects), server->client REQUESTS are always answered (with -32601 if no handler) because JSON-RPC mandates a response or the server hangs, and server->client NOTIFICATIONS are ignored by design (the pull model). Capability gating is fail-closed: an explicit false OR an ABSENT capability key throws LSP_UNSUPPORTED_OPERATION. All queries are serialized on one promise chain and each runs a transient didOpen -> request -> didClose(finally) lifecycle with the file's CURRENT bytes. Teardown is bounded in four steps (shutdown bounded by shutdownTimeoutMs, exit, a kill grace period, then kill escalation) and dispose is idempotent. Mount is ONE server per RUN enforced by a module-level reservation set: a second mount, even with a different name, is a hard error (multi-server is an explicit non-goal) because the tool surface has no server selector; a failed mount disposes the instance and releases the reservation.
INVARIANTS: One query at a time; a failed query must not stall later ones | An absent capability is not evidence of support | Dispose never waits forever on a hung server
FAILUREPOLICY: fail-closed on protocol and capability boundaries (undecodable/oversized frames fail all pending requests, unsupported operations throw, a hung initialize rejects with LSP_INITIALIZE_TIMEOUT, requests on a disposed instance throw); shutdown/exit during dispose and kill on a dead process are best-effort
