## A. 已核實的 bug（[✓ 核實]）

### BUG-1 [HIGH] `node:sqlite` 的 `ExperimentalWarning` 洩進 TUI 螢幕 → 全 TUI harness suite 失敗
- **檔案**：`packages/session-query/src/file-backed.ts:5` + `src/index.ts:1`（`import { DatabaseSync } from "node:sqlite"`）；`apps/cli/src/index.ts:13` 頂層 import `createFileBackedSessionQuery`。
- **根因**：M29 的 file-backed **搜尋索引**（非持久化）用 `node:sqlite`；**入口完全沒有對 `ExperimentalWarning` 做抑制**。Node 22 對 `node:sqlite` 噴 `SQLite is an experimental feature…` 到 stderr → TUI 的 PTY 把 stderr 併進螢幕 → 污染每個 case 的預期欄位。
- **失敗場景**：`pnpm --filter @i-harness/tui test` → `case-011/012/014/015/016/017/018/019/020/023` 全失敗；例如 `row 1: expected "  ⎇  ~/workspace" got " e⎇  ~/workspaceature and might change at any "`（警告字節嵌進 cwd 欄）。
- **影響**：Node 22 下 TUI 全 10+ case 紅；真實 TUI 螢幕也被警告污染。
- **修法**（不動 M29 設計）：在 TUI/CLI process 入口過濾/抑制 `node:sqlite` 的 ExperimentalWarning（`process.on("warning", …)` 只放行非 sqlite 警告），或確保 stderr 不進 PTY 螢幕。**注意**：此為 Node 22 限定（`node:sqlite` 在 22 仍 experimental；Node 24 可能已穩定不噴）。engines 允許 `>=22.18`，故 Node 22 是支援版本 → 真 bug。

### BUG-2 [HIGH] Gemini 同名並行工具呼叫被折疊成一個
- **檔案**：`packages/llm-gemini/src/index.ts:153-181`（`handleFunctionCall` / `finalizeCalls`）。
- [✓ 核實] `handleFunctionCall` 用 `pendingCalls.find((c) => c.name === fc.name)`（:155）——**按 `name` 去重**。兩個同名不同 args 的 `functionCall` 撞成一個 pendingCall；`finalizeCalls`（:166-181）JSON.parse 合併失敗時淺合併（`Object.assign({}, ...rawArgs)`），後 args 覆蓋前者。
- **失敗場景**：Gemini 回 `parts=[{functionCall:{name:"get_weather",args:{city:"A"}}},{functionCall:{name:"get_weather",args:{city:"B"}}}]`（合法並行同工具）→ 只 emit 一個 `{name:"get_weather",args:{city:"B"}}`，城市 A 與第二個呼叫整隻丟失。Bedrock 依 `contentBlockIndex` 處理並行正確 → Gemini-only 缺陷。

### BUG-3 [HIGH] `removeProvider` 對「只在 legacy `tui.providers`」的 provider 是靜默 no-op
- **檔案**：`packages/provider-runtime/src/index.ts:171-182` × `packages/settings/src/index.ts`（legacy read 投影 `normalizeLlmWithLegacy`）。
- [✓ 核實] `removeProvider` 先 `const llm = canonicalLlm(options.settings)`（讀 canonical `llm` 區，**不含** legacy 合併行），`if (llm.providers[id] === undefined) return`（:174）。對只在 `tui.providers`（M46a 舊態、從未遷進 canonical 平面）的 provider，`llm.providers[id]` 為 undefined → 早 return，**什麼都不刪**；settings 讀端又載入 legacy 行 → 每次 reload 復活。
- **失敗場景**：升級後 `tui.providers={"deepseek":{…}}`，UI 點「Remove provider」→ 沒刪，`settings.get().llm.providers.deepseek` 仍解析、重載即復活 → **該 provider 永遠刪不掉**。

### BUG-4 [HIGH] `scrollBy` 用整屏高度而非 scrollback 視口高 → 歷史尾不可達
- **檔案**：`packages/tui/src/app/loop.ts:1902-1912`（亦 `pageStep` :1968-1970、wheel `applyScrollLines` :1916-1920）。
- [✓ 核實] `scrollBy` 用 `const page = this.opts.renderer.buffer.height`（**整屏** grid 高度）算 `max = total - page + 1`；但正確視口高是 `layout.scrollback.h`（agent 佈局下 status+prompt+turn 行佔掉，scrollback.h 較小，`anchorDisplayLine` loop.ts:832-840 已用此模式）。`mouse.ts` 滾動條用 `layout.scrollback.h` → **鍵盤/滾輪與滾動條對「底部」永久不一致**。
- **失敗場景**：終端 80×24、歷史 100 行、scrollback.h≈21 → 真 bottom 應為 offset 80；`scrollBy` 的 `max = 100-24+1 = 77`。follow 時按 PageDown → `cur = max = 77` → 直接**向上跳**離底，且 94-100 行**永遠看不到**。最常見捲動手勢即觸發。

### BUG-5 [MED-HIGH] `windowedDiff` 大檔小 append 被算成巨幅改動
- **檔案**：`packages/text-diff/src/index.ts:87-136`（overlap 護欄 :113)。
- [✓ 核實] head/tail 視窗只在「兩側尾窗**絕對分離**」時才跳過 tail（:113 `overlaps`）；小 append 時 `aStart = bStart + delta`，兩窗**絕對重疊**但仍 diff 索引對齊 → `before[bStart+i]` vs `before[bStart+delta+i]` 因 append 偏移而逐行不同。
- **失敗場景**：60000 行 + 10 行 append（> `MAX_LINES` 50000 → 走 windowedDiff）→ 報告 ~9990 刪 + ~9990 增，而非 10 行 append。護欄註記「純 append 每行會被偽造成改變」但只在 delta≥window 才觸發 → **漏掉小 append 常見態**。
- **更正 2026-09-08**：實測（m50，60000 行 + 10 行 append）為 `added: 10, deleted: 10`（幻影刪除有界於 Δ，非 ~9990），修後 `added: 10, deleted: 0`；見 `docs/superpowers/plans/2026-09-08-m50-bugfixes.md`（BUG-5 範圍修正）。

### BUG-6 [MED-LOW] mcp-client 測試未 await 斷言
- **檔案**：`packages/mcp-client/test/oauth.test.ts:41`——`expect(provider.codeVerifier()).resolves.toBe("verifier-abc")` 未 `await`。
- [✓ 核實] 未 await 的 resolves 斷言；Vitest 3 將轉為失敗。屬測試品質（可能空洞通過）。

## C. 你問的「長 session 無法 rewind/resume」——結論
**未確認到確切 bug。** 三個面向：
1. **已確認的 rewind 限制**（非長 session 問題）：`packages/rewind` v1 honest scope——**shell / 外部編輯器改動不可回滾**（`service.ts:38`、`types.ts:69`），`unTracked` 只**列出**、不猜測恢復。
2. **候選觀察區**（長 session 相關、無缺陷實證）：`recorder` 的 **`turnIndex` 由 journal 長度推導**（`recorder.test.ts:113`）+ rewind 後 **`truncate(targetTurnIndex)`** 只保留前 N 個 point（`service.ts:223`、`store.ts:103-108`）——多次 rewind + 長 session 下 index/truncate 一致性是薄弱點；TUI 子代理檢查 rewind store/recorder/service 於被測 case 正確。
3. 若有具體場景（例「長 session 多次 rewind 後 resume 或 rewind 到某早期 turn」），可另寫重現測試來釘死；**在此之前不臆造為已確認 bug**。
