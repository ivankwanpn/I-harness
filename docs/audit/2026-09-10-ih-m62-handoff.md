## 4. 三個「文件與實作矛盾」的實測釘正

### 4a. 外殼批准是不對稱的（既有行為，非本輪引入）

`decide()` 的註解寫「any other non-readOnly tool requires approval」，但 `SHELL_TOOLS` 分支**只在 `classifyDanger() != "none"` 時**才 ask；安全指令掉到 `return undefined`（allow）。**確認它又被測試釘住**（`Layer 3: harmless bash command executes`）。→ 裁定：**不改行為，只讓註解誠實**（`src/index.ts` 加「三層 as implemented」總表 + 兩處就地註記），並補一條**判別性**測試（answerer 改成 `throw`，證明「不是被批准，是根本沒問」）。

### 4b. 危險分類器的繞過面：**實測推翻我自己的懷疑**

24 條指令走**與 `decide()` 完全相同**的管線。**引號、換行、`&`、`||`、wrapper、轉義、呼叫運算子全部都會問**——分類器比我以為的硬。真正漏的只有兩類：

1. **輸出重導向**（`echo hi > /etc/passwd`）→ **已修**（`>`/`<` 加入 `METACHAR`），突變證明：拿掉就紅在 `promise resolved … instead of rejecting`（真的執行了）
2. **清單外指令**（`chmod`/`mkfs`/`dd`/`Format-Volume`/`iex`）→ **未修**（denylist 的固有性質，擴充是打地鼠，**屬產品邊界**）

→ 完整 24 列 verdict 表在 `docs/audit/2026-09-10-m62-shell-danger-classifier-measurement.md`。

### 4c. web 路徑完全不隔離外殼（**已修**）

`settings.sandboxMode` **全倉庫只有寫入者、沒有讀取者**：`AssemblyOptions` 有 `sandbox` 且會真的組出沙箱，但 `SessionServiceOptions` 底下 `service.ts` 不見「sandbox」，`web.ts` 從不傳。**實測**：真 `createWebServer` + `"sandboxMode": "workspace-write"` → 外殼指令**照樣寫到 workspace 外**（`content: "ESCAPED"`）。web 內建的 `/sandbox` 指令因此是**假保證**。

**修法**：`WebServerOptions.sandbox` 明確覆寫 → 未給時讀 settings（**先 `await settings.load()`**）→ 傳給 `createSessionService`。**判別性回歸測試**：拿掉 `sandbox:` 那行 → 紅在 `a shell command escaped the workspace`。

**過程中兩個我自己的假陽性**（已寫進報告，因為它們比修補本身更值得記）：
- 測試的 `outside` 原本落在 `$env:TEMP` 根目錄，**那裡純 Windows 就拒絕寫入** → 「沒逃逸」是作業系統的功勞
- 測試交進**沒 load 的 `SettingsStore`**，而 `get()` 在 `load()` 前回的是**預設值** → 測試靠預設通過、**根本沒碰到設定**，突變體因此存活

### 4d. session 的 `cwd` 與模型看到的 workspace 不一致（**已量測、已加警告**）

**這是我在 §7b 列為第一順位的那一項，已執行完畢。**

**量測（真模型、真工具、可觀察）**：server 起在 `D:\ih-ws-A`，用 `POST /api/sessions { cwd: "D:\ih-ws-B" }` 建 session，然後叫模型執行**相對路徑**寫入 `Set-Content -Path 'relative-probe.txt'`：

```
tool/call:   pwsh {"command":"Set-Content -Path 'relative-probe.txt' -Value RELATIVE"}
tool/result: {"stdout":"","stderr":"","exitCode":0}
file created in SERVER  cwd (D:\ih-ws-A): true
file created in SESSION cwd (D:\ih-ws-B): false
```

**→ 模型（與外殼、沙箱可寫根、runtime-context）用的是 server 的 cwd，不是 session 的 `cwd`。** 用相對路徑是刻意的：**檔案落在哪個目錄就是答案**，不必依賴模型自己的敘述。

**根因（讀碼）**：`WebServerOptions.workspace` 是**單一全域值**（`apps/cli` 一律傳 `process.cwd()`），它是 attachments、plugin root、assembly 的 `opts.workspace`（→ runtime-context 的 instructions section、外殼預設 cwd、沙箱可寫根）的唯一來源；而 `SessionServiceOptions` 底下**沒有任何 per-session workspace 的解析器**——`service.ts` 全檔不見「workspace」二字（它靠 `...(opts)` 帶過去）。`POST /api/sessions { cwd }` **只**把 cwd 正規化後寫進 workspaceRegistry（`meta.workspaceId`，供列表分組），**執行面完全不看它**。

**影響**：把 session 指向別的資料夾的呼叫者，會得到一個**在別處執行**的 session。模型被告知的可寫範圍、外殼的工作目錄、沙箱邊界，**全部是 server 的啟動目錄**。網頁目前不暴露 workspace 選擇器，所以一般使用者是「一個 server = 一個 workspace」；但**API 層的這個承諾是假的**。

**處置：不拒絕，但讓它說出來。** 拒絕（400）會破壞一個**刻意的功能**（`workspaces-routes.test.ts` 明確釘住「cwd 自動建立並記錄 workspace」），所以改為**相加式**：

- `WebHostOptions.workspace?: string`（新增）——讓 host 知道 executor 實際在哪個 workspace 跑；`apps/cli` 傳 `opts.workspace`
- `POST /api/sessions` 的回應在 **cwd ≠ 執行 workspace** 時多一個 `workspaceWarning` 欄位，內容說明「cwd 只供分組，這個 server 一律在自己的 workspace 執行」
- **判別性證明（突變測試）**：拿掉 host 的 `workspace` 選項 → 新測試紅在 `workspaceWarning` 是 `undefined`；負控制（cwd 等於執行 workspace、或不給 cwd）**沒有**警告，兩者都綠

**沒有做**：真正的 per-session workspace 執行（那要把 workspace 解析器接進 assembly build、外殼 cwd、沙箱可寫根——一個 feature 級的改動）。**仍是單一 workspace 的 server。**

## 6. 方法論教訓（本輪學到的）

- **`SettingsStore.get()` 在 `load()` 之前回預設值，不是檔案值。** 任何拿 store 當真源的地方都必須先 load，否則**靜默忽略操作者的設定**。
- **不要用 PowerShell `Select-String` 掃 dist bundle**：對 5 MB 單行 UTF-8 內容會**假陰性**（`"Send a prompt"` 誤報 MISSING，`node -e` 的 `String.includes` 全部 true）。用 Node 讀檔比對。
- **並行跑測試會互相污染判定**：全套在背景跑 + `case-027` 在前台跑 → `packages/tui` 自報 **70 檔 / 772 測全過**，pnpm 卻判它失敗。
- **「測試綠了」不等於「驗到了想驗的東西」**：本輪兩次假陽性（§4c）都是這個形狀，只能靠**突變測試**（拿掉修補必須紅）分辨。
- **沒有複現就沒有根因**：`case-027` 我試過單獨／並行／CPU burner，只量到 2 倍慢化（4.4s → 8.2s），**不是 150 秒停滯**，因此拒絕憑猜測改一條 300 秒預算的場景。
