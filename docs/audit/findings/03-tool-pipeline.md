### F03-1: Guard enforcement is conditionally skipped — a non-`allow`, reason-less pre-execute decision dispatches the call and bypasses the monotonic guards

- **Severity:** Critical
- **Component:** `packages/core/tools/src/index.ts`
- **Evidence:** `packages/core/tools/src/index.ts:1475-1478` — the `tools/pre-execute` waterfall resolves to a `PreToolDecision` and feeds it straight into ask-resolution, with no runtime vocabulary check; `packages/core/tools/src/index.ts:1486-1488` — `denialReason` is computed only as `decision.kind === 'allow' ? this.guardReason(exec) : decision.reason`, so the monotonic guard layer runs ONLY for exactly-`allow` decisions; `packages/core/tools/src/index.ts:1489-1496` — denial happens only when `denialReason !== undefined`, so a `deny`-shaped decision without a reason and any non-vocabulary decision object produce `denialReason === undefined` and fall through to `return next({ kind: 'dispatch', exec })` at line 1501; `packages/core/tools/src/index.ts:704-706` — the documented monotonic guarantee that "guards have no allow result, listener ordering cannot turn a denial back into permission".
- **Disposition:** improved-writing
- **Reason:** the deny-only monotonic guard is the right invariant, but the implementation trusts an unvalidated runtime object; our kernel validates every pre-execute decision against the closed vocabulary and runs the guards before ANY dispatch, so no malformed or hostile decision can short-circuit them.
- **Details:** `PreToolDecision` is typed `allow | deny | ask` at compile time, but a listener-returned value is never re-checked at runtime. Any listener that returns an object whose kind is not exactly `'allow'` and whose `reason` is `undefined` — a code-generation typo `{ kind: 'deny' }`, a degraded hook, or a hostile plugin returning `{ kind: 'anything' }` — takes the `: decision.reason` branch, yields `undefined`, skips the denial branch, and dispatches the tool BODY while also skipping `guardReason` entirely (guards only run in the `'allow'` branch). This defeats the one property the registry advertises as order-independent — a denial cannot be turned back into permission. The `ask` path is safe (it resolves through `serviceAsk`, which always produces `allow`/`deny` with a reason), so the hole is specifically any decision that is neither `allow` nor `deny`-with-reason. I-harness's kernel should treat a non-vocabulary pre-execute return as a hard tool error and evaluate the monotonic guards unconditionally before dispatch, so a decision-shaped but malformed object can never reach a tool body.

### F03-2: OFFICIAL dsh performs no pre-execution approval on destructive commands — bash denial/approval is file-access-based sandbox escalation only (design observation)

- **Severity:** Minor
- **Component:** `packages/shell/tool-bash/src/index.ts` (+ `packages/shell/bash-sandbox`, approval policy in `packages/bundle/base/cordis.patch.yml`)
- **Evidence:** OFFICIAL `packages/shell/tool-bash/src/index.ts` has **no command-content consent gate and registers no `tools/pre-execute` listener**. Its only approval path is sandbox-mode escalation: `approveBashEscalation` at `:213-228`, delegating to `approveEscalation` (from `@deepseek-ai/dsh-sandbox`, imported at `:23`, called at `:223`), invoked from `execute` at `:334-335` for the `sandbox_permissions` + `justification` pair (validated at `:65-67`). Denial and approval are **file-access-based, not command-pattern-based**: `packages/shell/bash-sandbox/README.md:19` — denials are result facts inferred from the backend's own denial signatures (bwrap EROFS / Landlock EACCES / Seatbelt EPERM); `:25` — "Deny-only at the seam … the approval question lives in the tool layer (`dsh-tool-bash`), which drives the override"; `:88` — "`danger-full-access` deliberately bypasses `ctx.sandbox`". Approval policy matrix `packages/bundle/base/cordis.patch.yml:193-206` — `ask` for read-only/workspace-write, `never` for `danger-full-access` (`:205`). The official code itself acknowledges the gap: `packages/shell/tool-bash/src/index.ts:6-8` — `TODO(permissions): deployment policy belongs in tools/pre-execute and sandboxing executors`.
- **Disposition:** improved-writing
- **Reason:** official dsh performs no pre-execution approval on destructive commands — a `rm -rf` inside the workspace executes un-gated under the default `workspace-write` mode; an approval ask is reachable only as a *post-denial escalation* (`sandbox_permissions`+`justification` → `ctx.approval`), and under `danger-full-access` (approval `never`, `:205`) there is no human gate on any command. This is an explicit design stance (TODO `:6-8`), not a defect. I-harness's Windows-first approval+whitelist model should classify destructive operations at the parsed-effect boundary (after shell-quote stripping), which the official design leaves to the executor.
- **Details:** This finding originally described a `DESTRUCTIVE_COMMAND_RE` raw-string regex gate and a `tools/pre-execute` listener inside `tool-bash`; **that gate is our local modification and does not exist in the OFFICIAL tree** (full-tree grep: zero hits — see `docs/audit/reaudit-official.md`). OFFICIAL behavior to design against: no command-content consent anywhere in the shipped pipeline; the only human gate is the escalation flow after a sandbox denial, and `danger-full-access` (`approval: never`) removes even that. The `tools/pre-execute` allow/deny/ask gate exists as a kernel extension point, but official `tool-bash` registers nothing on it — the TODO at `:6-8` names exactly that seam as the intended home for deployment policy. For I-harness: keep the effect-time sandbox fence, but add a parsed-argv destructive-intent classifier at the pre-execute/effect boundary keyed on the capability identity that executes, so in-workspace `rm`/`rmdir`/`shred`-class effects hit the approval ask rather than relying on post-denial escalation alone.

### F03-3: `run_code` reserved transport re-enters the complete guarded pipeline per sub-dispatch — no policy shortcut

- **Severity:** Minor
- **Component:** `packages/core/tools/src/code-mode.ts` (+ `packages/core/tools/src/index.ts`)
- **Evidence:** `packages/core/tools/src/code-mode.ts:545-561` — each SDK bind call runs `scheduler.prepare` (pre-execute + monotonic guards, inside the ordered driver lane), then `scheduler.dispatch` and `finalize`/`finish` (post-execute) with per-sub-call `callId`; `packages/core/tools/src/code-mode.ts:477` — sub-calls carry `parent: exec.token` and the caller `agent`; `packages/core/tools/src/code-mode.ts:606-609` — the SDK bindings enumerate the CALLING AGENT's `registry.schemas(exec.agent)` view, so restricted globals vanish from bindings; `packages/core/tools/src/index.ts:1183-1189` — the transport is appended to the visible set outside capability filtering, but only for scopes whose mode presents it; `packages/core/tools/src/index.ts:1086` — `restrict()` refuses to name the reserved transport; `packages/core/tools/src/index.ts:1381,1423-1427` — under `mode:'code'` a model-direct call to any other name is collapsed to `UNKNOWN_TOOL` before the policy pipeline.
- **Disposition:** reuse
- **Reason:** no fault found — the reserved transport changes only VISIBILITY; every sub-dispatch re-enters the full guarded pipeline, so the approval/guard/sandbox policy stays uniform between native calls and program-issued calls.
- **Details:** the "outside the filterable layers" placement (`index.ts:1183-1189`) is presentation-only: the transport cannot be masked by a scope restriction and exists only for scopes whose presentation is not `native`. Each SDK sub-call is a first-class execution: it materializes arguments, runs `prepare` (pre-execute waterfall, approval `ask`, monotonic guards), dispatches under the around-waterfall, and is finalized through post-execute — so a policy that denies `write` also denies a program that calls `await tools.write(...)`. Cancellation is threaded correctly too: the run-scoped `runController` aborts on outer cancel AND on run settlement (`code-mode.ts:339,627`), and settled-but-aborted runs discard their result. Copy this transport design as the reference; the one property to preserve is "sub-calls re-enter the pipeline".

### F03-4: Timeouts are cooperative and opt-in — a missing watchdog plugin or an undeclared `timeoutMs` silently disables every deadline, and the registry cannot hard-kill a body

- **Severity:** Important
- **Component:** `packages/guard/timeout-policy/src/index.ts` (+ `packages/core/tools/src/index.ts`, `packages/util/timeout/src/index.ts`)
- **Evidence:** `packages/guard/timeout-policy/src/index.ts:58-59` — "A tool that declares no budget: no deadline, delegate unchanged", so a tool without `timeoutMs` runs ungoverned even with the policy mounted; `packages/guard/timeout-policy/src/index.ts:61-73` — the deadline is armed by THIS wrapper, which is itself an optional plugin a composition can omit (the base bundle mounts it, but nothing fails loud on its absence); `packages/core/tools/src/index.ts:230` — execute's JSDoc: "it cannot hard-kill same-process code"; `packages/util/timeout/src/index.ts:84` — `deadline()`'s signal "only notifies, so callers must stop their own work"; `packages/shell/tool-bash/src/index.ts:262` — bash advertises the executor's "configured default and cap, and kills the command on expiry" (real kill), while run_code declares no pipeline `timeoutMs` and relies instead on worker budgets (`packages/code-runtime/code-runtime-worker-thread/src/index.ts:240-242`, `computeMs` default 60000 / `maxWallMs` 600000 / `maxOutputBytes` 67108864).
- **Disposition:** improved-writing
- **Reason:** signal-based cooperative timeout is sound, but the effective-deadline depends on BOTH a per-tool `timeoutMs` declaration AND an optional composition plugin, and there is no fail-loud when the plugin disappears; the kernel must arm deadlines for every execution that declares one and gate the `TOOL_TIMEOUT` result on body quiescence.
- **Details:** two independent gates must both hold for a deadline to exist: the tool definition declares `timeoutMs`, and the `timeout-policy` wrapper is mounted in the composition. A regression that removes the plugin row from `cordis.yml` silently removes every deadline; a tool that omits `timeoutMs` silently runs without one. Second, enforcement is cooperative — `deadline()` only aborts the signal (`util/timeout:84`); the body must forward `exec.signal` and reach quiescence, and `execute` explicitly cannot hard-kill (`index.ts:230`). A body that ignores the signal settles late, AFTER the wrapper has returned `TOOL_TIMEOUT` to the model, so the model can retry a side effect that is still running. bash and run_code avoid this with executor-level kills and worker budgets respectively, but arbitrary in-process tools depend purely on the contract. I-harness should arm the deadline at the registry/loop for every tool that declares one (the wrapper existing only to customize), await the body's quiescence before materializing `TOOL_TIMEOUT`, and make a missing watchdog a load-time error in the base composition.

### F03-5: `bash` duplicate-registration pitfall — same-layer duplicates fail loud, but a scoped registration silently shadows the global `bash` and escapes every deny/allow restriction

- **Severity:** Important
- **Component:** `packages/core/scope/src/store.ts` (+ `packages/core/tools/src/index.ts`, `packages/subagent/subagent/src/child-agent.ts`)
- **Evidence:** `packages/core/scope/src/store.ts:45` — `NamedEntries.insert` throws when `data.has(name)`, the same-layer duplicate failure; `packages/core/tools/src/index.ts:727-728` — the duplicate error text itself points a per-agent variant to `agent.ctx`; `packages/core/tools/src/index.ts:1176-1180` — the visibility resolver adds "the scope's own registrations last, shadowing an inherited name and outside the filter above"; `packages/core/tools/src/index.ts:1075-1082` — `restrict()` requires a scoped context and its JSDoc states "scoped registrations remain visible"; `packages/subagent/subagent/src/child-agent.ts:174` — a child agent's `toolFilter` is applied exactly through `childCtx.tools.restrict(composition.toolFilter)`, which the same visibility rule exempts from the child's own registrations.
- **Disposition:** improved-writing
- **Reason:** fail-loud duplicate-in-layer is the right floor (spec §3.2 copies it), but the cross-layer path makes a per-agent `bash` shadow the deployment's global `bash` outside all `deny`/`allow` masks; the kernel must make scope-shadowing of a global name a deliberate, policy-checkable decision.
- **Details:** the shipped default mounts one `bash` (`packages/bundle/base/cordis.patch.yml:210-212`), so the composition the spec §3.2 describes — a sandboxed and an unsandboxed `bash` in one preset layer — throws at load (`store.ts:45`), which is loud but also means a preset can NEVER offer both: it must `disable` one row explicitly. The subtle path is cross-layer: a plugin registering `bash` through an `agent.ctx` inserts into the agent's OWN layer, which `view()` adds after the restriction filter (`index.ts:1176-1180`). That exemption exists for delegation machinery (the per-child reporting tool), and it generalizes: a subagent's `toolFilter` is a `restrict()` call (`child-agent.ts:174`), so a child that self-registers `bash` bypasses the parent's deny list by construction. Because dsh enforcement sits in the EXECUTOR (per-request shell/fs policy), not the tool name, a shadowed global `bash` is not automatically an unsandboxed escape — it depends on which executor the scoped definition resolves — so the real hazard is silent ambiguity about WHICH enforcement surface a `bash` name points at. I-harness must keep duplicate-in-layer failure, forbid or loudly flag a same-name scoped registration that shadows a global the deployment restricted or denied, and bind sandbox/approval to the capability provider that actually executes rather than to the tool name.

### F03-6: Restriction masks, approval, and sandbox are genuinely separate seams with no cross-bypass — but only approval and the effect-time fences are security boundaries

- **Severity:** Minor
- **Component:** `packages/core/tools/src/index.ts` (+ `packages/sandbox/sandbox/src/escalation.ts`, `packages/fs/fs-sandbox/src/index.ts`, `packages/interaction/user-approval/src/index.ts`)
- **Evidence:** `packages/core/tools/src/index.ts:1475-1488` — approval (`ask` via `serviceAsk`) resolves inside `prepare` and its `allowed-once` is still re-checked by the monotonic guards at :1486-1488; `packages/sandbox/sandbox/src/escalation.ts:158-186` — `approveEscalation` is an ordered fail-closed sequence (strict widening check at :162-163, missing approver/agent rejected at :165-172, only `allowed-once` grants at :183); `packages/fs/fs-sandbox/src/index.ts:131,145` — the per-call fs fence throws structured `FS_SANDBOX_DENIED` under `read-only`/`workspace-write`; `packages/interaction/user-approval/src/index.ts:307-312` — the `'never'` policy is decided inside the service's own request path, independent of answerer registration order; the `approval/asked` + `approval/decided` audit pair at :267-274.
- **Disposition:** reuse
- **Reason:** the three seams stay independent — restriction changes only visibility (dispatch re-resolves it), approval answers only the `ask` vocabulary and is audited, and sandbox enforcement runs where the effect happens — copy the seam separation, but document that `restrict()` is presentation, never a security boundary.
- **Details:** the separation is real and worth copying: `tools.restrict({allow, deny})` recomputes the visible set per scope and every dispatch re-resolves through the same view, so a masked tool is unreachable; the approval seam accepts only `allowed-once` and logs the `approval/asked`/`approval/decided` pair; sandbox enforcement lives at the capability that produces the effect — bash in the shell executor (per-call policy, `tool-bash/src/index.ts:343`), filesystem in the `fs-sandbox` fence (`fs-sandbox/src/index.ts:131,145`). An `allowed-once` grant is then re-checked by the monotonic guards before dispatch, so approval cannot widen policy. The one caveat to carry into the I-harness design: treat `deny`/`allow` masks as ergonomics (as dsh's `toolFilter` is), and put policy teeth exclusively in the guards and in effect-time approval/fences — otherwise the F03-5 scoped-registration escape silently widens what a mask was meant to forbid.

### F03-7: Catalog completeness gate checks doc freshness against default-config package boots — it cannot see agent-scoped, config-branched, or non-`tool-*` tools

- **Severity:** Minor
- **Component:** `scripts/gen-tool-catalog.ts` (+ `docs/tool-catalog.md`)
- **Evidence:** `scripts/gen-tool-catalog.ts:581-590` — `assertManifestComplete` globs `packages/*/tool-*` (`:582`) and fails only when an on-disk `tool-*` package is missing from `TOOL_PACKAGES`; `scripts/gen-tool-catalog.ts:599-612` — `assertToolsHarvested` throws only when a manifest-entry boot registered zero tools; `scripts/gen-tool-catalog.ts:184` — the `TOOL_PACKAGES` manifest; `scripts/gen-tool-catalog.ts:719-724` — the `--check` freshness mode; `:694` — the generator's guarantee statement ("a new tool cannot be silently undocumented"); `scripts/run-gates.ts:588` — `verify-tool-catalog` wired into `doc-sync`. The runtime model-visible set is assembled live from `view(scope)`, not from the catalog document (`packages/core/tools/src/index.ts:1166-1190`); `docs/tool-catalog.md:10` — each package is booted with its DEFAULT config, config-required branches are a recorded generator choice, and `examples/` demo tools are excluded.
- **Disposition:** improved-writing
- **Reason:** the doc-freshness gate is a good discipline, but it can stay green while the runtime shows tools the catalog never recorded (agent-scoped registrations, config-branched names, non-`tool-*` packages); our completeness check must diff the catalog against the assembled runtime set of the shipped default composition.
- **Details:** `verify-tool-catalog` guarantees only that the generated markdown matches what the generator itself produces for manifest-listed, default-config, package-level boots. Tools registered (a) per-agent (e.g. `tool-subagent-report` inside child scopes), (b) only under non-default config branches (the catalog itself documents load-time `toolName` aliases such as `subagent_fork`), or (c) by packages outside the `packages/*/tool-*` glob (e.g. `dsh-plan-mode` sits in the manifest by hand, not by glob) are invisible to the gate — and a NEWLY added non-`tool-*` package never trips `assertManifestComplete` because the glob only fires for `tool-*` names. The document being stale is harmless at runtime (schemas are derived live, `index.ts:1166-1190`), but the claimed guarantee — "a new tool cannot be silently undocumented" — is weaker than advertised. I-harness (§3.5 plan mirrors the discipline): boot the actual shipped base composition and diff its live `schemas()` against the catalog, closing the glob, config-branch, and agent-scoped holes.

### F03-8: OFFICIAL dsh ships exactly two loop-hygiene guard plugins and no bootstrap concept — the anchored-bootstrap technique has no upstream counterpart (note)

- **Severity:** Minor
- **Component:** `packages/guard/` family inventory (no `tool-bootstrap` in OFFICIAL)
- **Evidence:** OFFICIAL `packages/guard/` contains exactly two sub-packages — `packages/guard/repeat-tool-reminder` and `packages/guard/timeout-policy` (plus the family README). There is **no `packages/guard/tool-bootstrap`** and no `bootstrapTools`/`tool-bootstrap` anywhere in the OFFICIAL tree (full-tree grep: zero hits). The first-request catalog-narrow / promotion / fail-open-degrade mechanism described by the original finding exists only in our local modified copy.
- **Disposition:** improved-writing
- **Reason:** the anchored-bootstrap technique (the first request anchors the reasoning trajectory on a minimal tool pair, then promotes on durable use) is a proven I-harness concept — but it has **no official dsh counterpart to copy**, so it cannot be a `reuse` row. Implement it fresh per our spec §3.4, with per-platform anchor resolution and a loud (never silent) failure mode when an anchor tool is unavailable.
- **Details:** The original finding was anchored to `packages/guard/tool-bootstrap/src/index.ts` (an `applyBootstrap` catalog filter, `prepend: true` transforms, a `warnOnce` fallback to the full catalog). **That package does not exist in the OFFICIAL tree** (see `docs/audit/reaudit-official.md`) — the finding is withdrawn as written and the disposition moves from `reuse` to `improved-writing`. The two official guard plugins that DO exist (`repeat-tool-reminder`, `timeout-policy`) are covered in F02-8. For I-harness §3.4, implement the anchored bootstrap as a presentational first-request narrow keyed to the platform-available anchor pair, keep the promotion phase durable per session, and make a missing anchor a loud configuration error or a deliberate platform-appropriate substitution — never the silent full-catalog fallback the local implementation used.
