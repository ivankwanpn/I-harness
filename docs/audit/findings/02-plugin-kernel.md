# Section 02 — Plugin Kernel, Scopes, Waterfalls & Guards

Audit of the dsh plugin kernel and its extension seams: the vendored Cordis
kernel (`vendor/cordis/src` — service registration, scoped event dispatch,
fiber lifecycle, waterfall/compose semantics), the Service Definition pattern
(`packages/core/*` Service classes), the scope primitive and per-scope layer

monotonic guard pipeline (`packages/core/tools/src/index.ts`), the
`agent/pre-step`, `system-prompt/assemble`, `llm/stream`, and `tools/*`
waterfall consumers, and the loop-hygiene plugins in `packages/guard/*`.

### F02-1: Waterfall dispatch has no per-listener containment — a forgotten `next()` silently vetoes and a throwing listener aborts the whole chain

- **Severity:** Important
- **Component:** `vendor/cordis/src/events.ts` (+ `packages/core/agent-loop/src/agent.ts`, `packages/core/tools/src/index.ts`)
- **Evidence:** `vendor/cordis/src/events.ts:234-243` — the waterfall builds one shared `next` over a snapshot list; `next = () => { const cb = cbs.shift() ?? inner; return cb(...args) }`, so a listener that returns without calling `next()` returns its own value and the built-in `inner` never runs; `vendor/cordis/src/events.ts:165-176` — `dispatch` re-derives a fresh filtered callback array per call (`.filter(...).map(...)`), so a broken listener aborts only the in-flight chain, never the registry; `packages/core/agent-loop/src/agent.ts:234-241` — `await this.dispatch.waterfall('agent/pre-step', …)` is followed by `decision.kind`, so an observer that forgets `next()` (resolving `undefined`) turns the whole turn into a `TypeError`; `packages/core/tools/src/index.ts:1475-1498` — the `tools/pre-execute` gate defaults to `{ kind: 'allow' }`, and the same forgotten-`next()` listener yields `undefined` which tripped on `gate.kind === 'ask'` is folded into a generic tool error. The delegation rule itself is documented: `docs/cordis-primer.md:30-34` ("Call `next()` to delegate … return without `next()` to short-circuit").
- **Disposition:** improved-writing
- **Reason:** the around-middleware concept (wrapped `next` with veto) is stable and worth copying, but the kernel ships no containment, no distinguishable veto, and no way to detect that a chain was truncated — a broken listener either silently denies or fails the entire step/turn.
- **Details:** "Returning without `next()` short-circuits" is by design for decision-owning listeners (a policy may own the decision per `docs/cordis-primer.md:34`), but the same rule means an OBSERVER that merely forgets `next()` silently vetoes a call it meant to annotate. Worse for async listeners: `await next()` without `return next()` runs the rest of the chain and then discards its value at the top, which for `agent/pre-step` becomes `undefined` and crashes at `decision.kind` (agent.ts:241), surfaced as a turn error; for `tools/pre-execute` it becomes a `TypeError: Cannot read properties of undefined` folded into a tool result — a plugin bug indistinguishable from a tool failure. A listener that throws synchronously aborts every remaining listener plus the built-in `inner` for that dispatch; because each dispatch re-snapshots hooks, there is no persistent queue to strand — the failure is loud, but attribution lands on the step/turn rather than the offending listener. Calling `next()` twice re-runs the whole downstream (the shared `cbs` array shifts again). I-harness should give its kernel waterfall (1) a distinct veto signal, (2) per-listener error containment with attribution to the listener, and (3) a compile-time rule that the delegated value's promise must be returned, avoiding the "one aspect forgot `next()`" silent-deny and dead-turn bugs.

### F02-2: `tools.guard()` is a structurally monotonic deny-only guard — order cannot re-allow, only unmount can relax

- **Severity:** Important
- **Component:** `packages/core/tools/src/index.ts`
- **Evidence:** `packages/core/tools/src/index.ts:704-711` — `ToolGuard` is a synchronous `(execution) => string | undefined` and its JSDoc states guards have no allow result so "listener ordering cannot turn a denial back into permission"; `packages/core/tools/src/index.ts:747-753` — `ToolLayer.guardReason` returns the FIRST denial from a layer's insertion-ordered guard table; `packages/core/tools/src/index.ts:1110-1115` — `guard()` appends to the layer with `notify: false` and returns the exact disposer; `packages/core/tools/src/index.ts:1119-1128` — `guardReason` evaluates the global layer first, then every scope-chain layer; `packages/core/tools/src/index.ts:1486-1498` — guards are evaluated only after the full `tools/pre-execute` waterfall settles and only when the decision is `allow`, and a denial short-circuits before dispatch as a `post-result` error; `packages/core/scope/src/store.ts:122-136` — `AnonymousEntries.append` gives each guard its own symbol identity so disposers remove only their own entry.
- **Disposition:** reuse
- **Reason:** no fault found — the deny-only type, append-only per-plugin table, and post-pre-policy placement make it structurally impossible for a late plugin to re-allow a denied call within the pipeline; listener order can only choose which denial reason surfaces.
- **Details:** Can a late plugin re-enable? Within the pipeline, no. A `tools/pre-execute` listener that force-returns `{ kind: 'allow' }` without `next()` cannot bypass guards because guards run AFTER the gate settles (index 1476-1487); a `tools/execute` wrapper executes only after an already-allowed dispatch; `tools/post-execute` can rewrite the denied result but cannot re-run the tool body. A late plugin can only ADD denials — there is no cross-plugin API to remove another guard, and a pre-execute `ask` that resolves to `allowed-once` still reaches `guardReason` on the `allow` path. The only relaxation is lifecycle: when the plugin that registered a guard unmounts, its disposer removes it, re-allowing what it denied — expected HMR behavior, not a reorder. One cascade to note (not a gap): a pre-execute listener that denies short-circuits before guard evaluation, so guards only execute for calls the gate already permitted. I-harness should copy the mechanism verbatim: synchronous deny-only callback, first-reason surface, evaluation strictly between pre-policy and dispatch, and per-registration disposers.

### F02-3: Scope shadowing and unmount are correct — nearest-scope-wins, duplicates-in-layer fail loud, empty layers are reclaimed

- **Severity:** Important
- **Component:** `packages/core/scope/src/store.ts` (+ `packages/core/tools/src/index.ts`, `packages/core/scope/src/index.ts`)
- **Evidence:** `packages/core/scope/src/store.ts:43-59` — `NamedEntries.insert` throws the layer's `duplicateError` on a duplicate within one table; `packages/core/tools/src/index.ts:727-728` — the tools duplicate diagnostic directs per-agent variants to `agent.ctx`; `packages/core/scope/src/store.ts:192-201` — `chainLayers` returns farthest-ancestor-first, exact-scope-last; `packages/core/tools/src/index.ts:1160-1183` — the tool `view()` layering order: global, then chain shadows nearest-last (`inherited.set`), then the scope's OWN tools override last, with restrictions intersecting across the whole chain; `packages/core/scope/src/store.ts:221-263` — `effect()` creates the layer on first mutation, runs the atomic action, and on disposal undoes and deletes the layer only when `layer.isEmpty()` (line 259); `packages/core/agent-loop/src/index.ts:507-509` — agent teardown cancels the machine, waits idleness, then `machine.scope.dispose()`; `packages/core/scope/src/index.ts:137-155` — `createScope` backs the scoped context with a silent plugin fiber whose disposal drains every registration; `packages/core/tools/src/index.ts:811-815` — the layers emit `tools/change` on registration/disposal (except guard-only changes, `notify: false`).
- **Disposition:** reuse
- **Reason:** no correctness fault found — resolution order, duplicate handling, restriction semantics, and unmount reclamation are coherent, and the registry invariants (`packages/core/tools/src/invariant.ts`) plus the scope-carrier invariant (`packages/core/scope/src/invariant.ts:17-19`) enforce the dispatch side.
- **Details:** Nearest-scope shadowing is exactly right: `view()` seeds `inherited` from the global layer, applies chain layers nearest-last so a nearer scope's same-name entry wins, and then lets the scope's OWN registrations override everything inherited — an agent's own tool beats an ancestor's entry, which beats a global one. Restrictions (`allow`/`deny`) mask only the inherited surface, never the scope's own registrations (an explicit exemption the delegation runtime relies on for reporting/structured-output tools) and intersect across the whole chain (`layers.every(layer => layer.admits(name))`, index 1174). Duplicate names collide only within ONE layer (one scope); the same name in two scopes is shadowing by design, and the reserved `run_code` name is rejected at registration before any layer is created. Unmount: every registration is a Cordis fiber effect on the registration context; disposing the scope fiber (agent-loop index 507-509 → `scope.dispose` → `quiesceFiber`, scope index 115-117) runs each disposer in reverse order and pops the layer once fully empty — no orphaned layers, no cross-scope leaks. Copy the `ScopedLayers`/`NamedEntries`/`AnonymousEntries` pattern as a reference; it is a sound kernel primitive. (One adjacent caveat is filed separately as F02-7.)

### F02-4: Plugin lifecycle is fail-loud on startup and contained on disposal, but a non-settling disposer hangs the entire unload chain

- **Severity:** Important
- **Component:** `vendor/cordis/src/fiber.ts` (+ `packages/boot/app-boot/src/index.ts`)
- **Evidence:** `vendor/cordis/src/fiber.ts:646-673` — `_reload` catches a config/startup error, logs it (line 661), records `this._error`, forces the epoch INACTIVE, and the follow-on `_unload` drains any partial effects; `vendor/cordis/src/fiber.ts:704-712` — `await()` rethrows `this._error`, so startup failures reach the caller; `vendor/cordis/src/fiber.ts:675-702` — `_unload` runs all disposers concurrently via `Promise.all`, each wrapped so a throwing disposer is logged (line 684) and the rest continue; `vendor/cordis/src/fiber.ts:292-295` — `dispose()` loops `await this.inertia` with no bound, so one non-settling disposer hangs plugin removal; `packages/core/agent-loop/src/index.ts:507-509` — agent teardown awaits `machine.scope.dispose()` to quiescence, inheriting that hang; `packages/core/scope/src/index.ts:115-117` — `quiesceFiber` mirrors the same unbounded wait; `packages/boot/app-boot/src/index.ts:692-722` — the Loader audit fails loud on startup: FAILED fibers are awaited and rethrown with their stack, PENDING fibers are named with their missing services, so the bad case is visible at boot.
- **Disposition:** improved-writing
- **Reason:** fail-loud startup and per-disposer containment are the right shape, but the kernel never bounds disposer settlement, so one wedged disposer silently strands plugin removal, scope disposal, and whole-tree shutdown; dsh only bounds the terminal release in the app boot, not disposers.
- **Details:** Startup error handling is genuinely good: a plugin that throws during activation is marked FAILED, its `await()` rethrows, and the Loader audit (`assertEntriesActivated`) turns it into a named boot error with the original stack; PENDING fibers list exactly which services they await. Disposal is intentionally forgiving — each disposer error is logged and the rest run — which is correct containment. What is missing is the counterweight: `dispose()` awaits `this.inertia` in a loop (fiber 292-295), `_unload` `await Promise.all(...)` over disposers, so a disposer that never settles pins the owning fiber, then the agent-loop teardown (index 507-509), the scope `quiesceFiber` (scope 115-117), and finally the root `ctx.fiber.dispose()` in the app boot. I-harness should keep the per-disposer containment but add (a) a bounded quiescence budget with forced-unload escalation and (b) an explicit log naming the wedged disposer, so shutdown cannot be silently pinned by one plugin.

### F02-5: "Everything is a plugin" holds for the product spine — but three real privileged surfaces exist: Loader/include/group host glue, launcher-provided services, and blanket `internal/*` interception

- **Severity:** Important
- **Component:** `packages/boot/app-boot/src/index.ts` + `vendor/cordis/src/reflect.ts` + `vendor/cordis/src/events.ts` (+ `vendor/cordis/src/service.ts`)
- **Evidence:** `packages/bundle/base/cordis.patch.yml:24-27` and `packages/bundle/base/cordis.patch.yml:424-439` — `dsh-llm`, `dsh-session`, `dsh-tools`, `dsh-system-prompt`, and `dsh-agent-loop` all mount as ordinary named Loader rows; `vendor/cordis/src/service.ts:42-58` — every service registers through the same `ctx.reflect.provide` path as any plugin, so core == plugin at the registry level; `packages/boot/app-boot/src/index.ts:770-784` — the host glue alone provides `dshHomePath`, mounts `Loader` via `ctx.plugin(Loader)`, and audits the settled tree; `vendor/cordis/src/reflect.ts:153-154` — every `ctx.<service>` property read runs an `internal/get` waterfall any plugin can listen on, and `vendor/cordis/src/reflect.ts:191` the same for writes via `internal/set`; `vendor/cordis/src/reflect.ts:333` — `internal/service` observes every registration/disposal; `vendor/cordis/src/events.ts:165-174` — a non-internal dispatch emits `internal/dispatch` first (line 169); dsh itself consumes these hooks for runtime invariants (`packages/core/scope/src/invariant.ts:17-19`).
- **Disposition:** improved-writing
- **Reason:** the plugin-everywhere spine is real and should be copied, but "everything is a plugin" overstates it: framework builtins and boot glue run before any config row, launchers provide services ahead of the tree, and the `internal/*` hook surface gives any plugin blanket, undetectable interception of service resolution and dispatch.
- **Details:** The product spine is genuinely ordinary: `session`, `systemPrompt`, `tools`, `agents`, `agentLoop`, and `llm` are each a `Service` subclass whose constructor calls the same `ctx.reflect.provide` (service.ts:57) and each is a Loader row in the base bundle patch. Three things are NOT ordinary, which I-harness must name honestly: (1) the Loader, root `cordis:include`, and `cordis:group` are framework plugins mounted by app glue before any config row (`ctx.plugin(Loader)` + `mountRootInclude`, app-boot 771-774) — they are the one layer no `cordis.yml` can replace; (2) launchers provide `dshHomePath` (app-boot 770) and `configuredAgentIdentities` via `ctx.provide()` ahead of the tree; (3) the Cordis context proxy funnels every `ctx.<name>` read/write through `internal/get`/`internal/set` waterfalls (reflect 153/191), and publishes `internal/plugin`, `internal/status`, `internal/dispatch`, and `internal/service` for every lifecycle and dispatch step (events 165-174, 333) — dsh's own invariants exploit this for monitoring, which proves the surface is indistinguishable from kernel code. A buggy plugin could observe or rewrite ALL service traffic. I-harness should keep the plugin-everything spine but treat the interception surface as a documented, sealable privileged API — otherwise "no privileged core" is only cosmetic.

### F02-6: `emit` (fire-and-forget) dispatches through `Array.map` — a throwing listener starves later observers and propagates into the emitter

- **Severity:** Minor
- **Component:** `vendor/cordis/src/events.ts` (+ `packages/core/agent/src/dispatch.ts`, `packages/core/tools/src/index.ts`)
- **Evidence:** `vendor/cordis/src/events.ts:194-198` — `emit` is `this.dispatch('emit', args).map(cb => cb(...args))`: a synchronous throw aborts the map, skips every later listener, and propagates to the emitter's caller; `packages/core/agent/src/dispatch.ts:120-135` — dsh hand-rolls per-listener containment for agent notifications precisely because `emit` does not; `packages/core/tools/src/index.ts:1657-1680` — `notifyResult` hand-rolls the dispatched loop for `tools/result` with per-observer `try`/`catch`; the change emitters still use raw `ctx.emit` (`packages/core/tools/src/index.ts:811-815`).
- **Disposition:** improved-writing
- **Reason:** the concept (filtered, fire-and-forget notification) is right and should be kept, but the kernel's `emit` gives no containment while dsh's own busiest callers re-implement it — the kernel should own the discipline.
- **Details:** Notification storms such as `tools/change` (index 813) and `system-prompt/change` run through raw `ctx.emit`; a single throwing observer breaks every later observer for that dispatch and, when the emit is driven from a registration/disposal path, propagates back through the effect machinery, so a successful registration can throw and still be live — a confusing partial-write failure. dsh had to wrap containment by hand in three separate places (agent `emit`, `notifyResult`, and the agent-loop `config-start-failed` loop), and `parallel()` does contain errors but aggregates and rethrows (events.ts:183-190). I-harness should make emit containment-on-by-default with per-listener attribution, and reserve throwing observers for explicitly monitored categories.

### F02-7: `bindScopeParent().rebind()` re-parents inheritance under live layers with an unenforceable precondition

- **Severity:** Minor
- **Component:** `packages/core/scope/src/index.ts`
- **Evidence:** `packages/core/scope/src/index.ts:55-59` — the only check on a parent link is the cycle walk; nothing verifies the subtree is idle; `packages/core/scope/src/index.ts:72-84` — `bindScopeParent` returns a `rebind` that calls `linkScopeParent` directly, and the documented "valid only while nothing produced under the old parent is retained" is a holder-upholds contract with no runtime check.
- **Disposition:** improved-writing
- **Reason:** the bind-once primitive is good, but rebind can silently re-parent live scoped registrations and change their admission/inheritance without re-running any registration; the kernel must enforce idleness or invalidate descendants on rebind.
- **Details:** After a rebind, `scopeTarget`'s carrier filter (index 170-186) walks the NEW parents, so listeners tagged under the re-parented key start receiving dispatches they previously missed and stop receiving others; `chainLayers` (store 192-201) and the tool/prompt views resolve against the new chain — all without any registered contribution re-running. dsh's blank-session recompose contract forbids retained layers, but nothing checks it, and a session log cannot tell the rebinder what live registrations exist under the old parent. I-harness should forbid rebind on non-empty scopes or snapshot-and-invalidate descendant layers on rebind.

### F02-8: `packages/guard/*` loop-hygiene plugins are clean reference implementations for advice-style guard plugins

- **Severity:** Minor
- **Component:** `packages/guard/repeat-tool-reminder`, `packages/guard/timeout-policy`
- **Evidence:** `packages/guard/repeat-tool-reminder/src/index.ts` — counts consecutive identical calls in `tools/post-execute` (`:213-224`), always delegates, folds the reminder into `additionalContexts` for BOTH decision variants (block and allow), and never vetoes (`observe()` at `:189-207`); the per-agent chain is reset on any user-sourced message via `agent/pre-step` (`:229-232`); reminder text from `GENTLE_REMINDER` (`:63-67`) / `detailedReminder` (`:70-78`); helpers `canonicalize` (`:103-105`), `wildcardToRegExp` (`:108-111`), `previewArguments` (`:118-121`), `validateThresholds` (`:128-141`). `packages/guard/timeout-policy/src/index.ts` — a `tools/execute` wrapper (`:56-80`) arms `deadline()` from the tool's declared `timeoutMs` (`:61`), swaps `exec.signal` under its own deadline (`:65-66`) and restores the upstream signal in `finally` (`:78`), replacing the result only when its own `TOOL_TIMEOUT` fired (`toolTimeoutResult` `:41-47`, `TOOL_TIMEOUT` `:25`, check at `:73-74`).
- **Disposition:** reuse
- **Reason:** no fault found — these are the reference patterns for composing with the tool pipeline: enrich in post-execute, wrap around execution with signal ownership. (The original audit also listed a `tool-bootstrap` member; it does not exist in the OFFICIAL tree — see F03-8 and `docs/audit/reaudit-official.md`.)
- **Details:** Each guard plugin composes with the kernel exactly as the seams intend and stays discipline-clean: repeat-tool-reminder observes and enriches without vetoing (only a NEW user message resets the chain); timeout-policy takes the documented `tools/execute` signal-swap path and never leaves a derived signal behind (restored in `finally`, so post-execute listeners never see this plugin's possibly-aborted timeout signal). Neither plugin touches the monotonic guard table (F02-2), so they are purely additive to the security pipeline. These are safe templates for I-harness advisor-style plugins.
