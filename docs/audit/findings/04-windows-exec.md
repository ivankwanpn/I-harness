# Section 04 — Windows Execution Environment

Audit of the dsh Windows execution environment: the shell stack (bash/pwsh tools
and executors), the PTY/persistent-terminal path, the per-platform sandbox
stack (`sandbox-local` → Landlock/Seatbelt/`windows-acl`), the native
`landlock-run` launcher, and the subprocess/fs plumbing that must behave
differently on `win32`.
Target: dsh `0.1.0-rc.5`. Read-only; all `path:line` citations verified against
the dsh tree (see the Verification block at the end).

Bottom line up front: dsh composes cleanly for Windows — one shared
`cordis.patch.yml` toggles bash↔pwsh by platform, the sandbox seam is genuinely
per-platform pluggable, and the win32 runner (`sandbox-windows-acl`) is a real
restricted-token mechanism, not a stub. What breaks is deliberately-disabled,
deny-by-configuration rather than broken-by-forgetting: Windows has **no bash
tool at all, no persistent terminal**, and therefore **no first-request
bootstrap anchor** (the minimal-catalog bootstrap silently falls back to the
full catalog). Secondary gaps: no OS-level read/process visibility restriction
(`WRITE_RESTRICTED` only), a partial-enforcement sandbox boundary, a
one-shot-only pwsh dialect, and POSIX-flavored permission privacy that
degrades to skipped checks on Windows.

---

### F04-1: On Windows the shipped profile has no `bash` tool and no persistent shell — the bootstrap anchor silently degrades to the full catalog

- **Severity:** Critical
- **Component:** preset composition (`apps/cli/config/agent-presets/*`) + `packages/bundle/base/cordis.patch.yml` + `packages/guard/tool-bootstrap`
- **Evidence:** `apps/cli/config/agent-presets/standard/agent.cordis.yml:89` — `persistent-shell` group carries `disabled: !!js process.platform === 'win32'` (comment at `:80-83`: the PTY terminal inspector is Linux/macOS-only, so a persistent bash cannot spawn there); `apps/cli/config/agent-presets/standard/agent.cordis.yml:72` — the standard preset's own `tool-bash` row is `disabled: true` on every platform because `tool-bash-persistent` registers the same `bash` name (`:66-71`); `apps/cli/config/agent-presets/minimal/agent.cordis.yml:25` — Minimal's `persistent-shell` has the same win32 disable. The host layer re-disables the single-shot bash path: `packages/bundle/base/cordis.patch.yml:180` (`bash-sandbox ... disabled: !!js process.platform === 'win32'`) and `packages/bundle/base/cordis.patch.yml:212` (`tool-bash ... disabled`). The bootstrap guard pins a POSIX-only pair: `apps/cli/config/agent-presets/standard/agent.cordis.yml:34` — `bootstrapTools: [bash, str_replace_editor]`; when a listed tool is absent the guard fails open: `packages/guard/tool-bootstrap/src/index.ts:145-152` — a missing bootstrap tool logs `bootstrap disabled, full catalog exposed` and returns the *assembled, unfiltered* catalog for request #1.
- **Disposition:** improved-writing
- **Reason:** the "first request anchors the reasoning trajectory on a minimal tool pair, then promotes" concept is sound and worth keeping, but the implementation hardcodes a POSIX-only pair and fails open to the full catalog when the platform lacks it — exactly the V4 trajectory anchor the concept exists to preserve.
- **Details:** Net effect on a Windows host: the `bash` tool never appears in the tool catalog (single-shot `dsh-tool-bash` disabled at the host layer, `dsh-tool-bash-persistent` dead inside the disabled PTY group), and `str_replace_editor` + `tool-fs` remain. Minimal-all-the-way-down platforms (request #1 bootstrap, and the `minimal` preset itself) expose **only** `str_replace_editor` — no shell at all. I-harness (§4.3) must keep the minimal-catalog concept but (a) resolve `bootstrapTools` per platform (Windows: `pwsh` + `str_replace_editor`), and (b) treat a missing bootstrap tool as a loud configuration error or a deliberate platform-appropriate substitution, never a silent fallback that inverts the feature's purpose. dsh's own doc of the restore trap — `packages/bundle/base/README.md:7` — shows the two rows you must toggle together; the same completeness rule must apply to the Windows bootstrap pair.

### F04-2: Root cause of F04-1 — the terminal process inspector throws on `win32`, so `spawnTerminal` cannot create any PTY

- **Severity:** Important
- **Component:** `packages/subprocess/subprocess-local/src/process-inspector.ts` (+ its consumer in `packages/subprocess/subprocess-local/src/index.ts`, `packages/terminal/terminal-bash`)
- **Evidence:** `packages/subprocess/subprocess-local/src/process-inspector.ts:366-374` — `createProcessInspector(platform, arch, internals)` returns a `LinuxProcessInspector` (reads `/proc/<pid>/stat`, syscall tables `:293-311`) or a `MacProcessInspector` (runs `/bin/ps` `:324-335`) and otherwise `throw new Error('subprocess-local: terminal inspection is unsupported on platform win32')` at `:373`; `packages/subprocess/subprocess-local/src/index.ts:174` — every `spawnTerminal` call resolves the inspector up front, so the throw happens before `nodePty.spawn` regardless of the shell. `packages/terminal/terminal-bash/tests/local.spec.ts:107` and `packages/terminal/tool-terminal/tests/loader-composition.spec.ts:60` gate the PTY e2e suites to Linux/darwin.
- **Disposition:** improved-writing
- **Reason:** the /proc `foregroundPgid`/`isStdinWaiting`/`processSession` design is Linux-specific by construction and correctly refuses to guess on Windows, but the all-or-nothing throw is what forces the composition-level `persistent-shell` disable (F04-1) — a Windows kernel needs either a real win32 inspector or a first-class "no terminal capability" signal instead of an exception.
- **Details:** The preset comments (`standard/agent.cordis.yml:80-83`, `minimal/agent.cordis.yml:22-24`) document this as "Linux/macOS-only". dsh ships **no** Windows inspector implementation; the composable degrade is "disable the feature". For I-harness (Windows-first, spec §4.3), a persistent interactive shell is a headline capability; the reference implementation must add a win32 inspector (job objects + `NtQuerySystemInformation`/Console host process tree, or a ConPTY wrapper) and, in its absence, surface `SANDBOX_UNAVAILABLE`-style structured errors rather than cascade-disable entire tool groups. Note dsh's fallback exists at all only because the pwsh tool is one-shot by design (F04-5) — a correct, if weaker, product.

### F04-3: The sandbox seam is genuinely per-platform pluggable — one interface, three real backends, zero Linux leakage into call sites

- **Severity:** Important
- **Component:** `packages/sandbox/sandbox/src/index.ts` (Service Definition) + `packages/sandbox/sandbox-local/src/index.ts` (platform chain) + the twin executors `packages/shell/bash-sandbox` / `packages/shell/pwsh-sandbox`
- **Evidence:** `packages/sandbox/sandbox/src/index.ts:158-175` — `abstract class SandboxProvider` exposes one method `confine(argv: readonly string[], policy): ConfinedArgv`; argv is "the exact argv the caller is about to spawn, NOT a shell string" (`:172-175`); `ConfinedArgv` returns the runner argv plus `enforcement`, `denialSignatures`, and `runnerFailureRules` (`:82-115`) so each backend speaks its own denial dialect. The provider picks per platform: `packages/sandbox/sandbox-local/src/index.ts:165` — `PLATFORM_CHAINS = { linux: ['bwrap','landlock'], darwin: ['seatbelt'], win32: ['windows-acl'] }`. Both shell executors wrap through the identical seam: `packages/shell/bash-sandbox/src/index.ts:178` (`sandbox.confine(['bash', '-c', command], policy)`) and `packages/shell/pwsh-sandbox/src/index.ts:184` (`sandbox.confine(this.argv(spec), policy)`) — the only difference is the inner argv. Fail-closed is shared: `packages/sandbox/sandbox/src/index.ts:124` (`SANDBOX_UNAVAILABLE`) with a message that names bubblewrap/Landlock, sandbox-exec, and the ACL restricted-token runner (`:134-137`).
- **Disposition:** reuse
- **Reason:** no fault found — this is the exact cross-platform ablation I-harness §4.3 asks for (`ctx.sandbox` as an interface independent of any OS backend), and both consumers already thread the per-call policy instead of hardcoding one.
- **Details:** The proxy-shape of the seam (argv-in, argv-out) is what makes it portable: a Windows runner simply replaces the caller's argv with `[node, runner.js, --workspace …, --temp …, --mode …, --, …]`, and the caller never parses runner flags. `landlock-run` being Linux-only (`native/landlock-run/docs/support-matrix.md:15` — "win32: a Windows confinement launcher would be a different mechanism in its own repository, not a port of this one", and the Launcher package ships only `linux-x64`/`linux-arm64` platform tarballs) is absorbed by the seam rather than leaking: the resolved launcher path does not exist on Windows, the probe reports `unusable`, and `const PLATFORM_CHAINS` never offers it. The enforcement vocabulary (`'full' | 'partial'`) and per-backend `denialSignatures` (Windows: `['access is denied', 'access to the path', 'permission denied']` per `sandbox-local/src/index.ts:211`) belong in the seam contract. Copy this seam.

### F04-4: The Windows sandbox is a real restricted-token mechanism — but write-only, partial-enforcement, console-constrained

- **Severity:** Important
- **Component:** `packages/sandbox/sandbox-windows-acl` (`src/index.ts`, `src/token.ts`, `src/spawn.ts`, `src/runner.ts`, `src/ffi.ts`) + `packages/sandbox/sandbox-local/src/index.ts`
- **Evidence:** `packages/sandbox/sandbox-windows-acl/src/index.ts:4` — "a WRITE_RESTRICTED token whose restricting SIDs include … the workspace write SIDs" (ported mechanism, not a stub); `packages/sandbox/sandbox-windows-acl/src/index.ts:24-28` — documented boundaries: "writes are restricted; reads, network, and process visibility are NOT (WRITE_RESTRICTED intersects only write accesses)"; "console isolation is unavailable — children share the host console (CREATE_NO_WINDOW / CREATE_NEW_CONSOLE children die with STATUS_DLL_INIT_FAILED)"; `packages/sandbox/sandbox-windows-acl/src/token.ts:200-214` — token built with `DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED` and a mode-selected restricting list; `packages/sandbox/sandbox-windows-acl/src/spawn.ts:88-107` — children created via `CreateProcessAsUserW` under the restricted token with Win32 pipe plumbing (no OS admin needed for `CreateRestrictedToken` of an already-elevated/standard process token). Enforcement is honestly reported as partial: `packages/sandbox/sandbox-local/src/index.ts:186` — `'windows-acl': 'partial'` with its Everyone/hard-link rationale in the comment block (`:180-185`).
- **Disposition:** improved-writing
- **Reason:** a working, ffi-based, fail-closed restricted-token sandbox is a strong reference for the mechanism, but its contract (write-only, no read/process isolation, shared console, caller-owned writable dirs) is materially weaker than what the same `SandboxMode` vocabulary means under bwrap, so the policy claims must be scoped per platform rather than copied as a uniform promise.
- **Details:** For I-harness §4.3 this confirms the Windows-first decision: "approval + directory whitelist" as the primary enforcement (Windows) and OS sandbox later — dsh itself only constrains *writes* on Windows. Two specifics worth copying: (1) full-width exit-code mirroring in the runner (`runner.ts:189-196` — a child exit of 3221225477 is read back verbatim, no masking) and (2) the per-session random private temp directory with its own SID (`sandbox-local/src/index.ts:412-416`, `tmpdir/dsh-…` + `tempWriteSid`), TMP/TEMP rewritten for confined children (`runner.ts:104-116`). Two specifics to NOT copy: the `Everyone` residual (the restricted token must retain Everyone in both restricting lists for process init — `index.ts:22-24`) and the console/DLL-init trap for hidden-console children. If I-harness ships a Windows OS-sandbox at all, it must decide the write-only boundary is acceptable and say so in the tool schema, exactly as dsh does in `tool-pwsh`'s LongDescription (`packages/shell/tool-pwsh/src/index.ts:129-138` — ConstrainedLanguage mode in read-only, named-pipe EPERM).

### F04-5: The pwsh/bash shell split is two dialects over ONE capability seam — one-shot pwsh is a real capability loss on Windows

- **Severity:** Important
- **Component:** `packages/shell/bash-local`, `packages/shell/pwsh-local`, `packages/shell/shell` (Service Definition), consumers `packages/shell/tool-bash` / `packages/shell/tool-pwsh`
- **Evidence:** `packages/shell/shell/src/index.ts:2-16,40-48` — one Service Definition for `ctx.shell` ("host composes exactly one provider of `ctx.shell` (the win32 layer swaps the …)"), base class `ShellExecutor`; bash runs `bash -c <command>` with no intermediate shell (`packages/shell/bash-local/src/index.ts:212,243`), pwsh runs `pwsh -NoLogo -NoProfile -NonInteractive -Command <command>` with the command as ONE argv element and a UTF-8 preamble prepended (`packages/shell/pwsh-local/src/index.ts:48` for `ENCODING_PREAMBLE`; `:217-218` for the argv). Power-shell resolution is Windows-first and explicit: `packages/shell/pwsh-local/src/resolve.ts:67-77` probes PS 7 install, PATH (Store aliases), then Windows PowerShell 5.1, falling back to bare `pwsh`; `packages/shell/pwsh-local/src/index.ts:167` caches the resolved executable. The tool descriptions are dialect-locked: `package.json`-adjacent tool vocab says `bash` = "fresh shell, no state" (`packages/shell/tool-bash/src/index.ts:55-…`) while `tool-pwsh` documents "fresh pwsh process, no state persists" and the atteminated exit-code-1 marker (`packages/shell/tool-pwsh/src/index.ts:131-138,256`).
- **Disposition:** improved-writing
- **Reason:** the "one shell seam, one dialect per host, argv-level quoting-free dispatch" shape is exactly the `ctx.exec` cross-platform spawn abstraction spec §4.3 calls for, but dsh leaves the Windows dialect one-shot: without the disabled PTY group there is **no persistent PowerShell session** anywhere, so every Windows command pays fresh-process cost and loses cwd/env/prompt continuity entirely.
- **Details:** What I-harness must design for (§4.3): (1) pick ONE live dialect per host at composition time (dsh does this cleanly in `packages/bundle/base/cordis.patch.yml:179-186,211-216` with inverted platform guards — one shared patch, exactly one shell stack) — copy that pattern; (2) decide whether the first Windows release ships a persistent `pwsh` terminal (dsh does not — F04-2 is the root cause) and if not, say "one-shot only" in the tool description so the model never relies on `cd` state; (3) the `-Command` single-argv trick and the `ENCODING_PREAMBLE` (fixes Windows PowerShell 5.1 OEM-code-page output garbling) are small, correct details to reuse verbatim.

### F04-6: Subprocess/exec plumbing is Windows-correct (taskkill trees, PATHEXT resolution, case-insensitive env) — reuse-as-is

- **Severity:** Minor
- **Component:** `packages/subprocess/subprocess-local/src/spawn.ts`, `.../index.ts`, `apps/cli/src/plugin.ts`
- **Evidence:** `packages/subprocess/subprocess-local/src/spawn.ts:276-283` (`taskkillProcessTree` → `taskkill /PID <pid> /T /F`, outcome intentionally unchecked); `packages/subprocess/subprocess-local/src/spawn.ts:360` (`detached: platform !== 'win32'` — POSIX needs a group leader, Windows terminates by root pid instead); `packages/subprocess/subprocess-local/src/index.ts:113-115` — a relative command containing `\` is rejected on Windows (mirror of the `/` check), and `:139-140` — bare executable names are completed against `PATHEXT` (default `.COM;.EXE;.BAT;.CMD`); `packages/subprocess/subprocess-local/src/index.ts:188-193` — `PATH`/`PATHEXT` are looked up case-insensitively on Windows in a `Path`-case environment; `packages/subprocess/subprocess-local/src/spawn.ts:39-49` (`childEnv`) — env merging is case-insensitive-keyed on Windows; `apps/cli/src/plugin.ts:128-137` — pnpm is spawned with `shell: process.platform === 'win32'` because the `.cmd` shim refuses `spawn` without a shell after CVE-2024-27980 hardening.
- **Disposition:** reuse
- **Reason:** no faults found — every platform branch here is the right Windows answer (taskkill, PATHEXT, case-insensitive merge, shell-for-.cmd), and the three e2e suite skips (`packages/subprocess/subprocess-local/tests/process-exit.spec.ts:157`, `:114`) are targeted, not broad.
- **Details:** This block is the strongest single dev-time reference for I-harness `ctx.exec` (§4.3): copy the `signalTree` split (`spawn.ts:294-317` — POSIX negative-pgid, Windows taskkill, idempotent swallow), the `ExecutableCandidates` PATHEXT walk, and the `detached` flag difference verbatim, and port the CVE-aware `.cmd`-shim `shell` flag into the plugin/launch path. One nuance to preserve: Windows termination is force-only (`taskkill /T /F`), so the SIGTERM→grace→SIGKILL escalation is a no-op ladder on Windows — `packages/shell/tool-pwsh/src/index.ts:256` already tells the model "killed process settles as [exit code: 1] without a signal marker".

### F04-7: Filesystem isolation and atomic writes are Windows-aware — except POSIX permission-privacy silently degrades to skipped checks

- **Severity:** Important
- **Component:** `packages/fs/fs-sandbox/src/containment.ts`, `packages/fs/fs-local/src/fsio.ts`, `packages/fs/fs-local/src/win32.ts`, plus privacy-sensitive PKs (`packages/credentials/credentials-local`, settings, spill)
- **Evidence:** `packages/fs/fs-sandbox/src/containment.ts:58-82` — containment is case-insensitive on Windows (`caseSensitive = process.platform !== 'win32'` at `:61`) and falls back to filesystem-identity comparison for 8.3/casing aliases (`:80-94`); `packages/fs/fs-local/src/fsio.ts:551-552` — win32 atomic write injects `copyFileDaclWin32`/`replaceFileWin32`, applied at `:567` (copy the target's DACL onto the staged temp when `mode !== undefined`) and `:584` (`ReplaceFileW` instead of `rename`, so the target ACL survives replacement); the Win32 primitives use lazy koffi loading (`packages/fs/fs-local/src/win32.ts:27-81` — `GetFileSecurityW`/`SetFileSecurityW`/`ReplaceFileW` loading `advapi32`/`kernel32` on demand). The flip side: POSIX `0o600`-style privacy is a no-op on Windows, and dsh acknowledges it by *skipping the check*: `packages/credentials/credentials-local/src/index.ts:113` — returns early on `process.platform === 'win32'`; the same pattern appears across settings/storage/session tests (`packages/settings/settings-file/src/index.ts` position guard, `packages/storage/storage-json/src/atomic.ts:45`, `packages/session/session-persistence-jsonl/src/index.ts:521`), and `packages/util/launch-environment/src/index.ts:62` upper-cases the env key on win32.
- **Disposition:** improved-writing
- **Reason:** the DACL-preserving atomic write and identity-based containment are genuinely correct Windows engineering worth copying, but "POSIX permissions → silently skipped" is not a Windows privacy policy — I-harness must define Windows credential/settings protection explicitly (e.g., DACL restrict together with the `copyFileDaclWin32` mechanism dsh already has in `fsio`).
- **Details:** dsh's own win32 boundary is defensible (Windows ACLs, not mode bits, are the substrate; `stat().mode & 0o777` is synthetic on Windows per `packages/fs/fs-local/tests/fsio.spec.ts:627-629`), but the privacy covariance is caller-discipline: `credentials-local` skips the `0o700` document check, `settings-file` re-checks modes only on non-Windows (`tests/local.spec.ts:70`), and the atomic-write path protects DACLs only when a `mode` was supplied (`fsio.ts:567-570`). I-harness should make "credential document is private on Windows" a first-class, DACL-enforced invariant with the exact `copyFileDacl` mechanism as the reference implementation.

### F04-8: Canonical line endings and output decoding are already LF/UTF-8 — no CRLF hazard in the surface the tools see

- **Severity:** Minor
- **Component:** repo `.gitattributes`, `packages/subprocess/subprocess-local/src/spawn.ts` (collector decoding), `packages/shell/tool-bash-persistent/src/index.ts`, `packages/fs/tool-str-replace-editor`
- **Evidence:** `.gitattributes:7` — `* text=auto eol=lf` with an explicit note that in-repo text is LF with no checkout smudge, and a stated policy for future `.bat/.cmd` exceptions; subprocess output is decoded as UTF-8 on every platform with no newline normalization (`packages/subprocess/subprocess-local/src/spawn.ts` `OutputCollector.readFrom` → `.toString('utf8')` at `:429-441`); the PTY layer accounts for CRLF at the wire: `packages/shell/tool-bash-persistent/src/index.ts:70-77` (`quoteForBash` escapes `\r`/`\n`) and `:92-112` (marker parse accepts `\r?\n`); `ENCODING_PREAMBLE` in `packages/shell/pwsh-local/src/index.ts:48` pins pwsh output to UTF-8 so Windows PowerShell 5.1's OEM code page cannot garble non-ASCII bytes; the file edit tool normalizes LF before comparing and adopts the detected line-ending style at write time (`packages/fs/fs-local/src/fsio.ts` edit path, `"Line ending style detected before LF normalization"` at `:611-612`).
- **Disposition:** reuse
- **Reason:** no fault found — LF-canonical source plus UTF-8 decode plus explicit CRLF awareness at the PTY boundary means dsh's model-facing output never depends on the host newline flavor; I-harness can adopt this unchanged.
- **Details:** The one deliberate wrinkle is a POSIX-order artifact in the desktop documentation rather than code: `docs/user/guide/python-sdk.md:102` — "the persistent PTY backend requires a POSIX terminal substrate, so this composition does not support Windows agents" — a statement that will be false the moment a win32 inspector lands (F04-2). I-harness tests must replay on Linux first (`packages/terminal/tool-terminal/tests/loader-composition.spec.ts:60`) while CI owns the Windows signal (`package.json:58` — `check:windows-wine`).

### F04-9: E2B remote sandboxing is the only escape hatch for Linux-only features on Windows, and it is out-of-box-unavailable

- **Severity:** Minor
- **Component:** `packages/e2b/*` (opt-in family)
- **Evidence:** `packages/e2b/e2b/README.md:5` — "the [family map] lists the opt-in composition" and nothing in `packages/bundle/*/cordis.patch.yml` or the shipped agent-preset files mounts an e2b row (grep over `packages/bundle` matches no e2b row); `packages/e2b/subprocess-e2b/README.md:43` — "there is no Windows, escaped-session recovery, or network-partition fidelity layer" so the adapter itself assumes the remote Linux world; the E2B command protocol executes real `chmod`/`bash` in the remote VM (`packages/e2b/fs-e2b/src/index.ts:528-537`).
- **Disposition:** improved-writing
- **Reason:** the "remote Linux VM for platform-independent execution" concept is the usual Windows escape hatch, but dsh ships it as an out-of-tree opt-in POC with no profile wiring, so no shipped Windows profile can reach it; I-harness must decide explicitly whether remote/microVM execution is in the Windows story and mount it in the profile if so.
- **Details:** The relevant design fact is that E2B is a *whole capability-seam sibling* (remote subprocess + remote fs), not a `ctx.sandbox` provider — `docs/subsystems/sandbox.md:5` states that containers/microVMs/remote execution "are sibling implementations of whole capability seams, not providers of `ctx.sandbox`". If I-harness wants Windows agents to run bash in a Linux VM, it must first define its remote-exec seam and then mount it per profile; the dsh E2B family is a working reference for the adapter shape, not for the product wiring.
