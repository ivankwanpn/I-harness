# Section 05 — Interaction Model & UI Consumption

Audit of how approval and user questions reach the UI, how the web/client
half consumes session events, and what I-harness's `interaction` seam (spec
§4.2) should mirror or improve: `packages/interaction/*` (approval, user
questions, tool-ask-user, commands), the host/client wire contract
(`packages/host/apiproxy/src/api/*`, `packages/api/remotes`,
`packages/api/gateway`), the connection/websocket carrier
(`packages/client/connection`, `packages/host/webserver`), and the web client
data layer (`packages/client/runtime`).
Target: dsh `0.1.0-rc.5`. Read-only; all `path:line` citations verified against
the dsh tree (see the Verification block at the end).

Summary for the I-harness kernel: dsh's UI-consumption model is structurally
sound and worth copying at the seam level — a push-subscription wire contract
backed by one shared typed barrel, provider-neutral approval/user-question
seams, and pure `presentCall`/`presentResult` render intents that never enter
the session log. The real gaps are boundary questions: approval resumability is
process-local (fragile), no interactive non-Web consumer exists anywhere in the
shipped tree, and the wire contract lives as a hand-maintained interface + zod
mirror across two TypeScript aggregates.

---

### F05-1: UI-consumption wire contract is a push-subscription model — one shared typed `ApiProxy` barrel, two downlink streams, one `/api/respond` echo — the pattern to mirror for spec §4.2

- **Severity:** Important
- **Component:** `packages/host/apiproxy/src/api/events.ts` + `packages/host/apiproxy/src/api/index.ts` + `packages/client/connection`
- **Evidence:** `packages/host/apiproxy/src/api/index.ts:3-5` — the `/api` contract layer "has zero Node dependencies and is importable from the browser; the TS interfaces are the authoritative contract, while HTTP, WebSocket, and in-process SSE are merely physical channels (four-quadrant message model)"; `packages/host/apiproxy/src/api/events.ts:69-108` — `MuxFrame` union: `session/event` passthrough of the raw `SessionEvent` plus `approval/requested`, `approval/resolved`, `question/requested`, `question/resolved`, `session/queue`, `session/jobs`, `session/projection`, `stream/error`; `packages/host/apiproxy/src/api/events.ts:56` — the `mux` stream opener signature (`AsyncIterable<RpcRequest<MuxFrame>>`); `packages/client/connection/README.md:5` — "The browser carrier uses HTTP POST for unary and respond operations and opens one downlink-only WebSocket each for `events.mux` and `events.host`"; `packages/client/connection/README.md:13` — the downlink sockets "send only the corresponding `ServerRequest` text messages to the browser; the client sends no application data over these sockets".
- **Disposition:** reuse
- **Reason:** the typed push-subscription + unary + respond-echo framing is exactly the decoupled consumer contract I-harness's `Interaction` seam needs; copy the four-quadrant message discipline (client-request / server-request / response / stream) and the `RpcRequest<Frame>` pattern wholesale.
- **Details:** There is no polling anywhere: session activity is pushed on the `mux` downlink as raw `SessionEvent`s (lossless JSON, already the durable-log shape, see Findings 01), host-level lifecycle rides a separate `host` downlink, mutations go over unary POST `/api`, and answerable server-requests are settled by echoing the wire `rpcId` through POST `/api/respond`. The single shared type barrel means the editor (host) and the browser (client) compile against one TS contract, not two copies. For spec §4.2 this validates a two-pronged `interaction` seam: `requestApproval`/`askUser` are the response side of pushed server-requests, and `render`/`presentToolCall`/`presentToolResult` are consumers of pushed session events. One caveat to design around: reconnection is "reopen the stream + refetch history" — `packages/host/apiproxy/src/api/events.ts:53` — `"since: resume hook, unimplemented in v1 (ignored if passed); reconnection = reopen the stream + refetch history"`. A consumer must therefore be idempotent over event replay; I-harness should decide whether its own consumers get a `since` resume or the same reopen-and-refetch rule.

### F05-2: Tool render intent is a provider-neutral pure-function contract (`presentCall`/`presentResult` → card-tagged views), host-computed per frame, never persisted

- **Severity:** Minor
- **Component:** `packages/core/tools/src/presentation.ts` + `packages/core/tools/src/schema.ts` + `packages/host/apiproxy/src/api/events.ts` + `packages/client/ui-tool`
- **Evidence:** `packages/core/tools/src/schema.ts:528` — `presentCall?` and `packages/core/tools/src/schema.ts:535` — `presentResult?` are optional methods on the `ToolDefinition`; `docs/subsystems/tools.md:461` — "How a tool wants its call shown in a UI (an editor tool-call card, a CLI log line), provider-neutral so a tool describes itself without depending on any client protocol"; `packages/host/apiproxy/src/api/events.ts:24-32` — `ToolEventView` is "a pure derivation of args/result through the presenter registered at emission time — never persisted (the session log carries only the event), so the same event may carry a different view (or none) on a later delivery", with "an absent view means the client's documented default (generic JSON card)"; `docs/cookbook/adding-a-tool.md:86` — presenters "run on live streaming AND on session-log REPLAY, so they must be pure functions of args (+ the result) — NO I/O, NO reading session state, NO clock/random"; `packages/client/ui-tool/README.md:15` — "Unknown intent tags and malformed wire card data fall back to flattened Tool result text".
- **Disposition:** reuse
- **Reason:** no fault found — the card-tagged render-intent union (`generic`/`terminal`/`diff`/`search`/`read`/`web`) with purity enforced by the replay requirement is a stable cross-surface contract for TUI/Web/Desktop; mirror the `Payload` shape and the host-computes-views posture in `Interaction.presentToolCall`/`presentToolResult`.
- **Details:** Rendering is intentionally NOT coupled to the web app: the session log stores only the model-facing `tool/call` and `tool/result` events, the host derives the presentation view per frame by resolving the tool definition that actually executed (scope-sensitive, see `presenterScopeFor` in `packages/host/apiproxy/src/api-proxy.ts:1551-1576`), and replay recomputes it; a card a UI cannot render falls back to the generic JSON card. dsh's own web components (`ui-tool` registering atomic views into the keyed `tool.call.toolview` slot) are replaceable presentation; a TUI or CLI consumer implements the same union. Spec §4.2's `presentToolCall`/`presentToolResult` can adopt this vocabulary and the "pure function of args/result" rule unchanged.

### F05-3: Approval is resumable across a client disconnect, but only while the host process and the tool's open turn survive — a bounded resumability contract, not durability

- **Severity:** Important
- **Component:** `packages/host/apiproxy/src/api-proxy.ts` + `packages/client/runtime/src/client/sessions/manager.ts` + `packages/interaction/user-approval`/`user-questions`
- **Evidence:** `packages/host/apiproxy/src/api-proxy.ts:1410-1414` — the approval pending registry comment: "The proxy is the approval channel for every agent this host owns… The entry survives client disconnects — mux-open replays still-pending requested frames with the same rpcId (the refresh-recovery baseline) — and withdraws on the ask's own abort signal (turn cancel), pushing `cancelled` to subscribers"; `packages/host/apiproxy/src/api-proxy.ts:3446-3447` — the `mux` opener replays `for (const pending of pendingApprovals.values()) queue.push(requestedFrame(pending))`; `packages/host/apiproxy/src/api-proxy.ts:3437-3444` — pending user questions replay the same way; `packages/host/apiproxy/src/api-proxy.ts:3699-3705` — `respond()` routes purely by the echoed `rpcId` and rejects a mismatched audit correlation (`approvalId`/`sessionId`) as `bad-response`; `packages/client/runtime/src/client/sessions/manager.ts:884-895` — `handleDisconnected()` clears generation-scoped pending-interaction state because "mux-open replay re-adds every still-pending request with its live rpcId"; `packages/interaction/user-approval/README.md:59` — "Requests are valid only inside an open turn — an idle or between-turn caller throws before auditing"; `packages/interaction/user-approval/README.md:60` — "Only one-shot grants exist … no allow-always, remembered rule, revocation, or grant store"; `packages/client/ui-user-questions/README.md:25` — "Unsubmitted drafts are not durable — reconnect resync or a full page reload restores the host-owned pending request with the same rpcId".
- **Disposition:** improved-writing
- **Reason:** the refresh-recovery baseline (same-rpcId replay on stream reopen) is a good answer to the disconnect question, but resumability is process-local — the pending registry lives in host memory, dies on host restart/bundle reload, and a turn cancel settles `cancelled` — so I-harness must state its own approval durability boundary instead of inheriting dsh's implicit one.
- **Details:** The mechanism is precise: an approval ask becomes an answerable `approval/requested` frame with a minted `rpcId`; the host keeps the entry in `pendingApprovals`; a reconnecting client reopens `mux` and receives the same still-pending frame with the same `rpcId`, so a browser refresh or a temporary socket drop does not lose the question (verified by the connection fixture suite: `packages/client/connection/tests/fixture.client.spec.ts:493-519` replays the approved interaction and asserts answer-then-replay stops). Resumability ends at three boundaries: (1) the host process — the registry is not durable, and disposal settles every entry `cancelled` (`api-proxy.ts:1419-1421`); (2) the turn — the ask's `AbortSignal` cracks on turn cancel and settles `cancelled`; (3) the session policy — the only session-level states are `ask`/`never`, with one-shot grants only, so nothing survives the answered action. For spec §4.2, `requestApproval`/`askUser` should therefore be specified as "resumable across consumer disconnect while the request is pending in-process", and the durability decision (persist pending approvals across host restart or fail closed) must be made explicitly; dsh's implicit choice is fail-closed `cancelled`.

### F05-4: The host/client split is drift-guarded by two TypeScript aggregates sharing one wire barrel, but the same payload shapes are hand-repeated in zod validation schemas

- **Severity:** Minor
- **Component:** `tsconfig.host.json` + `tsconfig.client.json` + `packages/host/apiproxy/src/api/index.ts` + `packages/host/apiproxy/src/api/*.schema.ts` + `packages/api/remotes`
- **Evidence:** `tsconfig.host.json:3-8` and `tsconfig.client.json:3-7` — the aggregate split comment: "the two sides merge cordis Context under the same keys, one program cannot see both", with per-file face selection under `packages/client` (`*.client.*` vs `*.host.spec.ts`); `packages/host/apiproxy/src/api/index.ts:3-5` — the shared contract barrel "has zero Node dependencies and is importable from the browser"; `packages/client/runtime/src/client/sessions/manager.ts:9-11` — the client value-imports "the inline-safe wire layer" from `@deepseek-ai/dsh-host-apiproxy/api`, so `MuxFrame`/`HostFrame`/`EventsApi` compile identically into both programs; `packages/api/remotes/README.md:22-26` — `api-remotes` is "the only deliberate exception" that lists files in BOTH faces (`remote-events.ts`/`types.ts`) so the forwarded-event allowlist "cannot drift"; `packages/host/apiproxy/src/api/events.schema.ts:47-51` — the zod validation library re-declares the `approval/resolved` and `question/requested` payload shapes that the interface already defines in `events.ts`.
- **Disposition:** improved-writing
- **Reason:** single-source typing across the browser boundary is the right and rare thing to copy, but each wire payload still exists in two hand-maintained forms — the TS interface (authoritative) and the zod runtime schema (trust-boundary validation) — and the deduplication trick is a documented, gate-unguarded exception, so the split remains a latent drift source I-harness should close with generated schemas.
- **Details:** The structural contract cannot drift: `events.ts`, `sessions.ts`, etc. are one file tree importable from both aggregates, and the generated Typert `/remote` artifacts additionally give typed unary methods (`packages/api/gateway/README.md:39` — "Only strict generated contributions can mount on the Client face", and `:40` — "The package dispatches unary methods only. Incremental Session data uses a separate named-stream protocol over the same Connection"). What CAN drift: (1) the zod `*.schema.ts` mirrors of the same payloads, maintained by hand for host-side parse validation (the `respond` endpoint revalidates after routing); (2) the forwarded-event allowlist double-listing, which a comment records as intentional but no gate enforces face source-file disjointness (`packages/api/remotes/README.md:37-40` — "No gate enforces the faces' source-file disjointness"); (3) the `since` resume field that is typed but unimplemented on the host (`events.ts:53`). I-harness's kernel should generate its wire schemas from one source (as Typert does for unary methods) and keep the stream-frame contract in exactly one `.ts` + one schema-artifact pair.

### F05-5: The interaction seams are provider-neutral by design, but dsh ships no interactive human consumer except the web host — headless fails closed, the SDK approval flow is dead capability, ACP is machine-only

- **Severity:** Important
- **Component:** `packages/interaction/user-approval` + `packages/interaction/user-questions` + `packages/bundle/headless` + `packages/acp/acp` + `packages/sdk/protocol` + `packages/api/remotes`
- **Evidence:** `packages/interaction/user-approval/README.md:5` — "Channel-neutral one-shot approval seam … missing or failing answerers fail closed"; `packages/interaction/user-approval/README.md:62` — "No built-in answerer — headless or incompletely composed deployments resolve `unavailable` and fail closed; the service itself never prompts a human"; `packages/interaction/user-questions/README.md:45` — "One provider per context … with none registered `ask()` throws `NO_PROVIDER` rather than degrading"; `packages/interaction/user-questions/src/index.ts:137` — `throw new UserQuestionError('no user-questions provider is registered', 'NO_PROVIDER')` and `packages/interaction/user-questions/src/index.ts:67` — `DUPLICATE_PROVIDER` for a second registration; `packages/bundle/headless/README.md:5` — the headless bundle "mounts no Host, HTTP server, Web runtime, or browser plugin"; `packages/acp/acp/src/index.ts:215-228` — the ACP bridge answers `approval/request` with one-shot machine options (`allow-once`/`reject-once`) for its owned agents only; `packages/sdk/protocol/README.md:39` — "Server→client requests are dead capability — the transport supports them, but the server never sends one; the Python SDK's responder surface exists for future approval flows"; `packages/api/remotes/README.md:11` — "Its Client face can be reused by Web or a future TUI that provides the same React-free `ctx.remote` contract".
- **Disposition:** improved-writing
- **Reason:** the seam's provider/answerer neutrality is correct and reusable, but the shipped tree has no interactive human consumer besides the web GUI — `dsh`'s own CLI (`apps/cli` + headless bundle) cannot answer an approval or a question — so I-harness's `interaction-cli` (stdin/stdout) is net-new design, not a copy.
- **Details:** A non-Web consumer CAN implement the same contract: approval needs an `approval/request` waterfall listener (the ACP bridge is the proving example), user questions need a `registerProvider()` (the web host does this in `packages/host/apiproxy/src/api-proxy.ts:1369`), and a TUI can consume the shared `ctx.remote` client contract. But no shipped profile does human interaction: `headless` is one-task, stdout-only, non-interactive; the SDK wire carries no server→client requests; ACP is automation-only with machine policy. The consequence for I-harness is that `Interaction.requestApproval`/`askUser` need a first-class CLI back end (dsh deliberately has none), and the fail-closed behavior (`unavailable`/`NO_PROVIDER`/deterministic `never` policy) is the correct baseline to copy while adding a prompter.

### F05-6: The command channel is a UI-plane-only human-input path whose results never enter model history — a separate surface worth copying into the seam

- **Severity:** Minor
- **Component:** `packages/interaction/commands`
- **Evidence:** `packages/interaction/commands/README.md:15` — handler "Results are rendered directly by the adapter and never enter model history"; `packages/interaction/commands/README.md:27` — "Known slash commands execute in the UI command plane, and their `CommandResult` text is not submitted as a user message. Unknown slash-command input is rejected by shipped adapters instead of becoming a model prompt"; `packages/interaction/commands/README.md:11` — each execution logs the log-only `command/run` + `command/done` pair (with a `sourceEventSeq` pointing back at an owning domain event when one exists).
- **Disposition:** reuse
- **Reason:** cleaner than folding every human gesture into `user/message` — command steering is surfaced in the UI without polluting the model transcript, and the log-only `command/run`/`command/done` pair keeps it replayable; mirror the `parseCommand()` + registry + adapter-side rendering split in the interaction seam.
- **Details:** The command registry is itself a consumed `interaction`-family service: `ctx.commands.register/list/find/execute`, scoped shadowing under `agent.ctx`, and `commands/change` notifications so live UI adapters refresh discovery. Commands that must schedule model work do it explicitly through the `Agent` (e.g. `dsh-plan-mode`'s `/plan [message]`), keeping the seam's "no implicit submission" invariant. This is a distinct human-input channel from `ask_user_question` (elicitation) and `approval/request` (permission), and I-harness's `interaction` seam should retain all three rather than merging them.

### F05-7: Transient interaction-adjacent state (`session/queue`, `session/jobs`, `session/projection`) is push-only and never logged — every consumer must implement the same reconnect baseline/replay discipline or converge differently

- **Severity:** Minor
- **Component:** `packages/host/apiproxy/src/api/events.ts` + `packages/client/runtime/src/client/sessions/manager.ts`
- **Evidence:** `packages/host/apiproxy/src/api/events.ts:101-102` — `session/projection`: "Live push state, never logged — replay recomputes on the host (the tool-view posture)"; `packages/host/apiproxy/src/api/events.ts:84` — `session/queue` is "the whole snapshot [that] makes edit, deletion, cancel, and reconnect converge through one authoritative signal"; `packages/host/apiproxy/src/api/events.ts:98` — `session/jobs` is "stored as an absent key" with a full snapshot on every registry commit; `packages/client/runtime/src/client/sessions/manager.ts:714-735` (in `handleMuxEnvelope`) — on `session/subscribed`, the client truncates prior projection values and drops the previous generation's queue/jobs baselines so "last-wins cannot pin a phantom value over recomputed truth"; `packages/client/runtime/src/client/sessions/manager.ts:887-895` — `handleDisconnected()` drops generation-scoped state before the next generation's replay re-adds it.
- **Disposition:** improved-writing
- **Reason:** the push-only + whole-snapshot + host-recompute posture is consistent, but it puts a heavy and unstated contract on every consumer (re-baseline on reconnect, higher-seq-wins, absent-key semantics); I-harness should either log these transient facts or document the same discipline centrally rather than leaving it to client-code convention.
- **Details:** Pending inbox items, background jobs, and projection values are exactly the "how-to-draw / what-is-currently-happening" data the web layer refuses to log; the host pushes whole snapshots and the client keeps per-session value stores (higher-seq-wins, seeded from the history tail page's projections block). Reconnect handling is non-trivial: the client must drop stale baselines on `session/subscribed`, re-pull the list, and resync opened sessions, all while a `mux`-open replay re-delivers still-pending approval/question frames. This is the sharpest part of the UI-consumption model for a new consumer: a TUI implementing the same seam must replicate the baseline/truncate/re-baseline logic or define its own convergence rule, and I-harness should pick one (log it, or adopt the push-snapshot + documented re-baseline) up front.
