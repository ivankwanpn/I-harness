## Problem and deliberate read contract

An actual parent Agent could receive its child's completed native job, a retained result catalog and a real target frame pin, while the ordinary typed frame read still denied the original output. The original source policy could see the parent catalog but had no trustworthy link from that visible catalog to its member frame.

The [selected design](../superpowers/specs/2026-10-21-native-result-catalog-witness.md) repairs that link under the original artifact pin owner. A cross-owner member read supplies its exact frame `ref` and the enclosing original catalog as `viaCatalog`. Bare cross-owner frames without direct current visibility remain denied. This is a deliberate explicit-witness API; it does **not** make the previously failing bare query succeed.

Private genuine PreparedCall registrations supply the exact frozen ordered membership. The original catalog commits first; immutable per-catalog companion records then publish beneath each real target frame pin before ready artifact-set/F1 publication. Unknown acknowledgement retries the original scope/capture without native replay. Real known membership quota preserves the primary facts and truthfully reports unavailable dependencies with the original count.

Every witnessed read checks exact committed refs, operations, real pins and the selected bounded companion. It applies the catalog's own current policy and the frame's own current policy plus direct closed-catalog visibility, before and after bounded reading. Repeated catalogs never overwrite an older witness. Arbitrary JSON refs, unrelated visible artifacts, missing pins and invisible/revoked catalogs confer no permission.

Actual Gateway and CLI explicitly advertise `session-result-read` versions 1 and 2. Custom readers remain v1 by default; witnessed reads require2 in server dispatch, SDK client and Desktop main. Ordinary v1 reads retain their route. The actual model tool supports the selector. This adds no new product page or automatic catalog traversal.
