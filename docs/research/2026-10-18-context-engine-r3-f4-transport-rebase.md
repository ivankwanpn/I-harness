## Existing fact and transport boundaries

F1's `ManagedAction` is an ephemeral admission/fence capability; its `beginAction` is not a durable generation budget. `step/start.actionId` and B2's `ExecutionConfirmation.sendId` similarly are observation/grouping identities. A new durable response-action owner must link these actual records without treating a repeated call to beginAction/startStep as a fresh allowance. F1's current `seed-import` rejects context operational events and accepted-exchange v2; F4 must extend this explicit boundary for its new operational types, not rely on an unrecognized-event fallback.

`preparedExecution.confirm` is synchronous and marks itself confirmed before calling host confirmation/current checks. Its role remains attribution; an awaited durable reservation cannot be smuggled into that callback. The final physical gate needs separate awaited reservation and synchronous single-use issue semantics. `preparedControls` currently deduplicates callbacks but selects one signal; its future grant propagation must retain exactly one owned grant identity and intersect all applicable signals. `snapshotModelData` preserves only requestScope identity today; an object-shaped private grant would otherwise be cloned. These are concrete carrier changes, not a generic request boolean.

`system-fetch.ts` selects proxy asynchronously, may import/build a dispatcher, then calls global fetch. Its proxy catch erases the cause and rewrites errors to a generic connection failure. Therefore the new per-request guard must run after those awaits and outside that broad transport-error rewrite, or typed owner errors must be recognized and rethrown before redaction. There is no direct fallback/retry in this transport. Keep account/catalog/auth consumers unchanged. A separate guarded-generation entry point/argument is preferable to state on the shared singleton; no grant belongs in headers or RequestInit's wire fields.

`llm-openai/client.ts` resolves subscription credentials before confirmation but confirms before proxy work. It also wraps the actual fetch in describeTransportError. The future leaf must preserve the original owner-control failure through both layers. It must not create a provider TRANSPORT event and retry a rejected/uncertain reservation. API-key routes and subscription should use the same physical gate contract, with their existing separate auth/wire construction.

## Actual retry descriptor must follow the prepared client

`provider-runtime/src/selection/binding.ts` can await current settings and rebuild its inner client during prepare. A descriptor read from the outer stable client before prepare is therefore not necessarily the policy of the final prepared request. The F4 executable contract should carry the immutable effective retry descriptor on the prepared handle created by the actual raw/wait/retry composition, preserve it on derivatives, and bind the pending main action from the final main preparation before any summary send. It must not defer this binding until the first main network send, since summary can occur first. Summary's own prepared descriptor never enlarges the parent's pool. For independent auxiliary work the actual selected auxiliary preparation binds its own already-open origin once.

This preserves the requirement to start the action clock before resolving the client: action-open is already durable and permits no sends, then selected preparation yields the original policy descriptor and action-bind fixes the limits. A later client/settings rebind can consume/constrain the existing pool but cannot create a new one. The existing C1 textOutput/measurement wrapper-preservation pattern provides the real carrier precedent; use a closed supported-data policy descriptor rather than serializing live resolver callbacks into facts.

An approval child is a special trusted consumer of an existing parent-owned auxiliary grant. Its local accepted transcript can retain an observation/reference to that grant, but it cannot import the parent's operational log or certify its allowance by folding only its own child document. The future contract must distinguish owned normal-child actions from this borrowed approval capability, keep no-tools restriction, and leave every reservation/remaining-count/expiry decision at the original parent document owner. Cross-document scalar references alone are audit data, not a newly minted issue capability.
