## 1. Specify restore orchestration and both persistence snapshot modes

**Amend draft `plan-draft.md:15–17,25–26`.** The record/index owner can be cohesive and small, but “indexed restore” must not absorb the outbox/result/persistence authorities. Record this exact synchronous protocol in the execution plan:

1. `validateTaskDocument(doc)` completes before any registry mutation.
2. Upgrade `documentVersion` if version2; seed the task counter from **all** input task IDs.
3. Restore notification rows/counter through the existing `TaskNotifications` instance.
4. For each input task, in input order: reject an already present ID; mutate the actual supplied task for the original v1 bodyKind or v2 unqualification; insert that same object in records; perform original terminal retention classification; install identity and child indexes.
5. Publish input tasks only after the entire loop succeeds. Restore schedules no save, capture, terminal notification or callback.

This is the actual protocol at `packages/subagent/src/task/registry.ts:236–268`. A duplicate ID late in the input leaves version/counter/outbox/earlier task mutations applied and performs no final publication loop. Duplicate *identity* and duplicate *child* keys currently replace their index entry while both task records remain; a new owner must not reject them. `restored-anon` numbering resets on each restore call; it is not the live anonymous counter. Preserve these facts instead of converting restore to prevalidated atomic import. The registry should retain cross-owner ordering through a few narrow record-owner operations or a narrowly defined synchronous per-record hook; no bulk restore that duplicates notifications, result qualification, or callbacks. Exact internal method names remain the writer's choice.

“Pure restored-field normalization” is safe only as computed data applied to the original object at those same points. Existing `unqualifyRestoredTask` mutates that supplied object (`task/publication.ts:17–24`), and terminal retention classification follows records insertion (`registry.ts:253–254`). Do not replace supplied records with normalized clones.

Add the following precision to the persistence bullet:

> Preserve strict mode's **call-time outer task/notification snapshots**, including their existing shallow nested references, and legacy non-strict mode's **write-execution-time** snapshot. Keep one existing save chain, swallowed chain continuation versus returned operation failure, and quiescent flush with no extra write. Do not deep-clone, freeze, defer the strict snapshot, eagerly take the legacy snapshot, or add an async boundary to save/publish orchestration.

Evidence: `task/persistence.ts:14–24`; registry snapshot at `registry.ts:53–62`. Both modes matter even though the draft currently names only strict mode. Moving records ownership must not accidentally change snapshot shape or timing through a new record-owner snapshot method.
