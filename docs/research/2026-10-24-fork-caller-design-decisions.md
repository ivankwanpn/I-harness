# Fork caller integration: decisions after source preflight

Status: planning, not an accepted product cutover. Existing B1 exporter/compiler and B2 bootstrap/transfer owners remain the implementation foundation. The [independent source preflight](integrated-checkpoint-20261024/fork-caller-preflight.md) found concrete gaps in the earlier F1 draft; do not implement that draft verbatim.

1. Retain the complete original fork request: closed source/selection, creation metadata, project intent and invocation. A digest alone cannot reconstruct original intent after the source changes. Use the existing digest owner through a read-only preparation step; the client fixes operation/target IDs and time before its first mutating fork RPC. Preparation issues no target, seed, grant, input or model request. Desktop renderer must not import Node persistence code or invent a second hashing implementation.
2. Exact original retry branches before source profile, busy/idle, flush and export in the outer Gateway and CLI callers, as well as persistence. It still checks current actual caller/workspace and target authority. Inspection is only a routing hint; the original coordinator receipt/document decides adoption. Changed explicit parameters conflict, and insufficient original data blocks rather than silently creating a new fork.
3. Both renderer callbacks own their original operation across IPC errors, lost responses and dashboard-refresh errors. Retries reuse it; an explicit fresh fork is a separate user action. Closed validation maps coordinator `already-ready` to wire `adopted`; only validated ready/adopted results may select the target. Missing capability/token refuses before mutation. Nonfork actions retain their current contracts.
4. CLI handoff must share the accepted result-store owner and retain the whole request through acquisition, target preparation, transfer and cleanup. It cannot use sourceFor on a not-yet-ready target or construct a second store. The separately reviewed close/reader repair is a prerequisite, not an assumed success.
5. Real project-binding exclusion is needed for CLI's unmanaged staging. The existing Documents owner already serializes ordinary/strict writes with `doc:<key>` OS leases; reuse that owner. A made-up revision string is insufficient. The concrete extension must also account for metadata changes, deletion, coordinator close, partial acquisition and lock ordering. JSONL's ordinary getDocument currently conflates read errors with absence; a guarded authority read must distinguish true absence from unreadable/corrupt/tombstoned data. The bounded owner contract is being specified before implementation; no extra bootstrap format or project registry is authorized by this note.
6. Preserve selected native carrier observations through B1 while keeping B3's replay permission separate. The old post-ready Gateway callback also grants legacy retrieval sidecars, so it cannot be labeled entirely duplicate. F1 needs an explicit legacy-ref disposition and retained regression, together with genuine nonempty managed catalog/member transfers on both CLI and Gateway. No empty-closure or always-confirmed replacement qualifies those callers.

The forthcoming executable packet must freeze the authority/lock boundary and include actual SDK/CLI stdio, Gateway/IPC and both Desktop callbacks. The original consumed-proof-body fork test, native observation preservation, lost-response/cold adoption, scope invalidation, exact output validation and teardown cuts remain required. Source preflight does not close F1, child C2, detached D2, native B3, event delivery, R6 or release gates.
