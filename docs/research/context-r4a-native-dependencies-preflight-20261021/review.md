## P1 — Define a reachable uncertainty schedule; a held foreground acknowledgement blocks the primary, while a one-shot throw may heal before F1

**Draft:**41–44, with31–33.

`packages/exec/src/jobs/observation.ts:15–16,40` waits for retention observation before a foreground `exec.run()` resolves. `packages/exec/src/jobs/retention.ts:46–51` starts the current observation and also joins passive settlement; the later result finalizer settles those original handles again (`packages/session-executor/src/lifecycle/result-dependencies.ts:23–29`). Therefore a fixture that sequentially awaits two foreground runs and withholds the first native publication acknowledgement cannot also reach the stipulated second source and returned primary. A one-shot rejected acknowledgement can instead be recovered by the next legitimate settlement before F1; merely observing that rejection does not establish an F1 hold. An unresolved native I/O acknowledgement inside artifact `mutate` also holds the workspace mutation queue (`packages/context-output/src/artifact/ownership.ts:27–32`), so waiting for a subsequent primary artifact commit while that queue is held is another possible test deadlock.

**Adjustment:** require a short schedule table before the writer implements this control: selected source, native completion, original observer registration, other-source commitment, primary readiness, actual finalizer entry, uncertain storage disposition and release/reconciliation. Separate a real unresolved-I/O barrier from an acknowledgement that rejects and releases the mutex. If foreground composition cannot reach the desired checkpoint, use the existing real background job route within the same genuine prepared call, or select a different genuine storage cut; do not change `ExecService`, manufacture a dependency disposition or claim the primary artifact committed while the queue prevents it. Primary-inline readiness can qualify this uncertainty control if stated explicitly; the all-artifact lifecycle control can be a separate successful run.

Record whether original same-owner reconciliation already recovered the cut before the finalizer. That is a valid recovery control, but it cannot be the sole evidence for “F1 held while dependency remained unknown.” For that claim, require an observed finalization attempt or pending finalization checkpoint with the source still unresolved, no result fact then, and a later ready fact after same-operation settlement. Always release barriers before draining/closing the assembly in `finally`.

## P1 — Keep an actual deletion observer alive across the fresh-reader deletion checkpoint

**Draft:**58–60, and69.

The draft correctly retires every original lease before freshness qualification, but does not identify the fresh lease that observes the subsequent deletion. `acquireResultReadStore` installs the coordinator deletion observer through `packages/session-executor/src/lifecycle/result-store.ts:89–93,118`; the final release removes that observer and closes the artifact service at113. The shipping `SessionService.readResultPage` wrapper releases its temporary lease after each read (`packages/session-executor/src/service/result-reader.ts:26–27`). Thus “fresh page reads succeeded; then delete through the coordinator” can execute with no artifact deletion listener at all. The coordinator notifies only its current listeners after backend deletion (`packages/session-persistence/src/coordinator/lifecycle.ts:21–33`); no inspected startup path replays old deletions into a later result store.

**Adjustment:** state the exact fresh lifecycle. First prove all original leases retired and the fresh store/coordinator are distinct. Then retain a genuine fresh `acquireResultReadStore` lease on the deletion coordinator through the entire confirmed deletion and pin/member inventory; its source/availability policy must remain the original one. Drain producers before deletion, await the real observer receipt, verify physical pin/member disposition, and release the fresh observer lease afterward. If qualification instead uses a stable Gateway/native-context lifecycle, name that composition and show its observer remains installed through the deletion acknowledgement. A direct coordinator deletion with no observer is a different unsupported cleanup experiment and must not count as connected A5 deletion coverage.

For the child-origin control, name the lower supported close/document-manifest/coordinator deletion path explicitly. Shipping Gateway session management rejects `origin:'subagent'` before its delete path (`packages/desktop-gateway/src/session-management.ts:146,167`); attempting its ordinary UI delete route for this actual child cannot reach source-pin release. The existing draft's distinction between direct coordinator deletion and Gateway close should be retained, with exact close/observer receipts rather than treating the two as interchangeable.

## P2 — Distinguish native frame completeness from catalog completeness

**Draft:**52.

The phrase “native capture limit/interruption yields source-limited output” is ambiguous at the very assertion the test needs to discriminate. The actual native capture owner supplies `complete`, `capture-canceled` or `producer-incomplete` (`packages/exec/src/capture/output.ts:172–176`). A limited/interrupted frame does not necessarily have `ref.completeness:'source-limited'`. The catalog deliberately folds every non-complete source into its own `source-limited` completeness (`packages/session-executor/src/lifecycle/result-dependencies.ts:32–34`). Execution outcome is separately derived from native root/termination observations (`packages/exec/src/capture/completion.ts:11–17,80`).

**Adjustment:** require the chosen control to name its actual stop mechanism and assert three independent results: the exact leaf-frame completeness supplied by that mechanism; catalog `source-limited`; and the actual native/primary execution and diagnostic outcome. Add a complete-capture/nonzero-exit comparison when using failure as the operational contrast. Do not change native leaf completeness just to match the wording, or accept a nonzero exit as evidence of truncated bytes.

## P2 — Make the all-member fixture materialize a primary artifact, and name both reader contracts

**Draft:**31–33,58,68–69.

Ordinary returned two-process metadata can remain inline. The actual result capture keeps an eligible value inline at up to60000encoded bytes (`packages/output-retention/src/result/capture.ts:51`); that produces no primary artifact, operation or document pin. Consequently a small happy fixture can pass an inventory of “every primary/catalog/frame member and original pin” while exercising only catalog plus frames. This would leave the intended primary+catalog+two-frame lifecycle composition unqualified.

Also, raw native-body byte paging in existing fixtures uses the lower store `readResult({ref,offset})`. The shipping transport reader dispatches `exec-frames-v1` to `readExecResult` and explicitly rejects `offset` for that codec (`packages/context-output/src/result-page.ts:18–28,43–47`). Its cursor is `{recordOffset,sliceOffset}`. Copying the old raw-body helper into a `SessionService.readResultPage` test yields a range rejection, while using only the raw helper omits the actual caller-facing frame page route.

**Adjustment:** for the whole-set successful fixture, explicitly require primary retention `artifact` and author sufficient deterministic metadata to cross the real inline threshold without altering product force/admission policy. Require four committed original artifact identities/pins (one primary, one catalog, two distinct frames), with actual identity assertions before lifecycle steps. Keep inline primary as an explicitly separate valid case when useful for the uncertainty schedule above. Use bounded raw store pages for exact `IHEXEC01` bytes and independent hash/order oracles, and separately exercise the actual shipping frame reader with advancing typed cursors under the target's real policy. Never invent an offset-based native transport request or replace the original authorization callback.
