# Read-only review — physical retained-result crash qualification

Reviewed 2026-10-21 against the draft `following-physical-crash-plan.md`, completion-handoff A5, the retained-results contract, and the original implementation. No product writes, tests, subprocess fixtures, builds, or recursive agents were run for this review. This review file is the sole write. Runtime feasibility of native module mocks plus tsx is therefore **unqualified**, not a passing control.

**Verdict: revise before dispatch.** The bounded A5 scope and most physical fault seams are sound. Two concrete issues can otherwise give misleading passes: the supplied ContextOutputService bypasses the original source authorization composition, and returning an unknown outcome to the live producer can trigger its existing passive reconciliation before the parent kills it. Several counter/count/setup details also need to be made executable rather than left to interpretation. None requires inventing a new recovery owner or changing product behavior in advance.

## Findings requiring plan correction

### P1 — Supplying a bare ContextOutputService bypasses the source authorization path the test says it qualifies

Draft lines 54 and 99 require supplying/reconstructing a genuine ContextOutputService, but do not specify its source descriptor or authorization policy. Being the real store implementation is insufficient here. `packages/session-executor/src/lifecycle/result-store.ts:27` returns a supplied instance immediately, bypassing the automatic registration, source resolver, authorizeResult callback and deletion subscriptions. `result-retention.ts:16-17,27-34` obtains its descriptor only through the supplied `sourceFor`; without one, the artifact owner has no source. `packages/context-output/src/artifact/ownership.ts:93-94` requires original pin evidence but only calls authorizeResult if the operation has a source. A fixture with no descriptor therefore skips the source ACL under test. A fixture adding a source but omitting authorizeResult instead denies every page. A permissive authorizeResult would create a third, fixture-defined authority policy.

**Smallest safe correction:** use the shipping automatic result store in both producer and fresh reader, with no `contextOutput` injection, a real coordinator storageRoot, the same task-owned existing workspace, and an isolated settings path. Observe the authentic selected result batch's envelope/ref and inspect the original operation/manifest/pin files read-only at the location returned by `contextWorkspaceLocation`; the backend-intercepted authentic batch is already sufficient evidence for the before-issue case. No new scope, grant, capture or store registration is necessary merely to observe it. Do not read a ref from arbitrary artifact metadata and turn that into conversation evidence.

This correction is feasible for the proposed root session with no project-binding document. Automatic producer acquisition registers a producer (`result-store.ts:103-105`); fresh `service.readResultPage` acquires the original reader registration (`service/result-reader.ts:19-24`). The resolver uses actual profile and binding-document reads (`result-store.ts:43-73`), and authorization compares workspace/source identity before permitting the original owning session (`75-85`). A cold root-session read needs neither an assembly nor a fabricated project context. Add an unrelated session/ref negative control with zero **body** I/O; metadata/profile/pin I/O is expected and must not be mislabeled zero I/O.

### P1 — Unknown cases do not yet specify a stable cut before original passive reconciliation can run

Draft lines 82-83 and 89 require the original backend to return unknown before announcing the cut, but only the committed-withheld case explicitly parks its append wrapper. Forwarding genuine unknown to the coordinator permits original producer cleanup to advance the very storage state being tested. The normal tool path ends with `source.close()` even on failure (`packages/core-agent/src/tool-batch/join.ts:117-120`); that source drains original records (`join.ts:50`), whose `drainSettled()` calls `commitSlot(index,true)` (`record.ts:70-76`), selecting `slot.fact.reconcile()` (`record.ts:58`). Coordinator reconciliation can recognize and install the full frame, or truncate the partial frame (`managed-document.ts:360-379`; `fact-journal.ts:133-141`). Sending IPC and hoping the parent kills sooner is an unreliable oracle.

**Smallest safe correction:** after awaiting the genuine original append and validating its original unknown key, have the backend wrapper send the cut receipt and park **before forwarding that outcome to the coordinator**. Hold that exact append Promise until hard kill, and assert no same-key reconcile occurred. Name this evidence precisely: backend returned unknown to the wrapper, coordinator/caller disposition withheld. It is not a claim that the caller already observed unknown. If a separate owner-observed-unknown case is wanted, explicitly add a test-only gate on the same original key's reconciliation entry and record the observed original FactOutcome; do not silently fold that extra semantic case into the existing one. No fabricated backend return or product retry suppression is needed for the proposed five-case matrix.

### P2 — Frozen child counters cannot prove zero work in the fresh host

Draft lines 53, 100, 106 and 108 correctly demand incremental counts, but an IPC counter snapshot from a dead process is immutable. Re-reading it after a cold read or new submit will always produce unchanged counts even if the fresh service executes a new fixture body/getter/hook. An effect written only by the child likewise misses an accidental fresh-host tool implementation that does not use the same effect oracle.

**Smallest safe correction:** preserve the child's original counts as historical evidence and install fresh-host counters before constructing/reading through the new service. Register the same named fixture implementation in the fresh service and make every process append to the same task-owned effect ledger when it actually runs. Count fresh assembly creation via the real `service.onAssembly` hook (`service.ts:1154-1161`), whose assembly exposes `ctx` (`assembly.ts:369`), and attach tool-name-qualified hooks before any submit. Count fresh captures/begins at a genuinely observed original composition seam or state an equivalent artifact-operation inventory oracle; do not infer capture count from an unchanged child number. Parent-owned server request counts span both processes already. Require child body/getter/fixture post-execute = 1, fresh equivalents = 0 through cold reads/recovery/new text-only submit, and total effect ledger entries = 1. Count nested fixture hooks separately from outer `code_exec` hooks.

### P2 — The exact result-count oracle must distinguish original completion from conservative recovery

Draft line 105 says the original fact stays once after reopen, while before-issue and partial-frame cases intentionally have no original result fact. For an ordinary call, owned recovery adds a **different conservative result** for the same callId; simply asserting one tool/result for that callId cannot distinguish correct recovery from fabricated success. For Code Mode, counting all tool/result/code/result rows together can hide a duplicate nested result behind the outer unknown result.

**Smallest safe correction:** include an explicit per-case count table keyed by original ordinary callId, or nested cellId/callId plus outer code_exec callId. Before owned recovery, original selected result frame count is 0 for before-issue/partial and 1 for complete-unknown/withheld/install. After owned recovery, preserve those same original-frame counts. Missing ordinary result gets exactly one original conservative recovery result, with its unknown/replay:false payload and no artifact envelope fabricated from the orphan. Missing nested result remains 0; the outer code_exec gets its existing conservative result. Durable nested result remains 1 while outer completion is still independently unknown if absent. Repeated reopen adds no second recovery row and never changes the original selected frame/key/ref. Specify counts for both semantic rows and exact selected physical frames.

### P2 — Pin down the real service Code Mode call and yield horizon so a background observation does not move the cut

Draft lines 16/53/93 require the real guest path but do not pin mode, model arguments, or how the dynamically assigned nested call is selected. `registerCodeMode` creates the real `code_exec` tool and calls runtime.exec (`packages/code-mode/src/register.ts:76-85`); its model exposure is mode-dependent (`114-117`). Runtime default yield is only 1000 ms (`runtime/limits.ts:19`; `runtime/admission.ts:41-47,89`). A delayed artifact write can therefore return a running outer observation before the nested result reaches the intended cut. A literal nested invocationId guessed in the parent is also not an actual binding.

**Smallest safe correction:** pin codeMode.mode to `only` or `mixed`, return the actual SSE `code_exec` call with exact source such as `const value = await tools.fixture_result({}); text("guest-fulfilled");`, and set an explicit existing yield horizon longer than the bounded cut deadline. Read the actual durable nested code/call's cellId/callId/name/outer lineage, then select the corresponding code/result batch rather than inventing its identity. Count/forbid the continuation marker at every cut; add a no-cut setup control proving the same actual guest/tool path can fulfill once. Reject a premature outer running result as a missed cut/setup issue, with its evidence retained. Do not increase product timeout limits to make the control pass.

### P2 — Native mock feasibility needs its own setup gate and the helper files need an actual type-check scope

Draft lines 55-73 responsibly mark the native mock plus tsx combination unexecuted. Preserve that status. Importing the actual core index and forwarding its original functions is a plausible way to retain the shared WeakMaps; the genuine state marks and owner binding are in `packages/core-session/src/managed/view.ts:28-33,75`, and the factory is publicly exported (`core-session/src/index.ts`, createManagedSessionState export). The real coordinator stages before encoding and retains that staged install closure (`managed-document.ts:180-183`), so wrapping only that closure is the right phase. However, no source inspection proves that native mock interception resolves to the same tsx-transformed module in the exact child launcher. This must succeed before any install-case product RED is classified.

The proposed new `.mts` files are outside `packages/session-executor/tsconfig.json:3` (`src/**/*.ts`, `test/**/*.ts`). Running the package's ordinary tsc gate therefore does not validate their argument types or fault wrappers.

**Smallest safe correction:** first run an isolated setup/no-cut helper through the exact direct Node + `--experimental-test-module-mocks` + `--import tsx` launcher. Assert wrapper interception, unchanged authentic view/owner/source brands, a real staged install, and normal original commit/observation before arming the fault. Ensure no persistence/executor import precedes registration. Record launcher failure as setup failure. For the real cut, inspect the original outcome's `code: FACT_INSTALL_FAILED` (not merely the propagated generic `FACT_RECOVERY_REQUIRED`), original committed receipt/key, and zero selected observer publications. `committedFactSeqs` deliberately changes the thrown error code while retaining `.outcome` (`core-session/src/managed/outcome.ts:5-9`), so generic submit rejection alone is insufficient. Add an explicit helper typecheck scope or typed bootstrap project; do not claim package tsc covers `.mts`. If loader interception fails, return exact setup evidence and a proposed test-only import transformation to root before altering product owners.

## Confirmed source-grounded parts; keep these assertions

- **Exact raw-prefix assertions are possible for this fresh format10 fixture.** Backend framed repair reads the valid prefix, takes its original raw bytes and appends only new closer frames (`packages/session-persistence-jsonl/src/index.ts:169-177`). The coordinator's fenced semantic recovery appends additions when the original event prefix is unchanged (`coordinator/load.ts:110-125`). `repairFencedTail` copies existing events and appends only recovery results/closers (`repair.ts:257-280`). Capture raw pre-recovery bytes, original header newline boundary, journal valid-prefix byte length and selected frame bytes/key/digest. After recovery assert byte equality for the complete original prefix at the same coordinates, then independently decode only the appended recovery suffix. The torn 17-byte suffix is expected to disappear. Do not assert equality of the entire session file, physical inode or file replacement identity: repair atomically replaces the file (`index.ts:175`). A complete durable frame must survive byte-for-byte. This is an assertion the source supports, not an excuse to soften it to equivalent JSON.
- **Cold snapshot is the correct session operation.** `coordinator/load.ts:24-31` reads/migrates without backend repair. `load()` is unsuitable despite a historical read-only comment: it calls `backend.repair` (`load.ts:33-45`). `openManagedDocument` calls `loadOwned`, then the original owned prefix reader (`managed-documents.ts:31-35`), so instantiate services without implicitly opening/assembling them until the explicit recovery phase. The result page reader is `service.readResultPage`, not a nonexistent SessionService.readResult API. The raw store's readResult is a different lower-level operation.
- **Context-read capabilities are distinct.** The retained-body host read needs the real storage root/workspace/source/pin capability composition described in Finding 1; the registered `context_output_read` tool additionally requires a real ToolExec sessionId and abort capability (`context-output/src/tools.ts:13-16,54-59`) and running it is tool execution, so it cannot stand in for a zero-tool-work cold host read. `service.contextState` is another read-only observation (`service.ts:480-485`; `service/context-state.ts:15-29`) and may truthfully be unavailable without saved budget facts; it does not prove artifact readability. `get_context_remaining` needs a real budget reader/window (`core-tools/src/context-remaining.ts:21-25`), so do not add invented model supply/capabilities just to get a ready context state in this artifact test.
- **No nested completion is supplied by existing repair.** `repairFencedTail` recognizes only outer tool/call, tool/dispatch and tool/result, plus turn/step markers (`repair.ts:262-275`). The draft correctly leaves missing code/result absent. On a later actual Code Mode mount, the original register owner can add a code/cell interrupted marker for an open saved cell (`register.ts:32-37`); this is neither a nested tool result nor restored continuation. If it occurs during the intentional new-input assembly phase, record it with the original owner rather than treating every new event as forbidden or inventing a code/result to close it.
- **The five backend physical states are feasible at the named original seam.** Original append writes the exact `batch.bytes` object at known offsets, then syncs (`fact-journal.ts:81-91`); rollback must truncate and sync to prove absent (`97-103`). Native 17-byte write+sync followed by a controlled failure and refused rollback can genuinely leave torn unknown. Native complete write+sync followed by a controlled sync wrapper error and refused rollback can leave complete unknown. Preserve handle and byte-object matching; ordinary non-target writes and fresh owners remain native. Describe successful native sync followed by injected error honestly as lost durability evidence, not a real disk sync failure.
- **Hard-crash process ownership is materially improved.** Direct `process.execPath` with `--import tsx`, retained ChildProcess handle, nonce-bound IPC, an alive IPC listener, kill and `close` fence avoids the old tsx CLI wrapper and process.exit proof. Require successful kill/close and do not turn a child's spontaneous normal exit into a crash pass. On Windows, do not assume the POSIX signal field must literally equal SIGKILL; record the tested OS's actual close disposition. Cleanup failures must remain failures. No descendant executable is needed for this tool/QuickJS fixture.
- **Read-only does not mean zero filesystem activity.** Managed page reading uses the original mutation serialization/lease (`ownership.ts:27-30,98-104`), and automatic acquisition uses metadata/settings/profile reads. The intended prohibition is no journal repair/upgrade, result capture/commit, pin/grant mutation, assembly/model/tool/guest work. Compare durable session/artifact authority files and operation inventories, allowing task-owned lock lifecycle activity. Separately instrument protected body I/O for unauthorized cases.
