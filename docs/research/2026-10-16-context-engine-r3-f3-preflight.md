## Ruling: a named, finite pre-E target

For this bridge only, preserve current main admission rules and the resolved current compaction threshold. Let I be the calibrated measurement of the selected final candidate, R its actual current output reserve, W the configured window, and H=`ceil(W*(1-reserveRatio))`. Capacity fit includes `I+R <= floor(W*reserveRatio)`, supported-output minimum and complete input/valid final protocol. Actual main admission additionally retains its unresolved-recovery authorization restrictions; a pure candidate probe cannot consume that authorization.

Name the additional reduction target `ih-legacy-final-request-target-v1`:

```text
targetReady = capacityFit && I + R + H < thresholdRatio * W
```

The existing default thresholdRatio is.8. This is a deliberate reconciliation of existing gates, not a claim that the old code had this final-request target. A complete durable reduction can therefore be `reduced-over-target`; writing a marker or lowering input does not make it `ready`. Unknown W, incomplete input or unsupported native source cannot produce certified target readiness. Existing main compatibility behavior for unknown capacity remains separately labelled until E, not reclassified as fit by F3. Target readiness is explicitly independent of transport authorization: a valid recovery reduction may reach the target while recovery remains required. After its receipt, the real main recovery owner must validate progress and consume the one changed-input authorization during ordinary main admission. Do not make publication wait for an authorization that can only be obtained after publication, and do not set recoveryAuthorized=true merely to make a hypothetical assessment pass.

Literal independent oracle: W10000, reserveRatio.9, R600 gives H1000. I7399 is hard-fit but pressure8999 exceeds target8000; I6399 has pressure7999 and is ready; I6400 has pressure8000 and is not ready under the strict legacy threshold. A derivative whose input changes must use its own final I, never A's measurement. These numbers are local policy controls, not provider/tokenizer claims.

E still owns its approved additive effective-budget policy, sourced capacityDomain, catalog-default removal, .8/.7 hysteresis and accepted-exchange cooldown. F3 must not silently implement only part of those changes or claim a new shared-window truth for an input-only/unknown provider limit.

## Ruling: private preparation and pure calculation

Use two layers with one calculation:

1. The existing main owner injects an asynchronous private candidate-preparation port. It constructs the exact current main request from captured surface plus F2's candidate projection, including all retained inputs, accepted suffix, system/schema, media/native blocks and raw route options. It prepares through the actual captured client. It never streams, claims input, allocates an acceptance/reservation or publishes budget facts.
2. The pure calculation consumes that prepared request, immutable policy/recovery/expected-execution facts and the existing read-only calibration probe. It returns the selected handle, semantic/payload identities, budget facts and advisory calibration disposition. It performs zero writes, telemetry, retirement or execution-state mutation. Only the live main owner publishes current observations or consumes an existing recovery authorization.

Share data-only request construction; keep prefix fingerprints/rewrite telemetry on the real current-request path. Share scalar budget comparison; do not fabricate a Session merely to call an API whose fallback is unused. A hypothetical A anchor miss followed by compatible B must leave the live calibration anchor intact. A real committed rewrite still retires it once through B2's existing owner.

Private preparation returns `assessed`, `stale` or `blocked`; an assessment separately states `capacityFit: yes|no|unavailable`, `target: ready|over-target|unavailable` and recovery-required facts, bound to the exact selected handle/IDs and named policy. These are preparation facts, not transport permission. Reduction separately returns `unchanged`, `reduced-over-target`, `ready` or `blocked`, with publication disposition kept distinct and all committed outcomes requiring ordinary current main admission before transport. Keep the existing main snapshot's authorization-sensitive admission value; expose capacity-only comparison from the same pure calculation, not a second formula. Do not call `recovery.admit` during a hypothetical probe to mint the changed-input retry. Add a confirmed-overflow fixture that reaches its target, commits once, then obtains its single authorization through the real recovery owner; zero send before that authorization proves there is neither a circular recovery block nor a bypass.

## Ruling: complete checkpoint text, compatible output and provenance

Existing summary acceptance checks completion/refusal/truncation and500..4096 characters for the default retained hint1024, but accepts sectionless JSON and ignores a pre-end tool_call. The prompt already requests a specific checkpoint. F3 makes that actual contract enforceable without claiming semantic truth:

- Require the complete `<compacted-summary>` / `</compacted-summary>` framing, exactly one occurrence of each of the seven existing ordered section headings: Objective, Important Details, Work State, Next Move, Relevant Files, Sensitive Instructions, Tool Work Summary. Every section contains content or an explicit `(none)`. Reject partial framing, duplicate/missing/out-of-order sections and non-whitespace outside the checkpoint. Keep the existing complete/no-refusal/no-truncation and retained character bounds. These are JavaScript character/code-unit bounds, not UTF-8 bytes or provider tokens.
- Reject any summary tool-call output without dispatch, including a tool_call before end. Preserve terminal/usage observation honestly even when checkpoint acceptance fails. Manual instructions refine content but cannot waive source coverage, structural completeness or runtime authority requirements; adjust contradictory prompt wording that currently says they override the template.
- Determine text-checkpoint eligibility from the actual selected final body/resolved adapter owner. Known JSON-object/schema/enum-only output, forced-tool-only output or another known incompatible generation mode cannot qualify for this text contract. Preserve raw options. Use an already explicitly selected compatible summary binding, or return a typed blocked result. Unknown/custom eligibility is explicit, never asserted compatible solely because generic preparation passed. The executable plan must choose the narrow actual capability carrier and retain the distinction between known incompatibility and unknown coverage; no generic schema interpreter or silent option stripping.
- A previous summary participates only when it is in the selected span, with derived provenance. A selected tool/plugin/delegated observation must not be relabelled as a human instruction by the current keyword-based Sensitive Instructions prefill. Derive any human-instruction prefill from selected items' actual authority/provenance; retain other source text as attributed observation. Quoted imperative content does not gain authority through summarization. This follows the approved authority boundary, not a new permission system.

Cost: a model producing the old length-valid but incomplete format will now consume at most the existing two quality rounds and then block. A configured structured-output main model may require its already supported separate summary-model configuration. This explicit failure is preferable to persisting a false complete checkpoint; it is not a promise that the model's valid-looking summary is factually perfect.

The legacy defaults remain explicitly named until E: retained hint1024 → maximum4096 code units, minimum500, separate preferred generation output4096 and summary5% safety. Preserve explicit output preferences/floor handling and existing configuration; no E default migration is hidden here.
