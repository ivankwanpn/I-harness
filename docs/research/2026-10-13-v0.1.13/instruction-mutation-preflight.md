## Recommendation and the two required controller rulings

Extend the existing tool capture/preparer, batch scheduler, native filesystem mutation points, Session context handle, and Code Mode retirement owners. Capture native targets once from the frozen argument object, preflight the entire known mutation batch before any body, then recheck the source epoch at dispatch and native mutation boundaries. Instruction replanning must have its own typed disposition and stop-admission state, distinct from policy refusal and cancellation.

**Ruling A — instruction-file self-modification:** reject a known batch/call that both changes an instruction candidate and mutates another target in the candidate's scope, before any write. Ask the model, through the recoverable tool result, to split it into an instruction-only operation and a later code operation after a new provider request. Also reject multiple candidate mutations where an earlier candidate mutation can change the applicable rules for a later candidate mutation. A standalone candidate mutation may execute under the currently delivered rules; successful writing does not acknowledge its new rules. Candidate mutation inside Code Mode then ends that cell's executable lifetime through the host replan fence. The existing successful nested result remains recorded.

This is a conservative extension that needs an explicit controller ruling: approved prose says new discovered rules require replan, but does not specify how a not-yet-written candidate and code can share one operation. Returning replan for this shape must explain that splitting is required; there is no new disk snapshot yet, and the result must not pretend a new fingerprint exists. Use the current fingerprint plus a bounded reason/affected scope. Otherwise the identical operation can loop forever.

The workflow cost is concrete: a model that originally issued one mixed operation must generate a fresh candidate-only operation after rejection, then issue fresh code arguments from a further provider request carrying the resulting snapshot. That is two additional provider boundaries compared with immediately executing its original mixed operation; proactive splitting avoids the rejection and costs one additional boundary. The host performs no splitting, reordered execution or automatic replay. Treat shadowed/non-winning AGENTS/CLAUDE candidates conservatively as candidate writes for this shape check even when their current edit appears not to affect the winner; after standalone mutation, normal prepare may establish unchanged effective rules. This can reject a safe shadowed edit plus code and therefore is an explicit workflow restriction, justified by avoiding speculative winner predictions and priority-transition races.

**Ruling B — race contract:** guarantee zero mutation for a batch rejected at initial preflight, and zero *additional not-yet-entered native mutation points* after the host observes a relevant invalidation or unavailable/revoked source. Do not promise zero historical mutations for a batch whose earlier writes completed lawfully before a later source change, or filesystem atomicity against unobserved external writers. Preserve those completed side effects and results, and drain accepted producers. This clarifies the apparent breadth of spec acceptance item 5; a literal all-time zero-mutation promise for arbitrary concurrent external writes is unavailable without a substantially different execution model.

## One captured native plan, without authority from JSON

Split only the capture portion of existing prepare into a small trusted staging seam: clone/freeze arguments, retain registration and execute binding, schema validate, then invoke the registered native target capability. Stage those captures for the batch and pass them to the existing ordered policy/approval preparation; do not clone arguments a second time or collect metadata from one object and execute another. Pure capture cannot execute tools, ask approval or call a provider. Existing schema/argument failures retain their repairable disposition; metadata failure cannot default a known mutator to no targets.

The filesystem owner should parse and normalize its immutable execution plan at that point. A closure-owned map keyed by the retained frozen arguments is sufficient if the public descriptor remains `ResolvedTarget[]`; alternatively a trusted internal plan slot can travel in PreparedCall. Actual write/edit/read/list and patch execution consume this exact plan, including all normalized patch paths and hunks. No detached model-supplied plan, call-name heuristic or JSON authority marker is accepted. Direct registry use and Code Mode must share the capture seam; the absence of a Session context must be an explicit host capability policy, not a silent skip in product assembly.

Keep policy/ancestor/monotonic guards/approval capture/guardian-human order, and body sandbox escalation plus per-write guards. Do not hoist sandbox prompts or mutable filesystem authority into pure target discovery. Instruction descriptors are applicable-rule scope evidence, not write permission. The plan preserves lexical paths for scope; source service performs authorized canonical discovery/deduplication, including missing candidates, case aliases and junction boundaries.

Preserve tool-object receiver semantics: invoke target capability on its registered tool object (or capture the method once and use `.call(tool, ...)`); retain `prepared.tool.execute(...)` receiver and binding validation behavior. Do not spread tool objects to manufacture wrappers, eagerly enumerate lazy accessors, or invoke accessors just to copy metadata. If the new target capability changes during an approval await, its captured binding/plan must be treated as changed authority; native closure ownership is preferable to trusting a publicly mutable descriptor. The frozen baseline's execution getter accesses remain as currently required for validation/body invocation. Future tests should verify added metadata getter count/receiver separately, without accidentally asserting registry dispatch is single-use: baseline explicitly permits caller-owned repeated dispatch/finalization (`F:packages/core-tools/test/registry-contracts.test.ts:84`). I5 scheduler/Code Mode must simply never replay a blocked operation.

## Batch barrier, epoch rechecks and candidate mutation

Use one Session handle from I4, one instruction service from I2, and request delivery ownership from I3. Distinguish (a) current rendered snapshot fingerprint, (b) the exact instruction snapshot attached to the request that produced these tool arguments, and (c) dirty/source generation or unavailable/revoked state. A dirty source may still have the same old cached fingerprint; comparing fingerprints alone is insufficient. A newly appended snapshot or a tool read result is not an acknowledged model request. A running old Code Mode cell retains its original request epoch even if another request later sees new rules.

Sequence:

1. Capture all tool-owned targets for the completed provider batch, across exclusive group boundaries. Prepare their known source chains together. On unseen/changed rules or unreliable sources, persist the current snapshot for the next request and return typed replan for all blocked mutation calls, with truthful never-started status. Preserve one answer per call ID and ordinary read outputs if reads are admitted. There are zero mutation body invocations in this branch.
2. Analyze native candidate mutations against all batch mutation targets. Candidate recognition includes both AGENTS and CLAUDE, an absent higher-priority candidate, configured global sources, and known canonical aliases. **Overlap is resolved by the host instruction service's applicability policy**, not bare string-prefix or whole-filesystem ancestry: compute each target's chosen allowed root/boundary (most specific host root intersected with confirmed Git boundary), its lexical chain inside that boundary, explicit global-source membership and canonical aliases. A candidate overlaps a mutation when it is or could be an applicable candidate on that target's chain under this policy; its lexical directory subtree is clipped to the selected authorized boundary. For example, a parent directory's candidate is not applicable through a narrower independently selected root that excludes that ancestor; a root A candidate does not cover root B merely because of a lexical ancestor relationship. A configured global source overlaps every target that actually consumes that global policy, not foreign roots/Sessions with other global configuration. An unauthorized candidate location does not silently acquire instruction authority. Apply ruling A for overlap regardless of call/hunk order, including shadowed candidates in an applicable chain. Disjoint lexical scopes may proceed only when global/canonical dependencies also prove disjoint; conservatively block uncertain overlap.
3. Continue existing ordered prepare and rolling dispatch using retained plans. Reconcile dirty instruction state before dispatch as needed, and make a final synchronous epoch/reliability check after awaited execute hooks and immediately after final authority checks, outside `validatePrepared`'s refusal-catching block. Never introduce an await between final authority validation and body invocation. If a final synchronous check finds dirty state, it can block immediately; rebuild at the next safe context boundary rather than pretending it synchronously read new contents.
4. Repeat the synchronous source fence at native mutation boundaries after sandbox ladder, reads, preimage capture and other awaits; atomic replacement checks immediately before initiating rename, and direct writes/unlink immediately before initiating their I/O. An instruction-only writer needs a bounded self-write allowance for its own announced pending candidate operation; it must not waive sandbox, close/revoke or unrelated source invalidation. There remains an I/O interval after initiation which cannot be atomically fenced against external filesystem changes.
5. A candidate-only operation is exclusive in its owner scheduler; drain accepted earlier work before initiating it. Announce its candidate write as pending/dirty through the shared source observation contract before mutation I/O, and invalidate again upon settlement, before its result becomes successful/visible. Pending candidate state prevents another participating Session from preparing a supposedly reliable snapshot halfway through an owned write. This is source-local state attached to the planned instruction observation owner, not a generic filesystem lock. If I2/E7 do not expose pending native-write evidence, synchronous *success-only* invalidation cannot guarantee exclusion during the write interval; document that limitation or add this narrow seam before claiming the stronger native guarantee.
6. Once candidate mutation settles, pending affected mutations from old requests replan; the next actual provider request prepares and acknowledges the resulting disk snapshot. Do not use model-authored patch text as the effective post-write snapshot: writes can fail, shadow a fallback, change scope identity, or be externally replaced. An unchanged effective fingerprint after a shadowed-candidate edit can be proved by prepare; it need not cause a permanent epoch mismatch, although conservatively ending a self-modifying cell remains simpler.

On late replan, stop admitting additional work in the batch and fill not-started mutations with replan; do not abort the batch signal or revoke independent accepted producers. Already accepted unrelated work drains/finalizes normally. An affected in-flight native body can fail its next mutation boundary; retain any already applied paths and real outputs. A multi-file patch needs a typed outcome carrying `applied`, remaining/not-applied paths and replan fingerprint/reason, or equivalent explicit propagation; otherwise its catch erases the control disposition. This partial result describes a late invalidation, never an initial-preflight success. There is no rollback or original-argument replay.

For that drain guarantee, accepted native calls retain their captured applicable-source dependency set alongside the originating request fingerprint. A full Session fingerprint changing because another target was activated is not, by itself, revocation of an already accepted call in a provably independent scope. Its next native check uses relevant source generations/reliability and host authority; pending calls still go through the new batch/request snapshot barrier. Shared globals or applicable ancestors defeat independence. This is internal evidence from the one source service, not a second resolver or new model acknowledgment channel.

Normal filesystem errors remain per-call soft failures and policy/user cancellation retain their existing stronger ownership. A coincident actual policy refusal remains a refusal; a replan does not disguise it. Replan-only paths must not call existing refusal/cancel helpers.

## Code Mode: host latch and unwind through existing owners

Code cannot be statically expanded into a whole future target batch. Each native invocation captures/preflights through the same registry seam. A newly discovered read target can return its read result without giving the running guest permission to mutate under the new instruction epoch. Conservative implementation may end the cell on discovering an unseen applicable rule; minimally it must latch before any subsequent mutation. It is the outer provider request that acknowledges rules, never guest code examining the read result.

Add replan state to the existing host cell/broker admission owner. Latch it synchronously on trusted replan evidence before rejecting an invocation or resolving a candidate mutation result. Invocation/run/pump each refuse further admission from that cell, including items already queued but not admitted, and the dispatch/native fence prevents a previously prepared item slipping through. Runtime worker-events recognizes the separate disposition and requests retirement's **replan unwind**, rather than forwarding an ordinary catchable rejection.

The unwind stops the worker/guest continuation, blocks guest store completion/commit and preserves retained output. It does not abort call controllers or broker `cell.stop` for accepted producers solely because of replan. Existing `close`, `complete`, policy `retireCell`, and closed-event registration need disposition-aware branching because all currently abort producers. Keep the original cell object and its tracked producer set until their result/finalization drains; queued never-started invocations get a single replan result. Accepted reads remain in `code/result`, admitted output and ordinary inspection paths. A guest catch, timer or later host call cannot clear the latch because host admission checks it independently of the promise result.

Outer `code_exec`/`code_wait` observations carry the recoverable code/fingerprint/reason and retained result references without `policyRefusal`. Do not turn successful candidate write into a fabricated failed native write: record its actual success, then terminate the old guest with an outer replan disposition. The outer response must not imply the original cell can be resumed or automatically resubmitted. Restart behavior already prohibits continuation restoration; extend that principle, keeping cell/invocation IDs and completed side-effect provenance. Owner stop/revoke/dispose can still cancel under their original semantics; replan is not a revocation.

## Precisely achievable invalidation contract

**Native owned writes:** before a successful instruction-candidate mutation is exposed as settled, synchronous invalidation must have dirtied all relevant consumers through the same I2/E7 source owner. Emit per actual target mutation, not only tool-finalize or the whole patch's `ok:true`: a partial patch can have changed an instruction source before later failure. Announce pending candidate I/O to avoid reusing a cache during that interval. On an attempted direct write that fails after truncation/partial bytes, invalidate conservatively on settlement as well; success-only hooks are insufficient for failed writes with effects. The invalidation callback must be a reliable host path; a failed observer/notification cannot report mutation success while leaving stale authority usable. It cannot roll back disk effects, so retain the result and mark source unavailable/replan.

**Observed source events:** relevant changed/reset/unavailable invalidates the preparation generation before any subsequent admission/mutation-boundary validation. A rebuild racing another invalidation repeats until its captured generation is stable, as approved spec line 95 requires. Membership revocation/close prevents new calls immediately and clears appropriate current sections; old fork history and restored checkpoints grant no permission. Each Session retains independent effective targets and request acknowledgment; the shared observation/cache never shares acknowledgment.

**External concurrent changes:** until an event is delivered, the host can possess a clean old fingerprint. External writes may occur after any check or during asynchronous I/O. No source-generation check or success callback proves a filesystem transaction, and no per-request snapshot proves the model interpreted every sentence. The accepted proof is that the relevant snapshot was actually attached to the originating provider request and the known source state was reliable at the native fence. Watcher recovery requires one reconcile and degraded diagnostics, not speculative every-step rescans. Shell only advertises host-known cwd (`F:packages/shell/src/tools/foreground.ts:77`, line 82 and 133); opaque command-internal paths/writes are outside static target/mutation reporting, with explicit `instructions_get` for advance activation. No parser is proposed.

The approved acceptance phrase at spec line 134 should be bounded explicitly to unseen targets/observed source changes before mutation admission. If the controller instead intends a stable old epoch for an entire already-authorized batch regardless of later observed changes, that avoids partial late replan but allows subsequent writes under superseded known rules. That is a different semantic ruling, costs more safety, and is not recommended. If it intends atomic consistency against arbitrary external writes, I5 scope/architecture must change; adding a generic lock in this work would neither lock uncooperative external writers nor satisfy the stated requirement.
