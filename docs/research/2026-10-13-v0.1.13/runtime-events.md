# IH v0.1.13 runtime event research

Read-only source audit, 2026-10-13, baseline HEAD `460a2aee` (v0.1.12). No tests, providers, user profiles, branches, or product source were changed. This note owns internal runtime/task/completion semantics; Desktop transport/panes and instruction discovery have separate research. The user's Google examples are conceptual only: external webhooks/email/automation infrastructure are outside scope.

## Executive findings

1. The core turn executor and v0.1.12 wait observers already use push. Do not rewrite them as if they still poll. Preserve observer-versus-producer separation and exact live-session authority.
2. Initial background child completion has a durable-shaped task/outbox path and an idle-parent admission/wake adapter. Team results/messages have a related mailbox path. Generic exec/workflow completion has no parent wake path; Code Mode has durable cell facts but no completion-triggered parent turn.
3. Generalizing current child notification code directly would carry forward real limitations: document writes swallow failures, the notification drain is not itself serialized, its `woken` marker precedes the void wake call, and its post-publication recovery connection appears incomplete for ordinary subagent notifications. These are read-code findings, not executed reproductions.
4. A small host-owned completion coordinator, durable completion identity/facts, idempotent admission, a serialized drain, and durable stop generations are sufficient. A global broker is unnecessary. Advisory process-local notifications should only cause rereading durable facts; they must never become the facts themselves.
5. Remaining timers include legitimate deadlines, batching, retry backoff, intentional step-boundary control flow, and some native state polling. A truthful event-driven release must name backend exceptions rather than claim every timer is removable.

## Durability, recovery, and dedupe hazards to address first

### Document acknowledgement is weaker than its Promise shape

`SessionCoordinator.putDocument` serializes a document write but catches failures, reports them, and resolves (`session-persistence/src/index.ts:680-684`). TaskRegistry `save()` awaits that method (`task-protocol.ts:172-176`). Therefore `await tasks.save()` is not a strict storage success barrier in the current composition. Document leases are opt-in (`session-persistence/src/index.ts:308-319,423-433`); a lease around a write is not a transaction across parent session log plus task document.

Session log writes have a stronger explicit flush: `SessionWriteBehind` retains failed batches, pauses automatic retry, and retries on future enqueue/flush (`session-persistence/src/write-behind.ts:42-63,126-147`). `coordinator.flush` propagates failure (`index.ts:659-662`). `createDurableSessionLoader` mirrors appends and flushes turn/end (`session-executor/src/durable-session.ts:23-30`). Prefer completion facts in the parent session log and an explicit flush; if task docs remain authoritative, add a **new proposed** strict document API that shares the existing doc chain and leases but propagates rejection. Do not silently change all legacy `putDocument` callers.

### Current notification drain needs serialization and an explicit acknowledgement model

`registerSubagent` calls `notifDrain.drain()` on every terminalization and tracks promises in a Set (`subagent/src/index.ts:213-217`), without a drain mutex. A drain checks a candidate then awaits `admit` (`task-notification.ts:73-86`); another drain can select the same row. Service content-hash admission dedupes the parent log, but the generic adapter contract does not ensure that, and attempts/wake scheduling can repeat. Replace with one per-owner drain promise plus dirty/rerun flag; a signal arriving while it runs must schedule another pass (not be dropped).

Current code writes `delivered`, then `woken`, then invokes `wake` (`task-notification.ts:91-94`). A void wake can refuse or schedule work; it cannot prove a turn ran. The new state machine should distinguish `pending`, `admitted`, `scheduled` (advisory), `consumed/promoted`, `suppressed`, and retryable error; only durable admission and promotion/cancellation markers determine delivery/consumption. The only exactly-once claim should be a single logical inputId per source completion; inference itself remains susceptible to crash after promotion and before completion and must not be silently replayed.

### Apparent ordinary-child post-publication recovery gap (read-code concern)

`assembly.ts:1375` awaits `subagent.ready`; its restore chain drains notifications (`subagent/index.ts:280-290`) before `service.ts:658` publishes the assembly. The default service adapter requires that published exact assembly (`service.ts:301-303`). After publication service explicitly calls `assembly.drainParentNotifications` (`:679`), but this assembly method currently drains only team `drainLeadMessages` (`assembly.ts:1609`). Ordinary child `notifDrain` is not exposed by RegisterSubagentResult. A restored task notification can therefore hit temporary unavailable and remain error until another trigger; an executed reproduction was not authorized. Phase 1 should include a cold-start fake-model/fixture regression and expose ordinary-child recovery drain after publication as well as team drain.

### Stop identity should survive restart and later human turns

Current `cancelledParents` is in-memory; it cancels already-admitted parent-notify inputs and aborts controllers (`service.ts:281-292`). A later non-system submission clears it (`:717`). A completion from earlier work arriving after that reset could be eligible unless its source was separately cancelled. A new source binding needs an owner generation captured at launch, plus a durable Stop/suppression fence for that generation. Stop invalidates old completion admissions before and after awaited persistence; a later user turn opens a new generation without reviving old results. Result/output remains readable. Close/dispose must revoke admission immediately and join owners, pending commits, callbacks, retry timers, and drain promises.

## Proposed architecture (new APIs below are proposals, not existing contracts)

### Phase R0: establish invariants and fault-injection seams

Keep the existing `SessionExecutor`, `Inbox`, `waitForObservation`, execution supervisor, tool guards, and host session-operation fence. Document three separate channels: (a) source state facts, (b) advisory invalidation for views/waiters, (c) explicit permission for a source completion to become a system input. Only (c) can wake inference. Output chunks/status refreshes must not create turns.

Add tests proving the current gap/constraints before broad changes: generic background job finishes idle without a turn today; cold ordinary-child notification after assembly publication; document write failure; concurrent drain; Stop racing flush and later human submit. These are implementation-phase tests, not tests run during this audit.

### Phase R1: repair completion persistence and admission once

**Proposed subsystem:** `packages/session-executor/src/completion/`, host-owned per root assembly/session, no dependency on Desktop transport, with one public `completion/index.ts` entry. Cohesive internals can be `lifecycle-store.ts`, `coordinator.ts`, `admission.ts`, `recovery.ts`, `types.ts`, and source adapters under `completion/sources/`; these are internal implementation files, not parallel public APIs. **Proposed durable event schema** in `packages/core-session/src/index.ts`: a versioned completion record with `completionId`, `ownerSessionId`, `ownerGeneration`, `sourceKind`, `sourceId`, `attemptId`, terminal outcome, bounded summary and output reference. Followup turn seq/attempt is part of the identity. Store lifecycle and wake eligibility explicitly; do not hash rendered prose as the authoritative ID.

Preferred design uses owning parent session log for `work/registered`, `work/settled`, `work/notification-suppressed` and generation fences (final names to settle in implementation plan). Derive a pending completion inbox from these facts plus `agent/input/admitted/promoted/cancelled`. A session-log append + explicit flush offers one existing durable barrier and simplifies rebuilding without a new database. The coordinator writes a single deterministic `completion:<id>` system admission after the source terminal fact is flushed; the parent admission must flush before scheduling. Crash between commits is repaired by folding source/admission records. If existing task docs remain authoritative during migration, **proposed** `SessionCoordinator.putDocumentStrict(key,data): Promise<void>` should propagate errors on the same existing document chain/lease. Compatibility is a migration tool, not a reason to keep a weak authoritative path: the user explicitly authorizes targeted structural correction where IH's current structure obstructs this goal.

The central change should be an **authoritative completion lifecycle refactor**, not another callback bridge over mutable in-memory status. Add a small common `WorkLifecycleStore` (proposed name, in session-executor or a narrow dependency-neutral package if source package layering requires it) with asynchronous `register`, terminal-CAS `settle`, `snapshot`, `subscribe`, and `flush` operations. Allocate a durable UUID/attempt identity before launching side effects; source-specific display IDs can remain aliases during migration. Put registration inside the existing guarded/admitted tool path, but before the actual source launch. After a crash, registration without trustworthy launch/terminal evidence is recovery-required, never automatic redispatch. Physical process/worker/child owners remain in their domain packages and report settlement evidence to this lifecycle authority. This avoids moving sandbox authority or process cancellation into a projection package.

The user explicitly prefers cohesive subsystem folders and one public entry over growing flat files. Split orchestration out of `service.ts`/`assembly.ts` into `session-executor/src/lifecycle/` and `session-executor/src/assembly/` as required for these ownership boundaries; keep façade exports while consumers migrate. `completion/` owns completion facts/delivery, `lifecycle/` owns assembly publication/close/generation fences and session-operation coordination, and `assembly/` owns composition. Avoid a circular dependency: low-level exec/workflow accept lifecycle callbacks/types through dependency injection, never import session-executor. `context/` and settings `schema/`, `store/`, `watch/` can be separate coherent work streams; completion work must not scatter their logic across this subsystem.

Migration should fold/import existing task documents once per owner under a versioned marker, map known legacy notification IDs to canonical completion IDs, and recognize old deterministic parent-notify admission/promoted/cancelled evidence before sending anything. Do not assume a legacy `woken` field means the parent consumed a result, and do not manufacture recoverable live exec/workflow continuations from old `bash-N`/`workflow-N` rows. Old foreground task delivery stays observe-only. Updating internal API shapes and existing consumers/tests is appropriate when it removes ambiguous authority; keeping two competing outboxes indefinitely is not.

**Proposed APIs:**

```ts
interface CompletionBinding {
  ownerSessionId: string;
  ownerGeneration: string;
  sourceKind: 'subagent' | 'team' | 'exec' | 'workflow' | 'code-cell';
  sourceId: string;
  attemptId: string;
  delivery: 'observe-only' | 'parent';
}
interface CompletionCoordinator {
  recordSettled(binding: CompletionBinding, result: SettledResult): Promise<void>;
  requestDrain(): void; // coalesced advisory signal; never a fact
  recover(): Promise<void>; // only after exact owner + lane publication
  stopGeneration(reason: string): Promise<void>;
  close(): Promise<void>; // admission fence first, then join
}
interface CompletionAdmission {
  admit(input: { inputId: string; sessionId: string; generation: string;
    text: string; description: string; display?: InputDisplay }): Promise<'admitted' | 'consumed' | 'suppressed'>;
  schedule(inputId: string): 'scheduled' | 'already-scheduled' | 'consumed' | 'suppressed';
}
```

`SettledResult` should carry terminal evidence and bounded output reference; not unbounded stdout or a mutable Job object. `schedule` acknowledges scheduling, not inference completion, and must call service `submit(...admittedInputId)`/lane `runAdmitted`. Durable admission is the recovery anchor. A lost process-local scheduled marker cannot lose a pending input; recovery scans eligible deterministic input IDs. A promoted input without terminal turn evidence becomes visible interrupted/recovery-required, never silently rerun.

Drain is one promise + dirty bit; signal-before-subscribe is covered by initial scan. On a retryable storage/admission failure retain the row and visible error/attempt count. Retry on owner publication, explicit drain/recovery, or a bounded error-specific backoff; no success-path interval scans. Persistence rejection must not result in marking delivered or launching inference. A stop/closed/stale-generation error permanently suppresses that completion, retains output, and is not retried. Retry the same notification identity, never relaunch the producer.

Use explicit producer callbacks for critical completion persistence rather than an unguarded generic Session subscriber. View listeners must be exception-isolated or a dedicated safe invalidation seam used; never globally swallow guard/hook errors because hooks are control flow. Avoid ambiguous dual authority between old task doc and new log: introduce an adapter/migration that maps an existing task notification to one canonical `completionId`, preserve old consumed evidence, and never both send the old drain and the new drain.

### Phase R2: integrate source owners incrementally

1. **Children and Team first:** extract the existing admission bridge, preserve `tool` versus `parent` delivery, expose ordinary-child post-publication recovery, serialize drains, then route Team Lead completion through the same admitted-input scheduling seam. Include per-turn identity for followups; a status toggle on a reused job ID cannot mint the same completion twice. Keep the team mailbox as its own domain queue, avoiding two parent notifications for one Team result.
2. **Exec:** add a source lifecycle callback or owner-scoped aggregate subscription at `registerJob`, where both registration and actual `capture.complete`/settlement exist. Register source before publishing its job ID, bind exact execution owner and launch identity. Persist no claim of terminal completion on `rootExited` or incomplete settlement. Add durable lifecycle facts and bounded retained-output reference; source adapters do not bypass `currentExecCaller`, policy/approval, supervisor, or sandbox transport. Explicitly distinguish background/promoted model jobs from human terminal/search/internal helper work so completion does not wake the wrong actor.
3. **Workflow:** add a joinable runner handle and lifecycle callbacks to `WorkflowRunHandle`/`WorkflowExecutor`. Keep `killed` presentation separate from `settled` cleanup confirmation. Make retry backoff abortable. Completion is emitted once only after the step owner has settled, including final output retention; its source identity is unique across process restarts. Ownerless Desktop/manual workflows remain observe-only; no inferred parent. Route each workflow once, not also each internal exec step.
4. **Code Mode:** outer cell completion can use the coordinator only after a design decision on delivery, because `code_wait` consumes output windows. Preserve inner `resultConsumer:code` ownership: do not emit separate exec/workflow parent inputs for nested calls the guest still owns. Initial conservative integration records durable facts and views; when enabling idle wake, deliver a bounded completion notice referencing `cell_id`, without consuming/replaying the cell's output window or committing incomplete store writes. Restart remains interrupted, never resumes guest code.

Adopt a deterministic eligibility rule, persisted at source registration: background model work may request `parent`; foreground work and internal nested tools remain `observe-only` unless their owner explicitly transfers completion delivery at a legitimate yield/promotion point. Preserve v0.1.12 foreground child behavior. This is product semantics, not something `subscribeJob` can infer from a late listener.

### Phase R3: convert genuine runtime state polling without semantic drift

For optional schedule `start()`, **proposed** `invalidate(sessionId)` plus nearest-target one-shot timer, current-log reread when it fires, startup catch-up and stop/disposal cleanup. Events created while delivery awaits set dirty for a followup pass; never copy current `if (ticking) return` into a push-only driver without dirty catch-up. Continue anchored recurring coalescing and session-prefix ownership (`schedule/index.ts`, assembly seedLength slice). Preserve session-local pre-step integration unless idle reminder inference is explicitly added as a separate scoped feature. Watch wall-clock adjustment/resume; a deadline timer must recheck wall time, and a platform resume/time-change signal or documented bounded correction timer may still be necessary.

Native process polls require their own transport work, not a JS event bus. PSEC/WSL already expose event/ack settlement; legacy Windows can migrate pipe drain to equivalent native async pipe ownership. POSIX complete-group exit notification needs a supervisor/reaper/process ownership mechanism with explicit coverage limits; child root exit is insufficient. If not safely implemented in v0.1.13, retain explicit backend exceptions and scope the claim to internal model/task/view state polling.

## Release wording and unresolved decisions

Recommended eventual claim: internal work state changes and eligible completion delivery are event-driven; owner settlement, durable admission, recovery, and Stop fences are explicit. Name remaining native/protocol polling exceptions and keep deadlines/backoff/batching.

Before implementation, settle the exact persisted completion schema, source eligibility at launch/promotion, Code Mode outer-cell notification policy, whether cancellation is a user-visible notification or suppressed, and whether v0.1.13 includes native transport migration. These are design decisions; none require external automation, subscriptions, Kafka, or a second turn lane. Preserve session-local schedule semantics unless the user explicitly asks to change them.
