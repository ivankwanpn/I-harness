2026-10-23. Read-only source/evidence analysis for root review. ## Finding that should drive the work

The user's experience—other agents continue successfully while IH fails—is the product acceptance problem. A stricter contract, a newer architecture or many unit tests does not answer it. The strongest existing evidence identifies **different failure mechanisms**, including a compacted request with invalid tool order and an autonomous tool chain whose recovery summarizer could not slice the available material. Neither requires a giant archive to be transmitted. The appropriate next proof is an uninterrupted, measured host-level continuation through repeated compactions, tool results and child completions, including recovery and cold resume.

OpenCode's useful contrast is operational simplicity: select a completed checkpoint plus subsequent messages; preserve calls/results in one assistant projection; try compaction before each model step; retain a recent tail; and, if necessary, shorten a textual summary input progressively. IH need not reproduce every reference policy to test whether one of these simpler mechanisms can remove an actual failure. Conversely, OpenCode source is not evidence that it never fails, and its background child input is not uniformly bounded. The user's observed difference should motivate comparable execution evidence, not be dismissed because a static review can find imperfections in the reference.

## 1. Exact archive → selection → projection → protocol → body traces

### IH012 ordinary primary request

The old fold's lifecycle prepass and main pass skip shadowed events before handling step boundaries (`:669–674,694–732`). This matters to correctness, not just size.
3. Agent admits step-boundary input, appends step/start, invokes optional auto compression, enforces its budget, runs pre-step hooks, then derives messages (`012 packages/core-agent/src/index.ts:375–407`). It adds current system/schema/effort/cap to `LLMRequest` (`:409–439`).

It correctly includes cache reads when semantics say input excludes cache (`:13–20`); claiming012 simply ignored all cache usage would be wrong.
5. Anthropic serialization then projects images, chooses required max_tokens, translates thinking, replays matching thinking/tool block order, adds tool schemas/cache markers and serializes the payload (`012 packages/llm-anthropic/src/index.ts:202–278`). **The actual HTTP body** is `JSON.stringify(payload)` at`:284–287`, downstream of the budget decision. Neutral history token count is not a measurement of this body.

Consequences: retained raw archive can be huge while selected messages are small; selected active reasoning/schema/media can also exceed what the old neutral estimate counted. Both statements can be true. The old report's437837neutral estimate and later760610last-success usage are different-time/different-boundary facts, not a precise error ratio for one identical request.

## 2. Compression misses and recovery stalls: what can actually happen

### Missing cost in a new suffix can defer the trigger

012`estimateMessage` counts assistant visible content and tool arguments but never reads thinkingBlocks/providerContinuation (`token-meter/src/estimate.ts:12–33`). The Anthropic serializer may include those thinking blocks (`llm-anthropic/src/index.ts:230–256`). An existing provider anchor covers previous accepted input; the new assistant reasoning being replayed for the first time is still in the estimated suffix (`token-meter/src/context.ts:45`). After cold restart, a process-local anchor is absent until another accepted response records it (`:31–39`). Repeated moderate CJK/tool/reasoning growth therefore has a concrete route to delayed compression compared with a meter that prices the actual replayed body.

This is a **plausible contributor** to the original no-compaction trajectory, not proof of its four400s. Actual historical auto flag/limits and failure bodies are missing. The source had auto and hard checks, so “IH never implemented compression” is false. The current projection-price changes address this mechanism, but the relevant acceptance is repeated real host requests with changing suffix and cold restart, not a single estimator test.

### Cooldown and “compacted” can suppress useful work

012auto pressure uses `contextTokens`, but its prune-only and post-success sticky decisions use activeTokens (`compaction/src/index.ts:155–166,316–383`). The old neutral formula can therefore declare a prune pass resolved even when the representation sent by the adapter still has substantial reasoning/system/schema cost. The later architecture audit documented a synthetic4283neutral versus64511prepared estimate and a prune-only success still above the same intended soft goal (`docs/research/2026-10-15-context-architecture-reassessment.md:84–96`). These are estimates/control outcomes, not provider token measurements, and that audit is an intermediate revision rather than exactly012.

012default cooldown is three completed human turns (`compaction/src/config.ts:127`; `index.ts:357–363`). A single autonomous turn can contain many completed tool rounds without three turn/end markers. Its hard `enforceBudget` bypasses that auto gate (`core-agent/src/index.ts:272–294`), so the likely failure mode is delayed hard recovery, expensive summary, reset or failure—not necessarily an oversized main send. Per-result limits do not prevent such cumulative growth.

7706changes the default cooldown to accepted exchanges (`compaction/src/config.ts:158–178`; `core-agent/src/agent/context-reduction/automatic.ts:14–37`) and assesses baseline/candidate with the prepared path. This is an actual behavior change in current code. It deserves a continued autonomous-turn acceptance case because explicit human-turn overrides still exist, and failure/no-progress states remain legitimate branches.

### Proven summary-slicing stall and the remaining single-group edge

The documented uninterrupted12-read loop stalled after proactive compaction: main96383and summary97444estimated tokens; fixed system/schema about11.6k; each closed tool round about21.1k. The slicer allowed interior user-message cuts only and classified otherwise separable completed work as indivisible. Repair commit **`a8caab1f`**, `fix(compaction): split balanced autonomous tool rounds for summaries`, is present in local history. The historical host proof is described in `2026-10-15-long-session-reliability-verification.md:13–21`. The accepted tree retains the actual Gateway fixture at`packages/desktop-gateway/test/long-growth-host.test.ts:28–102`:12shipped reads, real Chat loopback,100k/150k windows, autonomous mode and exact dispatch sequence.

The current implementation has since changed: `7706 packages/compaction/src/summary/generate.ts:11–14,39–52` partitions **whole ReductionGroups** on prepared over-capacity or confirmed summary overflow; fewer than two groups throws `fixed-input`. It caps calls at8and checks complete checkpoint/coverage (`:23–24,57–66`). This is better targeted than user-only slicing, but **a single oversized source group is still a concrete blocking path**. Whether ordinary current tools can create one depends on actual bounded-result projection, grouping, images/native content and fixed schemas. That is a precise missing replay to run, not a declaration that the current code is broken for every long session.

OpenCode's fallback can shorten an individual newest exchange rather than insisting it be split: it clips/removes tool outputs, moves toward user-only text, omits old exchanges last, and refuses to omit the newest exchange (`OC compaction.ts:648–727`). It omits reasoning/media/instruction updates in that flattened summary request. This is a genuine availability tradeoff and a candidate replacement for IH's **single-group summary-input refusal path**, if a controlled case shows a useful bounded representation exists. Adopting it requires an explicit decision about retained source coverage, what may be shortened and how the user can recover original results. It must not be smuggled in as “same semantics,” or applied to live/unresolved tools. If policy requires complete opaque content and no portable representation exists, honest blocking remains necessary—but that is a supported limitation, not a successful long-session outcome.

## 3. A small compacted request can fail: the proven ordering400

The later incident is causally stronger than the original generic400s. Summary hid the current step/start after the step had started but before the next model response. Old projection skipped that marker and separated one assistant response into an assistant with tool_use, another assistant with text/thinking, then user tool_result. The actual controlled endpoint rejected nonadjacent tool results. The repaired projection produced assistant(thinking+tool_use) immediately followed by user(tool_result), and the matched synthetic control went200→old400→new200. Reported post-compaction bodies were roughly45–47kbytes with13–18kinput estimates; that failure was not demonstrated context overflow (`2026-10-15-compacted-tool-http400-repair.md:5–15`). No live request was made in this follow-up.

Repair source **`1f2dfa7d9c8f6803560d74fc151e6e90f26c5958`** is an ancestor of7706(`git merge-base --is-ancestor`, exit0). At7706the actual `deriveMessages → projectConversation` path uses `historyVisibility.lifecycle`, preserving shadowed step/start, step/end, step/failed and turn/start, while rewind still excludes them (`conversation/history/visibility.ts:4–19`; `history/group.ts:83,129`). This is a concrete implemented repair surviving the refactor. It should not be re-reported as an open defect merely because R4B is incomplete.

OpenCode's session assistant projection keeps text/reasoning/tool calls within one assistant message, and emits its completed local results afterward (`OC runner/to-llm-message.ts:155–219`). Its checkpoint-boundary model reduces reliance on reconstructing one active step from arbitrarily shadowed markers. A simpler replacement worth considering is **a single authoritative completed-exchange projection** feeding both main and summary requests. IH's current shared semantic history moves in that direction already. What remains necessary is a repeated main→summary→main actual-adapter sequence, including parallel tools, compaction during an open step, and cold reopen; a lawfully shaped isolated fixture is not enough.

Do not “solve” this by copying OpenCode's synthetic `Tool result missing` error insertion (`OC ai/tool-history.ts:6–61`). That can make a wire transcript sendable without reconstructing the true source exchange. The observed IH defect was repaired by correct grouping, not by manufacturing a missing result.

## 4. Tool and child ingress: where repeated content enters the selected request

### Ordinary tools

012already has a64,000-byte model-visible text spill guard (`output-retention/src/spill-guard.ts:21–59`). It preserves media separately; it is not a total packet bound. The documented give-up branch retains original output if the configured cap cannot even hold its replacement. Its retained files default to24h/512MiB GC. Many6k-character pages can each stay below prune/spill thresholds while the **sum** grows indefinitely without effective compaction. The historical12-read control intentionally exercises that mechanism. “All tool results are unbounded” would miss both the existing protection and its actual limit.

7706shipping result capture stores complete values through `session-executor/src/lifecycle/result-retention.ts:29` and dependency capture, while model/history receive bounded representations. This closes a concrete ingress problem for those configured current producers. It does not prove every later read/page, old inline result, media bundle, Code Mode output, or simultaneous result batch yields a request that fits. End-to-end replay should measure each distinct representation and prove retrieving original bytes after multiple checkpoints.

OpenCode's runner-level text cap occurs immediately after direct execution before tool result publication (`OC runner/step.ts:122–128`), offering a simple central control point. It still trusts producer `metadata.truncated`, passes files through and does not bound aggregate history (`tool-output.ts:69–119`). Its useful replacement idea is **one actual outer result-ingress cap with a retrievable original**, not its exact50KiB number. IH's present result capture already serves this purpose; the question is whether every shipping ingress actually reaches it.

### Background child completion

012terminalization stores full `resultText`, then notification copies it directly (`subagent/src/task-protocol.ts:179–209`). The notification renderer places this text in a task-result message, and the sink admits it as parent input (`task-notification.ts:36–44,87–89`). Direct tool output spill does not automatically cap that independent input path. This is a source-confirmed amplification mechanism: child output can be retained in task/job state and admitted again into the parent's selected messages. It does not establish how much child output was present in the historical incident.

7706`TaskResultOwner.capture` replaces ordinary task fields with a small JSON-byte-checked preview while retaining the full result separately (`subagent/src/task/result.ts:25–38,59–77`). `TaskNotifications.enqueue` copies that ordinary task field (`task/notifications.ts:27–34`). Shipping assembly passes `SHIPPING_REPORT_POLICY` (`session-executor/src/assembly.ts:1238,1432`), whose report limits are2048child preview/16384aggregate page (`subagent/src/report-policy.ts:6–7`). Current child result capture/publication and task retention code are connected, and R4A acceptance records its qualified consumer scope. The report policy by itself is not proof of all background inbox traffic; the actual capture-before-notification route is the relevant mechanism.

OpenCode also copies raw child completion text into synthetic input, outside its direct-tool cap (`OC session/subagent-completion.ts:21–45`; `session/session.ts:283–321`). Thus OpenCode's observed reliability cannot be explained by claiming it universally bounds background fan-in better. A controlled burst of completed children should compare **number of admitted notices × actual encoded preview bytes + schema/system/current task**, with exactly-once logical consumption and no repeated body materialization. IH's R4C durable delivery identity/receiver/epoch-aware wake remains unfinished according to `2026-10-21-context-r4a-acceptance.md`, so result retention acceptance alone does not close that continuation guarantee.

### Full-history child inheritance

Both012and7706default none. Explicit all/N in7706still calls`forkTurns(opts.parentSession.events,...)` (`subagent/src/child.ts:27–29`) and opens/imports raw seed events (`child/document.ts:8–17`). Accepted semantic export APIs are not used by this actual caller yet. An earlier controlled132018505-byte archive projected to two messages and467HTTPbody bytes (`2026-10-15-context-architecture-reassessment.md:49`). Copying that raw archive is a credible memory, serialization, persistence and startup cost; it is **not proof that its body is sent to the child**. Child projection can still honor copied compaction markers.

The simpler reference choice is ordinary child fresh context plus an explicit task packet (`OC tool/plugin/subagent.ts:184–213`). IH already has that default. For requested full inheritance, substitute a compiled current selected seed only when caller/host transfer work connects, and measure actual first-child body separately from archive-copy volume. Active host planTasks1–3build transfer/pre-ready capabilities; originalTask4still must change this caller. Claiming the raw-fork performance/reliability issue is already closed would be incorrect.

## 5. “Session dies”: distinguish failed drain, hidden provider error and teardown

012`SessionService` catches a lane error, emits`session/error`, and rejects the submission (`session-executor/src/service.ts:811–836`). The inspected error handler does not call assembly.dispose. A repeatedly rejected input can still make the chat unusable from the user's perspective; lack of automatic runtime destruction does not negate that failure. Historical logs lack runtime-close facts, and the separate reported gateway-job stall has no unique reproduced cause in the reviewed documents. Do not equate a400with process death, or with harmless error reporting.

There is also a concrete **current pending** issue independent of HTTP400: the R5 probe showed a valid Chat top-level `{error:{...}}` frame followed by DONE/EOF producing ordinary end, including after partial text/tool-call data (`2026-10-18-context-engine-r5-chat-error-evidence.md:5–22`, frozen probe source`fbd74bc6`). At7706`llm-openai-compatible/src/stream/fold.ts:59–73` still reads choices/finish_reason with no top-level error check; `stream/decode.ts:61–71` can finish normally. This can turn provider failure into apparent completion or suppress expected recovery. It is confirmed at the adapter boundary; whether a particular Agent accepts/executes partial tools requires the prescribed connected no-effect control. It is not a diagnosis of the original400s.

OpenCode reads protocol terminal/failure events separately and the step owner does not turn an observed provider error into ordinary success (`OC core/session/runner/step.ts:105–121,155–198`). This is a simpler mechanism to adopt locally at IH's **actual Chat protocol terminal owner**, with known error-carrier classification and residual-frame handling. It does not require a new ContextEngine architecture. R5already owns it; do not expand active transfer worker assignments silently.

OpenCode's job completion uses Deferred waiting and a coalesced session wake (`OC core/job.ts:300–307`; `session/run-coordinator.ts:69–170`). IH012already has listener-based jobs (`subagent/src/jobs.ts:47–61`) and notification admission, so “replace all polling” is not a causal diagnosis. The useful acceptance is completion arriving during parent wait/Stop/restart and producing one later consumed notice with no duplicated child effect. The current plan's remaining delivery work should be judged by that outcome.

## 7. Comparable end-to-end replay acceptance proposal

**Proposal only; nothing below was executed.** Reuse the existing real Gateway long-growth fixture and actual built CLI/SDK loopback patterns, rather than add another isolated estimator suite. Use immutable snapshots, isolated synthetic workspace/config/artifact roots, built-in adapters and an explicit loopback transport. No real keys, provider services or private conversation replay. The fixtures should run both the accepted baseline and the eventual integrated candidate; where practical drive the same semantic workload through the reference's own public entry. A reference run that is unavailable must be labeled unavailable, never replaced by a hand-written imitation and called equivalent.

For **every physical attempt**, collect: route/protocol, main/summary/auxiliary kind, logical action/attempt index, actual decoded HTTPJSON bytes/hash (and compressed bytes separately if applicable), messages/groups/calls/results count, selected versus archive count/bytes, system/schema/replayed-reasoning/media bytes, local estimate plus provenance, declared fixture limits, requested/effective output control, compaction source range/checkpoint ID/publication state, rejection classification, tool dispatch IDs/counts and parent notification identity/consumption. Bedrock SDK commands must be labeled command estimates rather than measured HTTP bytes. Loopback-provided usage is fixture evidence, not a live tokenizer truth. Keep one independent bytes/call-pairing oracle at the receiver.
