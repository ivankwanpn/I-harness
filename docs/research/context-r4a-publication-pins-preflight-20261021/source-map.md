## Future integrity observation — source risk only, outside this publication/F1 unit

`context-output/src/artifact/ownership.ts:168` currently implements host-internal `reconcileResult(operationId,id)` by deriving the managed directory, reading `operation.json` through boundedJson, checking supplied operationId against the record, and calling `reconcileArtifact`. It does not first call ownedPath for that operation file. `artifact/recovery.ts:32` returns a committed record's ref without performing the original validateManifest/validManagedArtifactRef checks there. By contrast `readResult` uses authorized→ownedPath/closed ref/committed identity/pin/source and then rooted manifest/index/body proofs, with a post-read authorization check.

This is an unqualified source-level integrity risk, NOT a confirmed defect, exploit, permission bypass, or finding against the active physical-crash unit. The operation lookup is a trusted host lifecycle port; public reader callers do not thereby gain mutation/source authority, and a returned storage descriptor does not certify F1 or task publication. Future integrity qualification should exercise corrupt/foreign/link-substituted operation metadata at this original host-internal lookup seam, then distinguish (a) bounded lookup disposition/ref evidence, (b) independently successful authorized bounded body read, and (c) actual F1 proof. Test before claiming cold lookup repaired or validated an artifact. Do not add a second validator/store or infer arbitrary external access from the source omission alone.
