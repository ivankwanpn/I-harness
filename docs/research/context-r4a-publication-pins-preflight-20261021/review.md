## Findings

### [P2] Assert the saved task baseline; flush does not establish successful persistence

**Plan locations:** `following-publication-plan.md:35` and `:93`.

The plan requires the initial `flushPersistence()` but then permits saved task documents to be absent at the cold assertion. That can hide a failed fixture setup. `TaskPersistence.save()` stores `next.catch(() => {})` as its chain (`packages/subagent/src/task/persistence.ts:23`), and `flush()` waits that caught chain (`:26`). The initial `submit`/`claim` saves are also deliberately fire-and-forget with caught rejection (`packages/subagent/src/task/registry.ts:178`, `:203`). Therefore a resolved flush alone is not evidence that the auxiliary document exists or contains the claimed running task.

The exact cold task state is also narrower than the plan currently spells out. After successful initial submit/claim persistence, this fixture's durable task row is `running`, without a result/outcome. At each of the ten selected cuts, terminalization has occurred in memory, but the original `retainResult` has not returned from result settlement and has not reached its terminal `save()` (`registry.ts:75`, `:92`). `announceTerminal` does not independently save a strict report-policy terminal snapshot (`:109`). Thus these ordinary crash cases preserve the earlier running document. They do not exercise cold restoration of a saved terminal/pending or retained result row: `unqualifyRestoredTask` returns immediately for that baseline (`packages/subagent/src/task/publication.ts:18`). Existing terminal-restore qualification remains separate evidence.

**Smallest correction:** Immediately after the initial flush, read the actual `coordinator.getDocument(taskDocKey(parent))`; require the real format-2 document and selected task's running identity, absence of terminal outcome/result, and independently record its bytes or bounded snapshot. Treat absence/mismatch as setup failure. At all ten cold cuts require that original baseline still exists and remains unchanged, restore it through the actual TaskRegistry, optionally run the original `qualifyRestoredResults`, and assert it gains no successful terminal publication or result from artifact metadata. Keep the broader rule about genuinely absent/incomplete documents as a conservative product rule, but do not allow absence to pass this fixture. Do not manufacture a terminal snapshot to reach a different cold branch. Report the original child's terminal outcome separately from the fresh registry's saved running observation.

### [P2] Specify a genuinely fresh store and distinguish durable source refusal from missing-artifact refusal after deletion

**Plan locations:** `following-publication-plan.md:91` and `:108`; also the coupled deletion paragraph at `:102`.

The physical matrix naturally crosses a process boundary. The coupled deletion fixture, however, is a live fixture and the plan does not explicitly say how its later “fresh read” obtains a new store instance. Creating a second coordinator and calling `acquireResultReadStore` while the original producer lease remains registered reuses the module-level `stores` entry keyed by canonical storage/workspace identity (`packages/session-executor/src/lifecycle/result-store.ts:14`, `:30`). That entry is retired only when its final user releases (`:110`–`:113`). A nominally fresh read lease can consequently deny through the old service's process-local `deletedDocuments` fence (`packages/context-output/src/artifact/ownership.ts:84`) and pass without proving the restart boundary.

Even a genuinely fresh `readResult` will not necessarily consult source/profile policy after this deletion: original parent deletion targets both pins and can remove the committed directory. `authorized` checks the operation path and record before `readPin`/`authorizeResult` (`ownership.ts:88`–`:94`). An ENOENT or missing-pin denial is correct, but it is not evidence that a durable deleted parent was rejected by source policy. The source map already identifies the appropriate separate deletion-receipt/profile check; the dispatch plan should make that distinction executable.

**Smallest correction:** After recording the live deletion and same-capture retry assertions, permanently close the component and release all original store leases, then create the read fixture; or use a separately owned fresh process. Require a distinct service instance in the same-process option. Cleanup/release must occur after the measured assertions and must not be credited as deletion/recovery. In the fresh fixture, independently check the actual `deletionReceipt(parent)` and actual `coordinator.profile(parent)` or the fresh lease's original `sourceFor(parent)` refusal, without recreating the session. Separately attempt the actual bounded artifact read when a candidate/original ref is available and record its real missing/deleted/unauthorized disposition. Do not require it to reach `authorizeResult` when storage already correctly refuses earlier.

Also name the required reader predicate: `acquireResultReadStore({... , readCallerAvailable: () => freshReadOpen})`, with that read component's own monotonic lifetime and the existing source/profile policy. Do not reuse the old producer's `current`/`ownerOf(parent)` predicate or acquire write ownership merely to make a reader available. A cold reader's profile call is read-only and does not acquire the producer lease (`packages/session-persistence/src/coordinator/types.ts:125`). These are read authority facts, not reconstructed execution permission.

## Source-grounded checks that do not require plan expansion

**Actual composition and retained work.** `acquireAssemblyResultStore` is an internal shipping composition leaf that supplies service, source resolver and original coordinator deletion observer. It is sufficient for this storage-owner component fixture. `prepareResult(task.id, undefined, current)` binds the original source through the existing `forSource` adapter. The transparent capture observer must preserve this prepared-store binding; observing only the unbound base adapter's capture could miss the actual call. TaskResultOwner mints the task revision once (`packages/subagent/src/task/result.ts:60`), and the retention adapter uses it as operationId. That revision and `ManagedArtifactRef.revision` are different identities: the latter hashes manifest bytes (`packages/context-output/src/artifact/manifest.ts:12`). Preserve each across retries rather than requiring them equal.

`terminalize` already calls retention, and the capture adapters coalesce concurrent `settle()` requests. An explicit concurrent retain must join the original pending attempt; a later explicit retry after recovery-required resumes that same handle. Joining `flushPersistence` never drains retained captures and must not be used as a surrogate retention attempt. Terminal notification/onTerminalized behavior in the plan is correct: the registry can notify on retention failure as well as success, so notification count is not an F1 or ready-artifact oracle. The original input getter reads occur in `settleTaskRecord`; they are not getter calls on its newly constructed plain body.

**The ten native cuts and cold phase map.** The selected operations exist in the stated order. Body and leaves sync precede index construction; index sync precedes digest finalization/staged operation save; staged operation save precedes manifest, first pin/access and committed operation publication. Original owner confirmation then publishes the second pin and overwrites the same access pointer. The expected disk phases are capturing for the first three cuts, staged for staged-save through first-access, and committed for committed-operation through second-access. After a successful rename whose acknowledgement is withheld, classify the new destination bytes rather than the old in-memory phase.

After-success live throws are uncertainty controls, not actual failed native syscalls. Physical gates must park before returning the original successful syscall promise so no later step progresses. IPC needs the original operation/task identities, selected destination, actual bounded transaction payload, native success, and absence of later transitions. The plan correctly requires positive native-interception qualification and original handle/path tracking; an unqualified ESM spy is a fixture failure. `atomicJson` first recognizes already matching destination bytes and syncs them (`packages/context-output/src/artifact/io.ts:43`), so live retry need not perform another rename or leave a `.pending` file. Do not demand a second rename as proof of reconciliation.

Body/leaves/index retries can repeat sync/build activity from original leaves. At staged-save uncertainty the digest has already finalized and in-memory phase is staged, so retry must preserve original manifest/ref and avoid a second digest finalization. These distinctions agree with the source. The two pins remain `state: "pending"`; no committed-pin transition exists to assert.

**Live and cold authority.** `reconcileResult`/`reconcileArtifact` inspect the existing record. Capturing/staged remain recovery-required, and committed can return its original ref. They cannot reconstruct the old scope/encoder or missing pins. A candidate staged ref can be retained as test evidence without becoming a usable read capability. Committed first-pin/access state can authorize a bounded native read before second-pin confirmation. The second-access cut can already have both pins and the final access target while task retention is still awaiting its lost acknowledgement. Neither state proves parent F1. The plan correctly keeps them separate.

For committed cold cases, read the complete literal JSON body by advancing original bounded pages if claiming a full-byte/digest check; a single successful page is only a bounded-read check. Keep capturing/staged inventories intact and refuse to use another producer registration, `prepareResult`, `beginResult`, owner confirmation or source reconstruction to make them readable. The known source-level lookup/path/ref-validation observation remains a future integrity question. Nothing in these trusted, uncorrupted fixture records requires using it as a publication-plan blocker.

**Direct deletion.** `deleteOwnedSession` closes admissions, joins existing document/write-behind work, enters the parent operation lane, deletes through the real backend and awaits subscribers. It does not drain ManagedDocument sources; Gateway's earlier `closeSession` drain is a different lifecycle. The plan is correct to avoid an artificial managed source and to perform direct deletion outside artifact/session-operation callbacks after uncertainty releases the queue. Manifest `{documents:[taskDocKey(parent)]}` is accepted; the listener forwards both parent and auxiliary identities, so it tests releasing both original pins, not individually deleting an auxiliary session.

At first-pin/access uncertainty, the staged directory may remain protected after the listener removes pins. A retained live publication can first resolve its already-issued metadata action, then meet the original deletion fence and refuse; do not impose zero transient metadata writes. At second-pin/access uncertainty the operation is committed and the last released pin can remove its directory; the same capture's confirmation then fails without reconstructing it. Missing storage on retry is legitimate. Do not require a successful strict task save after its auxiliary tombstone. Refused operation metadata can retain an old candidate `ref` field; assertions should prohibit a newly usable/ready committed reference, not demand all serialized candidate-ref fields vanish.

**Real quota.** The two targeted quota controls are feasible under the original accounting owner. Open reserves 196608; each admitted body write reserves bytes plus 131104; commit while capturing reserves independently computed index bytes plus 196608; second owner confirmation reserves 262144. A fixed body/quota can distinguish successful writes from commit reserve refusal, and the existing approximately 1.85 MB/2 MiB control supports second-pin refusal after commitment. The TaskRegistry body's JSON syntax and both fixed fields must be included independently. Obtain the real boundary and error through a transparent observer or equivalent actual native transition/inventory evidence; do not replace `requireSpace` with a fixture-made error.

Commit refusal settles ready/unavailable quota with observed bytes; second-pin refusal preserves first-pin committed body but caches an unavailable task result and deactivates the original capture (`packages/session-executor/src/lifecycle/task-result-retention.ts:40`). TaskRegistry may remove that settled capture from its pending map, so the known-refusal retry assertion should use `tasks.retainResult(task.id)` and inspect the existing unavailable descriptor rather than claim the registry still contains a pending capture. Protected artifact readability is separate from task result availability and operational outcome.

**Cleanup and claims.** Restore live native modifications in finally, retain and kill only the launched ChildProcess, await close before fresh-owner access, and keep graceful close/drain outside crash evidence. On this component fixture, final lease release closes/suspends storage handles; it must not be counted as a successful crash reconciliation. Record original process disposition and all setup failures. Source/type gates should include every new `.mts` explicitly. The planned sequential focused tests and relevant original controls are appropriate; existing passing behavior is qualification and does not need manufactured RED. No entire-A5/A6, power-loss, packaged-runtime or spawned-child/F1 qualification follows from this unit.
