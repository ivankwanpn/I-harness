# SDK approval preflight — source-only recommendation

Date: 2026-10-21. Bounded design review for root approval before A6 product edits. This preflight ran no tests, runtime, builds, profiles, package flows, or Git mutations. Only this requested note is written. Existing evidence is immutable.

## Recommendation

Add **SDK-process-only `--yes`** to `i-harness sdk`, routing the explicit boolean into the existing `createSessionService({ approveAll })` option in `apps/cli/src/index.ts:662`. Keep the existing absent/false behavior, do not forward persisted `settings.approvalMode`, and do not change `executionServiceOptionsFor`, the approval classifier, SDK wire protocol, or ACP. Update CLI usage and the SDK host contract. An actual producer test must launch the SDK with this flag explicitly; canonical Desktop `approvalMode: "full-access"` alone must remain insufficient.

Use **`--yes`, without `-y`** for this bounded fix. `run` already recognizes `--yes` (`index.ts:231,272,465`) and sends it to `runHeadless` as `approveAll`. It does **not** recognize `-y`: the run flag whitelist rejects it. Adding an alias is unnecessary new syntax and should not be described as pre-existing support. If root expressly wants an SDK-only alias it needs its own help/parser coverage, but it is not needed to repair the producer gate.

Prefer `--yes` over `--approval-mode`. The former reuses an existing intentional CLI operator opt-in and an existing assembly capability. The latter imports four Desktop policy modes, including live guardian semantics and the dangerous-mode routine-tool exception, into a host with no interactive approval channel or guardian wiring; that is a wider policy-design task. `--yes` here means process-lifetime auto-consent to approval asks, **not** a change of classifier mode or sandbox selection.

## Source contract and alternative routes checked

- `apps/cli/src/index.ts:640–886`: `runSdkCommand` builds the real session service but installs neither `approveAll` nor an `onAssembly` approval bridge. The command presently reads only `--session-dir` and ignores other arguments. Usage at line 77 advertises only that option. There is no currently supported SDK approval flag to turn on.
- `apps/cli/src/provider-runtime.ts:17–37`: shared SDK/ACP settings projection includes sandbox, Windows backend, WSL, web and context-output configuration; it deliberately does not include `approvalMode` or `approveAll`. Leave this shared function alone.
- `packages/settings/src/schema/types.ts:281–282`: `approvalMode` is documented as **Desktop tool approvals**. Defaults set it to `dangerous` (`schema/defaults.ts:23`). The root-reported persisted `full-access` setting is not an SDK approval authorization contract.
- `packages/session-executor/src/service.ts:116`: `SessionServiceOptions extends AssemblyOptions`; no new service option or dependency is needed. `assembly.ts:178–179,889,917–922` separates optional classifier mode from answerer registration. `approveAll: true` registers the existing normalized approving answerer; absent/false registers none.
- `packages/guard-approval/src/index.ts:158–164`: omitted mode preserves historical classification. Explicit `dangerous` additionally allows `ROUTINE_TOOLS`, including spawn and messaging operations. Wiring normalized settings by default would therefore silently change existing authority even when the saved/default mode looks conservative.
- `packages/core-tools/src/approval/identity.ts:15–40`: unanswered asks throw `approval required but no answerer registered (fail closed): ...`; a negative answer throws `denied by user`. The root label `approval-required-no-answerer` is an evidence classification, not the exact literal runtime message.
- `packages/sdk/src/protocol.ts` and `server.ts:799–866`: SDK exposes prompt/status/history and the other advertised methods, but no approval request/answer RPC. `HarnessClient.spawn` already accepts explicit process `args` (`client.ts:153–154`), so callers can opt in without a new SDK API, capability, or protocol version. Embedded hosts can already supply their own configured session service; that does not repair a real CLI subprocess.
- `docs/contracts.md:181,186`: ACP `autoApprove`/`--no-auto-approve` controls v0 prompt admission. `index.ts:892–931` builds a separate service and passes `autoApprove` only to `createAcpServer`. Do not route SDK consent into ACP or change its permission behavior. Update the outdated contract sentence that says both commands use only `--session-dir` to explain the SDK-only flag and preserve ACP's existing option.
- Existing real subprocess patterns are in `apps/cli/test/sdk-wire-v11.test.ts` and `packages/sdk/test/e2e.test.ts`: canonical loopback provider configuration plus an actual CLI child driven by the public SDK client. Their current text-only turns do not prove approval-required producers execute.

No existing CLI-supported host control provides the required opt-in today. Directly constructing a different in-process service would evade the real CLI producer boundary rather than fix it. A full approval RPC bridge would be a new capability with substantially more protocol and lifecycle work.

## Authority, defaults and compatibility boundary

1. No flag: byte-for-byte wire shapes/capabilities and existing fail-closed asks remain. Persisted Desktop settings (including full-access) must not install an SDK answerer. Omitted classifier mode remains omitted; do not normalize it to dangerous.
2. Explicit `sdk --yes`: only that SDK process's assemblies receive `approveAll: true`, including sessions created or resumed during that process. It is broad consent to existing asks, including dangerous tool asks; help and documentation must say this plainly. It does not persist to settings, metadata, resumed sessions in another process, or ACP.
3. Deny decisions and monotonic execution guards remain authoritative. `core-tools/src/registry/prepare.ts:69–77` checks guards and deny before consulting approval; `registry/dispatch.ts:9–25` revalidates authority/binding/guards at dispatch. The flag must not turn denies into asks or skip this path. Role registries remain restricted to declared tools (`subagent/src/child/role-tools.ts:24–42` and `child/assembly.ts:21–25`); an answerer does not add a missing role tool.
4. **Sandbox qualification must be precise.** Ordinary calls still receive the saved sandbox; the flag must not set `danger-full-access`. However, the same answerer also feeds `createApprovalEscalationApprover` (`assembly.ts:717–732`, `sandbox/src/call-policy.ts:73–110`). Therefore `--yes` **does approve well-formed explicit per-call escalation requests**, matching existing headless approveAll behavior. The grant is transient, not a standing sandbox change (`call-policy.ts:123–220`). Do not claim the flag can never widen a call's sandbox or introduce a second answerer to suppress this established behavior.
5. Structured user questions retain their existing missing-provider behavior. Approval consent is not a fabricated answer to `ask_user_input`.
6. Parse an actual standalone `--yes` option. Do not accidentally treat a consumed `--session-dir` value as consent. Validate missing flag values before installing the service. Avoid widening unrelated parser or ACP behavior as part of this patch.

Suggested help/contract language: `sdk [--session-dir DIR] [--yes]`; “`--yes` automatically approves tool approval requests for this SDK server process, including valid explicit per-call sandbox escalation requests. Without it, requests requiring approval fail closed because this stdio host has no interactive approval channel. The configured sandbox still applies to ordinary calls.”
