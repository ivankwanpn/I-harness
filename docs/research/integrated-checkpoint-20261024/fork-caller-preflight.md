## Promotion decisions / concrete edits

### 1. Freeze the complete retained request, not an invocation with an unrecoverable intent

The draft freezes wire `{sessionId,invocation,atSeq?}`, while its host adapter requires `requestIntent`. `bootstrap-project.ts:5–24` requires the latter, validates it against the invocation and rejects unmanaged mode at Gateway. `coordinator/bootstrap-intent.ts:36–48` hashes requestCore and project intent; a digest cannot recover either. `BootstrapRequest` itself (`bootstrap-types.ts:11`) has no requestIntent field, and the retained header stage (`bootstrap-header.ts:95–107`) does not retain this host intent. Thus a cold passive Gateway retry cannot reconstruct the original project from the invocation alone without reading changed source state. Merely checking that a caller-supplied requestCoreDigest hashes to requestDigest also does not verify that it describes the actual source/atSeq/overrides.

Minimal correction: freeze one closed fork request-core definition and a retained original request object at SDK/Desktop, including source ID, completed selection/atSeq, explicit creation overrides versus inheritance policy, and the original project intent. Specify its closed wire representation wherever Gateway needs it; validate the actual core against `requestCoreDigest`, then validate intent against invocation. SDK/CLI use unmanaged; Gateway captures actual project/unassigned intent before minting/sending the first mutating fork RPC, and broker validates it for new work. Renderer must not use a stale selected-project UI label as authority. No new durable registry or header format is necessary; callers retain their original request and cold resume with insufficient original data honestly blocks.

Concrete smallest viable capture seam: a **read-only first-operation preparation result** from the existing main/Gateway host, carrying the closed original requestCore (including resolved creation defaults or their exact frozen policy), original project intent, and digest produced by the existing `createBootstrapRequestIntent` owner. The renderer then locally fixes operationId/target/time before the first **mutating fork RPC**, retains both prepared data and invocation, and never calls preparation again for that operation. Root must freeze the existing qualified target derivation alongside this seam; preparation does not issue a target, header, seed, input or artifact grant and is not a second transaction owner. New-work authority/currentness is revalidated when mutation begins. Do not import persistence/node:crypto/bootstrapHash into the browser renderer, or reproduce canonical JSON/hash code there. `desktop/session/project/state` alone supplies only a project label, not full core/default metadata or the digest; dashboard/selected-project state is likewise insufficient. The narrow read-only preparation route/forwarding and a client that reuses its explicit original prepared request belong in F1's file/test scope. SDK can use the same owner-backed preparation concept for unmanaged requests if it otherwise lacks a legitimate shared digest owner, rather than introduce another hashing implementation.

Inherited title/workspace/model defaults are resolved once from the original source and retained in the original BootstrapRequest/stage. On passive resume, use original stage/receipts; do not re-profile to recompute defaults or silently accept changed explicit overrides. Define whether changed explicit parameters are rejected before resume (recommended), instead of relying on coordinator to compare a request which passive caller never supplies.

Oracle: read-only preparation has zero target/header/seed/grant/input/model side effects; locally fixed invocation exists before the first mutating RPC. First request for source in project P; lose response after completion, change source project/title/model and close/archive source; retry original object cold and adopt original target with original metadata, without source profile/export/project-query/preparation hooks. Change source ID, atSeq or override while reusing invocation/intent and refuse before mutation. Caller-supplied digest that omits or lies about those fields refuses. Retrying only an invocation when original host intent is unavailable is explicit recovery failure, never a new operation.

### 2. Move passive reconciliation before *outer* source accesses and busy gates

Persistence-first lookup alone is insufficient. Actual Gateway `router.ts:498–504` rejects fork for active prompts/compaction/model switches and occupies source modelSwitches. `session-management.ts:166–167` profiles/visibility-checks source, `:177–192` enters exclusive source fence and assertIdle, `:205` flushes, then `:206` invokes persistence. `assertIdle` (`:43–114`) inspects live resources, source snapshot, agents/children/tasks and pending interactions. CLI `apps/cli/src/index.ts:773` flushes before persistence. These accesses violate passive adoption after source change/close even if fork.ts is correct.

Minimal correction: validate complete request and retain current caller/workspace authority, then route exact existing-operation reconciliation before those source operations in **both** outer hosts. Only genuinely absent/new work enters current source visibility/idle/fence/flush/export checks. Passive resume still needs a live actual host and currently allowed target/project capability; it does not gain authority merely from knowing an invocation. Gateway passive preparation uses retained original intent plus target broker reconciliation; source availability/currentness hooks must not run. Do not blanket weaken busy gates for other actions or new forks. The SDK fork arm currently calls callback directly (`server.ts:463–477`); do not add `prepareSession(source)`/knownSessions as a new prerequisite. knownSessions is bookkeeping, not authority, and only ready/adopted targets enter it.

Inspection is only a routing hint: call `resumeSemanticTarget` for retained-operation adoption and accept only its owned receipt/document. `bootstrap.ts:159–161` adopts complete original state or returns payload-required; `:275–293` inspection alone is not receipt ownership. Handle unavailable/conflict without fresh source fallback. A caller retry of an in-flight original request should join/reconcile the original operation rather than be rejected merely because that same operation installed a source busy flag.

Oracle: instrument profile/flush/sourceFor/export/projectFor/assertIdle/assembly/model hooks; completed original retry with closed/archived/now-busy source has zero source-hook calls and returns same target/receipt. New absent invocation against the same unavailable source refuses. Current target revocation or host closure blocks passive adoption. Duplicate concurrent original requests do not create two targets or become a fresh operation.

### 3. CLI staging authority is a real remaining interface gap; a string revision is not a live policy fence

Sharing `acquireResultReadStore` and its exact canonical store owner is correct (`lifecycle/result-store.ts:26–34,118–128`); pre-READY target must not go through ordinary sourceFor/profile (`:47–87`). The accepted transfer API supports genuine scope registration, full binding and passive readback (`context-output/src/artifact/transfer-codec.ts:9–16`; `bootstrap-transfer.ts:34–67,150–166`). It requires **synchronous** target/source currentness callbacks after internal awaits. Draft §6 promises that these callbacks detect target binding/policy changes across every preparation/dependency await, but existing CLI registrations contain availability/readScope only (`result-store.ts:8–15`), ordinary unmanaged sourceFor returns sourceId without a revision, and coordinator offers asynchronous `getDocument`/`putDocument` with no project-binding change feed (`coordinator/types.ts:62–63,114`; `coordinator/documents.ts:16–42`). A captured absent binding plus arbitrary local revision cannot detect a later conflicting write or ABA. Inspection of the bootstrap reservation proves original-operation identity, not project-policy exclusivity.

Minimal correction before dispatch: name the actual bounded authority/exclusion that makes unmanaged target policy stable while its synchronous callbacks run, and the actual source-identity/currentness fence for new work. Freeze which writes that authority excludes and how host-close/revocation permanently invalidates it. Async binding refresh before/after the public transfer Promise is useful, but does not implement the stronger claim “policy checked after every internal await”; either supply an owner-backed synchronous epoch/exclusion, or root explicitly freezes the narrower supported unmanaged policy and refuses unsupported concurrent binding authority. Do not manufacture a ResultReadScope getter or borrow Gateway project roots/epochs. Do not silently change the accepted storage API to make this work; any necessary interface exception returns to root.

The helper must validate exact original invocation + reserved manifest, require no managed target binding, preserve actual workspace `contextWorkspaceLocation/contextSourceIdentity`, and expose no new store/map. Source-present confirm uses a genuinely authorized cold source registration plus source/document/Stop guards; source-absent passive acquires only a target-key reader lease and never calls target/source sourceFor/profile. Full transfer binding is operationId+manifestDigest+sourceSessionId+targetSessionId+targetDocumentId; source label alone is not a grant. A real unknown/failed store acquisition must return blocked, not an empty confirmed closure.

Oracle: real catalog + retained artifact member, source runtime closed, actual CLI stdio initialize→fork→result/read (catalog and viaCatalog member), then cold restart/read/adopt. Zero assembly/model/tool/input activity. Insert host close, source identity/policy change and target conflicting binding at named await cuts; no READY/page under invalid authority, no new invocation, original pins/publication retained. If ABA protection is claimed, test change-away-and-back with the actual owner epoch rather than equal final JSON. Target staging never invokes ordinary target profile. This decision cannot be replaced by the separately owned close/release repair.

### 5. CLI close must join admitted *whole requests*, including acquisition and release

Draft §6 correctly names this requirement; make its ordering executable. SDK `server.close()` (`server.ts:890–898`) only joins preparingSession/history work, not external fork callbacks. CLI teardown (`apps/cli/src/index.ts:857–874`) currently closes server→service→coordinator and retries the whole chain after error. A pending set populated after acquisition misses races during settings/location/profile awaits. Joining only dependencies misses preparation and release; a rejected fork must remain joinable until cleanup finishes.

Minimal correction: register the complete request Promise before its first await; synchronously close fork admission at teardown entry; preserve outcome/invocation before cleanup; close handoff admission, join all admitted preparation/dependency work, then release actual reader lease. Teardown joins all whole fork requests/cleanup before closing service/coordinator. Stop/host-close currentness must not depend on a flag set only after waiting for the work it should retire. Cleanup failure remains attached to original invocation/outcome; no replacement operation, no pin rollback and no falsely absent outcome. Use the result-store/service close retry behavior only after the **separate writer's result-store release retry plus underlying context-output close fix is accepted**. This report does not treat that repair as done or assign F1 duplicate ownership of it.

Oracle: EOF/SIGTERM during location/config/source acquisition, during target preparation, after dependency publication, after READY and during release failure. Check admission closes synchronously; server/service/coordinator close cannot overtake admitted work; every disposer is attempted as required; accepted cleanup retry succeeds with the same lease/operation identity and no duplicate target. Test actual CLI path, not only helper.close.

## Addendum — bounded existing-owner document read exclusion

Root's proposed `withDocumentReadLease(keys, callback)` (name not frozen) is a **viable minimal owner interface exception** to resolve decision 3, subject to the following explicit constraints. `coordinator/documents.ts:16–22` already acquires `doc:${key}` through the real Ownership owner for both ordinary and strict writes. `ownership.ts:15–23` resolves the actual configured lockRoot and OS lease; `fs-lock/src/index.ts:41–75` supplies synchronous held state and bounded conflict/unsupported failures. The new method can acquire sorted, unique, bounded exact keys, read/capture their closed data while all leases are held, and give the callback an unforgeable host-only synchronous guard over actual held leases + admission/fence state. This is exclusion, not an invented revision or new registry; no raw fs-lock handle crosses the coordinator boundary. Disabled/unsupported locking or unavailable capability must refuse/block, never silently degrade to unlocked reads.

- **Bound actual authority inputs.** Fresh CLI source resolution must discover the exact source binding chain using the existing sourceFor rules (`result-store.ts:62–87`), then acquire the complete sorted binding-key set plus target key and revalidate that the chain/closed binding data still matches. Never extend the held set incrementally or trust an unlocked preliminary lookup as final. Require unmanaged target absence and an actually authorized unmanaged/unassigned source; project roots remain unavailable at CLI. Hold the leases through preparation/transfer/bootstrap receipt acquisition. Passive resume takes only target binding authority and original retained intent; no source/ancestor profile, discovery or reader hook. A lease over `doc:<key>` fixes document contents only, not parentSession/origin/archive metadata or semantic payload.
- **Protect lineage and payload separately.** The true source ManagedDocument/assertReady and its immutable append witness can fence new source payload work; an owned Session label or equal observation hash cannot. External session mutations/deletion are excluded only while actual session ownership is held. `mutations.ts:107–118` does not generally make parentSession/origin immutable, and same-coordinator owners can still mutate metadata or append. Thus an inherited source chain additionally needs actual held/session-local metadata currentness/exclusion for every traversed identity, or a bounded typed refusal for unsupported lineage; document locks alone do not freeze ancestry. Revalidate the same managed view/witness and Stop/host lifetime across awaits. Do not open source models/assembly or claim that a document key lease protects event bytes.
- **Deletion is an explicit exception to the proposed exclusion.** `lifecycle.ts:21–34` closes local document admissions, then calls backend deletion under the session operation/ownership lane. JSONL `index.ts:320–354` directly tombstones/unlinks manifest document paths without `doc:<key>` leases. Therefore “all binding mutations are excluded across coordinators” is false if it includes deletion without an additional rule. Required closure: either deletion joins the same keyed document exclusion in a frozen lock order, or real source/target/ancestor session ownership excludes external deletion and local deletion synchronously invalidates affected callback guards and joins those operations before backend removal. `closeAdmissions(keys)` must fence active affected operations, not merely later puts. Deleted/tombstoned identity never becomes a fresh unmanaged absent binding. These lifecycle changes are a necessary bounded owner exception, not already-present behavior.
- **Avoid causal cycles.** A callback must not write, recursively lease, or await deletion of its held keys. Do not put its entire duration on the existing global docChain while allowing it to await any write queued behind itself, even to another key. Freeze a mixed session/document acquisition order: bootstrap/deletion currently acquire session ownership, while wrapping bootstrap in document leases would invert that order. Prefer acquiring required session ownership before the document set via the real owner; if an unavoidable reverse acquisition remains, use existing bounded conflict semantics and return the original-operation blocked outcome, never wait indefinitely or claim unconditional progress. Callback must not invoke/join coordinator.close or await its own pending operation. Sorted document keys solve document/document ordering only.
- **Admission and resource lifetime.** Register the whole acquisition→capture→callback→release operation before its first await. Coordinator close must synchronously fence new read-lease admissions, invalidate live guards, join these operations **before** managed owners/session leases are closed, and attempt release of every acquired key on partial acquisition, callback error, cancellation and close. Current `index.ts:79` closes managed documents before lifecycle.close; it must be adjusted for this new lifetime. Capture callback result/original invocation before cleanup; aggregate release failures without converting success/unknown into absence or minting a new operation. A method-local held guard expires before release and cannot be retained for ordinary target reads. This is separate from the already assigned result-store/context-output cleanup repair.

Minimal causal oracles for the exception: two real coordinators sharing the configured lock root contend on the same binding key; putDocumentStrict fails under the read lease and ordinary putDocument reports the failure without changing captured bytes; unrelated keys are not spuriously blocked by a callback/docChain cycle. Add same-coordinator and cross-coordinator deletion cuts, source lineage change during discovery/acquisition, source append witness change, target conflict, close during partial acquisition/callback, and one failing release among multiple held keys. Check all other releases are attempted, close joins, guards reject after retirement, and original invocation/pins/receipt truth survive. Passive target-only adoption has zero source hooks. These are bounded future implementation controls; none were run here.

This addendum supersedes decision 3's lack-of-owner concern **only if root accepts and freezes this concrete Documents/lifecycle interface exception and its deletion/metadata limits**. It does not remove the retained-intent, outer-routing, genuine nonempty handoff, or separate cleanup acceptance gates. No additional baseline research or product implementation was performed.
