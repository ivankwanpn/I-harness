## 1. Archive, selected context, and actual wire are different objects

The primary call chain is:

1. `SessionContext.select` captures session, selected agent, current instruction sources and tool snapshot (`OC packages/core/src/session/context.ts:126–165`). Permission narrowing applies to discovery and tool definitions. The instruction order deliberately goes from reusable catalogs/guidance to project and then date/environment (`:152–163`).
2. `SessionContext.load` resolves the model, invokes `SessionHistory.entriesForRunner`, and exposes the resulting active messages (`context.ts:168–183`). `SessionHistory.messageEntries` queries at/after the latest compatible completed compaction; it does **not** equate the entire message table with the model input (`history.ts:103–141`).
3. `SessionModelRequest.baseTranscript` combines fresh agent system text/current baseline and `toLLMMessages` (`model-request.ts:92–111`). The translator omits idle/agent-selection markers, maps synthetics into user-role text, replays native windows, or renders a textual summary plus recent context (`runner/to-llm-message.ts:240–322`). Its textual checkpoint explicitly labels the material historical context rather than new instructions (`:303–308`).
4. `SessionModelRequest.prepare` runs context/compaction hooks, builds the tool set by matching genuine registered definitions, applies unsupported-media/image shaping, and makes the canonical `LLMRequest` (`model-request.ts:229–313`). Hooks can change the output limit or remove it (`:244–255`). Model hooks can change URL/headers; HTTP hooks can replace a Web request, including its body (`:298–342`).
5. AI compilation normalizes tool history, merges route/model options, sanitizes surrogates, deduplicates/projections tool schemas, applies effort updates/cache policy, lowers the protocol body, and prepares transport (`OC packages/ai/src/route/client.ts:257–270,547–598`). HTTP preparation overlays `request.http.body` on the native body and encodes final body text (`route/transport/http.ts:35–63,79–110`). Thus even the canonical request is not the final bytes.
6. Responses WS may send a suffix plus `previous_response_id` rather than the full canonical history, but only after invariant fields and prior input+output prefix comparisons match (`protocols/open-responses-continuation.ts:104–121,147–164`). A shorter frame is still not a claim that the provider's logical input is equally short.

The durable transcript is primarily projected message rows. `SessionStore.messages` pages these rows independently of `SessionStore.context` (`OC packages/core/src/session/store.ts:143–182`). **Durable event payload retention is optional**, with `persist = options?.persist ?? false` (`bus.ts:208`); projectors and sequence allocation commit in a transaction regardless, while `EventTable` insertion is conditional (`:320–441`). Server composition passes the option (`packages/server/src/routes.ts:119`); workerd explicitly enables it (`packages/server/src/workerd.ts:69`). Do not describe every deployment as maintaining a complete immutable event archive. Nor is the projected message table an immutable operational ledger equivalent to IH JSONL.

Completed compaction updates the compaction projection and advances the instruction epoch (`OC packages/core/src/session/projector.ts:752–756`). The active history query then begins at the checkpoint. Old messages remain available for paged reads, native incompatibility fallback, and retained-tail reconstruction (`history.ts:103–181`). Explicit revert/deletion have separate destructive semantics; this report does not claim all history survives those actions.

Native windows only bound model-specific reads when provider ID and model ID match and the stored canonical window decodes; otherwise selection can re-expand original history before the native checkpoint (`history.ts:20–46,128–140`). This is a concrete reason archive size, active-window size and wire size diverge. Re-expansion can also make a later request much larger; it must be assessed again.

**IH comparison:** the approved redesign already separates archive bytes, semantic estimates, provider usage, wire bytes and billing (`docs/superpowers/specs/2026-10-15-context-engine-redesign.md:27–28,76–96`). The accepted implementation exposes validated prepared facts and distinct packet/body measurement (`IH@7706 packages/context-engine/src/admission/prepared.ts:28–76`; `admission/capacity.ts:6–51`). This comparison supports that architecture; it does not establish that every future fork/native caller has been wired to it.

## 2. Protocol lowering, native evidence, and cache-prefix semantics

### Native preservation starts with a weaker gate than IH requires

Core stores provider-specific event metadata as native fields on text/reasoning/tools (`OC packages/core/src/session/runner/publish-llm-event.ts:146–214,443–472,509–576`). On replay, `assistant()` calculates `sameProvider`, `sameModel`, and `reuseProviderMetadata = sameModel && no error` (`runner/to-llm-message.ts:155–158`). Interrupted reasoning becomes readable fallback or is omitted if empty (`:159–185`). Local tool call metadata is model-scoped; hosted tool result data can survive across models of the same provider (`:186–213`). These are useful distinctions, but the inspected gate does not establish route/account/credential epoch continuity or actual accepted-object provenance. An opaque serialized field remains serialized data.

IH's approved R4B deliberately demands a private live association with accepted objects and the actual successful owned terminal receipt, followed by final actual-credential validation; cold data cannot mint this capability (`IH spec 2026-10-22-context-r4b-semantic-inheritance.md:13–14,33–43,80`). Accepted `7706` foundations establish an owned terminal confirmation, not final transfer permission. The acceptance document explicitly leaves native acceptance/current-component/source-lifetime proof, final permit and per-protocol lowering open. Do not use OpenCode's same-model test to weaken those remaining gates.

### Cache strategy and what it does not prove

`OC packages/ai/src/cache-policy.ts:1–62` describes and implements automatic hints on last tool, first/last system parts and conversation tail, with four-breakpoint accounting and manual-hint preservation. It skips inline placement on protocols such as native OpenAI and Gemini whose caching semantics differ. Anthropic allocates budget in tools → system → messages order (`anthropic-messages.ts:1044–1065`); Bedrock uses positional cache markers. Core keeps tool definitions on the final allowed step and sets tool choice to none to preserve a prefix (`core/session/runner/llm.ts:235–241`).

Session affinity is immediate parent ID, otherwise fork source ID, otherwise own ID (`core/session/affinity.ts:5–8`). The request builder has an explicit TODO to persist root cache lineage for nested forks (`model-request.ts:287–288`). Reusing an affinity string cannot make different fresh child instructions/tools a matching prefix and is not authorization. The cache strategy is worth using as regression input, not as a claim that cross-child caching always works.

Responses WS continuation compares invariant native fields and comparable prior input/output; explicit stale continuation rejection can request a full replay (`open-responses-continuation.ts:109–121,147–188`). Core permits full recovery only before observed output and only once per logical step (`runner/step.ts:182–188`; `runner/llm.ts:208–209,326–328`). Prefix caching, WS delta transport, native reasoning continuity and credential ownership are four separate concerns.

## 3. Measurement, output reserve, compaction and recovery

### What is measured, and what is estimated

`OC packages/core/src/session/compaction.ts:1073–1096` finds the last assistant with provider usage, builds current transcript from that anchor, applies local media shaping, and excludes the anchor assistant itself from newly estimated content. Measured carry-forward includes input + cache reads + cache writes + visible output + reasoning; local tool results after that assistant are estimated because the provider had not seen them. Usage normalization separates visible and reasoning tokens (`session/usage.ts:9–18`), and protocol usage handling explains inclusive Responses totals (`ai/protocols/open-responses.ts:844–859`) versus Gemini visible candidates plus thoughts (`gemini.ts:514–540`). This avoids a simple obvious double-count when those normalized fields are complete.

However, the anchor qualifies on **provider ID**, not exact model ID/variant/system/tools/route or final semantic-prefix identity (`compaction.ts:1122–1127`). With an anchor, system and tool definitions are not independently added by the increment reducer (`:1092–1095`). A same-provider model change, changed system/schema, hook insertion or altered raw option therefore deserves a specific control; the code shown is not an exact semantic-anchor validity proof. Missing usage fields are normalized to zero in `session/usage.ts:9–18`; that is different from IH's explicit unknown-component handling.

Fallback token estimation is `round(string.length / 4)` (`core/util/token.ts:3–5`), with fixed media estimates (1,500 image / 2,000 PDF constants, `compaction.ts:143–145`). Tool schema names/descriptions/JSON and tool arguments/results count at canonical level (`:1153–1186`). Opaque compaction content can estimate as zero; auto compaction deliberately waits for provider usage after a native window (`:409–417`). This is a latency/availability tradeoff, not proof that opaque input costs nothing.

The default primary/compaction output cap is min(catalog output or 32k fallback, 256k), reduced by measured prompt plus a 15% margin on estimated increment, but clamped to at least 1,024 (`model-request.ts:47–54,85–89`). Hooks may override/remove that default. The trigger instead computes a ceiling from input limit or context window, subtracting configured valid buffer or max(15%,16k when the window is at least32k); unknown windows produce infinity (`compaction.ts:1104–1111`). Consequently the trigger, requested output and final body are not one unified proven inequality.

The inspected primary path does not perform an exact final HTTP-body-byte gate or provider token count after hooks/lowering/overlay. Image bytes have a separate bounded window: 25 MiB trigger, 15 MiB target, replacing oldest inline image parts (`model-request.ts:42–45,141–145,182–210`). Remote/provider references do not count toward that inline byte budget. It is not a total request-body/media/attachment cap, and dropping an image is a real projection change. ChatGPT zstd addresses transport size separately; it is not token compaction.

**IH comparison at accepted component scope:** accepted `admission/prepared.ts:35–76` validates initial prepared data, derives at most one output cap, revalidates/reprices the derivative, and returns the actual candidate. `admission/capacity.ts:15–51` distinguishes coupling, effective reserve, input/body/output dimensions, unknowns, strict policy and compatibility outcomes. The framework must stay in charge; do not regress to a chars/4 decision outside the prepared adapter. The existing acceptance document cautions that actual executed-cap evidence is not native send permission.

### Compaction selection and publication

Default configuration is auto on, keep15k, precompute off (`OC compaction.ts:253–260`). Auto-off also disables overflow-triggered compaction (`:284–291`). Summary model can be the configured compaction agent's model, otherwise current model (`:264–281`). The generated summary is required to match at least one expected heading and receives one template reminder before failure (`:453–483`); this is format validation, not factual/coverage proof.

The recent tail is chosen by estimated text size and moved to a user boundary to keep calls/results together. If everything fits it keeps the latest exchange rather than duplicating the entire conversation; a single exchange can be summarized with no tail (`:951–995`). The kept tail is stored as a `keepID` reference, and reconstructed later as serialized text. It is not replayed as original typed tool messages beside a summary.

Normal summary attempts preserve the full canonical conversation/tools while there is room, append the summary prompt, and refit output (`:424–503`). This helps reuse cached prefixes. If necessary, first send the prefix before the retained tail; otherwise flatten into text, omit reasoning/media/instruction updates, remove tool definitions, progressively clip/remove tool outputs, retain user-only material, then omit oldest whole exchanges. The newest exchange is never omitted, though it may be shortened (`:648–727`). A prior native window is preserved intact in the lead. These are deliberate lossy reductions for summary production, not transparent context-preservation claims.

Precompute begins near85% of the ceiling only with at least64k measured prompt and a suitable model/anchor, holds a background result privately, and waits to swap it until needed (`:147–157,321–406`). It checks model/initial/keep boundary compatibility and tail length; overflow does not reuse it. This could improve latency but adds cost and stale-candidate management. It is disabled by default and does not justify adding it during IH's current host-transfer wave.

Successful compaction publishes `Compaction.Ended`; failed/interrupted work publishes failure and does not become a completed history boundary (`:858–904`). The projector and bus transaction make completed projection/sequence durable together (`projector.ts:752–756`; `bus.ts:320–441`). This provides clear commit visibility but is not a demonstration of IH's fixed-byte JSONL uncertain-write reconciliation or semantic revision proof. In particular, a usable-looking summary is not remeasured as the next complete child/primary request before publication in this inspected flow; the runner reloads and prepares afterward.

IH@7706's reduction loop already prepares baseline/candidates, checks source currentness, bounds summary attempts, requires measured reduction progress and submits publication proof (`packages/context-engine/src/reduction/run.ts:35–84`). Its source groups and publication owner should remain authoritative; no parallel compaction coordinator should be imported from the reference.

### Typed failure recovery, not “HTTP400 means compact”

`OC packages/ai/src/provider-error.ts:251–307` classifies context overflow, payload too large, quota/auth/rate limits, transient errors and remaining invalid requests separately. The helper has a legacy text pattern for `400/413 (no body)` (`:70–72`), but the ordinary HTTP executor uses `Provider request failed with HTTP N` for an empty body (`route/executor.ts:81–103`); do not claim every bare400 automatically matches that regex.

Main-step overflow recovery requires no observed model output (`core/session/runner/step.ts:113–119,155–166`). One successful overflow compaction disables that recovery for the logical step (`runner/llm.ts:208,260–265,322–325`). Summary delivery shrinks on context rejection using85%,70%,50%,35% of the first rejected request estimate, then fails; payload-too-large on unchanged input gets a text-only retry first, and other retryable failures use session retry policy (`compaction.ts:558–645`). This is a bounded and useful recovery pattern, with a limitation: before the first rejection, if nothing fits it can send unchanged content anyway (`:595–602`). IH should retain preissue admission and refuse/reduce known violations instead of relying on the first provider failure.

IH's approved taxonomy already separates context400, size413, schema/order400, output cap, unsupported parameter, auth/quota and transient transport (`redesign spec:141–145,173`). Add only uncovered protocol-specific controls; do not create a blanket recovery or repeat tools after input rewriting.

## 4. Tools, MCP, Code Mode, retention, and child inheritance

### Output boundaries are path-specific

Direct model tool calls follow `SessionStep.executeTool → Tool.Snapshot.execute → normalized result → ToolOutput.truncate → publisher.toolExecution` (`OC core/session/runner/step.ts:122–133`; `core/tool.ts:144–153`). Generic truncation joins text, checks2,000 lines /50KiB, saves full joined text, returns a head projection plus file marker, and passes file parts through (`tool-output.ts:13–18,69–119`). The marker is additional to the selected text budget. A single oversized first line can leave zero retained lines. Most significantly, **any defined `metadata.truncated`, including false, returns before generic bounding** (`:70`). This trusts producer ownership; it is not a universal cap on arbitrary plugin output.

Retained files live in global data `tool-output` with7-day retention and hourly cleanup (`tool-output.ts:15,57,138–145`). Cleanup checks mtime and deletes old paths (`file-retention.ts:7–22`), with no session-dependent pin mechanism on this path. Full output path text is a retrieval hint, not an immutable ref, dependency membership receipt or authority capability. Ordinary read supports offset/limit capped at2,000 lines/entries (`tool/plugin/read.ts:19–23,169–203`). This is useful paging, but not IH's typed metadata-only catalog traversal and access-checked bounded result pages.

MCP conversion prefers machine structured output when available, normalizes content, and converts embedded binary resources to retained files; inline text resources become text (`core/tool/mcp.ts:88–105,150–158`). The direct outer tool call is later generically bounded. Whole MCP payloads can already have been materialized before this step; bounding model content is not a streaming-memory guarantee.

Core Code Mode inner calls return `executed.output` when present, else joined text/null, and collect returned files (`core/codemode/tool.ts:99–139`). Outer execute formats result/warnings/logs and returns machine output plus model content (`:125–148,333–344`), after which the runner's generic cap applies. The core runtime is created without `limits` (`:235–253`). The library supports optional timeout, max tool calls and max output bytes, but absence means no such configured limits (`packages/codemode/src/codemode.ts:22–40,133–149`). This does not imply the interpreter has no other safeguards; it means these three optional budgets are not set by this core call site. Arbitrary unused inner results are not all retained merely because the outer formatted output has a saved file; no complete per-inner-result dependency catalog was found in this traced path.

### Ordinary subagents are fresh; forks are a different operation

`OC core/tool/plugin/subagent.ts:56–59` explicitly advertises fresh context. Implementation creates a child with parent ID, role and model, then admits the new task; it does not call the fork path (`:184–213`). Model precedence is explicit override, configured agent model, parent model. Existing child continuation can switch role/model according to the explicit inputs (`:168–184`). Default nesting depth is1 (`:117–132`). These facts do not imply copied parent conversation or parent usage anchors.

Separate `Session.fork` resolves a message boundary and captures the parent's **current** instruction state/entries (`core/session.ts:326–365`). The projector copies settled rows through/before that boundary, retains sequence order, rekeys message IDs and `keepID`, and copies project/location/agent/model/permissions; aggregate cost/tokens start at zero (`session/projector.ts:150–240`). It excludes active assistant/shell/compaction rows (`:197–200`). It is a batched projection-row clone, not IH's typed semantic-seed export with source-connected omissions and dependency-transfer authority. Copied message data still include their historical usage/native observations; setting aggregate counters to zero is not the same as discarding all possible copied usage anchors.

**IH mapping:** approved R4B already requires none/all/N/completed selection, whole unresolved exchange exclusion, separately retained current input observations, fresh role/task instructions, no parent calibration/permissions imported, and exact retained-result dependencies (`R4B spec:19–31,53,75–80`). Accepted product has seed codecs/history integration and READY semantic-reference read foundations, while real callers remain unfinished. The active host plan specifically preserves original operation IDs/refs, all catalog occurrences, target pins/v2 witnesses, bounded metadata pages, source/current target authority and exact passive confirmation. OpenCode's file-path retention and row clone do not replace any of that work.

## 5. Completion, wakeup, steering, cancellation and polling

Jobs use `Deferred` completion rather than model polling: `Job.wait` awaits the done deferred with optional timeout (`OC core/job.ts:300–307`); foreground block races done versus backgrounded (`:329–351`). `SubagentJob.start` resumes the child, reads its last20 messages, picks a completed error-free assistant and joins its text (`session/subagent-job.ts:44–62`). A background observer is unique per child ID/start generation and awaits the job (`:24–40`). Durable notification marker/output is retained until parent notification admission (`job.ts:174,200–206,462–466`).

Completion calls `sessions.synthetic` with the stable notification ID and child status/metadata, then clears the background marker (`session/subagent-completion.ts:21–45`). Synthetic admission persists text and delivery mode, then wakes unless resume=false or parent is reverted (`session/session.ts:283–321`). This path **does not invoke generic ToolOutput.truncate**. Foreground subagent tool output reaches the outer runner cap; background completion text enters as synthetic input. The direct source trace confirms no bound at those latter boundaries; whether a later general request reduction makes a particular payload fit is a separate question. Multiple child completions can therefore require aggregate fan-in budgeting even if each direct tool response is capped.

Prompt admission and wake are separate (`session/session.ts:155–185`). Repeated user/synthetic item IDs reconcile against pending inbox or delivered message; same session/type is first-admission identity (`session/inbox.ts:69–74,113–151`). Delivery projection consumes inbox work and inserts the visible message under the bus transaction (`session/projector.ts:640–647` and associated inbox projection). The stable notification ID is stronger than a best-effort text notification, but it is not an exactly-once physical signal guarantee.

`SessionRunCoordinator` serializes one busy period per session while allowing different sessions to run; `pendingWake` closes the last-drain/idle race, coalesces repeated wakes, and can start a successor after late admission (`session/run-coordinator.ts:6–42,69–140`). `interrupt` accepts cancellation promptly but cleanup may finish later; `awaitIdle` joins settlement and possible successors (`:142–170`). Existing queued wake intent is cleared on stop; a new wake during cleanup is treated as a new admission (`:153–160`). Durable execution claims survive shutdown/process death but deliberate stop/terminal completion release them (`session/execution.ts:73–78,112–126`). This is process-local ownership/recovery, not cluster fencing or a remote exactly-once executor.

Steering is boundary-based: normal run reloads context for each explicit model call; queued work is promoted at idle while steers can enter between continuing steps (`session/runner/llm.ts:73–192`). Compaction steer takes priority within the next move boundary so new steer text stays verbatim after the checkpoint (`session/inbox.ts:542–557`). Cancellation, steering and job completion must therefore be tested independently; “no polling” alone says little about loss/duplication/stop semantics.

IH already specifies `execution settled → result durable → parent input admitted → wake scheduled → consumed`, logical idempotency, Stop preventing wake and later delivery after steering (`redesign spec:135–137`). OpenCode supplies good race-control examples, but its new-wake-during-cleanup semantics and background text path should not override IH's policy. The active host plan is not a delegation scheduler rewrite.

## 7. Narrow recommendations for root review

No blanket redesign, automatic adoption, new provider capability, or pause of current implementation is warranted. Most useful findings are **regression inputs within existing contracts**, not new scope.

1. **Actual-request identity controls:** retain a fixture where archive size grows while selected wire stays small, and another where a small message count contains one huge active tool/schema/media item. Add or verify hook-added system/tools, same-provider model switch, raw options, changed instructions, output-cap derivative and full-replay-after-WS-failure controls. Assert admission sees final selected representation and reports bytes versus token estimates honestly. This is already R2/R5 architecture; only missing controls justify additions.
2. **Native disposition controls:** per-unit tests for empty encrypted Responses reasoning, native-window incompatibility re-expanding source, Anthropic prefix changes caused by fresh role/tools, Gemini signed-first/unsigned-sibling ordering, and Bedrock unresolved ambient credential continuity. Never count the Gemini skip sentinel or Anthropic drop instruction as genuine inherited proof. If IH is to permit provider-side drop of opaque native state, root must explicitly rule on how final preservation/disposition is evidenced; existing portable-or-block behavior should remain until then.
3. **No synthetic closure:** use the reference's `normalizeToolHistory` as a negative control: missing result must not cause inherited local success, fake error result, invented acceptance or tool execution. Already covered by R4B grouping/omission intent; verify real child entry rather than a serializer-only test.
4. **Output ingress controls:** direct tool, MCP structured/text/media, Code Mode inner versus outer, foreground child, background child completion, and multi-child fan-in must each demonstrate bounded model projection and honest retrievability. A cap on direct tool content alone does not qualify background inbox data. Preserve raw results and exact dependency catalog associations through current host transfer; do not claim an outer saved text file retains all inner machine results.
5. **Optional latency optimization, separately scoped:** precomputed cache-preserving summaries are worth future study only if measured latency/cost warrants it. Any IH implementation must reuse the current reduction/publication owner and same source/currentness/Stop/receipt contracts. It should not enter this transfer-host wave merely because the reference has it.
6. **Delivery race controls:** stable notification retry after landed-admission/lost-response; completion during parent stop; steer releasing a foreground wait; late wake during cleanup; multiple completions concurrent with compaction; result survives without duplicate consumption or reexecution. Existing IH delivery design already calls for these. Match IH's explicit stop policy, not the reference's semantics by analogy.
7. **Capability evidence:** if proposing to adopt the export's ChatGPT token-sharing path, compression policy, model-name-based limits or prefix-binding defaults, require independent source/capability confirmation under a separately authorized task. This read-only reference study cannot validate service availability, authentication ownership, price/plan caps or current provider behavior.

Do **not** copy: provider/model string equality as native-transfer authority; raw projected-row clone as semantic inheritance; synthesized missing tool results as completion; path-only7-day retention as durable dependency ownership; producer `truncated` labels as universal bounds; missing usage as measured zero; a universal16k/15%/256k capacity policy; first-failure probing of known over-limit requests; request-hook/raw-overlay mutations after the bytes used for IH admission; or model-name heuristics as confirmed capability facts.
