## What a 100 MB session does and does not imply

There are at least five different quantities: durable session/archive bytes, UI transcript bytes, active canonical history, provider-projected request bytes, and provider tokens. Neither reference treats these as interchangeable. Old tool output, failed stream attempts, retries, UI metadata, raw summaries, child events, and repeated request snapshots can remain on disk after their original text has left active input. A session can therefore exceed 100 MB while each physical request remains within a model window. Conversely, a small log can contain a single huge image or tool schema that makes a request too large.

DSH explicitly maintains an append-only log and a separate ordered `surface` whose replacement operations shadow old nodes. `DSH/packages/core/session/src/surface.ts:78-105` distinguishes append-origin human transcript material from replacement copies that are model-only. `deriveEventMessage` at `:120-151` excludes attempts/boundaries/log-only events. `DSH/packages/core/session/src/index.ts:984-1004` derives only current surface nodes; a replacement/content generation invalidates the derived cache. Thus physical log deletion is not required for model compaction.

ZCode persists messages/parts and session events, reconstructs the selected branch and latest compact boundary, then builds a separate runtime history. `ZC/apps/zcode-cli/packages/core/src/agent/session-history-hydrator.ts:201-255` applies branch/rewind/compact selection. Its `ModelRequest` event also stores projected request messages (`runtime/methods/turn-model-step.ts:194-206`), and summary requests do likewise (`runtime/methods/compact-active.ts:365-380`). Repeated full-prefix request snapshots can inflate logs faster than unique conversation content. That is an architectural explanation for possible large archives, not an attribution of the user's particular 100 MB log (that log was not inspected).

Neither audited loading path is a proof of bounded-memory archive paging. DSH JSONL persistence `packages/session/session-persistence-jsonl/src/index.ts:799-869` stats, reads stable file bytes, scans/decompresses, validates and freezes an events array; its bounded cold-log cache is count-based (`:872-879`). Live Session also retains its log. ZCode SQLite `apps/zcode-cli/packages/adapters/src/storage/session-store/repositories/messages.ts:221-256` selects all session message rows and all part rows with `.all`, without LIMIT/OFFSET, then joins them in memory before active selection. Active context bounds and archive-load memory bounds are separate engineering problems.

## DSH: disk → surface → pressure → compaction → wire

### State and request ordering

`DSH/packages/core/agent-loop/src/agent.ts` owns one session driver and typed idle/maintenance/running phases. `preStep (:267-287)` claims inbox input, assembles system prompt/context, and runs the `agent/pre-step` waterfall. A step then resolves provider/model (`prepareRequest :564-612`), refreshes context, logs changed system/user inputs, builds a request from the session surface (`step :400-442`), and finally streams the prepared adapter (`:453-460`).

`buildRequest (:616-703)` canonicalizes/logs request header changes, records model context metadata, freezes header/messages, calls `session.deriveMessages()`, and supplies tool history, schemas, session ID and signal. The model request is a projection of admitted events, not the entire log. Tool schema additions/removals get explicit developer messages tied to the historical header (`:652-664`).

One practical gap: automatic `agent/pre-step` compaction happens before `step` appends the newly claimed user messages/runtime context (`:427-440`). It also chooses the last durable routed header, not a freshly resolved prospective request (`compaction-basic/src/index.ts:274-278`). Therefore a first/new huge prompt, new toolset, or changed route can make the immediate request larger than the pressure measurement that preceded it. Overflow recovery can address history pressure, but cannot guarantee that irreducible new content fits. IH should budget the fully assembled prospective request, including pending inputs and final schemas, at the dispatch boundary.

### Estimation and budgets

`DSH/packages/llm/token-meter/src/estimate.ts:12-19,42-101` uses text characters/4 plus role/block framing, counts tool name/arguments, and estimates tool schemas from JSON. It is an explicit heuristic, not a tokenizer. Structural image-reference text alone is not an image token count. The route-aware meter asks the adapter for image pricing.

`token-meter/src/index.ts:146-190` synchronizes replay state, selects effective canonical header, prices current surface, and optionally uses the latest successful usage anchor only when the header matches and provider usage is at least the complete heuristic anchor price. Pressure is `max(0, baseline + signed surface delta)`. This preserves reductions after prune/summary and reprices when route/header changes. Provider usage is not blindly reused as a permanent absolute cursor. The code states measurement is O(surface) and clones returned nodes (`:126-144`). Usage buckets in `:70-75` are input + cache read + cache write + output; reasoning is already part of output.

`DSH/packages/compaction/compaction-basic/src/config.ts:153-216` computes message budget = context window − reserved completion, pressure budget = that − headroom, trigger = floor(min(window × threshold ratio, pressure budget)), retained tail = configured tokens or ratio of message budget. It rejects impossible/contradictory values with a typed target-pressure error. Output reservation comes from effective request cap or adapter default (`index.ts:65-67`). This is a coherent shared-window policy, but its accuracy depends on model metadata and approximate counting.

### Reduction and commit semantics

`compaction-basic/src/index.ts:158-175` installs pressure compaction at pre-step. Failure logs a warning and continues (including once-per-target warning suppression for invalid pressure configuration). A failed automatic compactor is therefore not a hard preflight blocker. `:269-347` measures, optionally runs the model-free pruner, remeasures, selects a balanced range, summarizes, and remeasures after each attempt. Pressure convergence failure is thrown and then caught by the pre-step continuation policy.

`compaction-basic/src/region.ts:117-155` retains a priced recent tail and adjusts the cut backward until tool pairing is balanced; initial system head is excluded. Validation at `:339-355` rejects cuts splitting assistant tool-call/result steps. `compactSurfaceRegion (:173 onward)` synchronously writes a compaction/start marker before summarization yields, tracks stage and closure, and applies a stability check. `:431-468` rejects whole-surface/selected-span changes during the asynchronous summary. `:386-427` frames the checkpoint and refuses any replacement whose framed token estimate is not smaller than the selected route-priced span.

`region.ts:491-509` logs summary metadata/raw output and appends a replacement user message with inclusive start/end seq and source-event references. Original events remain for UI/replay. `summarizer.ts:120-180` replays the conversation's system/tools/prefix and appends one summary directive; it logs the actual auxiliary call envelope/output through the result. Empty summaries, visual summary output and max-token truncated summaries fail (`:164-170,197-220`). Cache reuse is an intended consequence of preserving prefixes, not a guarantee that a provider will bill a cache hit.

Overflow recovery is bounded and requires actual durable progress: `compaction-basic/src/index.ts:190-234` only handles `CONTEXT_WINDOW_EXCEEDED`, checks max overflow retries, runs forced reduction, and retries only when `replaceGeneration` increased. If pruning committed before later summarization failed, that reduction can still justify retry. `:294-301` bypasses normal pressure/retention for overflow. A successful assistant event resets overflow recovery budget (`:182-188`). IH can adopt this “retry only after changed input or eligible transient failure” discipline.

### Tool output retention and paging

There are three independent layers, not one universal tool truncation knob:

1. Per-tool/process output behavior can cap in-memory tails and retain full output paths (for example `DSH/packages/shell/tool-bash/src/render.ts:11-14,89-108` renders truncation/spill-path/lost-ring-output notices).
2. `DSH/packages/spill/spill-policy/src/index.ts:48-54,91-129` optionally enforces `maxInlineTokens`, saves full ordered text/image descriptors under session ownership, reserves notice cost and retains head/tail. Images use route cost; retained images stay whole (`retention.ts:48-103`). The policy runs after downstream post-execute acceptance (`index.ts:133-150`) and preserves canonical program values. It skips `read`, value overrides, unsupported block families and some text-only PTC paths. Missing storage/image pricing/owner or an oversized notice logs and keeps original inline content. It is recoverable but fail-open for context pressure. The base bundle actually mounts spill-local and sets `maxInlineTokens: 12500` (`DSH/packages/bundle/base/cordis.patch.yml:411-417`); standalone/plugin compositions may omit it.
3. `DSH/packages/compaction/compaction-tool-result-pruner/src/index.ts:136-181` rewrites current oversized tool results using adjacent prune-price and replacement events. Defaults are 8192 Unicode code points threshold, 4096 head, 1024 tail (`config.ts:10-14`), and base bundle repeats those values (`cordis.patch.yml:425-430`). Non-text blocks are kept. This pruning is lossy in active context but original log content remains; it is a pressure-stage pass, not necessarily immediate retention for each result.

Spill references and file/read tools provide recoverability by path; this audit did not establish a universal paged-tool-result service with guaranteed lifetime. Archive reads and model tool-output caps must not be conflated. A file path being reported does not itself guarantee the model will successfully reread it after session migration or cleanup.

### Streaming, tools, failures and physical request

The DSH loop consumes the complete assistant stream before dispatching tools (`agent.ts:453-460,529-555`). It durably settles successful assistant output before execution. Cancellation can save interrupted blocks; other failed attempts are log-only (`:462-502,505-526`). Tools are not re-executed as a consequence of blindly replaying an already committed assistant.

`DSH/packages/core/agent-loop/src/tool-calls.ts:60-102,122-246` uses exclusive barriers and a bounded rolling parallel pool. Dispatch can overlap, but policy/finalization, result appends and additional contexts commit in model order (`:146-160`). Abort stops replenishment, drains started tools, and emits synthetic error results for unstarted calls (`:238-259`). Scheduler failures drain and the step's `ToolCallRecovery` supplies missing outcomes (`agent.ts:333-358`). Exact result/call seq links and private UI metadata are stored separately from model-facing content (`tool-calls.ts:269-289`).

The actual direct transport is Anthropic-style DeepSeek Messages, not Chat Completions: `DSH/packages/llm/llm-deepseek/src/adapter.ts:138-165` POSTs to `<messagesApiRoot>/messages`, content-type JSON, accept SSE, anthropic-version header, optional files/tool-changes beta. The final body is an extension-prepared payload. `serialize.ts:57-168` maps assistant reasoning to thinking, calls to tool_use, tool results to user/tool_result, coalesces adjacent same-role messages, places pending system updates, and enforces unique call IDs plus immediate complete results (`:131-146`). It sets max_tokens, thinking/output_config, system and JSON tool input_schema. Images can be inline base64 or uploaded file IDs (`:65-78`), so request bytes are not inferable from text tokens alone.

Transport exceptions normalize TIMEOUT, ABORTED and TRANSPORT (`adapter.ts:65-88`). HTTP/in-band error classifier `transport.ts:22-43` produces stable codes AUTH, QUOTA, RATE_LIMIT, CONTEXT_WINDOW_EXCEEDED, INVALID_REQUEST, SERVER and request/retry-after facts. Some provider classification still uses provider error text through explicit helper classifiers; “typed errors” does not mean raw vendors always provide reliable machine codes.

`DSH/packages/llm/llm-retry/src/index.ts:194-240` executes provider-owned retry policy, skips noneligible normal codes, persists `llm/retry` before cancellable backoff (`:149-191`), uses provider Retry-After when bounded, and limits normal retries by durable per-step state. `always` mode can retry without a normal bound and delegates specialized recovery first. `agent.ts:511-526` rebuilds the request from current durable state after a retry decision. Plugin order/configuration is material; an “always” policy is not a universal reliability guarantee.

### Children, context and wakeup

DSH makes inheritance explicit. Spawn provider contributes no seed (`DSH/packages/subagent/subagent-spawn-in-process/src/index.ts:38-54`); fork copies the completed-turn prefix only, excluding current unbalanced tool turn (`subagent-fork-in-process/src/index.ts:46-77`). The seed is captured once at child creation and becomes the child's own durable history. This preserves compaction surface decisions already in that prefix, but also physically duplicates ancestor events in a seed and does not mean parent and child share a live mutable context.

`DSH/packages/subagent/subagent/src/continuation-messages.ts:80-95` tells child that parent does not receive its transcript/tool output/reasoning automatically. `createSettlementMessage (:138-167)` adds a runtime stop-state notice, closing text only, optional structured result and diagnostic to the parent; it does not paste child trace. Closing text is not capped in that formatter. `manager.ts:1187-1205` delivers after cleanup, queues when parent idle or steers when running; closing parents receive inject without waking. Delivery errors are warned, so there is no exactly-once durable-delivery proof in that method alone. Final child flush is best effort (`:1208-1215`).

The loop differentiates followup (next turn), steer (next step), inject (no wake), and cancellation (`agent.ts:154-180`). `wakeDriver (:214-242)` latches wake behind maintenance/aborted activity and `whenIdle` follows replacement activity promises. This is materially better than a generic “child done → append string” path, but is a lifecycle implementation requiring focused race tests.

## ZCode: disk → runtime entries → projection → reduction → SDK wire

### Canonical history and cold restore

`ZC/apps/zcode-cli/packages/core/src/agent/message-history.ts:49-66` separates message entries, attachment entries, source metadata, committed usage and query-local continuation markers. Usage metadata is explicitly not sent to provider (`:53-56`). `MessageHistoryImpl :135-235` owns entries; normal append and replace create clones; readonly borrow is restricted to synchronous readers, while asynchronous callers must snapshot. Compaction/rewind replace active entries, not historical database messages.

Hydrator `session-history-hydrator.ts:54-199` rebuilds selected active messages. It refuses pending/reserved shared context until attached, preserves synthetic source identity, reconstructs assistant reasoning/tool declarations, restores completed/error model-facing output, resolves media attachments, and supplies an interrupted-tool-result placeholder for pending tools. Empty assistants with valid usage are retained as anchors (`:118-145`). Tool error UI text and persisted model-facing text are distinct (`:175-184`). `:201-255` makes branch-cut vs legacy compact/rewind ordering explicit, illustrating how cold/live parity becomes a first-class problem.

### Prospective request and pressure

`ZC/apps/zcode-cli/packages/core/src/runtime/methods/turn-loop.ts:43-103` drains runtime commands, runs local microcompact, then auto summary compact at the beginning of each model round. Tools/MCP and current mode/todo/output-style additions follow (`:105-167`), then `buildRuntimeProviderRequestMessages (:172-186)` projects final entries. This is closer to prospective request accounting than DSH's durable-only pre-step measurement, yet compaction still precedes some fresh tool schemas and reminder additions. Final wire admission remains a separate concern.

Provider projection `runtime/helpers/provider-request-messages.ts:48-99` records origins, reorders attachment-like entries around causal stops, projects supported mid-conversation system messages, renders/strips runtime metadata, and assigns cache control after projection. Adjacent-user merging is deliberately disabled in provider-neutral projection (`:39-41`); protocol adapters own that. The origin map matters for latest real user and media protection; role/text heuristics alone are insufficient.

Auto pressure `runtime/methods/compact.ts:184-214,313-349` builds projected messages and scans the latest committed assistant usage baseline. It adds local estimated messages after that anchor (or includes assistant if output coverage is unknown). This avoids a stale absolute cursor. `agent/message-history-usage.ts:11-51` treats input/total/cache-only legacy data carefully. After compact, preserved assistants' old-prefix usage is zeroed in projection, not mutated in store (`message-history.ts:426-441`). However this override does not itself verify same provider/model/tools as the current request. IH should key any usage anchor by actual request identity, route, schema hash and projection generation.

Two local estimators differ: `compact/manual.ts:102-137` counts visible/reasoning text plus tool name/input JSON with shared divisor 3 (`ZC/packages/shared/src/usage-stats.ts:9`); `context/utils.ts:11-17` adds double weight for Chinese ideographs before dividing by 3. UI breakdown also estimates serialized tool metadata including nonwire fields (`runtime/methods/context-usage.ts:310-334`) and labels itself estimated/low confidence (`:234-251`). A displayed context breakdown can disagree with actual compact trigger and physical provider input without either being an exact tokenizer. This is a concrete warning against copying several independent token formulas into IH.

`compact/policy.ts:67-154` subtracts output reserve capped at 21K from context window, then a buffer, checks enough history and a consecutive-failure circuit breaker, and chooses usage override or estimate. `runtime/methods/model-token-limits.ts:7-40` uses model max output or 32K fallback, caps each request by estimated remaining window minus 1000, but when estimate leaves no positive space retains baseline and relies on provider recovery. It is explicitly not hard fail-closed admission. Tool schemas are not included in `estimateMessageTokens(messages)` itself; usage anchors may include prior schemas but unanchored/new-schema cost is not guaranteed by this function.

### Microcompact and summary

`compact/microcompact.ts:83-169` clones input, triggers by pressure/time, retains at least one and default five recent groups of eligible tool results, replaces old text with a fixed cleared marker, and requires 256-token minimum savings. Groups are assistant-tool rounds (`:197-238`), not arbitrary independent result count. Errors are protected unless enabled, and media results are protected (`:222-227,249-255`). Default compactable tool names and thresholds live at `:12-29`. This is a model-free, low-cost first reduction, but cleared result content is lost from active input and must be retrieved from archive/artifacts if still needed.

`runtime/methods/compact-active.ts:142-257` snapshots immutable entries, selects summary vs preserved recent groups, records operation/timeline, uses a model snapshot, and drops compact-request schemas when total tool count exceeds 100. The latter is an explicit temporary heuristic; 99 enormous schemas can still be expensive, while dropping tools can lose prefix-cache alignment. Automatic summary allows three outer attempts; manual/reactive one (`:72-73,203`).

Summary requests use common media policy and log model request projection (`:309-409`). On media-too-large it strips media once; on context overflow it reselects preserved groups or truncates earlier summary input and retries (`:417-479`). The model may therefore summarize a reduced source input on overflow; that is a data-loss tradeoff and must remain observable. `compact-active-helpers.ts:93-120` refuses returned tool calls and empty summary. `compact-summary-model-request.ts:74-109,258-299` privately buffers summary deltas and permits stream→HTTP fallback only before a content block commits and excluding cancellation/context/media/setup failures. It distinguishes raw provider start/block stop/stop-reason from SDK synthetic finish (`:200-255`), preventing a synthetic clean EOF from masquerading as a complete summary.

After summary, `compact-active.ts:484-631` builds summary + preserved entries + plan/read-state reminders, calculates both provider summary-call usage and true estimated post-compact input, persists summary/boundary/timeline, replaces active history, clears read-file state. These two metrics are separately persisted (`:545-572`): provider summary-call token usage is not the next prompt size. `compact.ts:257-310` warns/returns failed and continues for noncancelled auto failure; it is not a universal “compaction failure stops send” gate. Rapid-refill protection is checked at `turn-loop.ts:77-101` and can throw a typed breaker error when repeated compaction quickly refills.

### Tool output and tool round integrity

`ZC/apps/zcode-cli/packages/core/src/tool/executor/result-serialization.ts:33-40,46-99` applies default maxInline/maxModel 100,000 UTF-8 bytes, or tool-specific budget, and supports artifact strategy. Full content is persisted only when configured artifact-enabled strategy; otherwise generic truncation is possible without a full artifact. `:178-217` returns persisted preview/path or a budget-sized head/tail plus omission suffix. Hook augmentation is re-budgeted (`:220-270`). `:294-325` catches artifact-write failure and ordinarily falls back to bounded truncation.

Material exception: `:161-175` deliberately retains original content if a tool's explicit maxModelChars threshold demanded artifact persistence but writing failed. Protected official CUA image/reference pairs also use a separate raster budget and can exceed ordinary text serialized size (`:101-158`); returnedBytes adds structured media bytes. Thus “all tool output is always 100KB” is false. Byte budget and token budget are different: 100KB may be tens of thousands of tokens depending on language/code, and artifact-preview format can be tool-owned.

ZCode can start completed tool calls while assistant streaming is still underway; `runtime/methods/turn-tools.ts:67-114` accepts streamed results and ledger state. After full model step, results are keyed by call ID then reordered by declared `coreToolCalls` (`:235-244`). They persist to tool parts and commit runtime tool-result entries in order (`:281-366`). Stop passes aborted signal through execution so each committed assistant call obtains an error result (`:142-145`); checkpoint cancellation is deferred until sibling results commit (`:367-381`). Cold restore's declaration selection/order is its matching path. This streaming execution model has a larger recovery surface than DSH's stream-complete-then-tools model and needs call-ledger/idempotency evidence before IH adopts it.

### SDK mapping, physical request and retries

`runtime/methods/model.ts:36-126` resolves attachment paths and projects input capability/media budget after the earlier generic provider projection, then builds the Model request. A pre-media `ModelRequest` session event is not necessarily byte-for-byte physical JSON. Adapter `model/transform.ts:46-155` maps roles/reasoning/tool calls/results to Vercel AI SDK messages, requires tool identity, textifies unsupported structured results, and defers media user parts until a complete consecutive tool-result run ends so media cannot split sibling results.

`ZC/apps/zcode-cli/packages/adapters/src/model/model-execution.ts:283-310` uses OpenAI Responses for openai, Anthropic SDK for anthropic, and OpenAI-compatible adapter for compatible providers. There is no blanket claim that every endpoint is Chat Completions. `runner-options.ts:36-156` maps messages/tools/options and sets SDK `maxRetries: 0`; the project's own adapter owns retries. `model-option-map-fetch.ts:19-30` reads actual JSON body, applies compiled option maps, optionally captures patched body, JSON.stringify's it, and passes it to fetch. Unexpected nontext bodies fail closed (`:33-51`). Therefore the correct point to measure physical request bytes/hash is after option maps/SDK serialization, not runtime history string length.

Retry policy defaults to ten retries/eleven attempts with exponential backoff, 2s base, 60s max and jitter (`retry-policy.ts:13-30`); workflow budgets can be unbounded (`runner-generate.ts:77-81`). `stream-retry-boundary.ts:1-24` buffers retry-safe prelude/tool-input events and empty deltas until committed visible content; nonempty text/reasoning ends this hidden retry opportunity. `runner-stream.ts:429-434` yields visible events; catch/recovery then has to respect whether output/tool work became observable. Summary has a stricter private commit rule described above. Request admission is per attempt and released before backoff (`runner-generate.ts:123-157`), with linked attempt IDs/status events.

`model/failure-classifier.ts:39-47,81-190` returns typed code/reason/retry reason/retryability/retry-after/status, distinguishes malformed request/response, abort, stream idle timeout, provider business errors, timeout and rate limit. Provider diagnostics preserve request/code/message separately (`:55-79`). More classification follows for auth, quota, context etc.; this audit does not assert all vendor variants are exhaustively handled. SDK error parsing, raw transport business errors and finish-body errors all exist because HTTP status alone is insufficient.

### Child isolation, results and wake

`ZC/apps/zcode-cli/packages/core/src/runtime/methods/subagent.ts:93-143,239-330` creates a separate child AgentRuntime/session. Child gets profile prompt, selected instructions/environment/current date and its own optional persistent memory; it does not clone parent conversation or project context (`:262-267`). It inherits concrete model/streaming/media-related configuration and explicit ports, while recursive child spawning is disabled (`:284-287`). Parent-shared tool event mirrors are observability, not wholesale parent context ingestion.

Runner `subagent/runner.ts:1116-1188` waits for child session-ready and completion, packages only final child response text + usage/count/duration, not full child transcript. Background completion writes artifacts, produces a formatted notification including result/outputFile, updates registry, and enqueues parent notification (`:1494-1539`). Local-agent notification is capped at 120,000 characters (`runtime-task/notification.ts:18,144-158`); that can still be ~40K heuristic tokens. Child-to-parent explicit messages use a separate response command with source identity, drop stale branch generations, persist raw content and source metadata (`runtime/methods/subagent-messages.ts:25-105`). Their formatter has no local size cap.

`runtime/methods/runtime-command-queue.ts:23-69` enqueues and drains one owned queue, batches task notifications to avoid a model round per result, and respects promotion leases. `background-notifications.ts:19-82` rejects shutdown/stale-branch notifications and writes an admission ledger. The queue itself is process memory: comments at `:58-60` explicitly say resumed sessions discard admitted notifications because background work/notification is not replay-restored. `:166-217` merges a notification batch into one persisted synthetic user message and marks each admission promoted. This is observable loss-on-restart semantics, not durable exactly-once delivery.

## Transferable design for IH

The strongest transferable idea is a single authoritative request projection with traceable transformations, not a particular compression percentage or a permissive large-log limit.

1. Keep immutable archive events/artifacts and a separately materialized active context. Every replacement records selected IDs/range, generation, reason, source IDs and content hash. Human transcript must survive model compaction. DSH's surface is the clearest model; ZCode demonstrates the cold-restore/branch hazards that need explicit tests.
2. Build a prospective dispatch plan containing route/model/capacity, final schemas, pending user/steer/child messages, system sources, output reservation and media projection. Budget that same plan immediately before physical dispatch. Avoid DSH's prior-header/pending-message blind spot and ZCode's post-compaction fresh-reminder/schema drift.
3. Use one estimation service, with method/confidence units. Count text, reasoning replay, call arguments, schema JSON, framing and route-specific images. Provider usage anchors must point to request ID + route + schema/projection hash, and be invalidated/rebased after replacement or model change. Separately display archive bytes, active text/media bytes, estimated input tokens, provider-reported input/cache/output and actual serialized wire bytes.
4. Bound tool outputs before they become history. Preserve complete data in session-owned artifacts, return useful head/tail/summary + stable reference + omitted quantity, and make rereads paged and budgeted. Missing artifact storage should have an explicit policy rather than accidental fail-open growth. Keep image/reference atomicity and budget notices/hooks too.
5. Reduce in stages: deterministic old-result pruning/offload, then balanced-round summary with retained recent work, then validated atomic replacement. Reject empty/truncated/no-shrink summaries. Summarizer input itself needs budget/overflow behavior; if source is truncated, record omitted IDs and communicate recovery references. Do not call “provider summary usage” the resulting context size.
