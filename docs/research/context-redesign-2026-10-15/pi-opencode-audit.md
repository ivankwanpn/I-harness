## Decision-relevant findings

1. Large archive support is primarily **selection and storage architecture**, not a large-model-request feature. Pi retains append-only JSONL branches and compaction records while selecting summary + tail. OpenCode retains SQLite message/part/event rows while selecting a completed compaction and subsequent context. Consequently a 100 MB archive can produce a small active request; a tiny archive containing a large image or malformed replay can still fail HTTP 400/413.
2. **Tokens, JSON wire bytes and archive bytes are three different measurements.** Both products have substantial token heuristics and provider error recovery, but no aggregate serialized request-byte admission guard was found on the traced paths. A token estimate must never be used as proof of request-size safety.
3. Pi has stronger canonical provenance/edits than a simple mutable messages array: raw failed attempts remain on disk, persistent omission edits remove them from future projection, compaction has stable source IDs, and usage anchors are invalidated when projection changes. OpenCode V2 similarly reloads projected durable history for each provider turn and gives system baselines explicit context epochs.
4. Both distinguish transient retries from compaction recovery. Pi and OpenCode V2 use bounded overflow retry, avoiding repeating an unchanged too-large request indefinitely. Classification still mixes token overflow and byte overflow and remains incomplete for unknown provider 400 bodies.
5. Do not copy all mechanisms blindly. OpenCode has materially different legacy, optional-native, and V2 code paths. Pi also ships a separate durable harness. Their guarantees and weaknesses differ, even within the same version snapshot.

## Pi coding-agent: archive to effective model request

### Call chain and storage

`SessionManager._persist/appendMessage` -> `buildSessionPath` -> `buildContextEntries` -> `buildSessionProjection` -> `AgentSession` request preparation -> agent loop `transformContext` -> `convertToLlm` -> `normalizeContext` -> `streamFunction` -> API-specific body builder/converter -> provider SDK/transport.

* JSONL session schema version is 3 (`P/packages/coding-agent/src/core/session-manager.ts:41`). Entries have IDs/parent IDs; compaction stores summary, first-kept ID, tokens-before, optional usage/details/system prompt checkpoint (`:91`). `_persist` appends JSON of one entry; initial flush writes all entries individually (`:1172`). `_appendEntry` also holds all raw entries and ID index in memory (`:1191`). This is append-only retention, not deletion of old summarized data.
* `loadEntriesFromFile` uses `StringDecoder` and a reusable read buffer, parsing complete lines and skipping malformed lines (`:627`). This avoids reading a whole archive as one giant JavaScript string. It nevertheless accumulates **every parsed entry in memory**, and `pending` still grows to the largest physical JSONL line. It also appends a missing trailing newline after valid header validation (`:661`), so merely calling it on a live source file would not be a strictly read-only probe; this audit did not call it.
* Branch path follows parent IDs, selects latest compaction on that path, emits newest checkpoint first, retained non-system entries from `firstKeptEntryId`, then entries after compaction (`:390`, `:476`). It excludes other branches and summarized history. Canonical projection applies latest retained `context_edit` per target; `replacement:null` omits an entry, older retained compaction entries contribute nothing (`:519`, `:543`). Custom metadata entries are not context, while custom messages and branch summaries can be (`:439`).
* `AgentSession._installAgentRequestProjection` rebuilds context from this projection, keeps callable implementations separate from message-declared provider tools, invokes prior preparation, then routes a virtual model and checks the routed model's context limit (`P/packages/coding-agent/src/core/agent-session.ts:787`). `_compactBeforeNextAssistantResponse` runs before the next continuation (`:776`, `:898`). Extension transforms can still alter messages later: agent loop transforms before conversion (`P/packages/agent/src/agent-loop.ts:381`). This means canonical projection counts are not a final wire-payload measurement.

### Tokens, usage anchors, output reserve

* Coding-agent defaults: enabled=true, reserve=16,384, keep-recent=20,000 (`P/packages/coding-agent/src/core/compaction/compaction.ts:126`). Trigger is strictly `contextTokens > contextWindow-reserveTokens` (`:267`). The estimate uses the last successful nonzero assistant usage plus estimates of trailing messages, otherwise sums estimates (`:148`, `:196`). Total prefers provider `totalTokens`, otherwise input+output+cache read+cache write (`:140`). This is current-context inference, not sum of all historical billed usage.
* Projection-aware estimation locates usage provenance and discards that anchor if a later context edit or compaction invalidates it, then counts the current system checkpoint and visible messages (`:227`). This directly avoids recurring compaction after keeping pre-compaction assistant messages whose original usage describes a larger prefix.
* Coding-agent fallback estimate uses `ceil(chars/4)`; tools include name + JSON args; images are fixed 4,800 “characters” regardless of image bytes, dimensions, number of patches or provider detail (`:276`, `:298`). The comment “conservative” is not universally true, particularly for non-English/code/token-dense text.
* Separate AI utility uses **chars/3.5**, fixed 4,800 chars/image, includes tool declarations in system messages, and selects usage by prefix timestamps (`P/packages/ai/src/utils/estimate.ts:15`, `:47`, `:75`, `:100`). This is not a calibrated tokenizer and is a separate formula from coding-agent compaction.
* `buildBaseOptions` clamps requested output to `contextWindow-estimatedContext-4096`, with minimum 1 (`P/packages/ai/src/api/simple-options.ts:15`, `:18`, `:36`). It prevents oversized output allocation but does not make an oversized input fit; it can still send a request with one output token. Thinking has separate shared-ceiling handling reserving 1,024 answer tokens (`:70`, `:88`). Responses later raises max_output_tokens to its own provider minimum and ChatGPT sign-in omits unsupported fields (`P/packages/ai/src/api/openai-responses.ts:328`, `:340`). Final admission must run after these adjustments.

### Compaction and recovery

* `prepareCompaction` operates on projected visible entries, finds newest active summary, finds valid cut points by walking backward to keep budget, and can split a long turn into a history summary plus a turn-prefix summary (`P/packages/coding-agent/src/core/compaction/compaction.ts:802`, `:872`). It never starts at a tool result; assistant call + following results remain together (`:351`, `:389`, `:446`). Keep budget is approximate: a giant latest call/result group can exceed it.
* Compactor serializes messages as text before asking the model, incorporates prior summary, strips protocol mechanics from summarization input, bounds summary output at 0.8*reserve (turn prefix 0.5*reserve), and rejects error, length-stopped summaries and tool calls (`:585`, `:696`, `:965`, `:1076`). Summary is not committed until generation finishes. Manual and auto paths share the default summarizer, permit extension cancellation/replacement, append a compaction checkpoint and refresh canonical context (`P/packages/coding-agent/src/core/agent-session.ts:2785`, `:3122`, `:3202`). No recursive chunked summarizer or aggregate-byte preflight was found here; an already huge summary prompt can itself overflow.
* Its summary serializer omits thinking/system/media and caps **each tool result at 2,000 characters**, preserving user/assistant visible text and tool arguments (`P/packages/coding-agent/src/core/compaction/utils.ts:94`, `:120`). Thus both summarization payload and retained replay tail can be much smaller than original archive, but unbounded user text/tool arguments remain a failure mode.
* Post-response check guards against wrong model, pre-compaction stale response, context edits and omitted attempt before trusting usage (`:2972`). Successful responses over context cause compact-without-retry; explicit context overflow/recoverable length causes persistent omission of failed attempt/tool results and **one** compact-and-retry (`:3028`, `:3044`, `:3066`). A second failure emits a terminal recovery error. Threshold compaction does not repeat the completed answer (`:3074`).
* Retry classifier handles overload/network/premature-stream errors; billing/quota/subscription limit phrases are excluded (`P/packages/ai/src/utils/retry.ts:7`, `:30`, `:192`, `:253`). Agent retry explicitly excludes context overflow (`P/packages/coding-agent/src/core/agent-session.ts:3734`), preserves failed raw attempt while omitting it from model projection (`:3811`). Summary retries reuse policy and disable cache writes (`P/packages/coding-agent/src/core/compaction/compaction.ts:619`).
* Overflow regex includes request_too_large as well as token overflow; bodyless HTTP400/413 is considered overflow only for Cerebras. Rate-limit phrases exclude overflow even if generic token wording matches. Silent overflow uses measured input+cache read, and a length stop with zero output at >=99% context is recognized (`P/packages/ai/src/utils/overflow.ts:42`, `:90`, `:171`). Arbitrary HTTP400 is not automatically fixable by compaction.

### Tool output and subagents

* Built-in read/bash previews default 2,000 lines/50KiB (`P/packages/coding-agent/src/core/tools/truncate.ts:10`). Head/trailing strategies respect UTF-8 bytes; a huge first read line returns empty with explicit too-large flag, bash tail can keep a partial last line. Bash `OutputAccumulator` switches from buffered raw chunks to a temp file after crossing preview limits and maintains a bounded rolling tail (`P/packages/coding-agent/src/core/tools/output-accumulator.ts:35`, `:64`, `:182`, `:239`). Full output is externalized; display context carries a preview and path (`P/packages/coding-agent/src/core/tools/bash.ts:342`). Structured bash result has a separate 1MiB cap (`:24`, `:390`), so “50KiB maximum everywhere” would be false.
* Output files live in OS temp, created with exclusive writes and mode 0600 (`P/packages/coding-agent/src/utils/output-files.ts:1`, `:21`). No fixed retention sweeper is defined in this file; retention is therefore not guaranteed by the preview path. User/tool retrieval must tolerate expired or cleaned temp paths. These built-in caps are not proof that arbitrary extension tools are bounded globally.
* Shipped coding-agent subagent is an **example extension**, not intrinsic parent-history inheritance. It launches a separate Pi JSON process with `--no-session`, supplied task/system prompt/model/tool selection, no parent's conversation message list (`P/packages/coding-agent/examples/extensions/subagent/index.ts:277`, `:300`, `:341`). It keeps complete child messages in tool `details` but model-facing `content` generally contains final assistant text (`:170`, `:324`, `:362`, `:689`). Parallel results are explicitly truncated per task and full output preserved in details (`:193`, `:670`); single/chain results lack that explicit per-task cap. Detail/history size can therefore be much larger than model-visible result size. No background wake contract is provided by this example.

## Pi durable harness: additional mechanisms, not the JSONL CLI path

Pi also ships `packages/durable`. This is a separate store/task state machine, not proof that the coding-agent CLI uses it.

* Context captures immutable head/tail bounds on serialized Session line; scans only head-to-tail range in pages of 256; caches and extends context when head unchanged, rebuilds on edits/head changes (`P/packages/durable/src/harness/context.ts:23`, `:67`, `:138`, `:234`). Latest head marker precedes retained range; error/aborted/deferred assistant outputs are omitted (`:9`, `:183`, `:251`). `orderToolResults` orders results immediately after issuing assistant, synthesizes missing results and drops unmatched results (`:259`). This is stronger balancing than coding-agent transform's missing-result fill alone.
* Generation prepares rendered system sections/tool changes before estimation; starts blocking compaction at context-reserve and optional earlier background compaction, only if cut exists; deduplicates background compaction (`P/packages/durable/src/harness/generation.ts:151`, `:168`, `:181`, `:322`). Before-request hooks still run after that selection (`:207`), so a final request gate remains useful.
* Compaction snapshots tail before requesting summary, rejects incomplete/error/tool-call/empty summary, stores usage and retry state durably, and admits background summary as a write submission at safe boundary (`P/packages/durable/src/harness/compaction.ts:150`, `:155`, `:262`, `:314`, `:332`, `:417`). Overflow recovery requires a successfully placed summary checkpoint and retries only once; transient retries preserve compacted marker (`P/packages/durable/src/harness/generation.ts:136`, `:489`). This is a useful concurrency/staleness model for IH, though the detailed durable subagent task/wake lifecycle was outside the completed trace and should not be inferred from the CLI example.
* Separate durable subagent **examples** illustrate more than CLI subprocesses. Foreground creates task-owned child, scans ownerTaskId to reuse after replay, inherits agent configuration rather than conversation history, submits with stable `subagent:<taskId>` request ID, waits and returns answer (`P/packages/durable/test/examples/22-subagent-foreground.ts:54`, `:57`, `:67`). Background creates a terminal anchor background task owning child, durable Reporter phases deliver then report, records reported answer EntryIds and deduplicates both child submission and parent report IDs (`P/packages/durable/test/examples/23-subagent-background.ts:61`, `:79`, `:90`, `:102`, `:111`, `:186`). Parent report is followUp input, starts parent when idle or waits after current answer; Esc drops a report already queued but a later report may start a new turn. This is example policy, not an implicit guarantee for every Pi host. ProviderDoc uses fresh identity for forks (`P/packages/durable/src/harness/provider.ts:11`).

## OpenCode: three paths must stay distinct

### Legacy session path (still default AI SDK execution)

`SessionPrompt.loop` -> `MessageV2.filterCompactedEffect` -> latest/tasks/threshold check -> resolve tools/system/plugins -> `MessageV2.toModelMessagesEffect` -> `LLM.Service.run` -> `LLMRequestPrep.prepare` -> `streamText` with middleware `ProviderTransform.message` -> installed AI SDK provider serializer.

* Persistent messages and parts are SQLite rows; message page query returns limit+1 and hydrate loads parts for selected IDs (`O/packages/opencode/src/session/message-v2.ts:98`, `:438`). `stream` pages backward 50 at a time, then accumulates **all history** before `filterCompacted` selects active context (`:482`, `:534`, `:587`). Thus pagination in this path improves database access but does not bound all-history memory. Completed summary requires summary+finish+no error; retained tail can be moved after summary for model consumption (`:554`, `:577`).
* Loop reloads filtered history, handles queued compaction, checks last-finished usage, runs model and creates compaction on processor result (`O/packages/opencode/src/session/prompt.ts:1092`, `:1149`, `:1164`, `:1262`, `:1321`). This is not the V2 SQL active-range loader described below.
* `toModelMessagesEffect` converts stored UI parts to AI SDK messages; skips failed assistant except meaningful aborted partial; converts pending/running calls to interrupted output errors; clears provider metadata on model switch; keeps a single-space separator around signed Anthropic reasoning (`O/packages/opencode/src/session/message-v2.ts:131`, `:254`, `:272`, `:362`, `:375`). Tool text may be replaced with `[Old tool result content cleared]`, preserving call/result shape (`:302`). Media is routed inside tool content for supporting provider/model combinations, otherwise injected into a separate user message (`:147`, `:311`, `:393`).
* `LLMRequestPrep.prepare` assembles agent/provider/user system, invokes plugins, merges provider/model/agent/variant options, sets maxOutputTokens, filters/sorts tools and sets strict:false for Responses-family SDKs (`O/packages/opencode/src/session/llm/request.ts:56`, `:91`, `:114`, `:148`, `:181`). OAuth moves system into `instructions` (`:99`). Plugin parameters may expand request after upstream estimates.
* LLM.run defaults to AI SDK and calls `streamText` with maxRetries=input.retries??0, explicit maxOutputTokens, prepared messages, provider options/tools and middleware (`O/packages/opencode/src/session/llm.ts:106`, `:224`, `:280`, `:320`). ProviderTransform applies media support, UTF-16 surrogate sanitization, empty/signed reasoning preservation, tool ID scrubbing, DeepSeek reasoning, interleaved fields, provider metadata remapping, and stateless Responses ID removal (`O/packages/opencode/src/provider/transform.ts:101`, `:168`, `:224`, `:253`, `:303`, `:465`, `:501`). This is actual pre-serializer mutation, so measuring stored messages is insufficient.
* **Limit of this offline evidence:** no node_modules is present. Installed SDK source lowering/transport could not be read without installing dependencies, prohibited by task. Lockfile/manifests and local patches certify selected dependency versions/changes, not complete external serializer behavior. Native serializers below are fully local source and were read. Do not present native byte shapes as proof of all default SDK requests.

### Legacy compaction, pruning, accounting and errors

* Usable budget: prefer model.input-reserved, otherwise model.context-maxOutputTokens. Reserved defaults min(20k, max output); count prefers total, otherwise input+output+cache read+write (`O/packages/opencode/src/session/overflow.ts:8`, `:10`, `:22`). `maxOutputTokens` caps at configured runtime outputTokenMax or catalog model output (`O/packages/opencode/src/provider/transform.ts:1481`). No learned provider/model tokenizer calibration found.
* Usage normalization clamps nonfinite/negative components, subtracts cached input from inclusive AI SDK v6 input, separates reasoning from output, stores SDK total (`O/packages/opencode/src/session/session.ts:338`). A caveat: overflow fallback component sum excludes separated reasoning when total absent (`overflow.ts:31` vs `session.ts:371`), potentially undercounting shared context.
* Legacy compaction keeps recent turns under budget by estimating JSON of converted model messages (chars/4); recent budget defaults clamp(25% usable, 2k,15k), tail_turns can bound selection and it can split a turn (`O/packages/opencode/src/session/compaction.ts:115`, `:140`, `:215`, `:223`). Tools are parts inside assistant messages, so splitting at message boundary does not split one tool part's call/result.
* Summary serialization truncates each tool output to **2,000 characters**, media becomes attachment labels, prior completed summaries update incrementally (`:30`, `:54`, `:97`, `:319`). Plugins can replace summary prompt or add context (`:372`). Runs a tools-disabled compaction agent through processor (`:358`, `:425`). If summary itself overflows, marks error and stops (`:450`); no divide-and-conquer fallback was found.
* Overflow compaction may set aside most recent real user turn and replay it afterward with media converted to labels, while newer synthetic continue text warns attachments were removed (`:340`, `:468`, `:527`). This can recover HTTP413 media bodies by actually removing bytes, but changes effective task inputs and must be visible to the user.
* Pruning runs only if cfg.compaction.prune truthy: skip last two user turns, protect latest 40k tool-output tokens, skip skill tool, stop at prior summary/already compacted part; only mark older results compacted when >20k reclaimed (`:271`). It sets time.compacted while retaining raw output, and projection replaces it. This preserves history without resending all older outputs.
* Legacy ProviderError treats **any HTTP413 as context_overflow**, or recognized body/message/code, while other HTTP400 stays API error (`O/packages/opencode/src/provider/error.ts:172`). SessionRetry excludes ContextOverflowError, retries 5xx/transient SDK/body text, max retries=5, exponential jitter, retry-after headers (`O/packages/opencode/src/session/retry.ts:26`, `:47`, `:85`, `:183`). This broad 413 mapping is a recovery tactic, not evidence the failure was token context.

### Tool bounds and retention

* Legacy `Tool.wrap` invokes truncator unless tool already declares metadata.truncated (`O/packages/opencode/src/tool/tool.ts:102`, `:131`). Explicit metadata is a bypass/trust boundary, not a universal enforced limit.
* Truncator defaults 2,000 lines/50KiB, returns head/tail preview + path to full file, independent line/UTF-8 byte cap, writes all text to managed directory (`O/packages/opencode/src/tool/truncate.ts:12`, `:85`, `:127`). Hints encourage scoped retrieval/delegation. Retention=7 days, cleanup hourly after initial delay (`:53`, `:143`). An oversized single line can yield empty preview; no partial-line fallback in legacy truncator.
* V2 `ToolOutputStore.bound` similarly bounds contextual text but retains full `structured` data durably and preserves media outside text cap; preview includes head+tail and marker **within** limits (`O/packages/core/src/tool-output-store.ts:13`, `:107`, `:135`, `:161`). `ToolOutput.toResultValue` prefers content, so retaining structured data does **not** automatically resend it (`O/packages/llm/src/schema/messages.ts:104`). Registry settlement calls bound before publication (`O/packages/core/src/tool/registry.ts:75`). Retention is 7 days, global hourly sweep (`tool-output-store.ts:176`, `:199`). ### Optional native adapter and V2 runner

* Legacy native gate is per request and feature flagged. It supports selected OpenAI/opencode/Anthropic IDs and SDK packages; OAuth requires provider fetch override and a configured key; unsupported cases fall back (`O/packages/opencode/src/session/llm/native-runtime.ts:48`, `:60`, `:73`; `llm.ts:226`). It applies same ProviderTransform then native lowers request, dispatches tools itself and yields shared LLMEvent (`native-runtime.ts:84`). Native adapter's tool-result conversion only explicitly handles text/error-text/json; richer AI SDK output shapes require careful testing (`O/packages/opencode/src/session/llm/native-request.ts:67`), and the gate is narrower than model()'s support list.
* Core V2 path: SessionRunner -> context epoch initialize/prepare -> SQL entriesForRunner -> canonical toLLMMessages -> request with system baseline/tools -> compactIfNeeded -> one llm.stream -> durable tool settlement -> reload before continuation (`O/packages/core/src/session/runner/llm.ts:173`, `:198`, `:200`, `:205`, `:224`, `:241`, `:405`). Durable prompt steering promotes only at safe provider-turn boundaries and resets agent steps; queued prompts promote after idle (`:187`, `:396`). Interrupted pending/running tools are failed before replay (`:119`, `:399`).
* V2 admission calls `SessionInput.admit` before advisory execution.wake unless resume=false (`O/packages/core/src/session.ts:360`, `:368`, `:382`). Process-global execution resolves Session location at drain start (`O/packages/core/src/session/execution/local.ts:12`). Coordinator has one active owner per Session key, `run` joins active Deferred, wake sets one pendingWake bit and may coalesce, settle starts a successor drain, interrupt clears pendingWake and interrupts owner (`O/packages/core/src/session/run-coordinator.ts:24`, `:51`, `:67`, `:81`, `:94`). These are process-local in-memory scheduling guarantees, not durable wake delivery or distributed ownership. Durable inbox admission is what survives process loss; absence of a repeated wake must not be confused with no pending work.
* V2 history queries only >= newest compaction sequence plus system updates newer than baseline (`O/packages/core/src/session/history.ts:13`, `:24`, `:66`, `:90`). Context epochs persist baseline+snapshot; after compaction replace baseline, otherwise reconcile differences as durable system updates (`O/packages/core/src/session/context-epoch.ts:40`, `:59`, `:72`, `:122`). This bounds request history independently of full database size.
* V2 assistant conversion retains provider metadata only for same model without error, converts foreign reasoning to text; local call/results are emitted separately, provider-executed call/results together; checkpoint becomes one user historical-context block (`O/packages/core/src/session/runner/to-llm-message.ts:70`, `:101`, `:147`). Managed/remote media URI materialization is TODO and unresolved URIs fail rather than being treated as bytes (`:41`).
* V2 compaction defaults buffer=20k, recent=8k, tool-output summary cap=2k chars, summary output=4096 (`O/packages/core/src/session/compaction.ts:12`). Admission estimate JSON of system/messages/tools -> chars/4, threshold context-max(output,buffer) (`:83`, `:232`). Summary prompt itself must fit context-summaryOutput or compaction returns false (`:178`, `:190`). This guard prevents a knowingly too-large summarizer but can allow original too-large request to proceed when compaction cannot help.
* **V2 recent is serialized text, not retained structured tail**: select serializes all non-compaction messages, chooses recent under token budget, summarizes head, publishes summary + recent text (`:95`, `:137`, `:222`). Next history projection wraps those two strings (`to-llm-message.ts:147`). Thus tool args/results/reasoning signatures/media in recent history are not retained as native protocol replay after V2 compaction. Useful size reduction but potential fidelity loss; do not copy if IH requires structured tail.
* V2 overflow recovery only before assistant starts and only recognized context-overflow; one retry after compaction, disabling further overflow recovery (`runner/llm.ts:240`, `:291`, `:364`). Automatic threshold compactions can recur without a progress guard; no hard post-compaction “must shrink/fit” assertion was found. Summary success checks error/nonempty text but does not explicitly reject length finish (`core/session/compaction.ts:199`); a truncated summary could be persisted, unlike Pi's explicit guard.

## Actual multi-protocol native serialization

### Pi

Common `transformMessages` downgrades images for nonvision models, normalizes cross-model call IDs, keeps signatures only when same provider/API/model, converts foreign reasoning text, removes error/aborted assistant messages, synthesizes missing tool results and holds system messages until tool flow closes (`P/packages/ai/src/api/transform-messages.ts:58`). It **does not** generally drop arbitrary unmatched tool result messages; durable harness does. Therefore corrupt hand-built histories still require validation.

* Responses: `convertResponsesMessages` emits `input_text/input_image(detail:auto,data URL)`, assistant output_text with IDs/phase, complete reasoning item parsed from thinkingSignature, function_call + output; item IDs removed on model/type mismatch and foreign IDs hashed (`P/packages/ai/src/api/openai-responses-shared.ts:81`, `:145`, `:255`, `:296`, `:332`). Request builder explicitly `store:false`, includes encrypted reasoning when enabled, sends tools and max_output_tokens (`P/packages/ai/src/api/openai-responses.ts:311`, `:330`, `:363`). No ordinary previous_response_id-only session replay is used in this traced path; client sends selected history again.
* Chat: tool calls under assistant.tool_calls, text in tool messages, image results lifted into user image messages after all contiguous results; compatibility bridges assistant after tool result, name fields, reasoning_content/reasoning_details and different max-token field conventions (`P/packages/ai/src/api/openai-completions.ts:1193`, `:1291`, `:1360`, `:1406`, `:842`). Images do not share Responses' explicit detail:auto field here.
* Anthropic: signed thinking/redacted opaque data preserved, unsigned thinking usually converted to text (compat allow-empty-signature exception); tool_use in assistant, contiguous tool_result blocks in one user message, images base64. System updates deferred so they cannot split call/results (`P/packages/ai/src/api/anthropic-messages.ts:1330`, `:1344`, `:1440`, `:1498`). Cache control on last eligible user/system block is cache behavior, not removal from model context (`:1519`).
* Gemini: leading systemInstruction, other system state collapsed; same provider/model valid base64 signatures preserved even for empty signed blocks; model calls carry functionCall; tool results functionResponse; Gemini3+ uses images nested in functionResponse.parts while older Gemini lifts image user turn, groups consecutive results (`P/packages/ai/src/api/google-shared.ts:149`, `:191`, `:228`, `:284`). Signature bytes are replay state; the fixed image/token heuristic and visible text lengths do not account for their serialized bytes.

### OpenCode native packages/llm

`LLMClient.compile` merges defaults/cache policy, protocol body.from, validates body schema, prepares transport. Route encodes schema to JSON; HTTP transport computes final bodyText, applies allowed non-protocol overlays, auth and headers, POSTs, then frames/decodes stream (`O/packages/llm/src/route/client.ts:167`, `:226`, `:344`; `O/packages/llm/src/route/transport/http.ts:73`, `:87`, `:126`). `LLMClient.prepare` exposes compiled body without sending (`client.ts:361`). This is a good preflight seam, but returned PreparedRequest omits final bodyText/byte count and transport overlays; a byte gate belongs after final bodyText construction too.

* Responses defaults store:false. Under store:false reasoning blocks merge by item ID and replay encrypted content without server IDs; reasoning without encrypted state is removed. Under store:true it emits item_reference for reasoning and provider-hosted tool results; local call/result remain full (`O/packages/llm/src/protocols/openai-responses.ts:283`, `:346`, `:389`, `:416`, `:446`, `:478`, `:991`). Media becomes native input_image/data URL, not JSON-encoded base64 as a text string (`:308`, `:325`). Detail is omitted in this native shape. References reduce wire bytes while still referencing server-side context: local serialized token heuristic cannot know referred content size.
* Chat flattens assistant text, puts reasoning in reasoning_content, calls under tool_calls, results in tool role; result images accumulate and flush as user content after contiguous tool results (`O/packages/llm/src/protocols/openai-chat.ts:231`, `:264`, `:293`, `:344`).
* Anthropic uses typed signed thinking and server tool calls/results in assistant content; local results user tool_result, four-breakpoint cache budgeting; rejects mid-history system updates splitting local call/result rather than silently reordering (`O/packages/llm/src/protocols/anthropic-messages.ts:402`, `:449`, `:473`, `:506`). Output max defaults to model/route output or4096, not shared-context clamped here (`:510`, `:546`).
* Gemini emits model parts with thoughtSignature on reasoning/calls, user functionResponse and separately inline media; context system is systemInstruction and later wrapped user updates (`O/packages/llm/src/protocols/gemini.ts:193`, `:205`, `:251`, `:302`). Unlike Pi converter, this native code does not preserve a text-part thought signature, explicitly insert function IDs, or nest Gemini3 multimodal functionResponse.parts. Treat these as differences requiring protocol-fixture evaluation, not blanket parity.
* Per-media native guard: max encoded28MiB/decoded20MiB, valid canonical base64 and mime allowlist (`O/packages/llm/src/protocols/shared.ts:162`, `:174`). This bounds one media value only. Multiple valid images + signatures + tool JSON can exceed provider body/proxy limits; **no aggregate byte admission was found** in compile or HTTP preparation.
* Native RequestExecutor retains redacted HTTP evidence, request ID, retry-after/rate limits; default status retry count=2, exponential jitter; InvalidRequest statuses400/404/409/413/422 only classified context-overflow when body regex matches (`O/packages/llm/src/route/executor.ts:36`, `:225`, `:277`, `:345`). Therefore native 413 without recognized body differs from legacy all413 compaction. Error classifier excludes rate limits from token overflow (`O/packages/llm/src/provider-error.ts:4`). Native transport retries happen before session recovery and must be included in a total retry budget.

## Recommendations for IH, ordered

1. **P0: define three observables and one immutable request artifact.** Archive bytes/row count; active semantic projection estimate; exact final serialized body bytes plus provider-token report. Persist provenance mapping from selected entries to request items and hash of final payload shape (exclude credentials). Measure final body after images/base64, signatures, JSON escaping, tool schemas, plugin transforms, provider refs, output max and HTTP overlay. Do not log raw sensitive content by default.
2. **P0: admit a prepared request by both token and byte budgets.** Differentiate context tokens, max input/output, answer/reasoning reserve, per-image bytes, aggregate body bytes, and runtime serialization/memory limits. Tokenize known protocol text where possible; calibrated conservative fallback for unknown model. Provider cached-input still consumes context. Server references need a logical token estimate even when wire bytes are tiny. Unknown limits should be explicit model/provider capabilities, not silently zero/unlimited.
3. **P0: archive-preserving projection with stable IDs and epochs.** Port the principle of Pi projection/context edits and OpenCode active SQL range; retain raw messages/tool outputs for UI/audit. Invalidate provider usage calibration when system/tool/model/selection epoch changes. Keep measurement tied to exact request fingerprint; avoid timestamp-only validity for mutable prefixes.
4. **P0: protocol-valid call/result groups before/after compaction.** Atomic call/result retention, interrupted-call error settlement, drop or quarantine unmatched results, cross-model metadata rules. Add final structural validation for each protocol; a400 caused by missing result/signature must not trigger blind summarization.
5. **P1: typed recovery actions.** Classify token overflow, request-byte/media overflow, schema/signature/pairing invalidity, transient transport/overload, quota/auth. Compact/reselect for context; externalize/downsample/drop media only with explicit task consequence for bytes; repair replay or stop for schema; retry same payload only for transient failures. One bounded recovery with required request change and shrink/fit evidence; count lower-level and session retries together.
6. **P1: tool/child return budgets at ingress.** Bound text preview centrally, store full content and structured data externally/durably, preserve a retrievable stable reference and checksum. Text caps must include hint markers, UTF-8 and single giant lines. Include attachment aggregate limits and child result caps for single/parallel/background, not only common built-ins. Separate child transcript/detail retention from parent-visible final summary.
7. **P1: compaction admission and progress contract.** Check summarizer request itself before sending; chunk/reduce locally or hierarchically if needed. Reject length-stopped or empty/tool-calling summaries. Commit checkpoint atomically only against captured epoch/head/tail, and reprepare after concurrent user/child/system updates. If no useful cut/shrink, surface an actionable error instead of repeated threshold compaction or unchanged oversized request.
8. **P2: optimize large archive traversal independently.** Pi JSONL streaming still builds all entries; legacy OpenCode pages then hydrates all history. Prefer indexed active-range retrieval, paginated UI history, lazy external blobs and incremental projection. This is how100MB archives become routine without raising request limits.

## Unresolved questions and validation limits

* IH's actual failing provider400 body/status, transport route, final body bytes, model context/output limits and exact replay group are needed to attribute its incident; this audit does not diagnose IH source. “Send too large” could mean local IPC/string/frame/body limit, gateway limit, input tokens, media bytes or malformed serialization.
* No empirical100MB archive load or request was run. Source proves selection mechanisms, not a tested maximum archive size, memory profile or provider guarantee.
* Default OpenCode external AI SDK serialization and SDK transport code were unavailable offline; native local protocol source and integration boundary were audited. No dependency install was authorized. Some local patches/AGENTS describe behavior that differs from source; source-specific claims should retain path citations.
* Full Pi durable scheduler/storage crash recovery was not exhaustively audited; foreground/background examples and OpenCode core SessionExecution coordinator were read. Verified foreground/background legacy Task behavior: creates/resumes independent child session, passes supplied prompt, returns last text; background completion injects a synthetic parent prompt (`O/packages/opencode/src/tool/task.ts:136`, `:200`, `:227`, `:256`, `:328`). It does not copy parent history. Persisted admission identity/retry-conflict policy should be reviewed separately before transferring to IH.
* Native OpenCode local media URI TODO, richer legacy->native tool result shape mapping, Gemini3 signature/media differences, V2 summary length-stop acceptance and no-progress auto-compaction are concrete areas for focused offline fixtures, not reasons to copy the entire architecture.
