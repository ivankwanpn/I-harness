# Unified format addendum: DSH, ZCode and IH

2026-10-15; read-only source inspection. No provider requests or product changes. DSH is the extracted `0.2.1-alpha.3` copy, ZCode root `3.14.0` / CLI `0.16.9`; neither has `.git`. IH comparison uses the current source files, with root audit owning baseline `81bca938`.

**The hypothesis that only IH normalizes multiple protocols into a unified format is contradicted by both references.** DSH has its own unified durable messages/blocks and then converts them to either direct DeepSeek wire or a second common pi-ai Context. ZCode has unified runtime/model contracts and converts them to the AI SDK's common messages before protocol serialization. IH similarly has a common `LLMMessage` plus protocol continuation sidecars. The meaningful differences are information preserved, compatibility checks, active-context projection and where protocol-specific work is owned.

Path abbreviations: `DSH/` = `D:/ih_reference_project/deepseek-harness-dsh-v0.2.1-alpha.3/`; `ZC/` = `D:/ih_reference_project/ZCode-main/`; `IH/` = `D:/I-harness-main/`. All citations are exact source paths and line numbers after expanding those prefixes.

## DSH is explicitly a common format over multiple providers

`DSH/packages/llm/llm/src/message.ts:9-20` defines assistant provider/model attribution plus adapter-private replay state. `:138-196` defines the common immutable durable role union. `types.ts:61-150` defines neutral blocks. `:448-460` defines opaque response/per-block replay halves; `:470-482` defines the neutral stream protocol. Every provider response is assembled to these blocks; provider wire JSON is not the canonical session format.

`DSH/packages/llm/llm/src/assembler.ts:49-95,130-149` maintains first-seen block order, takes block-end as authoritative, and applies one shared keep/drop decision to content and replay metadata. A max-token finish drops unsafe tool calls and their matching metadata; inconsistent replay block count discards the envelope. This is a concrete fidelity mechanism beyond merely saving a raw metadata object.

At the final common LLM boundary, `llm/src/index.ts:1096-1118` projects files to handle text, images for text-only models, and tool updates according to declared route capabilities. `forAdapter (:1022-1036)` strips historical replay state if that historical provider is no longer owned by the target adapter instance. It leaves neutral text/reasoning/calls and source identity intact and leaves the durable log untouched. The condition is adapter ownership, not simply equal provider-name strings. Same adapter owning several routes can receive replay for those histories and apply native compatibility rules itself.

The direct DeepSeek adapter serializes these common messages into Anthropic-style Messages (`llm-deepseek/src/serialize.ts:57-168`). Native thinking signature state is `{response:{kind:'deepseek-messages',version:1,model},blocks:[type,signature?]}` (`replay.ts:7-30`). Replay checks envelope kind/version, source-model agreement, count/type alignment and signature type; cross-target-model signatures are omitted (`:39-64`). Invalid state emits a degradation diagnostic and sends neutral content without those signatures. This adapter does not store all original provider blocks verbatim; canonical text is authoritative and only minimal native thinking metadata is retained.

### The full pi-ai route is a second normalization layer

`DSH/packages/llm/llm-pi-ai/src/provider.ts:47-50` explicitly maps custom routes to pi-ai OpenAI Completions, OpenAI Responses and Anthropic Messages implementations. `buildProvider (:167-191)` reuses catalog providers when no protocol override is declared; it delegates both stream methods to the catalog object (`:144-158`). Thus the three custom protocols do **not** define the complete protocol breadth. Catalog-native Bedrock/Azure/Codex/other providers can retain their own auth/dispatch implementations. The comments at `:29-45` explain why custom overrides intentionally do not offer protocols requiring credential/project/region parameters this config cannot express.

`llm-pi-ai/src/models.ts:75-91` maps exact model compatibility flags into supported mid-conversation system/tool-update modes, including Anthropic, OpenAI Completions, OpenAI Responses/Azure/Codex Responses. Protocol repointing does not blindly inherit the old protocol's compatibility flags (`catalog.ts:800-826`).

`llm-pi-ai/src/adapter.ts:344-425` freezes model/profile/provider collection for the request, converts common history with `toPiContext`, then invokes `snapshot.models.streamSimple(model,context,options)`. This is common DSH message → common pi-ai message → native protocol, not a bypass around the unified format.

`context.ts:148-167,170-255` splits leading system messages into pi-ai systemPrompt, maps developer changes to pi-ai system updates, reconstructs assistant history, recovers tool result names from call IDs and turns DSH tool role into pi-ai toolResult. Image path `:330-374` resolves normalized bytes, checks exact base64 byte budget, replaces offloaded occurrences with handles and maps retained images to pi-ai image content. Unsupported assistant/system images are refused (`:49-64`); generic unsupported user block families are skipped (`:67-98`). Therefore normalization has explicit limits; extensible canonical blocks do not imply every provider can consume each block.

`llm-pi-ai/src/replay.ts:15-40,77-109` retains a version-2 envelope containing API, provider, requested model, optional response model/ID/thinking level, native stop reason and aligned metadata: textSignature, thinkingSignature/redacted, tool thoughtSignature/namespace. It deliberately avoids duplicating canonical text/tool calls. `replayedAssistant (:187-231)` checks source identity and block alignment, reconstructs pi-ai native common blocks and restores those fields. `toPiAssistant (:247-258)` degrades wrong-kind/version/malformed/stale metadata to foreign history; `foreignAssistant (:152-183)` sets `api:'dsh-foreign'`, converts canonical reasoning to unsigned thinking, preserves text/calls and rejects assistant images.

Crucial limit: the DSH bridge does **not** itself compare reconstructed historical API/provider/model with the new target in `toPiAssistant`; it passes native history identity to pi-ai, which then owns protocol compatibility. DSH's manifest imports pi-ai **1.1.0**, while the separate reference checkout is pi **1.2.0**. The local 1.1.0 patch only removes repeated partial-JSON reparsing across stream implementations. That patch is not complete dependency source, so this addendum does not claim the 1.2.0 downstream transform is exactly what DSH executes. Verified DSH behavior is the ownership filter, validated envelope/foreign degradation and pass-through of native identity; precise downstream cross-model signature dropping needs the installed 1.1.0 implementation or version-matched test.

`stream.ts:142-233` maps pi-ai events back into DSH blocks/usage/finish; successful finish carries replay state, failures carry normalized terminal failure. It JSON.stringify's pi-ai parsed final tool args (`:194-205`): the durable result is semantic JSON, not guaranteed original argument whitespace or byte spelling. Comments at `:34-41` acknowledge upstream error causes were flattened, requiring text-based classification. Multiple protocol support has costs even with a common schema.

## ZCode also uses a common format, with different replay tradeoffs

`ZC/apps/zcode-cli/packages/contracts/src/model/index.ts:320-412` declares neutral roles, parsed tool calls, media blocks, reasoning with opaque providerOptions, and common ModelInputMessage. `core/src/agent/message-history.ts:26-66` adds canonical runtime metadata/usage and attachments. `:179-205` constructs assistant content from reasoning blocks followed by visible text; `:350-376` repeats this factory pattern. Common assistant tool calls are separate, so provider transform later appends calls after content (`adapters/src/model/transform.ts:266-290`). Exact original interleaving of text/tool/reasoning is thereby reconstructed into a canonical order, unlike DSH's one ordered block sequence and IH's explicit block-order sidecar.

Metadata preservation is intentional: `adapters/src/model/runner-normalization.ts:42-59` turns SDK reasoning providerMetadata into common reasoning.providerOptions. Streaming maps it on reasoning start/delta/end (`:88-109`); core updates those fields and persists reasoning parts with metadata (`core/src/runtime/methods/model.ts:278-320`; `turn-model-step.ts:551-560`). Cold hydration maps persisted part metadata back (`agent/session-history-hydrator.ts:562-575`). This supports signed/redacted Anthropic replay without storing all raw provider response blocks.

`adapters/src/model/transform.ts:46-155` turns common messages into AI SDK messages, validates tool identity and projects tool media after the complete sibling result run. `:292-332` maps reasoning with providerOptions; assistant media become text. Request model execution selects OpenAI Responses, Anthropic or OpenAI-compatible factory (`model-execution.ts:281-310`), and option-map fetch can patch final protocol JSON (`model-option-map-fetch.ts:19-30`). Native transport remains provider-specific despite the common interfaces.

Cross-model cleanup is explicit but scoped. `adapters/src/model/runner.ts:358-372` runs `normalizeReasoningHistory` once at logical request entry only for target provider kind Anthropic. `reasoning-history-normalization.ts:94-120` removes signed/redacted reasoning when historical known model/provider differs, allowing configured compatible provider-ID groups; missing historical identity does not trigger removal. The criterion `isSignedOrRedactedReasoning (:267-272)` examines Anthropic.signature/redactedData. Ordinary unsigned reasoning is not blanket removed by that pass. Other passes remove reasoning-only assistants, trailing reasoning and whitespace-only assistants or repair empty content (`:31-40,145-208`). These are request-local copies, not canonical history deletion.

On a narrowly recognized HTTP 400 thinking-signature rejection it removes signed/redacted reasoning from the projected request and retries once (`:64-91`; runner-generate/stream signature-repair paths). This is recovery by changing replay input, not evidence that all signatures are universally portable.

For Anthropic, serializer helper preserves existing signature/redacted metadata and adds `signature:''` for retained unsigned thinking (`anthropic-reasoning-metadata.ts:10-34`). For non-Anthropic kinds it forwards providerOptions. OpenAI Responses has its own stateless rule: when no previousResponseId/conversation and store is not false, reasoning blocks carrying openai.itemId are omitted at SDK transform (`transform.ts:300-307,335-377`) to avoid invalid item-reference replay. Thus “providerOptions retained” does not imply “same raw native state always replayed”. There is no corresponding general Gemini/Bedrock continuation union in the inspected ZCode model contract; SDK/provider support and DSH catalog breadth must not be imported as claims about ZCode.

Tool call normalization retains ID/name/input/providerExecuted, not arbitrary native metadata (`runner-normalization.ts:173-210`; contract `model/index.ts:322-327`). Some tool-result/finish metadata remains separate (`:213-253`), but it is not a general call-block replay envelope. Raw chunks may be observed for diagnostics/compact commitment; the neutral stream converter drops unmapped variants (`:62-169`). Unknown native blocks should therefore not be assumed losslessly preserved.

## Compactors act on typed history, then use ordinary provider adaptation

DSH `compaction-basic/src/region.ts:544-562` builds SummarizationInput from derived neutral system head/current span and request-header tools. `summarizer.ts:120-180` appends an identity-free final user directive to those typed messages and calls common `ctx.llm.stream`. The same per-route projection and native replay rules then run. It does not compact raw Messages/Responses JSON. Replacement is a text-only user checkpoint; native metadata of shadowed assistant messages remains in archive but leaves active surface.

ZCode selects common RuntimeMessageEntry groups, retains recent entries, and builds summary request through `buildProviderRequestMessages` (`runtime/methods/compact-active.ts:183-199,309-363`; `compact-active-helpers.ts:80-90`). Common media projection and the ordinary Model adapter follow. It similarly does not manipulate raw SDK HTTP request JSON. Preserved history remains typed; original provider token baselines are invalidated for preserved assistants because they described the old prefix (`agent/message-history.ts:426-441`).

IH also has a common compactor: `IH/packages/compaction/src/summarizer.ts:205-250` accepts typed prefix messages and appends a directive to LLMRequest. For distinct summary bindings it instead builds a text projection preserving call semantics/image descriptors while excluding foreign signed continuation/base64 (`:214-231`); native prefix replay and cross-binding text summarization are deliberately different paths. Consequently all three architectures need to reconcile compaction with native replay compatibility. Changing the common format alone does not remove this obligation.

## Concrete implication for IH

`IH/packages/core-session/src/projection/types.ts:1-29` already preserves more explicit protocol continuation variants than the inspected ZCode schema: Anthropic order/prefix fingerprint/tool bindings, Responses raw reasoning items/output order, Gemini call/thought/text signatures/bindings and Bedrock signed/redacted reasoning. `IH/packages/llm-seam/src/index.ts:88-125` checks source model/provider and validates block order against canonical text and complete reasoning/tool coverage. `IH/packages/llm-anthropic/src/request/messages.ts:23-68` additionally checks prefix fingerprint/tool bindings and invalidates a thinking chain after prefix changes. Those checks are a substantive capability, not evidence that IH is uniquely burdened by a unified schema. Legacy missing provenance remains accepted by canReplayContinuation, which must be understood in any redesign.

A useful redesign target is **typed semantic history plus adapter-owned, versioned replay metadata and a single final request projection**. Preserve exact ordered semantic blocks where ordering matters, namespace native state, validate it against route and content generation, and explicitly degrade or reject incompatible replay. Record what was omitted. Keep compaction over typed semantic history and final wire measurement after provider serialization. DSH offers a strong example of adapter opacity plus aligned metadata; IH offers stronger explicit binding checks in its Anthropic path; ZCode shows practical SDK metadata preservation but also order reconstruction and provider-specific cleanup. There is no source basis for replacing IH's common representation merely because other agents support more protocols.

Unverified: version-matched pi-ai 1.1.0 cross-protocol implementation, actual provider acceptance of repaired signatures, exact token effects and behavior on the user's large logs. No dependency install or live probe was performed to fill those gaps.
