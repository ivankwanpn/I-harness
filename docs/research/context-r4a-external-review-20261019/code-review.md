## Findings

### 1. [P1] Validate the task publication schema that the task owner actually persists

**New regression.** `packages/subagent/src/task/validation.ts:15` now calls `validResultPublication(task)`. That shared validator is the state/job schema: `packages/subagent/src/result-publication.ts:17` rejects every saved-observation key except `status` and `execution`. The actual task owner deliberately writes `{ status, outcome, execution? }` in `packages/subagent/src/task/publication.ts:9`; the task type also requires `savedObservation.outcome` (`task/types.ts:32`).

Trigger: retain a real terminal v2 task, cold-restore it, and save that registry. The first restore creates its real saved observation; a subsequent restore throws `Unsupported retained task publication metadata`, whether the original parent F1 fact was committed or absent. Qualification also leaves this observation on the committed row, so successful cold recovery is affected. A persisted task document can consequently prevent a later assembly from restoring its task registry. This is reachable with owner-produced JSON, without fabricated accessors or arbitrary non-schema objects. The submitted no-owner test stops after its first resave, and the cold tests stop after their first restore.

Correction boundary: validate the closed task observation with the actual task status/outcome domain, preserve and validate `outcome`, and retain the state/job domain at its existing owner. Add genuine restore/save/restore controls for both committed and unqualified task rows, including cancellation. A broad relaxation of state validation would not preserve either closed schema.

Confirmed by root's sequential `task-roundtrip-probe-v2`: **2/2 tests fail at the second restore**, for both `committed=false` and `committed=true`. Its stdout records the genuine saved observation with `outcome: completed`, then the expected no-throw assertion fails with the production publication error. Probe: `task-roundtrip.probe.test.ts`, derived from the actual `retained-task-cold.test.ts` fixture and using the real coordinator/store/registry. Receipt and raw output: `root-runs/task-roundtrip-probe-v2.json` and `.stdout.txt`/`.stderr.txt`.

### 2. [P1] Register the settled native dependency with the actual output observer

In addition, `packages/exec/src/jobs/records.ts:24` returns its one permanently cached observation promise, so `getOutput`/`listJobs` never even invoke observation registration again after automatic completion.

Trigger: start a background shell command, allow startup to return before EOF, let passive completion store its frame artifact, then read it through shipping `job_output`. The startup envelope already took its dependency snapshot at `session-executor/src/lifecycle/result-retention.ts:38`, before EOF and automatic registration. The output query uses a different genuine prepared `ToolExec`. Its native dependency is never registered, and `subagent/src/tools/status.ts:79` exposes only stdout/status from the exec view, dropping the new `retained` field. Thus neither durable tool envelope contains the frame dependency catalog; the only new reference is the live internal `BackgroundJobView.retained`. After restart it is undiscoverable through that actual result, and the model's output observation is a truncated preview without the retained full native source. The prior observe path registered the current querying producer.

The captured `targets` also fixes the target to the original binding session, which must equal the original execution owner at begin; it cannot implement the earlier current-observer grant when an authorized different owner observes the source. This is the same incorrect association boundary, not a separate speculative security finding.

### 3. [P1] Do not permanently memoize an uncertain settlement as a completed void operation

**New regression.** `packages/exec/src/jobs/records.ts:24-40` stores `Promise<void>` forever even when `owner.observe` returns `recovery-required` or rejects. `registerJob` additionally stores that same finished promise at line 66. Later explicit output queries and disposal reuse it.

Trigger: the original native frame sink's first `finish`/write reconciliation is unknown, then becomes resolvable. `output-retention/src/result/exec-frames.ts:36-48` intentionally does not cache a recovery-required result; the same original capture can reconcile on its next settle. The new job wrapper prevents every later allowed query/list/close path from making that retry. It instead permanently exposes `retentionFailure: recovery-required`, and close joins a successfully resolved void promise while the artifact remains uncertain. This is an inability to retry existing original work, not a request to add an automatic retry policy or replay the producer.

Correction boundary: coalesce only in-flight settlement, keep the original recoverable handle, and preserve a settled cache only for confirmed ready/known-refusal outcomes. On authorized observation or close, retry the same capture/operation after uncertainty and clear stale failure state after actual success. Required original source/close handling must remain active until that work settles; catching it into a void promise is not a settlement receipt.

Confirmed by root's sequential `background-retry-probe-v2`: **1/1 test fails**, with `launches: 1`, `apiAttempts: 1` and `apiObservations: 1` after queries/list/dispose. A direct retry of the **same original capture** calls finish a second time and returns `ready` with the known `unavailable/storage-refused` disposition. This proves recoverable settlement classification without another launch; it does **not** prove artifact publication success after a cut. Probe: `background-retry.probe.test.ts`, based on the real exec controlled backend pattern and using actual `createExecFrameCapture`. Receipt and raw output: `root-runs/background-retry-probe-v2.json` and `.stdout.txt`/`.stderr.txt`.

### 4. [P2] Treat the real unsupported store adapter as unavailable during restored retention qualification

**Inherited unaccepted WIP behavior left unresolved by the submitted A1 fix.** `packages/subagent/src/task/registry.ts:253` passes `Boolean(resultOwner)` to the new `restoredRetention` helper. A `TaskResultOwner` existing proves only that a `TaskResultStore` object was supplied. Shipping assembly always supplies `createTaskResultRetention(opts.contextOutput, ...)` (`assembly.ts:1238`, also 1378/1434), including the explicitly supported custom/unsupported coordinator path where `acquireAssemblyResultStore` returns `service: undefined` (`lifecycle/result-store.ts:23`). That factory still returns the adapter, but its `read` immediately throws `Task result owner unavailable` (`lifecycle/task-result-retention.ts:54-56`).

Trigger: restore an artifact-backed v2 task in this actual unsupported-store composition. It is still marked `durable` although the adapter cannot read it. The same issue is reachable with a normal JSONL coordinator if current context-output configuration fails to load: `result-store.ts:27-28` also returns an undefined service, while assembly supplies the nonempty adapter. The new test omits `results` entirely, so it verifies a different composition and does not close the stated no-store/unsupported-owner obligation. This is a source-traced actual API contract gap; no runtime probe was executed for this fourth branch in this review.

Correction boundary: expose/check the adapter's real retained-body read capability or compose an absent reader when the durable service is unavailable, while retaining the v2 descriptor and original result revision. Do not infer durable readability from the wrapper object's presence. Current ACL failure remains a separate read authorization result and should not erase the original stored descriptor.
