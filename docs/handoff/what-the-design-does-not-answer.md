# What the design does not answer — recorded, not papered over

Written 2026-09-15 by the controller, near the end of the goal, because the goal's own constraint says: *"record honestly anything the design does not answer rather than papering over it."* This is that record. It is deliberately split by **category**, because "unanswered" has three very different meanings here: a question still open, a question that got answered during the work, and a question nobody asked until the code made it visible.

**Where this lives:** tracked in the repo at `docs/handoff/`, alongside `HANDOFF.md` (the takeover guide) and `FINAL-REPORT.md` (the closed goal). Section labels are local to this file — `C9`–`C12` here are **not** the same items as the final-review plan's `C1`–`C8`, and `D1`–`D6` here are **not** that plan's documentation items of the same name. Cross-references elsewhere name the item, not the label.

## A. Still open — the design's own §7, and only one item survived

**A1. Should IH have project-level settings trust?** (spec §7, last item.) grok has a definite answer (`build-provenance-folder-trust-gate`); IH's `settings` is user-level only. The design says it lacks enough information to judge, and **nothing in this goal supplied it**. This is a product-positioning question — *who is allowed to change behaviour for a repository: the person who cloned it, or the person who wrote it?* — and it is the one item in §7 that remains genuinely unanswered. Nothing in this work depends on it, and nothing in this work should be read as having settled it.

## B. Answered during the work — listed because "unanswered" should not be claimed for these

**B1. 3.1's performance (spec §7 item 1) — ANSWERED, and this entry was WRONG TWICE before the review caught it.** The conclusion survives; both supporting claims I wrote here did not.

*First error — the number.* I recorded **0.056–0.125 ms** per resolve over a 20k-event session against a 0.5 ms budget. The final review could not reproduce it (Scope A A-7, Scope C F4; spec §7 corrected). It was a one-off measurement whose machine and warm-up state nobody recorded, and **it must not be quoted as though it were a benchmark**. What is still true and is the actual answer: the per-call resolve is far enough inside the budget that **no cache and no invalidation rule were added**, and adding either would have been inventing a mechanism for a requirement that does not exist.

*Second error — the mechanism.* I attributed the residual cost to the **O(n) `slice`** of the event array (`assembly.ts:336-337`). Scope C measured the slice at **~0.0013 ms** and identified the **scan** as the real cost. So "linear in session length by construction" is right; my reason for it was wrong.

*What is still true, stated so it bounds the answer rather than decorating it:* cost is linear in session length by construction; **nothing was measured above 20k events**; and **IH has no benchmarking harness** (dsh does), so even the surviving conclusion rests on one-off measurement rather than on a CI assertion that would catch a regression.

**B2. Terminal product impact (spec §7 item 2) — ANSWERED, and the original fear was wrong.** "The TUI's PTY feature disappears under a confined mode" was corrected on 2026-09-15: `node-pty` is a **devDependency** of `tui`/`tui-core` (test harness only), and `packages/tui/src` opens editors/pagers through ordinary `child_process.spawn`. **The TUI does not use a PTY.** The only production PTY consumer is `packages/terminal`, so the decision's blast radius is "can the model open a PTY", not a product feature.

**B3. `fs-search` and ripgrep (spec §7 item 3) — ANSWERED by ruling out a change.** Behaviourally verified on the binary `fs-search` actually resolves (`@vscode/ripgrep@1.18.0` → ripgrep **15.0.0**): `--replace BYE` rewrites stdout while leaving the file byte-identical, `--output` is unrecognised, and of 145 listed flags only `--files-without-match` matches `write|output|out`. Routing `rg` through the runner would confine nothing while breaking two working read-only tools. **The revisit condition is written down** (when §3.5 acquires a concrete input), and the consequence — does the spawn need a runner for cwd/env/timeout/kill-tree? — is left for the final review rather than closed by this ruling.

**B4. Read isolation (goal step 5) — ANSWERED "do not build", with its precondition recorded as a concrete seam.** IH has no input that names paths; grok can deny reads only because an enterprise policy enumerates them, and inventing a default list (`~/.ssh`, `*.env`) would be *my* guess at someone else's threat model shipped as a security claim. **The precondition that flips this: a host that supplies a concrete path list** (project config, an org policy file, or a `--deny-read` surface) — and spec §3.5 now names the seam that would have to exist rather than leaving it as "wait for an answer": a `denyRead?: readonly string[]` field that `SandboxExecutionPolicy` does **not** have today, plus a backend that declares `capabilities.readIsolation: true`, which **no backend does** (bwrap and the local dispatcher say `false` explicitly; `sandbox-windows-acl` omits the declaration entirely). The harder fact §3.5 now records: this is not "unwired", it is **unimplemented** — `requireReadIsolation: true` currently makes every confined call throw. This is a decision, not an omission — but it is also **not built**, and the report must not read as though read hiding exists.

## C. Discovered during implementation — questions the design never asked, now on the record

**C1. Deferred minor #3 is TWO-AXIS, and only one axis was known.** The known axis was the code duality (`FS_SANDBOX_DENIED` on the tool result vs `SANDBOX_DENIED` on the shared denial). Task B found the second: on the fs surface the same `SandboxDenial` is **encoded** two ways — JSON inside `error` (guard path, deliberately byte-identical for three existing parse-back tests) and a structured `denial` field (ladder path). Its own assembly-test helper had to branch on the encoding. **A model keying on `code` still meets two vocabularies**, which is the thing spec §3.2 exists to prevent.

**C2. The `reason + escalation` message helper now exists TWICE** — `denialMessage` in `packages/fs/src/index.ts` and `messageFor` in `packages/terminal/src/tool.ts` — because `denial.ts`/`call-policy.ts` were outside Task B's file list, so it flagged the duplication instead of merging it. Nothing pins the two as equivalent. **This is a "two places for one rule" pattern**, and drift between them would be silent.

**C3. No assembly-level end-to-end test exists for the shell or terminal ladders.** Task B's four end-to-end cases cover **fs** (`sandbox-escalation.test.ts`). The shell and terminal ladders are unit-tested against real service/exec spies, not driven through a real assembly turn. The declared reason is scope; the consequence is that a wiring break specific to those two surfaces' *assembly* path would be caught by the schema test and the unit tests, not by an end-to-end one.

**C4. The `sandboxPolicy` second read.** The ladder reads the policy through `deps.sandboxPolicy()` while the fs guard closes over the assembly's `sandboxPolicyNow` — the same thunk, so the same events, read **twice per call**. Correct today because nothing appends a `sandbox/mode` event mid-call; if a producer ever appeared between the two reads, the ladder would escalate FROM one mode while the guard CHECKS under another. A latent boundary, not a defect.

**C5. The once-per-call property has no STRUCTURAL guard — but it is not unguarded, and my first version of this entry said it would fail open "silently", which the review falsified.** `packages/fs/src/patch.ts` is untouched and its callback is still typed `void`-returning, so a refactor that `await`s inside `guardWrite` would compile clean. I wrote that the tests "would catch the behaviour change only if the refactor also changed the prompt count". **The reviewer tested it instead of reasoning about it, and both variants redden loudly:** the per-hunk-ask refactor makes the one-ask test fail with `expected [...] to have a length of 1 but got 6` (1 outer + 5 hunks), and the non-awaited-async variant reddens `apply_patch DENIES a hunk that resolves outside the workspace` **and reports an unhandled rejection**. So: no structural guard, a two-test behavioural net, and **corrected from "silent" to "caught"** — the hazard is real; the claim that nothing would notice was mine and wrong.

**C6. On the shell, escalation is reachable only if the MODEL chooses to retry.** The shell has no pre-call "mode too narrow" refusal: the OS backend denies at runtime and the refusal is a runner-failure fact in `stderr`. So the ladder is reached by a model that reads the denial text and passes the arguments — which is the designed choreography (dsh behaves the same way) but means a model that does not retry gets nothing, and nothing in IH prompts it.

**C7. `apply_patch`'s approval subject is the path as the PATCH writes it**, so it can be relative or forward-slashed, unlike `write`/`edit`, whose subject is the resolved absolute target. Deliberate: resolving a hunk path up front would make `resolvePath` throw on an escaping relative path and turn one hunk's error entry into a whole-call failure. The trade is a less canonical subject in the prompt, taken to preserve the patch tool's per-hunk error model.

**C8. On an `approveAll` host, every model-requested escalation is granted without a prompt.** Not a hole — `approveAll` already means "do not ask me anything", so the ladder inherits the host's own standing decision — and the real hole (no channel at all) fails closed. Recorded because a reader running `--approve-all` with a confined mode should be told that they have also handed over *widening the sandbox mode*, rather than discovering it. **Being written into spec §3.3 point 2 as part of the same docs commit that fixes the plan's surviving pre-redesign sentence.**

**C9. The two denial markers are DEAD CODE, and one of them carries a sentence the shipped text deliberately does not.** `sandboxDenialMarker` and `escalationHintMarker` (`sandbox/src/escalation.ts:27`, `:31`) are re-exported (`sandbox/src/index.ts:79-80`) and pinned by `sandbox/test/seam.test.ts:57-60` — so they read as load-bearing — but **nothing in `packages/*/src` or `apps/*/src` calls them**. Spec §3.3(a) originally described the argument names as coming "from the marker text", implying the markers reach a model; they do not. The live text is hand-built elsewhere. Worse, the dead marker says "the **narrowest wider mode that suffices**" (`escalation.ts:32`) while the shipped sentence says "a **wider** mode" — the dead copy is the one stating the rule that P1 was about (the narrowest wider mode does **not** always suffice: for an out-of-workspace write under `read-only` it must be `danger-full-access`). **Not deleted in this round**: they are exported API with tests, and deleting them is a separate decision from correcting the two documents that mis-described them.

**C10. `exitCode: -1` carries SIX meanings, and C's audit found four.** Scope C recorded four (bash absent · ladder refusal · sandbox-unavailable refusal · exec spawn failure). Reading `exec` adds two more that no artifact lists: **`exec/src/index.ts:209`** — `child.on("close", (code) => doneFn(code ?? -1))`, so a process **killed by a signal** (or force-killed on Windows) is also `-1`; and **`workflow/src/runner.ts:222`** synthesises `-1` for a **thrown** error. So a consumer that treats `-1` as "the binary is missing" — which is what `fs-search/src/index.ts:89` and `:136` document — is wrong for five other cases. The mitigation that does hold, and it is the one worth keeping: both sandbox refusals put **parseable JSON** in `stderr`, so a model that reads `stderr` can tell them apart; **bash-absent is the only prose case**, and the prose is legible.

**C11. The mechanism the design exists for had NO PRODUCER when this was written — and that was overtaken within a day. CORRECTED 2026-09-15.** Verified first-hand at the time, not inherited: a repo-wide search for `sandbox/mode` found **the event-type declaration (`core-session/src/index.ts:43`), the reader (`sandbox-policy/src/session-mode.ts:9`), and tests** — no production file appended one, and `sandbox-policy` exported **no writer at all** (no `setSandboxMode`; IH kept the fold and not the dsh setter). **M1 Phase B's Task 1 (`34c746e6`, on `m64`) then added the first production producer — at CONSTRUCTION time (`packages/session-executor/src/assembly.ts:354`), recording the mode a session starts under — so the blanket form of this claim is false now while its load-bearing half survives:** the "session tightened mid-run" scenario that §3.1 was written to fix is still **unreachable in production**, because it needs a host that appends the event *after* construction (and **no shipped host does** — **corrected 2026-09-15**: this parenthesis said the only shipped one was `/sandbox` in the frozen `apps/cli/src/web.ts`, but that command appends nothing. Measured: `/sandbox` writes `settings.sandboxMode` and answers that it takes effect for sessions created *later* (`apps/cli/src/web.ts:273-282`), and `web.ts:470-475` reads that setting **once** at construction. It is a tightening *surface*, not a mid-session appender; the event's sole producer is `assembly.ts:354`, at construction). What per-call resolution buys today is the escalation ladder (which *is* reachable) plus correctness whenever that mid-session host appears. And on the TUI — the main interactive surface — the word `sandbox` **does not occur in `apps/tui/src/index.ts`**, and the embedded session service is built with no `sandbox` key, so the fs guard, the shell policy and the terminal refusal are all inert there and the ladder is unreachable (branch 3). Confinement is enabled by the CLI and the web host only. This is a **reachability statement, not a defect** — but a reader who assumes the TUI is confined has it backwards, and `docs/CAPABILITIES-DETAIL.md:285` used to mislead them by naming `sandbox-policy (session-mode.ts)` as the event's producer when it only reads (corrected 2026-09-15: the producer is the assembly, at construction).

**C12. The same `sandbox_permissions` argument is declared on eight schemas but has no single audited home.** Scope D's F13 claimed nine tools; `ESCALATION_DECLARING_TOOLS` lists **eight** and the reviewer's own enumeration contained eight entries while the sentence said nine. Recorded because it is the second reviewer finding on this branch that did not survive checking — and because the *underlying* question F13 was reaching for (is the declared set the same set that can be refused?) is real and is answered by the refusals, not by the count.

## D. Parked by the final review — found, ruled on, deliberately NOT fixed in this round

These are **not** unanswered questions (that is section A) and not implementation residuals (section C). They are findings the final review raised that this fix round declined to act on, each with the reason, so that "why wasn't this fixed?" has an answer that is not "nobody noticed".

*Label warning:* `D1`–`D6` here are **this file's** parked-findings entries. The fix plan's `D1`–`D6` are documentation-correction items — a different list in a different file. Cross-references elsewhere name the item, not the label.

**D1. The advice-bearing refusal is the one without the structured shape (Scope A A-2 / plan P3).** On the fs guard path the denial is **encoded into `error` as JSON**, and `softFail` (`fs/src/error.ts:58-68`) returns only `{error, code}` — so `"denial" in result` is false exactly when the model most needs the retry instructions, while the ladder path returns `{error, code, denial}`. **Ruling: park.** Three existing tests parse the JSON back out of `error`, so making it structured **without** changing the message or the code is a change to the model-visible payload that deserves its own task and its own red-first test — not a rider on a fixes-and-docs round. The correct shape is recorded in the plan (carry the denial through `FsToolError`).

**D2. `modeOverride` is passed even when nothing was granted (A-4 / P4).** The assembly re-reads the policy and then overrides with `ladder.mode`; for branch 2 (no args) that is the fresh read anyway, so a mid-call tightening can be nullified by the parameter that carries the grant. **Ruling: park** — the fix must keep a single explicit argument at the `guardWrite` call site, which is also the subject of an existing mutation proof, so it needs a mutation proof of its own rather than a rushed edit.

**D3. Branch 4 silently discards a NARROWER request (A-6 / P5).** `base: danger-full-access` + `{sandbox_permissions: "read-only"}` proceeds unconfined with no prompt and no denial. Not a fail-open — the defect is answering a request it did not honour. **Ruling: park, and pin it as a test plus a comment** saying the request is ignored deliberately (the call is already maximally permitted); refusing it would contradict P2's ruling. Not done this round only because the round's budget went to P1/P2, which are defects rather than honesty items.

**D4. Scope D's remaining stale claims in `docs/CAPABILITIES-DETAIL.md` (~18 citations).** Pre-existing debt, not this range's. **Ruling: park all but the one this range falsified** — `:285`'s producer claim, corrected here because a mechanism claim this range *disproved* must not be inherited silently by the next reader (C11).

**D5. The shell's runtime OS denials are unclassified (A-8 / C6).** `classifyDenial`'s only callers are tests, and `denialSignatures` is published onto `ConfinedArgv` and read by nothing (`exec` reads `runnerFailureRules` only). **Ruling: document, do not implement.** It is pre-existing (the `git diff` over `sandbox-local`/`exec` for this range is empty), and §3.2's normative sentence plus `denial.ts:11-13` are what overstate it.

**D6. No lint gate covers the still-latent `patch.ts` fail-open (C F11).** No eslint config, no `lint` script. **Ruling: record, do not add.** What actually protects it is one test; saying so is honest, whereas adding a lint gate to a repo with zero lint configuration is a different project.
