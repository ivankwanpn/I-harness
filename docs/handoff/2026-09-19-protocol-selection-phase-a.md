## 1. 這個單元在做什麼

**移除一個靜默預設。** 一條沒有宣告線協議（wire protocol）的 provider 路由，**以前會安靜地解析成 `openai-completions`** —— 使用者的 API key 就是這樣被送到一個從來不說那個格式的端點。

spec：`docs/superpowers/specs/2026-09-19-protocol-selection-design.md`（§10 定義階段 A，並界定階段 B 不是什麼）
計畫：`docs/superpowers/plans/2026-09-19-protocol-selection-phase-a.md`

**階段 A 的四件事：**

| # | 內容 | 落點 |
|---|---|---|
| 1 | **移除發送路徑的尾巴** —— 鏈上找不到協議 ⇒ 大聲、可行動的拒絕 | `packages/settings/src/sections.ts`（`resolveProviderProtocol` 只有**一個**呼叫點） |
| 2 | **移除探測路徑的第二條尾巴** —— 探測有自己的 `openai-completions = Bearer` | 在 `provider-runtime` 邊界拒絕，讓生產呼叫者碰不到它 |
| 3 | **session 的模型選擇可以說出自己走哪條線** —— durable 型別加 `protocol?`，且 header 重寫不得靜默刪掉它 | `session-persistence` + `session-persistence-jsonl` |
| 4 | **兩個 CLI 列表停止印出沒人宣告的協議** | `i-harness provider list`、`i-harness models list` |

**解析鏈是 `selection > 模型行 > 路由`** —— 只有三層全空才拒絕。**這一條在下面出現很多次**，因為它是兩個真實缺陷的成因。

### ⚠ 全套跑有一半的機率會紅一條 —— **那不是這個單元的回歸**

> **⚠ 2026-09-20 更新：這一條已經修好了（`65838d8b`）。** 這段文字**寫於它還活著的時候**，所以**原文保留** —— 那是當時的事實。今天讀到這裡的人請去看 `docs/handoff/2026-09-20-queued-work.md` §2（W1）：那裡有修正、以及**證據證明了什麼**（「機制被關上」，**不是**「比率歸零」—— 那個區別在那份文件裡是明文寫著的）。

`packages/settings` 的 `test/layering.test.ts:201`（*"M40 A6 settings/changed hot-reload"*）會以 `expected 2 to be 1` 失敗，**在平行全套跑裡大約一半的機率**，而隔離跑必定通過。

**機制（從程式碼推出來的，不是靠反覆跑）：** `watchSettings`（`packages/settings/src/index.ts:1305-1349`）用 **10ms 的 `setInterval`** 比對 `${mtimeMs}:${size}`，**沒有 in-flight guard**；`writeFile` **不是原子的**，所以一次寫入可以呈現兩次 stat 變化；store 回呼（`:1251-1263`）**先同步快照 `before`，然後才** await `reloadFromDisk()` —— 落在同一次 reload 延遲內的兩次偵測**都看到改動前的狀態**，於是**各發一次 `settings/changed`**。

**一次改動，兩個事件。這是一個既有的產品缺陷，不是測試假陽性**，而且**這條分支碰不到那條路徑**（watcher 本身零改動）。

**看到它紅：重跑一次、繼續。** 修法很小且獨立（加一個 in-flight guard），但**不屬於這個單元** —— 見 §5 的 P4。

### 4.2 T2 的核心裁定：**SDK 的 wire 型別不動**

實作者自己舉手：`packages/sdk/src/server.ts:715` 有**它自己的**白名單 parser，不認得 `protocol`。於是 **wire 宣告了一個 server 會靜默丟掉的欄位**。

**但修法不是把它接上。** spec §4.3 是**使用者的話**：*「session 的協議**不寫進任何檔案**（使用者決定）」*；§7 再列一次；而 `setSessionModel` 呼叫 `coordinator.updateMeta(...)` —— **那就是寫檔案**。

**裁定：把謊從源頭收掉。** wire 型別回退，durable 型別與 jsonl parser 留下，SDK parser 補一句註解說明「不接」是刻意的（並指向 §4.3/§7）。

**代價：phase B 要把它加回 wire 型別 —— 一行**，而且會跟「接受它的 parser」同一個提交落地。

### 4.3 T3 的核心裁定：**那條路由是能用的**

兩個列表寫著「cannot be used」。**假的** —— 鏈是 `selection > 模型行 > 路由`。

**量到兩次：**（1）路由沒有協議 + 模型行帶 `protocol: "gemini"` ⇒ 列表在一行說「不能用」，**下一行印 `protocol: gemini`**，而 `resolveModel` 回 **`ready`**；（2）用 `roles set … --protocol gemini` ⇒ 同一條路由 **`ready`**。

**這是這個單元存在理由所要消滅的說謊方式。** 措辭改成只陳述**路由自己**的事實：`no protocol of its own — set one with: …`。

## 8. 已知邊界

1. **階段 A 不寫入任何 session 協議。** durable 型別有 `protocol?`，jsonl parser **保留**它（header 重寫不得刪掉不認得的欄位），但**沒有東西寫它** —— SDK 的 parser 刻意不收（§4.2）。**這是有意的**：`coordinator.updateMeta` 是公開 API，型別現在接受 `protocol?`，所以**嵌入者仍可以寫入一個** —— spec §4.3 的字面（「不寫進任何檔案」）**比出貨的東西稍強**。
2. **`plugins.subagentModel`** 與角色模型的行為未受本單元影響。
3. **`--max-tokens` 仍無消費者** —— 卡片的 `maxOutputTokens` 被解析、驗證、顯示、警告，然後**沒有地方可去**：`LLMRequest`（接縫的請求型別）**根本沒有 max-output 欄位**。這不是一行沒接，是**接縫要加欄位、五個適配器各自翻譯**。
