## 2. 四件事

### 2.1 usage：四個生產者

| 轉接器 | wire 位置 | 欄位名 |
|---|---|---|
| `llm-openai`（Responses） | `response.completed.response.usage` | `input_tokens`／`output_tokens`／`input_tokens_details.cached_tokens` |
| `llm-gemini` | 末塊的 `usageMetadata` | `promptTokenCount`／`candidatesTokenCount`／`cachedContentTokenCount` |
| `llm-bedrock` | `metadata.usage` | `inputTokens`／`outputTokens` ＋ **`cacheReadInputTokens`／`cacheWriteInputTokens`** |
| `llm-openai-compatible` | `stream_options` 買來的尾端 usage-only chunk | `prompt_tokens`／`completion_tokens`／`prompt_cache_hit_tokens` |

**兩條鐵律沿用了 anthropic 自 M5-T2 立下的規矩**：①每個欄位只在 `typeof v === "number" && Number.isFinite(v)` 時才取；②**一個可辨識的數字都沒有 ⇒ `undefined` ⇒ 不發事件**（捏造的 `0` 會被讀成一次沒人做過的測量）。四個 mapper **各自一份**（見 R3）。

**bedrock 那格的範圍是被量測改寫的**：本樹自己的 M5-T2 wire 欄位表只列了 input/output，但裝著的 `@aws-sdk/client-bedrock-runtime@3.1123.0` 的 `TokenUsage`（`dist-types/models/models_0.d.ts:3777-3808`）**宣告了 `cacheReadInputTokens?`（:3797）／`cacheWriteInputTokens?`（:3802）** ⇒ 依計畫的條件一併映射。**那張表在 bedrock 那列是不完整的**（殘餘 §4.6）。`totalTokens` 刻意不映射（seam 沒有總數欄位；它就是 wire 自己的和）。

### 2.2 openai-compatible：先問才有

這是五家**唯一**一個「預設不送 usage」的協議，所以送 `stream_options: { include_usage: true }` 是**請求形狀的改變**——不支援的 gateway 可能拒收。

- **預設開**，per-route 用 `usageInStream: false` 關掉（**關掉時一個鍵都不送**，不是送 `include_usage: false`）。
- 值走**與 `maxTokensField` 完全相同的一條鏈**：settings 型別＋normalizer＋FieldSpec 列 → `ProviderView` → `providerView`（user-else-template）→ `runtimeProfile` → `ProviderProfile`／`WireClientConfig` → `buildClient` → 轉接器 config。**全鏈不注入預設**（缺席即缺席），`false` 全程存活（`!== undefined`／`typeof === "boolean"`）。
- 鍵寫在 `...(config.options ?? {})` **之前** ⇒ route 的原始 `options` 仍可覆蓋它（有一條測試釘住這個順序）。
- **`sections.ts` 的第一列布林 FieldSpec**（`FieldType`／`isRedactable`／`validateValue` 本來就帶 boolean 臂 ⇒ 格架不用改）。

### 2.3 reasoning

`delta.reasoning_content` 在本階段之前**全樹零讀者**（只有 `docs/CAPABILITIES-DETAIL.md:525` 把它列為 wire 欄位）⇒ DeepSeek 家族的推理內容**整段被丟掉**。現在它是 `{ type: "reasoning"; text }`，**在 `content` 之前**（同一幀同時帶兩者時，模型是先想再答），空字串不發事件。

### 2.4 anthropic 的必填退路進鏈（階段 Ⅱ 的 I1）

`ANTHROPIC_MAX_TOKENS_FALLBACK` 過去是**在轉接器裡**選的（那裡沒有窗口）⇒ 它**永遠沒被夾過**，而 `input 100K + 128000 > 200K` 正是「上下文快滿」時最容易發生的請求。現在它**在 provider-runtime 解析**（**只有 `anthropic-messages` route**），帶著 `maxOutputTokens` 進 binding ⇒ `core-agent` 的夾取看得到它。轉接器自己的常數退化成「直接使用轉接器的人」的最後手段。

### 2.5 structural：compat 的兩個 frame 迴圈合成一個

`llm-openai-compatible` 原本有兩份逐字近似的解析（主迴圈 ＋ 殘餘 flush），而 flush 那份**從不累積 `tool_calls` 片段** ⇒ **只在無邊界末幀出現的工具呼叫會被無聲丟掉**（階段 Ⅱ 的殘餘 §5.4）。現在兩者共用**一個** `handleFrame(event) => { events, done }`，所以本階段後面的 usage 與 reasoning 兩條規則**各自只落一處**；截斷字面也只有一個讀取點。附帶效果：無邊界末幀的**不完整**工具參數現在會被報成 `malformed tool args`（以前無聲忽略）——那是既有失敗通道與幀邊界無關化，不是新規則。

## 4. 殘餘（本階段**不做**，逐條具名）

1. **拒答仍沒有自己的通道**（`content_filter`／`SAFETY`／`RECITATION`／`refusal`／`model_context_window_exceeded`）——階段 Ⅱ 的殘餘 1 原封不動。
2. **`compaction/src/summarizer.ts:181`** 自己組 `LLMRequest`、不帶 `maxOutputTokens` ⇒ 在 anthropic 上仍走**轉接器內部**的 fallback、**仍不被夾**——T7 的可達殘餘（階段 Ⅱ §6 就指定了它）。**候選修法**：把上限放進 compaction 的設定，讓摘要請求帶自己的 cap。
3. **`reasoning` 的語意仍不一致**：四個生產者取自四個**無關**的 wire 概念（anthropic 的 thinking、openai 的 **summary**、bedrock 的 `reasoningContent`、compat 的 `reasoning_content`），而 **gemini 的 thought parts 仍不讀**（`thoughtSignature` 全樹零命中）。要一致化就得替密封上一個「這是原始思考還是摘要」的位——**產品決定**。
4. **`"off"` 在 anthropic／bedrock 仍等於 unset**（API 的關法是 `{type:"disabled"}`）——需要產品決定，spec §3 已列。
5. **usage 事件沒有 per-response 去重**：若某個 gateway 在 finish chunk 與尾端 usage-only chunk 各報一次，consumer **逐欄 last-write-wins**（`core-agent:408-415`）⇒ 今天良性；**但若哪天有 gateway 被看到重複回報**，這裡要加去重。
6. **本樹自己的 M5-T2 wire 欄位表在 bedrock 那列漏了 cache 欄位**（本階段量到它們真的存在）。
7. **`llm-mock` 仍發不出 `reasoning`**（core-agent 的推理測試因此自帶 fake client）；`MockStep` 只有 `usage`。
8. **mapper 的 `Number.isFinite` 那半四家都沒被釘住**（pre-existing，anthropic 自 M5-T2 起）：`JSON.stringify(Infinity)` → `null`，所以四個轉接器的 fixture helper **表達不出來**；要釘得用生 SSE 字串寫 `1e999`（`JSON.parse("1e999")` 才是 `Infinity`）。
9. **tracked 文件裡仍有那條假註解的「原件」**：`docs/superpowers/plans/2026-09-23-provider-boundary-phase-3.md:190-192` 的 Step 3 範例仍寫著「被取代的註解說 seam 沒有 usage 事件」（M72 Ⅲ 正是從計畫抄進檔案的，而檔案已修正），`docs/superpowers/specs/2026-09-22-provider-boundary-design.md:23` 也仍用 M72 Ⅱ 之前的措辭描述那條假註解。**照著計畫走的人可以再抄一次那句假話。**
10. **兩處註解仍比程式知道的多**（R17）：`packages/llm-anthropic/test/anthropic.test.ts:436`、`packages/llm-openai-compatible/src/index.ts:279-282`。
11. **`response.incomplete` 仍丟掉 usage payload**（R14）——**候選修法已寫在 R14**。
12. **OpenAI 形狀的 cache 拼法沒被讀**（R16）。
13. **13 條 deferred minors** 在原 ledger（已隨工作區刪除，內容併入本節各條與 §3）。

## 5. 它不保證什麼（明說）

1. **不保證每個 provider 都接受我們送的東西**——預設送的 `stream_options` 對嚴格 gateway 有已知風險；閘門是 **per-route 的 `usageInStream: false`**，不是自動退讓。
2. **不保證 usage 的數字可比**——不同 provider 對「沒回報」與「真的是 0」的處理不一致；本樹維持 **absent ≠ 0**（本階段四個生產者都遵守）。
3. **預設打開改變了每一條既有 openai-compatible route 的請求形狀**——這是刻意的（spec §1.4／§4），**且是行為改變**。
4. **`reasoning` 現在算「已產出」**：seam 的重試包裝（`llm-seam:192-193`）因此**不再靜默重試**一個先吐了 `reasoning_content` 才失敗的相容往返。這更正確（避免重複的可見推理），但**是一條沒寫在任何地方的行為改變**——見 §6。
5. **不保證 usage 是完整的**：被截斷的 Responses（殘餘 11）與 OpenAI 形狀的 cache 欄位（殘餘 12）今天仍看不到。

## 6. 給 PR 與下一個接手的人

**PR 描述必須講三件事**（終審要求）：

1. **預設打開 `stream_options` 改變了每一條既有 openai-compatible route 的請求形狀**；逃生口是 per-route 的 `usageInStream: false`，而它**只能改 `settings.json`**（`provider set` 沒有這個開關，與 M61 的 `inputModalities`、階段 Ⅱ 的 `maxTokensField` 同形狀 ⇒ 先例，但同樣不易被發現）。
2. **`reasoning` 算「已產出」⇒ 有推理輸出的往返不再被靜默重試**（§5.4）。
3. **殘餘**：compaction 的未夾路徑（§4.2）、`response.incomplete`（§4.11）、OpenAI 形狀的 cache 拼法（§4.12）、被加寬的 docs 殘餘。

**下一個動 provider 邊界的人**：

- 本階段的四個 mapper 是**故意的四份**（R3）；要抽共用模組就得**同時**允許一個新的 seam 匯出（spec §2.4 目前禁止），而那一次也正好是替 `isFinite`／`null` 兩半 guard 找一個共同測試地點的時機。
- **計畫的突變預測要當預測看**：本階段兩次不成立（T1 (b)、T5 (c)），階段 Ⅱ 五次。有用的產物是「要釘哪條規則 ＋ 找出會讓它紅的突變」，不是那行字面編輯。
- **Global Constraints 的「一條規則只落一處」在寫的時候要說清楚範圍**：照字面讀，它與計畫自己「四個 mapper」的設計互相矛盾；寫「同一個轉接器內」才對。
