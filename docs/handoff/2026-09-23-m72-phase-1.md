## 7 · 殘餘（寫出來，不是藏起來）

1. **M62 fetch 階段的 abort 不對稱**：四個 fetch 轉接器仍把**呼叫端 abort** 變成 `error` 事件（`describeTransportError` 會標成 "request aborted by the caller"），而同一個 signal 在**新加的** mid-stream 守衛是重拋。今天的爆炸半徑小（該訊息不匹配任何重試 regex、`core-agent` 在 switch 前先看 `abort?.aborted`），但這是一條**已知的兩套規矩**，留給下一階段決定（四個檔各 4 行 ＋ 測試）。
2. **`SSEParseError` 不帶 `cause`**：解析位置／期望值遺失；若未來讓四條 catch 分辨「壞 chunk」與「中途傳輸失敗」再補。
3. **四條迴圈 catch 比「壞 chunk」寬**：body 中途的傳輸失敗（`reader.read()` 拒絕）也成事件，且**不經** `describeTransportError` ⇒ 可能顯示成 `TypeError: terminated` 而不是診斷字串。
4. **`llm-openai` 的 `parseSSE` 不看 SSE 的 `event:` 行**：只認 JSON 的 `type`；若某 provider 送 `event: error` 而 body 無 `type`，仍會落到 `return []`。
5. **空字串 `systemPrompt` 的跨轉接器不一致**：`llm-openai`／`llm-anthropic` 仍**照送**（本階段只記錄不動）。
6. **一個未量的風險**：本階段沒有對任何真實 provider 發過請求 ⇒ 內建 `deepseek` profile 是否接受 `system` 訊息是**假設**；若某個 gateway 拒絕該角色，今天的行為是 **400**（而舊行為是靜默丟掉 prompt）。
7. **`systemPrompt: undefined` 會拋 TypeError**（在 transport try 之前）；已量測 repo 內全部建構點都供應字串 ⇒ 今天不可達。

**給階段 Ⅱ 的三條明確指示**（終審建議，已採納）：①`truncated` 要**以 reason 值**為準，**不要**以事件名為準（`response.incomplete` 不等於截斷——`content_filter` 也走它）；②把 gemini 的 `finishReason`／`promptFeedback`、anthropic 的 `stop_reason:"refusal"` 明確處理掉——那是本樹**最後一類**「200 空成功」；③截斷與拒答要分開表述，不要一起掉進 `truncated`。
