# v0.1.13：完成交付與 scope 清理的補充驗收條件

2026-10-14，只讀源碼分析，固定提交 `a11ef95153d0166e3e800aa8c3294cc03998d07a`。這份文件補足已核准 E1／E2／I4 的實作接縫；**尚未執行這些新行為的測試，也不宣稱已修復**。純結構拆分仍保留原行為，後續功能提交才建立失敗案例並修正。

## 完成事件不能只看記憶體日誌

基線 `core-session` 的 `append` 先加入事件，再呼叫 persistence hook，最後通知 subscribers。相同的 thrown error 可能表示入列前拒絕，也可能只是入列後的觀察者錯誤。`coordinator.flush` 在沒有對應 write-behind 時可以直接成功，因此「事件存在＋flush 成功」不能充當保存收據。

E1 採用既有 Session owner 內的受控 critical append 接縫：驗證與複製事件、確認正確的 Session／coordinator／sessionId 綁定、取得既有 write-behind 對該 sequence 的接受證據，才同步發佈至 live log。入列前失敗不能留下 sequence 缺口；已接受但 flush 失敗只重試原批次，不再 append terminal。無法判定任意自訂 hook 是否接受時應拒絕並協調恢復，不能猜測成功。保持同一個 writer，不新增另一條 backend append lane。

一般 Session subscribers 可個別隔離並回報錯誤；persistence hook、flush、plugin emit／waterfall／cascade、approval／guard 及 stop veto 仍須傳遞失敗。completion fold／terminal CAS／generation mutation 由單一 per-Session owner 序列化。gateway `sessionOperation.run` 是管理操作的准入 fence，並不是這個 CAS 的互斥鎖；也不能持有 coordinator operation gate 再等待需要同一 gate 的 flush。

`putDocumentStrict` 共用既有 document chain／lease，但把原始 operation Promise 交給 strict caller，僅將內部 chain tail 正規化以允許下一筆繼續。原有 `putDocument` 行為保留。基線 JSONL document 的 temp＋rename 沒有 file／directory fsync；增加錯誤傳遞不代表提高斷電保證。明確區分記憶體模式、持久化單 writer 與跨程序 lease，不能宣稱未提供的 exactly-once 或穩定儲存保證。

## 正在運行的主代理也必須等待提交

基線服務會先 append completion steer，再 await admission flush；此時 active agent 可以由 `Inbox.claimAtStepBoundary` 先領取。只把 idle wake 放到 flush 之後仍會漏掉這條路。

E2 讓同一 Inbox 的 lane selection 與 step-boundary claim 共用 completion readiness／generation 權威：入列時先不可領取，對應 admission 保存成功且仍未撤銷才開放。恢復後從可信保存事實與 exact assembly 重建 readiness，不靠 ID prefix 或 raw pending 推論。

completion promotion 也需在同一 lane／Inbox 接縫，於 provider 副作用開始前完成必要 checkpoint。基線沒有這個一般屏障；未提交 promotion 在 crash 後可能只剩 admitted 證據。測試必須分清排入、領取、提交與實際執行，失敗不能自動重跑原工具或已開始的模型回合。

普通子代理的 cold restore drain 在 assembly publication 前執行，而基線公開的 post-publication hook 只涵蓋 team。E2 必須在 exact assembly 與 lane 發佈後，對普通子代理與 team 各做正確的 initial reconcile，沿用單一 drain Promise＋dirty bit及同一模型 lane。

## Scope 退休與非同步資源回收分開

基線父 scope 把 child 存入自己的強引用 Set，child `scope.unmount()` 卻刪除 child 自己的 Set。這是源碼可確認的保留問題，但 Set 沒有其他用途；只修 Set 不會停止舊 callbacks，也不會執行資源 disposer。

I4／E2 保留 `scope.unmount(): void`，加入同步退休與正確父 detach；退休後的操作派發及 await 後續派發需被 fence，不能脫離祖先 guard 變成無限制 root。已進入 callback 的任意程式不能撤回，factory 仍須在 await 後檢查自己的身分和關閉狀態。服務讀取與 named-plugin teardown 保留清理所需的能力；scope 退休不冒充 async producer join。

既有 child／assembly lifecycle 以共用的 close attempt 協調 `SessionContextHandle.close()`、turn、Code Mode、plugin 及完成交付的 drain。先撤銷新准入／晚到發佈，再取消並等待原 owner，確保一個 disposer 失敗不會跳過其他租約釋放，同時保留清理失敗給既有 close retry。人類 steer／暫停中的 resident child 不因此銷毀 context。

完整 acquired-resource lifetime 要有 rollback：fresh spawn 與 resume 都有 mount 後模型解析或稍後 factory setup 失敗的路徑。guardian reviewer 的 `finally` 在基線直接呼叫 `entry.unmount`，必須改由相同的 awaited `entry.dispose` owner；普通 close 和 team 路徑也要共同驗證。這會讓某些舊 scope 操作被明確拒絕，審批回傳亦可能等待資源 drain，需以行為測試確認。

基線 runtime-context 捕捉父 Session，沒有 exact Session filter 或 disposer；I3／I4 必須各自建立 context 並移除自己的 callback。舊 instructions loader 沒有 watcher lease，不能把未加入的 watcher 說成已存在的洩漏；I2／I4 新增租約時才驗證釋放與晚到讀取。

## 必須先建立的故障案例

|工作|驗收案例|
|---|---|
|E1|入列前拒絕、接受後 observer 拋錯、flush 拒絕再重試、錯誤或不存在的 mirror pair、相同 terminal 的 concurrent CAS、resultRef 保存早於 terminal、schema／UTF-8 邊界|
|E2|active parent 穿越 held／rejected admission flush；promotion checkpoint 失敗不得先呼叫 provider；同一 identity 的 admission／schedule／promotion 各 crash 邊界；exact publication 後恢復普通及 team 通知|
|E2|Stop 穿越 flush、Stop 後新 human turn、Stop 後重啟三項獨立測試；單 drain／dirty／error-only backoff；legacy migration 中斷不雙重交付|
|I4|退休 scope 不再開始下一個 snapshot callback／cascade final；祖先 guard 保留；fresh／resume 每個 setup failure 回收部分資源；兩次 close 等待同一 drain|
|I3／I4|child pre-step 不修改父 Session；兩個 child context 隔離；watcher lease 最後一位 owner 關閉才釋放；關閉後的讀取不發佈；guardian 正常／失敗／timeout 都等待正確 disposer|

實作按拆分後的公開入口與 owner manifest 接線，不重建舊 monolith。完成、失敗與權限相關事件不是同一種通知，不可用 blanket catch 或第二條模型 pump 來簡化。
