# IH v0.1.18 長會話效能與驗收

開發分支為 `codex/desktop-v0.1.18`，從 v0.1.17 驗收紀錄 `7fc1111f` 開始。Windows x64 候選產品提交為 `d32700e93fe090d9926329b9808bcb65d97c2238`。Desktop 與 Gateway 的產品版本同為 0.1.18。用 GitHub 帳號 `ivankwanpn` 提交及推送。[候選 CI](https://github.com/ivankwanpn/I-harness/actions/runs/45458985507)

## 根因與修正

| 路徑 | 修正 | 驗證 |
|---|---|---|
| JSONL 日誌解碼 | 重用同一次同步解碼已持有的位元組片段，分段核對 canonical frame、length 和 digest。只在 bootstrap 需要時建立 frame index。 | 既有損壞、非 canonical、部分寫入及跨 chunk 測試通過。單獨的解碼微量測沒有穩定的整體 RSS 差異。 |
| 請求準備 | 在一次持有者與前綴核驗下批讀已準備輸入及其 admission 依賴。普通模型請求減少重複的訊息投影、正規化與配置。 | 三組交錯 A/B 使用 5,992,131 與 6,002,929 bytes 日誌，投影項目逐次一致。完整掃描由 2 次減到 1 次，約 12 MB 減到 6 MB，準備階段中位數 1,414 → 695 ms，採樣 heap 增量 57.0 → 33.8 MiB。另以 9,409 筆事件單測模型訊息投影，六組交錯中位數 55.5 → 19.6 ms，配置樣本 36.37 → 12.38 MiB。 |
| 冷啟動恢復 | 執行附件恢復時，依賴讀取使用目前持有者已驗證的事件。安裝執行附件前重新核對檔案，完成後依照原流程釋放恢復用資料。 | 固定回歸以一次輸入準備及八次模型交換重現。恢復時完整依賴掃描由 9 次減到 0 次。恢復後按需讀取仍驗證原始日誌。恢復途中修改檔案時會拒絕建立執行附件。 |
| 長跑觀測 | 依程序實際角色分開採樣 Windows 私有記憶體、工作集、CPU 與 renderer 的視窗／連線狀態。驗證乾淨退出後，每次預期回覆剛好存檔一次。 | `scripts/bench/desktop-soak.test.mjs` 2/2。兩次相同三循環的舊候選，Gateway 最後一筆私有記憶體相差約 89 MiB。短時結果只用於驗證操作及觀測器。 |

## 實際運行

- **兩份大型日誌的 Gateway 重播。** 從 v0.1.17 的雙會話兩小時長跑取兩份約 6 MB 的合成日誌，各自註冊原對應專案。每組並行循環包含兩個工作區各一次提交、一次實際唯讀工具呼叫、第二個 Responses 請求及存檔驗證。舊版依同一份專案設定重跑 150 秒，觀察到零次模型請求，達觀察上限後停止。修正版首個本機請求抵達約 54 秒，三組循環各用時 94.3、57.8、65.6 秒。六筆結果均可讀回。這是 Gateway 端測試，沒有 Electron 顯示或外部供應商網路時間。關閉過程的兩條 `FACT_CLOSED` 是內部 readiness 訂閱先收到停止訊號的診斷紀錄，出現在六筆回覆已核對之後。Host 關閉及測試退出均成功。
- **Windows 封裝版。** 運行候選的實際 EXE，使用隔離測試 profile、兩個各具 700 輪資料的會話、本機 Responses、真實工具讀取。兩輪單工作區與五組雙工作區共 12 筆回覆，在程式乾淨退出後逐筆核對存檔。這次與安裝器建置有重疊，耗時供該次驗收追溯。約 6 MB 的日誌重播與 700 輪桌面用例的資料量不同。
- **Windows 故障恢復。** 同一封裝版獨立重跑三次持久化收件。前端顯示供應商串流故障，輸入區停止按鈕能中止執行，之後仍可送出新輸入並收到回覆。
- **回歸。** Core Session 套件 952/952，更新的日誌及準備輸入定向檔 19/19。Core Agent 48/48、Context Engine 105/105、LLM Seam 定向 15/15。JSONL 相關 63/63、Session Persistence 定向 61/61、最後的冷恢復測試檔 4/4、Gateway fork 與恢復定向 5/5。套件邊界 128 條與基線一致。候選 CI 的全套件型別、Gateway 編譯與 Windows ACL 皆通過，push 觸發的完整 `verify:all` 略過。

## 剩餘延遲的分段量測

用候選包內的 Gateway 再重播兩份約 6 MB 日誌。既有 Gateway 時間標記加上測試程序內的 archive reader 計數，得到一組冷、暖各兩個工作區的並行樣本。測試期間有 Setup 建置，絕對耗時用於這組路徑定位。

| 階段 | 冷路徑 | 暖路徑 |
|---|---:|---:|
| 提交到兩個工作區都返回已接收 | 23.9 秒 | 0.22 秒 |
| 接收到第一個本機請求 | 27.8 秒 | 26.0 秒 |
| 第一個請求到工具後第二個請求 | 28.8 秒 | 29.2 秒 |
| 第二個請求到兩個工作區都收到 `turn/end` | 4.9 秒 | 5.1 秒 |
| `turn/end` 後讀回 40 筆歷史 | 12.6 秒 | 0.05 秒 |

暖態兩個工作區本輪共 34 次完整依賴掃描，約 196 MiB 邏輯讀取量。10 次在首個請求前、16 次在工具與第二個請求之間、8 次在收尾。冷態首次分頁另觸發兩次全量歷史讀取及兩次完整依賴核驗。記錄為 `shared-replay-timing.log`，其中第一行提供時間和掃描收據的位置。分段採樣以兩個並行工作區最早的請求及最晚的完成為界。

## 尚待改善

1. **長歷史暖態仍有重複全檔讀取。** 在同一個原生寫入持有者及驗證過的前綴內，確認每個批次需要的依賴，再減少逐事件掃描。保留封存、刪除、前綴改變及釋放持有者時的原有拒絕行為。利用與本輪相同的兩份日誌比較一個和兩個並行會話，同時追蹤掃描次數、讀取量、各段時間與 heap，避免用常駐完整會話交換時間。
2. **冷開與歷史分頁各自量測。** 恢復前的載入／修復與執行附件各取得歷史證明，普通日誌也會為確認 namespace 讀取整份原始檔。先分別計數，再評估共用同一次核驗及限定讀取範圍。首個小型 `session/history` 查詢可能建立完整相容會話，需以正常 SDK／桌面入口量讀取量和保留 heap，再改從已驗證來源提供有界分頁。
3. **等輸入與歷史路徑變快後重跑等量長測。** 分開比較工作量、日誌大小、Gateway 記憶體、renderer 活動及視窗退出。本輪證據涵蓋局部配置及讀取改善，長時間 RSS 趨勢仍需以相同工作量的長測核對。

本機證據集中於 `.tmp/desktop-v0.1.18/`。長日誌重播記錄為 `shared-replay-v17-matched.log`、`shared-replay-after-scopes.log`，封裝桌面與故障復原結果為 `native-d32700e9.log`、`recovery-d32700e9.log`。原生程序與持久化收據路徑在記錄首行。A/B 資料在 `.tmp/memory-history-ab.log` 與 `.tmp/memory-gw/request-alloc.log`。
