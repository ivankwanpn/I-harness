# IH v0.1.18 長會話效能與驗收

開發分支為 `codex/desktop-v0.1.18`，從 v0.1.17 驗收紀錄 `7fc1111f` 開始。Windows x64 候選產品提交為 `d32700e93fe090d9926329b9808bcb65d97c2238`。Desktop 與 Gateway 的產品版本同為 0.1.18。用 GitHub 帳號 `ivankwanpn` 提交及推送。[候選 CI](https://github.com/ivankwanpn/I-harness/actions/runs/45458985507)

## 修復原則

修復前先檢查最接近該功能的參考項目，順著原始碼和測試核對責任歸屬、資料流與生命週期。已有成熟且符合需求的實作時，採用可驗證的做法，按 IH 的 Windows 桌面流程、套件邊界、持久化格式和舊資料相容性調整。驗收以 IH 的公開入口、相關回歸和實機操作為準。

## 根因與修正

| 路徑 | 修正 | 驗證 |
|---|---|---|

## 實際運行

- **兩份大型日誌的 Gateway 重播。** 從 v0.1.17 的雙會話兩小時長跑取兩份約 6 MB 的合成日誌，各自註冊原對應專案。每組並行循環包含兩個工作區各一次提交、一次實際唯讀工具呼叫、第二個 Responses 請求及存檔驗證。舊版依同一份專案設定重跑 150 秒，觀察到零次模型請求，達觀察上限後停止。修正版首個本機請求抵達約 54 秒，三組循環各用時 94.3、57.8、65.6 秒。六筆結果均可讀回。這是 Gateway 端測試，沒有 Electron 顯示或外部供應商網路時間。關閉過程的兩條 `FACT_CLOSED` 是內部 readiness 訂閱先收到停止訊號的診斷紀錄，出現在六筆回覆已核對之後。Host 關閉及測試退出均成功。
- **Windows 封裝版。** 運行候選的實際 EXE，使用隔離測試 profile、兩個各具 700 輪資料的會話、本機 Responses、真實工具讀取。兩輪單工作區與五組雙工作區共 12 筆回覆，在程式乾淨退出後逐筆核對存檔。這次與安裝器建置有重疊，耗時供該次驗收追溯。約 6 MB 的日誌重播與 700 輪桌面用例的資料量不同。
- **Windows 故障恢復。** 同一封裝版獨立重跑三次持久化收件。前端顯示供應商串流故障，輸入區停止按鈕能中止執行，之後仍可送出新輸入並收到回覆。
- **回歸。** Core Session 套件 952/952，更新的日誌及準備輸入定向檔 19/19。Core Agent 48/48、Context Engine 105/105、LLM Seam 定向 15/15。JSONL 相關 63/63、Session Persistence 定向 61/61、最後的冷恢復測試檔 4/4、Gateway fork 與恢復定向 5/5。套件邊界 128 條與基線一致。候選 CI 的全套件型別、Gateway 編譯與 Windows ACL 皆通過，push 觸發的完整 `verify:all` 略過。

## 尚待改善

1. **長歷史暖態仍有重複全檔讀取。** 在同一個原生寫入持有者及驗證過的前綴內，確認每個批次需要的依賴，再減少逐事件掃描。保留封存、刪除、前綴改變及釋放持有者時的原有拒絕行為。利用與本輪相同的兩份日誌比較一個和兩個並行會話，同時追蹤掃描次數、讀取量、各段時間與 heap，避免用常駐完整會話交換時間。
2. **冷開與歷史分頁各自量測。** 恢復前的載入／修復與執行附件各取得歷史證明，普通日誌也會為確認 namespace 讀取整份原始檔。先分別計數，再評估共用同一次核驗及限定讀取範圍。首個小型 `session/history` 查詢可能建立完整相容會話，需以正常 SDK／桌面入口量讀取量和保留 heap，再改從已驗證來源提供有界分頁。
3. **等輸入與歷史路徑變快後重跑等量長測。** 分開比較工作量、日誌大小、Gateway 記憶體、renderer 活動及視窗退出。本輪證據涵蓋局部配置及讀取改善，長時間 RSS 趨勢仍需以相同工作量的長測核對。

本機證據集中於 `.tmp/desktop-v0.1.18/`。長日誌重播記錄為 `shared-replay-v17-matched.log`、`shared-replay-after-scopes.log`，封裝桌面與故障復原結果為 `native-d32700e9.log`、`recovery-d32700e9.log`。原生程序與持久化收據路徑在記錄首行。A/B 資料在 `.tmp/memory-history-ab.log` 與 `.tmp/memory-gw/request-alloc.log`。

## 共用日誌核驗與回合收尾 `4835460e`

歷史分頁、工具依賴及寫入驗證原本都會重新解碼完整日誌。現在原生 JSONL 讀取器從完整核驗過的前綴記住框架位置與位元組摘要。下次從原持有者的描述元讀取已提交的前綴，核對實際位元組，重新解碼所選框架，並從已核對的位置續解新框架。記住的位置屬於同一持有者，事件正文只保留到該次讀取完成。讀取仍會檢查檔案身分、長度、刪除標記、出生證明和持有權。寫入需要取回相依事件時才開啟讀取描述元。含舊式未框架化正文的日誌沿用完整解碼。普通會話冷開的 bootstrap 分類只需讀檔首，在 197,250 bytes 的原生測試日誌中由全檔降至 65,536 bytes。語意出生仍使用完整證明。[整合提交 CI](https://github.com/ivankwanpn/I-harness/actions/runs/45512934815)

以同一 Windows 執行檔和同一份隔離日誌做公開入口配對。清單有 199 筆合成已結算工作及一筆具原始輸出的背景工作。基準 `acd3889c` 的兩次冷讀為 3.91 和 3.08 秒，編譯候選為 1.42 和 1.14 秒。兩版的 200 筆清單及原工作 72 個位元組輸出相同。記錄為 `fixed-saved-selection-batch-candidate.log` 及 `many-cold-jobs-wire-batch-paired-*.log`。

先獲准開始的冷程序清單會完成原觀測，同一會話的背景暖載入才開始建立相容執行。暖載入只等待當時最早的一筆清單，之後的輪詢、其他會話和使用者實際送出的輸入都維持原精確持有者的流程。當暖載入先開始，程序清單仍使用既有的持有者交接。

## 終端證據與閒置面板刷新

參考 DSH 的工作清單先訂閱並合併所有者的狀態變更，以及 OpenCode 按會話區分終端狀態與輸出兩種讀取。IH 的程序面板在首次讀取前訂閱同工作區、同會話的相關事件，合併同一批事件，並由原 Gateway 查詢重新核對資料。即時工作使用原 1.5 秒輪詢，閒置清單每 15 秒再核對一次。視窗恢復可見時立即核對，背景更新等目前讀取或操作完成再開始。

歷史 PTY 清單將各筆終端的固定證據納入同一個驗證。原事件位置只驗證一次，日誌前綴與後續追加也共用分析。選定終端的身分、Code cell 所屬、rewind 和原始事件內容維持各自核對。單筆輸出採用同一個驗證流程。

基準 `bf8187c7` 的可見 Windows 面板結束暖載入並顯示歷史輸出後，在約 9 秒閒置期間自動讀取六次。純 Gateway 的 200 筆已存 PTY 基準使用 10,682 筆有效事件，兩次公開冷讀為 2.64 和 2.22 秒。收據為 `native-cold-job-idle-bf8187c7.log` 及 `many-cold-pty-wire-bf8187c7.log`。

## 未變更的冷程序日誌

參考 DSH 將 Session projection 視為重播結果、Pi 將持久會話快取限制在受控持有者內的做法，IH 的 JSONL backend 只保留一份有上限的已解碼冷日誌。後續每次先核對目前路徑和檔案識別，再以實際完整雜湊確認內容。只有重取同一份凍結日誌，才會重用已通過預檢的會話及附件引用集合。這些資料只供計算。每一請求仍獨立取得文件和會話權限，並於發佈前再次核對完整位元組。關閉原始讀取持有者會清除保留項目。

對照由同一 Windows 執行檔冷開同一份 6,049,498 位元組日誌。基準 `d2fd87e4` 三次清單為 1,113.0、910.9、868.6 ms，編譯候選為 1,049.4、106.1、98.4 ms。另一次原始保留輸出讀取為 965.5 和 190.9 ms。四次請求皆完成兩次全量位元組核驗，解碼及格式預檢各由四次降到一次，回傳的清單與 72 個位元組輸出一致。記錄為 `processes-cold-reuse-paired-*.log`。

隔離外部改寫案例涵蓋等長合法改寫、相同 mtime 和長度的損壞、不同 inode 的替換、發佈前改寫、專案撤權、封存及恢復。改寫時讀回新資料，損壞、撤權及封存均拒絕讀取。原始歷史保持一致。記錄為 `processes-external-inflight-reuse-candidate.log` 與 `processes-scope-cycle-reuse-candidate.log`。

## 首次冷讀的驗證分工

程序清單的原生首讀沿用既有封存解碼器完成日誌形狀及對話關係驗證。JSONL 原持有者將完整解碼結果與會話 ID、讀取世代及不可變檢視綁定。只有原後端能識別的同一份檢視才會在持久化層沿用其驗證。持久化仍檢查已註冊事件、操作欄位、忽略事件及會話標頭。舊式前綴、替換的檢視或不同的 JSON 序列化環境仍走完整預檢。每個請求的檔案、文件、專案及最終雜湊核驗沿原流程執行。

以同一 Windows 執行檔及同一份 6 MB 日誌做序列對照。基準 `3eb059dd` 首次清單 1,073.9 ms，編譯候選 573.2 ms。兩次重讀分別為 107.6／101.6 ms 及 109.2／100.6 ms。獨立計數確認，首次的對話形狀和關係掃描各由兩次降到一次，仍保留一次持久化操作欄位檢查。四次查詢合計仍做八次全檔雜湊及核驗 48,395,984 位元組，清單和 72 個位元組保留輸出相同。紀錄為 `processes-first-cold-paired-plain-*.log` 與 `processes-first-cold-native-single-pass-parity.log`。

## 一般對話的暖載入與請求座標

兼容的 `loadOwned` 使用既有持有者的乾淨歷史證明載入格式 14 日誌，資料仍由原流程建立可寫會話。中斷回合、舊前綴、待寫入資料及自訂修復沿用原來的恢復處理。固定同一 Windows 執行檔，以兩份約 6 MB 日誌對照，兩個工作區的明確暖載入由 9.13／9.09 秒降到 4.51／4.48 秒，四份模型請求、原日誌正文及新增工具和回覆序號一致。記錄為 `explicit-warm-clean-match-parity.json`。

原生持有者也開始按原始事件辨識只追加請求觀察資料的情況。基準的 20 次完整擷取有 12 次只追加綁定、預算或保留紀錄，而且完整重算的語義、保護範圍及分支均相同。現在只在目前格式、原持有者、不可變且連續的會話中，沿用這些純量座標並更新日誌的實際事件數和末尾序號。下一次發現其他追加仍重算內容，提示詞、工具及請求執行核驗均照原流程讀取。記錄為 `explicit-warm-frontier-summary-639c8085.json`。

兩項修正合併，再以同一 Windows 執行檔、同兩份日誌和四次本機 Responses 模型請求做序列對照。暖載入就緒由 7.95／7.99 秒降至 4.13／4.09 秒。就緒後從提交到首次模型請求由 4.67／5.19 秒降至 2.40／2.34 秒。從工具啟動到下一次請求由 3.30／5.21 秒降至 2.20／2.04 秒。完整上下文擷取從 20 次降至 8 次，12 次重用均來自同一原始會話的觀察追加。模型請求、日誌正文和持久化結果均核對一致。記錄為 `explicit-warm-combined-match-parity.json` 及 `explicit-warm-combined-match-phase-summary.json`。

## 共用原會話的對話驗證索引

參考 DSH 由會話持有者維護投影及其資料版本的做法，IH 的 Context Engine 可直接從原持有者取得已驗證的邏輯歷史。這條路徑限定於目前格式的普通會話，核對原持有者、不可變事件、連續序號和原 JSON 序列化環境。讀取前後再次核對提交位置。舊格式、分支、可變資料或序列化環境變動時仍執行原來的完整驗證。接著仍以目前的擷取函式轉換每筆入模資料。

執行環境核對也涵蓋對話驗證使用的 UTF-8 編碼及 Buffer 方法。注入不同的 acceptance 大小計算或 runtime context 名稱長度計算時，重用入口交回原來的完整驗證，由原驗證器裁決。

模型送出前的座標命中、只追加觀察事件的座標推進，以及完整快照沿用同一份會話與執行環境證明。這也覆蓋已暫存資料外層凍結、內層來源欄位仍可改動的情況。座標讀取會按當前欄位完整擷取，避免拿舊摘要當作這次請求的身分。

以同一 Windows 執行檔及同兩份約 6 MB 的日誌，對照 `c9e4b207` 和編譯候選。暖載入後的八次座標和完整快照投影均沿用原索引，整段通用索引重建由十四次降至六次。兩個工作區首次模型請求由 2.27／2.34 秒變為 1.87／1.82 秒，工具啟動到續跑請求由 2.07／2.23 秒變為 1.84／1.38 秒。初次暖載入就緒由 4.15／4.12 秒變為 4.34／4.32 秒。這是一組帶計數探針的本機 Responses 對照。四份模型請求正文、兩份原日誌及兩個新完成回合的保存結果均一致。記錄為 `owned-projection-match-parity.json`、`owned-projection-match-phases.json` 和 `owned-projection-spans-candidate.json`。

## 指令對帳與回合收尾讀取

參考 DSH 的 runtime context 投影只跟進同一會話已提交的指令快照。IH 從原持有者的索引找出目前分支最後一筆可見的 runtime context，核對前沿後只對該筆內容計算摘要。尚未安裝的提案無法改變目前指令，rewind 和明確清空仍由既有可見性與發布規則決定。讀取完成後仍由原發布程序處理寫入、拒絕與待確認的結果。回合結尾則在原定的 `turn/end` 與同步 telemetry 之後，從已核驗的投影選最後一則可見訊息。舊格式、分支、未核實的持有者與非原生編碼環境沿用完整驗證。

舊版可能將不合形狀的裁剪記錄留在目前格式的日誌。會話持有者在載入原事件及安裝新事件時查驗這個條件。若舊裁剪記錄需要原投影完整處理，指令摘要也會走原入口，保留原有的報錯及發布行為。

以同一 Windows 執行檔及兩份約 6 MB 的日誌對照 `a4643bae` 和編譯候選。暖載入後四次指令對帳和兩次回合收尾共六次通用索引重建降為零，暖載入本身仍有六次通用驗證。兩工作區首次模型請求由 1.92／1.86 秒變為 1.37／1.44 秒，工具啟動到續答請求由 1.71／1.56 秒變為 1.01／1.16 秒。四份本機 Responses 請求、兩份原始日誌正文與兩次新增回合的保存結果均核對一致。記錄為 `managed-current-context-paths-paired.json`、`managed-current-context-phases-paired.json` 和 `managed-current-context-parity.json`。

## 首次載入的歷史證明與寫入交接

參考 DSH 逐筆驗證已載入的日誌，再把通過的資料交給會話持有者。IH 仍從實體檔案讀取並核對身分、EOF、目錄及摘要。對原生普通 v14、完整框架及空舊格式前綴，原解碼器在驗證框架後沿用已核對的事件形狀，只建立一次該讀取需要的語義索引。解碼失敗會交回原驗證器，以保留格式錯誤的判定順序。

上層只有在原持有範圍還有效，且同一份深度凍結的資料以原生編碼完成 JSON 複製時，才沿用該份語義驗證。回傳仍是獨立可變的資料，並檢查事件註冊與操作欄位。舊格式、修復路徑及非原生後端沿用原流程。遇到超深的舊資料時，仍回報 `SESSION_EVENTS_TOO_DEEP`。寫入器獨立核對前綴，並維持原來的截尾及同步責任。

具備原生載入證明的相容會話只在該證明和寫入器讀得的前綴相同時掛載。同事件數、同位元組長度的替換測試仍會因摘要不同而拒絕掛載，並允許載入新的正確內容。進入掛載階段的並行開啟共用同一個交接，舊唯讀視圖在前綴改變後先結清並失效。實體日誌回歸涵蓋連續換檔、重開後寫入，以及關閉舊讀取器時維持新會話可用。

同一 Windows 執行檔載入同兩份約 6 MB 的日誌。在這組配對樣本，首次載入就緒由 5.21／5.14 秒變為 3.97／3.93 秒。語義索引處理由八次降至六次，其中兩次沿用解碼時核對過的事件形狀。獨立形狀掃描由六次降至四次。四次完整解碼、兩次寫入器同步，以及八次檔案摘要複核均有觀測記錄。四份本機 Responses 請求、兩份原始日誌和新增回合保存結果相符。記錄為 `owned-warm-history-paired-counts.json`、`owned-warm-history-paired-phases.json` 及 `owned-warm-history-paired-parity.json`。

## 寫入前綴的同一描述符

普通 JSONL 寫入器在同一個受追蹤的 `r+` 描述符讀取固定檔案範圍與 EOF，並在需要時由該描述符截尾、同步及關閉。操作前後核對描述符和路徑所指的檔案。截尾已發出後的失敗進入原來的恢復流程，關閉失敗繼續由原持有者追蹤。

截尾會改變檔案時間戳。寫入器以同一描述符重新核對保留的位元組，才會承認截尾後的檔案狀態。即使保留部分被等長改寫，也不會據此回傳改寫前的前綴。

原生乾淨歷史保留原始前綴及完整檔案摘要。寫入器以自己的描述符重新計算標頭與正文的摘要，並在同步後再次核對檔案身分及範圍，才沿用已解碼前綴。缺少合資格的證明時，解碼、必要的修復和同步也經同一描述符完成。回歸測試涵蓋開啟前改寫等長標頭或正文、同步期間改寫、截尾後失敗和待重試的關閉。

兩份約 6 MB 的會話並行驗證，寫入器合計重新核對 11,995,060 個位元組，完整解碼由兩次降到零，各同步一次核對過的原描述符。替換 JSON 解析器的回退對照執行兩次完整解碼及兩次同步。新舊版的四份本機 Responses 模型請求、兩份原日誌及新增回合保存結果一致。候選樣本的首次載入由 3.41／3.45 秒變為 3.05／3.03 秒。暖載入後的雙回合保存時間由 4.15 秒變為 4.65 秒。記錄為 `writer-one-descriptor-verified-counts.json`、`writer-one-descriptor-timing-phases.json` 和 `writer-one-descriptor-native-parity.json`。
