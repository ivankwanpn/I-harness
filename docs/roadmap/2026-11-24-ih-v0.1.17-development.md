# IH v0.1.17 開發計劃與長時間執行交接

**目標是讓 Windows 使用者能在同一個 repo 同時進行兩個長任務，清楚知道每個任務正在做什麼、改了哪些檔案，並能指定變更範圍交給模型複核。** 先量清 DeepSeek Flash 的等待發生在哪裡，再依證據調整串流或後端。最後用舊版資料升級、實際桌面長跑與故障恢復驗收。

## 里程碑與依賴

| 階段 | 完成後，使用者能得到什麼 | 依賴 |
|---|---|---|
| M0 | 可重現基線、獨立 dev 資料與工作分支 | 交接提交 |
| M1 | 知道 Flash 的等待發生在哪裡，已重現的 IH 瓶頸有前後對照 | M0 |
| M2 | 同一 repo 的兩個長任務能安全修改各自的工作樹 | M0；可與 M1 的量測準備平行 |
| M3 | 可對指定變更發起模型審查，並回到正確版本與檔案位置 | 普通 repo 可先做；完成前整合 M2 |
| M4 | 一個鍵盤入口找得到命令、會話與檔案 | 既有搜尋；納入 M2、M3 的命令 |
| M5 | 可從歷史位置試另一個方案，辨認分支並返回原對話 | 既有 fork/lineage；整合 M2 的執行根 |
| M6 | 數小時工作、重啟、故障及 v0.1.16 就地升級有實測證據 | 基線資料在 M0 留存，最終使用整合候選 |
| M7 | 有固定 SHA 的 Windows 可攜與安裝候選、驗收報告 | M1–M6 |

首要順序是模型延遲、檔案隔離、審查。每個里程碑完成即可打獨立 dev 包供試用；若使用者先想試前半程，交付中間候選後仍接續餘下里程碑。

### M0 建立能接續的開發環境

1. 用 `scripts/dev-desktop.ps1 -IhDevRoot <獨立絕對路徑>` 啟動 dev。分開開發 profile、工作區、安裝目的地與正式 IH 資料。
2. 準備一個可重建的小型 Git 倉庫、一個固定提交的較大專案、舊版 profile 測試副本。可用已授權作測試的 `ivankwanpn/stock_predict`，記錄來源、SHA、測試分支。改寫、故障注入與升級只在副本進行。
3. 留下兩個可辨識的長會話、同文重送、損壞會話旁的健康會話、中文搜尋、首次向上翻頁等基線案例。先覆驗即將觸及的路徑。既有 `.tmp` 收據可輔助比較；乾淨 checkout 要能從 repo 測試或 fixture 重建案例。
4. 在開發分支建立簡短進度表，記錄當前 SHA、環境、執行命令、已驗收項、現存故障、證據位置與下一個可做動作。實際跑過才標為完成。

### M1 實測並改善 DeepSeek Flash 的反應

- 在同一請求關聯六個時間點：按下送出、Gateway 收件、請求送往供應商、首個回應事件、第一段正文實際顯示、首次工具開始。區分思考與正文，使用本機相對時間或已校準的時鐘。另記工作區點選、清單可見、可輸入與 runtime 就緒。
- 固定 repo SHA、提示詞、模型實際 ID、端點、協議、推理強度、工具及冷暖／快取條件。至少涵蓋冷開新對話、暖續聊、兩個長會話同時工作、連續工具呼叫。以本機可控服務大量重播，再用 dev 沿用已配置的 DeepSeek Flash 走真實任務，優先 Messages 或 Responses。記錄實際協議。
- 先少量真呼叫驗證路徑與額度，再按可用額度擴樣；長跑主要用本機服務。條件相符時與 DSH、OpenCode 比較，同一任務交錯跑基線與候選。條件不同則分列。報樣本數、錯誤、原始範圍與 P50；需要報 P90/P95 時列出足夠樣本與計算方法。只留時間、大小、用量、識別碼等必要資料，排除金鑰與私人會話。
- **驗收**：慢的場景能歸因到本機準備、供應商或畫面；已證實的 IH 成本有對照修正，首段不重複、停止與重試正確、切回仍有完整前綴。外部等待占主因時，以同條件結果結案該場景。真模型未能執行時記明原因，其他階段繼續。

### M2 會話與 Git 工作樹

- 新會話提供「目前資料夾」「建立獨立工作樹」「使用既有工作樹」。顯示來源 repo、分支、實際目錄及未提交狀態。重開後仍能回到原來的工作目錄。
- 沿用 `packages/desktop/src/main/workspaces.ts`、`project-runtime.ts`、Gateway 的 `project-scope.ts` 與 `ProjectGitPane.tsx`。資料模型分開**側欄中的專案歸屬**與**這個會話的執行目錄及寫入授權**。既有多資料夾專案保留原契約。隔離任務的 shell、Code Mode、子代理、檔案編輯、Git index 與差異檢視落在對應的工作樹。
- 由同一生命週期負責建立、綁定、重試、重連及清理。區分 IH 建立和使用者匯入。涵蓋並行建立、重複點擊、中途退出、分支已被占用、路徑移動與 dirty worktree。關閉會話、移除管理關聯、刪除實體工作樹及刪分支是不同動作；可能丟失使用者修改時保留內容並由使用者決定。
- **驗收**：在桌面開 A/B 兩個任務，各自改同名檔並跑工具，檢查內容、cwd、索引、diff 和權限。A 無法寫入 B 的根；重啟仍綁對工作樹；建立回執遺失後重試只留一份；故障後能清理自己的資源。普通單資料夾、既有多資料夾及非 Git 專案仍能開始任務。

### M3 指定範圍的模型程式碼審查

- 從專案 Git 或會話選三種目標：未提交變更、相對基準分支、指定提交。清楚呈現 staged／unstaged／未追蹤檔的納入規則。基準分支固定 merge-base 與目標 OID；root commit 與 merge commit 顯示實際比較對象。
- 重用 `packages/desktop-gateway/src/review.ts` 的 Git 讀取、現有唯讀工具、模型執行與取消流程。捕捉實際版本、檔案集合和工作中內容識別；之後移動 HEAD 或再改檔，結果仍指得回受審內容並提示已過期。審查結果至少含問題、位置、影響與理由。大型、二進位、刪除、重新命名與截斷的 diff 交代覆蓋範圍。套用修改由使用者另行發起。工具核准 guardian 繼續負責其原有工作。
- **驗收**：用帶已知缺陷的測試倉庫核對三種輸入的內容、定位、取消、零變更、斷線、歷史恢復及工作樹歸屬。受控模型驗精確資料與狀態；真模型補跑一次完整審查。結果可回到正確檔案和版本。

### M4 統一鍵盤入口

- 預設評估 `Ctrl+K`，先核對終端、編輯器和現有快捷鍵。接現有命令、會話及檔案搜尋，結果標明來源、專案、工作區。沿用各自的中文比對、取消、結果上限與可見範圍。
- **驗收**：輸入框已有草稿時可用鍵盤找會話、開檔、執行「專案 Git」或「審查」，Esc 返回時保留草稿與焦點。測繁中輸入法組字、同名檔、跨工作區相同 session ID，以及舊搜尋回應晚到。

### M5 對話分支導航

- 使用現有 `fork-operation.ts`、SDK 的 durable fork 與 lineage 查詢，呈現父子會話、分叉點、目前位置與返回路徑。先用 IH 的持久化父子會話達成「從 A 試 B，再回 A」，另行評估 Pi 單檔歷史樹的儲存成本。
- **驗收**：從 A 中段分叉 B，兩邊各進行一輪後重開，核對歷史、待辦、草稿、執行中任務、工作樹與可見範圍。切換思路不會回滾磁碟檔案。舊會話缺分叉資訊時只顯示能證明的關係；遇封存或無法讀取的分支仍可回到健康會話。

### M6 長時間使用與舊版升級

- **長跑**：建議先以兩個長會話連續運行 2 小時，再對量到的問題加壓。本機服務持續產生串流和工具事件，穿插少量真模型任務。記錄實體 Electron、renderer 和 Host 的 CPU／記憶體、捲動與輸入反應、進程數、活動持有者、視窗消失與進程退出時間。分開記錄冷啟、穩態及停止後的狀況。
- **故障恢復**：在測試 profile 注入網絡中斷、短暫檔案鎖、收件後回應遺失、取消、關窗與重開；在可用實機驗睡眠／喚醒。確認已收件的任務不重做、狀態不倒退、沒有跨工作樹寫入、不完整清單不覆蓋健康資料，閒置後可回收。失敗要保留第一次的日誌，再驗修正。
- **就地升級**：取雜湊可核對的正式 v0.1.16 資產，在隔離 Windows 安裝環境升級到候選。事前保存會話、附件、設定、專案綁定與測試檔雜湊。驗正常升級、執行中保護、複製中斷、重新啟動和卸載。如果中斷會使程式不可啟動，修正安裝流程，或交付實測可重複的恢復方式。既有安裝器 fixture 的舊 payload 與正式版就地升級分開記錄。
- **驗收**：升級後能回原會話繼續工作、工具選到正確工作樹、使用者資料與額外檔案保留。每個曾卡住的案例都有基線、候選結果與重跑方式。需外部條件的待驗項明列，不用模擬結果替代。

### M7 固定候選與交付

- 以同一產品 SHA 建 Windows x64 可攜版與 Setup。現有入口是 `pnpm --filter @i-harness/desktop dist`、`pnpm --filter @i-harness/desktop installer`；使用獨立 release label 保留先前建置。核對包內 Desktop/Gateway 版本、資產大小與 SHA-256。
- 直接運行封裝內的 Electron/Gateway，重驗雙長會話、工作樹、審查、分支切換、歷史翻頁和正常退出。交付分支、提交、可安裝候選、驗收摘要、已知限制、實際執行及略過的檢查。
- 公開發布是後續獨立動作。使用者要求發版後，依既有流程核對 GitHub 帳號、main、tag、Setup、ZIP、校驗檔與 release manifest。

## 長時間執行與交接規則

- **每個增量**先重現問題，再改正負責該行為的模組，補足有辨別力的回歸案例，最後回到正常產品入口。避免新增第二份專案目錄、第二套任務狀態或常駐背景服務來掩蓋狀態衝突。
- **測試依改動範圍選擇**。例如 `node scripts/test-env.mjs pnpm --filter @i-harness/desktop exec vitest run <相關測試檔>`；搭配受影響套件的 `typecheck`。跨套件改動跑 `pnpm verify:boundaries`，Gateway／封裝改動跑 `pnpm verify:gateway`。一般 push 與手動／排程的完整矩陣分列。每跑完一個套件，報告通過數、失敗數及需要處理的異常。
- **開發安排**可平行處理量測、fixture 和互不相依的實作；跨 IPC、權限、工作樹和選取狀態的改動先確認單一負責處。每一個可用增量用登入帳號提交，普通推送至開發分支。在里程碑交界實際使用 dev 版；涉及路徑、原生工具或安裝器時用封裝版複驗。
- **中斷後接續**先查工作樹、最後提交、測試日誌、執行中的程序與 CI run。觀察逾時先查原工作是否仍活著，避免重開同一長測。進度表附目前里程碑、完成證據及下一個動作。若報百分比，同時給已完成項目與分母。
- **決策與完成**：一般實作自行決策；缺真實憑證／額度、需處理使用者原始資料或需擴大產品範圍時，說明阻礙並推進獨立工作。先前的「約 73%」是規劃估算。完成依 M0–M7 的產品行為、故障案例及固定候選證據判定。
- **候選之後的清單**：依實際需求評估 Codex 風格的非互動 JSONL／結構化輸出、簽署與自動更新、遠端工作區。若新發現現有流程的正確性問題，保留重現並按影響排序；避免用新增功能數取代穩定度驗收。
