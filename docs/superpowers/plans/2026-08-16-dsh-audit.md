# Sub-project 1: DeepSeek Harness Risk Audit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce an evidence-backed risk audit of `deepseek-harness-master` that outputs a three-column disposition table (reuse / rewrite / improved-writing) per risk or component point, serving as the design-and-implementation input for the I-harness runtime kernel.

**Architecture:** Read-only investigation of the dsh monorepo at `D:\agent-complete\deepseek-harness-master`. Each task audits one subsystem, writes a findings markdown file into `I-harness/docs/audit/findings/`, and the final task consolidates all findings into the disposition table at `I-harness/docs/audit/dsh-risk-audit.md`. Every finding MUST carry `path:line` evidence locations and a severity; the audit never modifies dsh source.

**Tech Stack:** Read-only inspection (glob/grep/read/webfetch only). Deliverables are Markdown documents. No code written in this sub-project.

## Global Constraints

- Audit target: `D:\agent-complete\deepseek-harness-master` — an EXTERNAL read-only source tree. NEVER modify, stage, or commit anything inside it.
- Audit artifacts live in: `I-harness/docs/audit/` (findings sections + consolidated report). Reports are committed to the I-harness repo.
- Every finding MUST include: severity (`Critical` | `Important` | `Minor`), affected component (exact package/path), evidence (`path:line` refs that actually exist), and a disposition candidate (`reuse` | `rewrite` | `improved-writing`) with a one-line reason.
- Disposition meanings per spec: `reuse` = audit confirms component is clean enough to copy reference into I-harness; `rewrite` = fault found, do not copy; `improved-writing` = stable concept but our implementation should write it better (state the bug it avoids).
- The audit MUST cover the named spec risk areas (§4.4/§5.2): session persistence format/version stability, plugin scope shadow pitfalls, tool execution pipeline safety seams, monotonic guards/waterfall semantics, Windows execution issues (persistent-bash/sandboxed-bash disablement, pwsh), Landlock Linux-only sandbox, interaction model consumption by TUI/Web.
- Do NOT re-read the five research reports under `I-harness/docs/research/` as substitutes for evidence — they are orientation only; findings must cite the dsh source tree directly.
- English for all audit documents (consistent with project docs).
- Commits: one per audit section task + one final consolidation commit. Commit messages follow project style (`docs: audit ...`).
