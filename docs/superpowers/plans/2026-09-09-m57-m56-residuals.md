## T1：刷新失敗事件帶**真實**生命週期 state（不再硬編碼 `"ready"`）

現況：`packages/session-executor/src/assembly.ts:220-224` 的 `bindAuthRefreshStatus` 永遠發 `state: "ready"`。`supervisor.ts:49` 有 `state(): McpServerState`，而 `types.ts:27-33` 的註釋本意就是「state 保持它原本的值」——硬編碼只是碰巧在多數時候正確。

做法：

1. `bindAuthRefreshStatus(serverName, onStatus, opts?)` 擴充可選第三參數 `opts.currentState?: () => McpServerState | undefined`；發射時 `state: opts?.currentState?.() ?? "ready"`（`?? "ready"` 只覆蓋「該 server 尚未發過任何狀態」的情形，需在註釋寫明）。既有兩參數呼叫與既有測試（`assembly.test.ts:382-392`）必須不變地通過。
2. `createSessionAssembly` 內維護 per-server 最後狀態：在 `mcpStatusHook`（`assembly.ts:426-428`）裡把 `ev.server`/`ev.state` 記進一個區域 `Map<string, McpServerState>`（**不導出**），並在 `prepareMcpConfig`（`:435-441`）把 `() => states.get(cfg.serverName)` 傳給 binder。宣告順序：map 必須在 `mcpStatusHook` 之前。
3. 註釋同步更新（含「telemetry 關閉時本回調是 no-op」這點仍然成立）。

**RED 測試**（`packages/session-executor/test/assembly.test.ts` 的 `bindAuthRefreshStatus (M56)` 塊內擴充，pre-fix 會失敗因為第三參數被忽略）：

- (a) `currentState: () => "reconnecting"` → 事件 `state` 為 `"reconnecting"`（**pre-fix 得 `"ready"`，真 RED**）；
- (b) `currentState: () => undefined` → `"ready"`；
- (c) 既有無選項的案例仍為 `"ready"`（回歸）。

## T2：不覆寫宿主自帶的 `onAuthRefreshFailed`

現況：`assembly.ts:437` 直接以 `bindAuthRefreshStatus(...)` 覆蓋 `cfg.auth.onAuthRefreshFailed`（今天無人設置，但這是 API 陷阱）。

做法：由同一枚導出函數負責合成——`bindAuthRefreshStatus` 的 `opts` 再收 `hostHandler?: (message: string) => void` 與 `onHostError?: (err: unknown) => void`。回傳的 handler 行為：**先呼叫 `hostHandler`（若存在），其拋出被 try/catch 吞下並交給 `onHostError`**，**再**發射 status 事件（宿主異常不得讓我們的可見性事件消失）。`prepareMcpConfig` 傳入 `cfg.auth.onAuthRefreshFailed` 與一個 `console.warn` 的 `onHostError`。

**RED 測試**（同塊）：

- (d) 給了 `hostHandler` → 它被呼叫（**pre-fix 從未被呼叫，真 RED**），且事件仍發射；順序為宿主先、事件後；
- (e) `hostHandler` 拋出 → 事件仍發射且 `onHostError` 收到該錯誤；
- (f) 無 `hostHandler` → 事件照發（回歸）。

**測試覆蓋聲明**：`createSessionAssembly` 內「map → binder」的 4 行接線本身不做單元測試（無現成 MCP fixture 可驅動真刷新失敗）；binder 契約由 (a)-(f) 釘住，接線由 review 覆核。實作者不得為此新增 mock 框架或導出新 API。

## T3：`tokens()` 第二次 store 讀失敗時回舊 token（fail-soft）

現況：`packages/mcp-client/src/oauth.ts:191` `if (!due) return (await get<OAuthTokens>("tokens")) ?? current`——第二讀若 reject 會直接拋出，而修正前該路徑回的是 `current`。

做法：包 try/catch，失敗時 `console.warn` 後回 `current`（與 `:184-189` 到期檢查的 fail-soft 同款措辭）。**不動**進入時的第一次讀（`:180`，既有暴露面，本次範圍外）。

**RED 測試**（`packages/mcp-client/test/oauth.test.ts`，用既有的 Map-backed `McpTokenStore` 形狀）：store 的 `get` 對 `"tokens"` 第一次回 `{access_token, token_type}`（**無** `refresh_token` → `due=false`）、第二次拋 `Error("store offline")`；斷言 `provider.tokens()` **resolves** 到第一個 token（**pre-fix 是 reject，真 RED**）。
