# M55-shell（D1）：shell/PTY 工具忽略 assembly workspace（跑在進程 cwd）

日期：2026-09-09 · 分支 `m55-shell`（自 `m55` @ `0063bac`）
發現：M55 整合門反覆出現 `apps/tui/node_modules` 被清空 → 追查為測試的 mock `rm -rf node_modules` 跑在 **vitest 的 cwd**，而非 assembly 的 workspace。

## 症狀（controller 已複現）

```
assembly workspace: C:\Users\inkik\AppData\Local\Temp\cwd-probe-IEgfSI
process cwd       : D:\I-harness-main\.worktrees\m55
bash tool result  : {"stdout":"D:/I-harness-main/.worktrees/m55\n", ...}
```

`bash`/`pwsh` 的 `pwd` 是**進程 cwd**。根因：`packages/shell/src/index.ts:183`（與 `:180`、`:200`、`:203`）呼叫 `deps.exec.run({ argv, abortSignal, ... })`——**沒有 `cwd`**；`packages/exec/src/index.ts:125` 只在 `cmd.cwd` 存在時才設定，undefined 即繼承父進程 cwd。對照：LSP 有正確傳（`packages/session-executor/src/assembly.ts:441` `cwd: cfg.cwd ?? opts.workspace`）。

**影響**：
1. `i-harness tui --workspace <dir>` / `--workspace` 下的所有 shell 命令跑在**啟動目錄**，而 fs 工具（read/write/edit）解析的是 workspace → 兩套工具在**不同樹**上工作。
2. web-host 的 per-session workspace（`/api/sessions` 可指定 workspaceId）失效。
3. 測試中的 mock `rm -rf node_modules` 刪到 vitest 的 cwd（`apps/tui/node_modules`）→ 反覆的 infra flake（CLI spawn 測試 `ERR_MODULE_NOT_FOUND @i-harness/tui-core`）。

## 範圍

1. **修**：讓 shell（bash/pwsh）、terminal（PTY）、以及任何經 exec 生成的工具使用 assembly 的 workspace 作為 cwd。最小做法：`registerShell`/`registerTerminal`/`fs-search` 的 exec 呼叫帶上 `cwd`；由 `assembly.ts` 把 `opts.workspace` 傳進去（與 LSP 同源）。**不得**改 exec 的預設語意（未指定 cwd 時仍繼承父進程——那是 exec 層的契約）。
2. **測試**：
   - 新增 focused 測試：assembly 的 workspace 為 temp 目錄時，`bash pwd` 的輸出等於該目錄（**RED 於現行代碼**）；`pwsh` 同理（平台可用時）；PTY 工具的 cwd 亦同。
   - 既有測試若依賴「跑在進程 cwd」→ 改為明確以 workspace 表達意圖（報告列出每一處）。
3. **連帶**：`apps/tui/test/tui-app.test.ts:558/580/611` 的 mock `rm -rf node_modules` 在修好後會跑在 temp workspace（安全）；**仍建議**改成明確的臨時檔名（例如 `rm -rf probe-dir`）以免未來再有人把 workspace 指到套件目錄——若改，需說明不影響斷言意圖。
