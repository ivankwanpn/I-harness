## §1 Real-Protocol Tool History (Important #1)

### 1.1 The defect

`core-agent` appends `tool/call` + `tool/result` to the session log, but `deriveMessages` (`packages/core-session/src/index.ts`) only projects `user/message` and `assistant/message`. With real protocol clients, step N+1's `request.messages` is identical to step 1's — the model never sees its own tool call or the tool result, so a tool-requiring task loops to `maxTurns` or "answers" without tool context.

### 1.2 Session event pairing

- `SessionEvent` `tool/call` and `tool/result` each gain `callId: string`.
- `callId` is generated by `core-agent` when it receives a `tool_call` stream event (sequence `call_1`, `call_2`, …), written to both the `tool/call` and the matching `tool/result` events.
- Protocol plugins pass the callId through to their API format (OpenAI `call_id`; Anthropic `tool_use.id` / `tool_use_id`) so multi-turn tool history round-trips correctly.

### 1.3 Neutral `LLMMessage` shape (owned by core-session, re-exported by llm-seam)

```ts
export type LLMMessage =
  | { role: "user"; content: string }
  | { role: "assistant"; content: string; toolCalls?: { id: string; name: string; args: unknown }[] }
  | { role: "tool"; toolCallId: string; content: string }
```

- `deriveMessages` folds `tool/call` into the preceding/current `assistant` message's `toolCalls` (by callId) and `tool/result` into a `{ role: "tool" }` message (by callId). Pairing is exact — not positional.
- `assertMessagesFromLog` (`llm-seam`) is updated to the SAME projection so the audit seam stays consistent (it compares model-visible messages to a projection of the session log).

### 1.4 Protocol translation

- **llm-openai** maps neutral messages → OpenAI Responses `input` items: `assistant.toolCalls` → `{ type: "function_call", call_id, name, arguments }`; `tool` role → `{ type: "function_call_output", call_id, output }`.
- **llm-anthropic** maps neutral messages → Messages API: `assistant.toolCalls` → `tool_use` blocks (with `id`, `name`, `input`); `tool` role → user `tool_result` blocks (`tool_use_id`, `content`).

### 1.5 Verification

Mock-level integration tests (no real API key):
- llm-openai: intercept fetch; first mock step returns a tool_call; assert the SECOND request body's `input` contains a `function_call_output` with the executed result.
- llm-anthropic: same pattern; assert second request `messages` contains a user `tool_result`.
- core-agent integration test: mock client simulating two turns (tool_call → final reply); assert the loop completes without hitting `maxTurns` and the second turn's `request.messages` includes the tool result.
- Existing 96+ tests stay green; `pnpm -r typecheck` clean.

## §2 decide() Dual-Run Hardening (Important #2)

`decide()` currently runs twice per pre-execute: once as the plain-listener seed, once inside the waterfall handler. Today it is correct because at most one producer exists per emit and the seeded value passes through the chain unchanged. Hardening:

- `decide()` becomes tolerant: if the payload is already a decision object (`{ kind: ... }`), pass it through unchanged rather than re-parsing it as a `ToolCall`.
- Add a comment documenting the single-producer property (a nearer policy's seeded decision object reaches farther ancestors, which never re-evaluate the original call).

## §3 Minor Hardening

| Item | Fix |
|---|---|
| Tool-arg delta accumulation | llm-openai accumulates `response.function_call_arguments.delta` events; llm-anthropic accumulates `input_json_delta`. Tool args no longer arrive as `{}` for split JSON. |
| reasoning forwarding | Both protocol plugins map their provider's reasoning tokens to `LLMStreamEvent.reasoning` (core-agent already handles it). |
| Buffer hardening | Both protocol clients flush any residual SSE buffer before yielding `end`. |
| Nearest-wins multi-level downgrade | Add a comment documenting the single-producer property; a `resolveStrictest` walk is a no-op today (verified unreachable — no path double-mounts the policy). |
| `[DONE]` break | llm-openai's `[DONE]` marker breaks both the inner parse loop and the outer read loop (or equivalent). |
| fs `resolvePath` | Eliminate the wasted `resolve(path)` on the relative branch (compute abs only when needed). |
| exec `taskkill` | `await` the kill/taskkill operation before resolving (no fire-and-forget). |
