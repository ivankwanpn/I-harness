# Windows packaged execution and console observation

These fixtures run only on Windows x64 with the repository's installed toolchain and built artifacts. They never rebuild the production native helper. Keep generated evidence under an owned `.tmp/sandbox-redesign-*` directory.

Build the CLI with `node scripts/build-dist.mjs --out .tmp/sandbox-redesign-task5-cli`. Build Desktop with `IH_DESKTOP_RELEASE_LABEL=release-sandbox-task5` and its normal `dist` script. Application versions stay unchanged. Run `run.ps1 -Label UNIQUE` to compile the owned GUI-subsystem observer and launch the actual packaged Desktop main window, followed by an Electron Node-mode workload parent. All background launches use hidden startup. `-WorkerFile supplemental.mts` covers local Git plugin helpers, assembled Agent auto, owner lineage, revocation and reference read/write denial. `-WorkerFile visibility.mts` holds an owned legacy console probe for exact HWND and hosting-window attribution. `-WorkerFile promotion.mts` verifies the legacy assembly's complete-tree promotion and explicit retained-background refusal.

The observer records timestamps, PID/start identity, parent relationships, window class, visibility flags, HWND correlation, message-only membership, area-presence booleans, cloaking and iconic state. Related owner/root-window queries record the same bounded metadata, including whether the hosting process started after the observer. Rectangle queries produce only `hasArea` booleans; coordinates and sizes are never recorded. It never reads window titles, content or screenshots. An actual Desktop `Chrome_WidgetWin_1` SHOW is the positive control. This proves the SHOW hook operates; it is not a positive visible-console calibration. Hidden ordinary console windows are sampled separately. Unknown/destroyed HWNDs and newly visible hosting windows do not qualify as a clean negative result, even when a pseudo window itself has zero area.

`FindWindowEx(HWND_MESSAGE, ..., null, null)` tests actual message-only membership. Microsoft documents message-only windows as not visible, but a failed membership test does not establish displayability. Similarly, `IsWindowVisible` reflects visibility style state. The GetConsoleWindow documentation's non-local-display statement applies when the application is associated with a pseudoconsole; a class name alone cannot establish that association. See [window features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features), [FindWindowExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-findwindowexw), [GetConsoleWindow](https://learn.microsoft.com/en-us/windows/console/getconsolewindow), and [IsWindowVisible](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindowvisible).

The source/package workload fixture exercises Node, nested CMD, native Windows PowerShell, unrestricted Bash, binary streaming, one-spawn promotion, background cancellation, legacy readonly and workspace writes, search, SDK gateway entrypoints, LSP and PTY cleanup. A separate confined Bash attempt failed; the fixture retains that result instead of retrying it on every run. `bash-exit.mts` was used once to capture its exact root exit and native settlement. Do not rerun it to search for a permissive policy.

`node-descendant.mts` opens a trusted query handle to the owned Node child while the parent waits for a file gate. It records STILL_ACTIVE before releasing the parent, then the actual child exit, markers and native settlement. It does not change the native token, Job, console or policy. Its observed missing-marker case remains unqualified; generic native self-child retention is separate evidence.

The committed fixtures are reproducible instruments, not security certification. Actual observations and known failures are recorded in `docs/sandbox-distribution-acceptance.md`. Preserve prior failed evidence when running a new label.
